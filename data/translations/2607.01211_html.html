Ⅱ-AII-A 基准选择Benchmark Selection

我们研究了三个直接针对编码代理的存储库级基准 性能优化。 请注意，我们不是 调查代码模型的每个效率基准，也不是每个开源 基准神器。我们仅在基准测试 (1) 评估时才纳入基准测试 存储库级编辑，(2) 具有可执行文件的目标运行时优化 比较代码状态的工作负载或测试，并且 (3) 显示为最新的、可见的 经过同行评审的基准论文，而不是仅排行榜、仅代码或 未发表的提案。这些标准选择 GSO、SWE-Perf 和 SWE-fficiency 因为它们将可执行任务与经过审查的任务定义结合在一起，并且 可能会被重新用于评估有关代理绩效工程的主张 能力。We study three repository-level benchmarks that directly target coding agents on performance optimization. Note that we are not surveying every efficiency benchmark for code models, nor every open-source benchmark artifact. We include benchmarks only when they (1) evaluate repository-level edits, (2) target runtime optimization with executable workloads or tests that compare code states, and (3) appear as recent, visible peer-reviewed benchmark papers rather than leaderboard-only, code-only, or unpublished proposals. These criteria select GSO, SWE-Perf, and SWE-fficiency because they combine executable tasks with reviewed task definitions and are likely to be reused to evaluate claims about agents’ performance-engineering ability.

RQ1：官方参考补丁在以下情况下仍然有效吗？ 跨机器重放？RQ1: Do official reference patches remain valid under cross-machine replay?

动机：Motivation:代码性能优化基准是 与机器无关：他们的任务要求代理优化程序，而无需 针对特定的 CPU 型号或机器配置。此设置假设 每个基准测试的参考补丁，以及用于 区分补丁，产生在合理范围内生存的性能信号 机器变异。因此，跨机器重播很重要：如果参考 跨机器优化不稳定，稍后在同一台机器上提交比较 基准建立在一个不稳定的目标上。回放检查每个任务是否 仍然可评估，比基础更快，并且根据其原始基准规则有效。Code performance-optimization benchmarks are machine-agnostic: their tasks ask agents to optimize a program, without targeting a particular CPU model or machine configuration. Cross-machine replay is therefore important: if the reference optimization is not stable across machines, later submission comparisons on the same benchmark rest on an unstable target. First, most reference patches are runnable across machines, so the main issue is not basic evaluability. Second, runnable does not imply benchmark-valid: all three benchmarks contain reference patches that become slower than the base program in at least one machine-round, and reapplying each benchmark’s original construction rule narrows the valid set to 39 GSO tasks, 11 SWE-Perf tasks, and 411 SWE-fficiency tasks. This does not make the benchmarks useless; it changes what they are good for. They are still useful for studying the last step from “faster than base” to “as fast as the reference patch,” but less suitable as the only evidence of general performance-engineering ability.

对于未来的基准设计师：更接近全面性能 工程问题。For future benchmark designers: move closer to the full performance engineering problem.当前的基准测试提供了可执行的工作负载和可重现的任务工件， 但他们经常通过公开优化的代码区域来简化任务， 对代理进行工作负载或压力测试。生产绩效工作通常开始 早期：工程师检查配置文件、火焰图、痕迹、延迟故障、 或仪表板，然后选择大型代码库中哪些热操作值得 改变，推断哪个测量重要，并判断本地编辑是否会发生 帮助实际工作负载，无需现成的压力测试即可获得即时反馈。 未来的基准测试应该在添加此诊断的同时保留可执行重放 层：从配置文件或痕迹进行热点定位，模糊优化 目标、针对补丁搜索期间不完全可见的工作负载进行验证，以及 资源指标超出一个运行时数量。 CPU 时间、延迟、分配 行为、内存占用和回归风险都很重要，并且优化其中一项 会伤害另一个人Current benchmarks provide executable workloads and reproducible task artifacts, but they often simplify the task by exposing the optimized code region, workload, or stress test to the agent. Production performance work usually starts earlier: engineers inspect profiles, flame graphs, traces, latency breakdowns, or dashboards, then choose which hot operation in a large codebase is worth changing, infer which measurement matters, and judge whether a local edit will help the real workload without a ready-made stress test for immediate feedback. Future benchmarks should preserve executable replay while adding this diagnostic layer: hotspot localization from profiles or traces, ambiguous optimization targets, validation against workloads not fully visible during patch search, and resource metrics beyond one runtime number. CPU time, latency, allocation behavior, memory footprint, and regression risk all matter, and optimizing one can hurt another[43]。我们的目标不是放弃今天的 基准测试，但为了让下一个测试更难的工作流程：找到 瓶颈，选择合理的优化，跨过正确的实施 代码路径，并证明它可以改善重要的工作负载。. The goal is not to discard today’s benchmarks, but to make the next ones test a harder workflow: finding the bottleneck, choosing a justified optimization, implementing it across the right code paths, and proving that it improves the workload that matters.

七VII有效性的威胁Threats to Validity

内部效度。Internal validity.我们的重播和度量重新计算可能 仍然受到实现选择、硬件变化和发布的影响 工件质量。因此，重放分析使用严格的全重放规则： 仅当参考补丁满足基准测试的任务时，任务才是重播有效的 所有 12 轮机器重播均采用原始构建规则。这种保守的 规则可能会低估可用任务，但它可以保护后续分析免受不稳定的影响 参考信号。Our replays and metric recomputations may still be affected by implementation choices, hardware variation, and released artifact quality. The replay analysis therefore uses a strict all-replay rule: a task is replay-valid only when the reference patch satisfies the benchmark’s original construction rule in all 12 machine-round replays. This conservative rule may undercount usable tasks, but it protects later analyses from unstable reference signals.

外部效度。External validity.结果涵盖了最近的三个 存储库级性能优化基准和特定公共 排行榜快照，而不是所有编码代理或性能工程设置。 我们对 10 份公开提交的分析也是一个任务覆盖率代理， 不是新设计的多代理工作流程或对任何单个提交的声明 配置。未来的底层模型、代理支架、硬件和基准策略可能会改变确切的结果 很重要。The results cover three recent repository-level performance-optimization benchmarks and specific public leaderboard snapshots, not all coding-agent or performance-engineering settings. Our analysis across 10 public submissions is also a task-coverage proxy, not a newly engineered multi-agent workflow or a claim about any single submitted configuration. Future underlying models, agent scaffolds, hardware, and benchmark policies may change the exact counts.

数据构建有效性。Data construction validity.我们依赖每个基准的 发布的任务、参考补丁、公开提交和评分记录。 SWE-Perf 被排除在指标和 RQ3 任务分析之外，因为 类似的公共代理输出工件不可用。We rely on each benchmark’s released tasks, reference patches, public submissions, and scoring records. SWE-Perf is excluded from the metric and RQ3 task analyses because comparable public agent-output artifacts were unavailable.

八VIII相关工作Related Work

代码效率基准已从小型代码单元扩展到完整的代码单元 存储库。 PIE 研究提高性能的编辑，而 EffiBench、Mercury、 ENAMEL、ECCO、EvalPerf/DPE 和 ACECode 评估是否生成或修改 代码保持正确，同时提高效率Code-efficiency benchmarks have expanded from small code units to full repositories. PIE studies performance-improving edits, while EffiBench, Mercury, ENAMEL, ECCO, EvalPerf/DPE, and ACECode evaluate whether generated or revised code remains correct while improving efficiency[41, 14, 6, 34, 44, 21, 48, 10]。 COFFE 增加了功能 - 和 文件级轨道，而 EffiBench-X、KernelBench、AlgoTune 和 PerfCodeBench 扩大跨语言、GPU 内核、数值程序的评估范围 系统级高性能代码. COFFE adds function- and file-level tracks, while EffiBench-X, KernelBench, AlgoTune, and PerfCodeBench broaden evaluation across languages, GPU kernels, numerical programs, and system-level high-performance code[31, 33, 28, 32, 16]。在存储库和项目级别， GSO、SWE-Perf 和 SWE-fficiency 评估对真实存储库的编辑 可执行工作负载、参考补丁和特定于基准测试的指标. At the repository and project level, GSO, SWE-Perf, and SWE-fficiency evaluate edits to real repositories with executable workloads, reference patches, and benchmark-specific metrics[39, 11, 23]。 PerfBench、PEACE/PeacExec、 ISO-Bench、FormulaCode 和 CppPerf 分别覆盖真实世界的性能 bug、混合编辑的项目级效率优化、推理 工作负载、大型代码库代理优化和性能改进 C++ 提交. PerfBench, PEACE/PeacExec, ISO-Bench, FormulaCode, and CppPerf respectively cover real-world performance bugs, project-level efficiency optimization with hybrid editing, inference workloads, large-codebase agent optimization, and performance-improving C++ commits[8, 35, 26, 38, 12]。这些基准共同表明， 从功能级效率转向存储库规模性能 工程. Together, these benchmarks show a clear shift from function-level efficiency to repository-scale performance engineering[13, 7, 52].

相反，我们不会引入另一个基准或报告新的代理 排行榜。我们审核现有存储库级别背后已发布的工件 基准测试：官方参考补丁是否可靠重播，评分规则如何 更改公开提交排名，哪些重播有效任务仍然分开 来自参考补丁的公开提交。In contrast, we do not introduce another benchmark or report a new agent leaderboard. We audit the released artifacts behind existing repository-level benchmarks: whether official reference patches replay reliably, how scoring rules change public-submission rankings, and which replay-valid tasks still separate public submissions from reference patches.

IX 结论Conclusion

性能优化基准现在影响如何判断编码代理， 但他们的分数并不是不言自明的。我们最近对三个 存储库级别的基准测试说明了原因。重播740官方参考后 跨四台云机器和三轮打补丁，只有 39/102 个 GSO 任务， 11/140 SWE-Perf 任务和 411/498 SWE-fficiency 任务保持其原始有效性 每次重播时都会发出信号。排行榜排名还取决于评分规则： 在 GSO 和 SWE-fficiency 共享的八份公开意见中，官方 排名在 9/28 成对顺序上不一致，以及最差的十个低加速 SWE 效率任务占得分权重的 58.5%–82.8%。最后，很多 至少一项公开提交内容已经涵盖了重播有效的任务： 384/450 匹配或击败参考补丁，449/450 击败基本程序。 对于剩下的任务，问题通常是找不到任何工作 优化，但缩小了与参考补丁的最后加速差距。Performance-optimization benchmarks now influence how coding agents are judged, but their scores are not self-explanatory. Our audit of three recent repository-level benchmarks shows why. After replaying 740 official reference patches across four cloud machines and three rounds, only 39/102 GSO tasks, 11/140 SWE-Perf tasks, and 411/498 SWE-fficiency tasks kept their original validity signal in every replay. Leaderboard ranks also depend on the scoring rule: among the eight public submissions shared by GSO and SWE-fficiency, the official rankings disagree on 9/28 pairwise orders, and the worst ten low-speedup SWE-fficiency tasks carry 58.5%–82.8% of the score weight. Finally, many replay-valid tasks are already covered by at least one public submission: 384/450 match or beat the reference patch, and 449/450 beat the base program. For the remaining tasks, the problem is usually not finding any working optimization, but closing the last speedup gap to the reference patch.

因此，下一代性能优化基准应该测试 不仅仅是在固定工作负载下修补预先指定的入口点。他们应该 要求代理根据性能症状或概况进行推理，选择优化 目标，并验证运行时改进以及内存、延迟和 其他资源成本。The next generation of performance-optimization benchmarks should therefore test more than patching a pre-specified entry point under a fixed workload. They should ask agents to reason from performance symptoms or profiles, choose optimization targets, and validate runtime improvements together with memory, latency, and other resource costs.
