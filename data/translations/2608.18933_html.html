摘要Abstract

基于大语言模型 (LLM) 的代理在自动化软件问题解决方面表现出了卓越的熟练程度，但由于缺乏特定于项目的知识，他们常常难以解决特定存储库中的问题。现有的自我进化方法从存储库历史或在线修复轨迹中获取此类知识，但它们要么依赖于可用的历史问题解决信号，要么会产生大量的每个问题测试时间探索成本。 在本文中，我们提出了 SkillForge，这是一个自蒸馏框架，可以主动从存储库本身获取特定于项目的知识。 SkillForge 不是等待真正的问题来暴露项目特定的知识差距，而是通过重新实现存储库的测试覆盖的核心功能来综合项目特定的问题。通过解决这些综合问题，SkillForge 将可重用的项目特定知识提炼为基于实体的技能，并将它们与相关存储库实体相关联，以供将来解决问题。 使用开源和闭源模型进行的大量实验表明，SkillForge 在强大的基线上持续提高了问题解决性能。这些结果表明，在解决实际问题之前主动获取项目特定的知识可以显着改善下游软件问题的解决Large language model (LLM) based agents have demonstrated remarkable proficiency in automated software issue resolution, yet they often struggle to resolve issues in a specific repository because they lack project-specific knowledge. Existing self-evolving approaches acquire such knowledge from repository history or online repair trajectories, but they either depend on available historical issue-resolution signals or incur substantial per-issue test-time exploration cost. In this paper, we propose SkillForge, a self-distillation framework that proactively acquires project-specific knowledge from the repository itself. Instead of waiting for real issues to expose project-specific knowledge gaps, SkillForge synthesizes project-specific issues by re-implementing test-covered core functionalities of the repository. By resolving these synthetic issues, SkillForge distills reusable project-specific knowledge into entity-grounded skills and associates them with relevant repository entities for future issue resolution. Extensive experiments using both open-source and closed-source models show that SkillForge consistently improves issue resolution performance over strong baselines. I 简介Introduction

基于大语言模型（LLM）的代理在软件问题解决方面表现出了卓越的能力Large language model (LLM) based agents have demonstrated remarkable capabilities in software issue resolution[2, 5, 24, 30, 10, 25, 22, 23, 8, 13, 14, 21, 31, 37, 27]。通过自主导航存储库、调用工具和迭代地提出补丁，现代软件工程 (SWE) 代理（例如 SWE-agent）. By autonomously navigating repositories, invoking tools, and iteratively proposing patches, modern software engineering (SWE) agents—such as SWE-agent[49]和张开双手and OpenHands[44]——可以解决以前需要专家人工干预的复杂的、现实世界的错误。在日益强大的基础模型和更好的脚手架设计的推动下，这些代理在 SWE-bench 等标准基准上取得了令人印象深刻的结果—can resolve complex, real-world bugs that previously required expert human intervention. Driven by increasingly powerful foundation models and better scaffolding designs, these agents have achieved impressive results on standard benchmarks such as SWE-bench[24, 33, 45, 1, 51, 52, 12]，展示了跨不同代码库和问题类型的强大泛化能力。, demonstrating strong generalization across diverse codebases and issue types.

尽管取得了这些进步，但当在特定项目上部署代理时，会出现一个关键瓶颈：他们通常必须从头开始解决问题，而无需了解特定于项目的知识。现实世界的项目通常表现出结构规律：重复出现的故障可能涉及相同的脆弱模块，正确的补丁可能需要保留特定于存储库的 API 契约，并且相关的 API 通常通过隐式执行路径耦合。缺乏此类特定于项目的知识的代理必须在解决问题期间反复重新发现这些约定。这种限制造成了冷启动问题：在获得特定于项目的知识之前，即使是能力很强的代理也会被简化为通用存储库浏览器，并且可能会反复陷入相同的特定于项目的陷阱。Despite these advances, a critical bottleneck emerges when agents are deployed on a specific project: they typically must solve issues from scratch, without project-specific knowledge. Real-world projects often exhibit structural regularities: recurring failures may involve the same brittle modules, correct patches may need to preserve repository-specific API contracts, and related APIs are often coupled through implicit execution paths. Agents that lack such project-specific knowledge must repeatedly rediscover these conventions during issue resolution. This limitation creates a cold-start problem: before project-specific knowledge has been acquired, even a highly capable agent is reduced to a generic repository explorer and can repeatedly fall into the same project-specific pitfalls.

为了解决这一知识差距，最近的工作探索了自我进化的 SWE 代理，这些代理从先前的问题解决信号中获取特定于项目的知识To address this knowledge gap, recent works have explored self-evolving SWE agents that acquire project-specific knowledge from prior issue-resolution signals[5, 28, 43, 32, 16, 26, 47]。历史驱动的方法，例如 EvoCoder. History-driven methods such as EvoCoder[28]和 SWE-Expand SWE-Exp[5]从历史问题、提交或代理轨迹中提取可重用的知识。相反，在线方法通过在当前问题上生成额外的轨迹来在测试时探索期间完善代理。虽然有效，但这两种范式都会被动地获取特定于项目的知识。历史驱动的方法受到过去问题的丰富性和覆盖范围的限制：存储库行为、API 组合和尚未被历史轨迹运用的长尾组件提供的学习信号很少。在线方法减少了对历史的依赖，但它们为每个目标问题付出了大量的轨迹、代币和时间成本distill reusable knowledge from historical issues, commits, or agent trajectories. Online methods instead refine the agent during test-time exploration by generating additional trajectories on the current issue. While effective, both paradigms acquire project-specific knowledge reactively. History-driven methods are bounded by the richness and coverage of past issues: repository behaviors, API combinations, and long-tail components that have not been exercised by historical trajectories provide little learning signal. Online methods reduce this dependence on history, but they pay substantial trajectory, token, and time costs for each target issue[9]，并且只有在问题已经到达后，获得的指导才可用。, and the acquired guidance becomes available only after the issue has already arrived.

在本文中，我们提出了 SkillForge，一个主动的自我蒸馏框架，用于解决项目特定问题解决中的冷启动问题。 SkillForge 不是等待实际问题解决历史记录的积累，而是从当前存储库中综合项目特定的问题。给定存储库快照，SkillForge 从测试覆盖的核心功能开始，跟踪执行跟踪来识别共同实现相同功能的代码区域，并在受限上下文下重写这些协调的片段。由此产生的综合问题是可执行的，并且由存储库测试提供行为依据。然后，SWE 代理解决这些综合问题，生成 SkillForge 从中提取项目特定知识的轨迹。In this paper, we propose SkillForge, a proactive self-distillation framework for addressing the cold-start problem in project-specific issue resolution. Rather than waiting for real issue-resolution history to accumulate, SkillForge synthesizes project-specific issues from the current repository. Given a repository snapshot, SkillForge starts from test-covered core functionalities, follows execution traces to identify the code regions that jointly implement the same functionality, and rewrites these coordinated segments under constrained context. The resulting synthetic issues are executable and behaviorally grounded by the repository tests. A SWE agent then resolves these synthetic issues, producing trajectories from which SkillForge distills project-specific knowledge.

II 方法论Methodology

SkillForge 是一个自蒸馏框架，用于解决项目特定问题解决中的冷启动问题。关键思想是直接从存储库本身主动获取特定于项目的知识，而不是等待现实世界的问题解决轨迹积累。为了实现这一目标，SkillForge 综合特定于项目的问题，使用 SWE 代理解决这些问题，并将生成的特定于项目的知识提炼成可重用的技能，这些技能可以在后续的实际问题解决过程中检索。SkillForge is a self-distillation framework for addressing the cold-start problem in project-specific issue resolution. The key idea is to proactively derive project-specific knowledge directly from the repository itself, rather than waiting for real-world issue-resolution trajectories to accumulate. To achieve this, SkillForge synthesize project-specific issues, resolves them with a SWE agent, and distills the resulting project-specific knowledge into reusable skills that can be retrieved during subsequent real-world issue resolution.

Given a repository snapshot and its test suite, the framework consists of four stages: (1) generating project-specific synthetic issues by rewriting core functionalities; (2) resolving these issues with a SWE agent through iterative patch generation, tool execution, and test feedback; (3) distilling project-specific knowledge from the resulting resolution trajectories and organizing it as reusable skills in a dual-level skill repository, comprising a global diagnostic skill set that captures reusable project-level knowledge and a local intervention skill set that records entity-specific guidance; and (4) retrieving the relevant skills during downstream real-world issue resolution whenever the corresponding repository entities are encountered. Each stage is described in detail below.

Ⅱ-AII-A 项目特定问题综合Project-Specific Issue Synthesis

为了在不依赖历史问题报告的情况下获取项目特定的知识，SkillForge 通过重写功能关键代码段并将导致的测试失败视为解决目标来综合项目特定的问题。该框架并没有明确地注入手工错误，而是要求法学硕士在受限环境下重新实现存储库功能，鼓励重写的代码自然地表现出与实际软件开发过程中引入的错误类似的实现错误。更重要的是，由于模型必须在不访问原始实现的情况下重建功能，因此重写的代码反映了其一般编码知识，而不是存储库的特定于项目的知识，从而暴露了代理需要学习的特定于项目的行为。在整个过程中，监督仅来自存储库的代码库和测试套件，而不依赖于历史问题报告或人工编写的错误描述。To acquire project-specific knowledge without relying on historical issue reports, SkillForge synthesizes project-specific issues by rewriting functionality-critical code segments and treating the resulting test failures as resolution targets. Rather than explicitly injecting handcrafted bugs, the framework asks an LLM to reimplement repository functionality under constrained context, encouraging the rewritten code to naturally exhibit implementation mistakes similar to those introduced during real software development. More importantly, because the model must reconstruct functionality without access to the original implementation, the rewritten code reflects its general coding knowledge rather than the repository’s project-specific knowledge, thereby exposing the project-specific behaviors that the agent needs to learn. Throughout this process, supervision is derived solely from the repository’s codebase and test suite, without relying on historical issue reports or human-written bug descriptions.

测试驱动的范围和跟踪。Test-driven scope and trace.给定一个代码存储库Given a code repositoryℛ\mathcal{R}, SkillForge 确定了行使核心存储库功能的测试用例，因为这些行为为特定于项目的知识获取提供了最信息丰富的监督, SkillForge identifies test cases that exercise core repository functionalities, since these behaviors provide the most informative supervision for project-specific knowledge acquisition[3, 6]。对于每个通过的测试用例，SkillForge 在覆盖率检测下执行它以获得执行跟踪：所执行的源文件集和行范围。该跟踪定义了用于重写的候选代码区域，因为执行区域内的修改更有可能影响可观察的测试结果。然后，我们从跟踪区域中提取连续的代码段（完整的函数或内聚的执行片段），并为每个段附加周围的上下文（例如，前面和后面的行）。. For each passed test case, SkillForge executes it under coverage instrumentation to obtain an execution trace: the set of source files and line ranges that are exercised. This trace defines the candidate code regions for rewriting since modifications within executed regions are more likely to affect observable test outcomes. We then extract contiguous code segments from the traced regions—either complete functions or cohesive execution fragments, and attach surrounding context (e.g., preceding and following lines) for each segment.

选择关键部分。Select critical segments.跟踪段的数量可能很大。我们使用法学硕士来选择一小组The number of traced segments can be large. We use an LLM to select a small set of批评的critical最有可能代表此测试用例功能的段。 LLM 会获得测试的目的和场景（源自测试代码或描述）以及候选片段的摘要（文件、行范围和代码内容）。它返回排名靠前的子集segments that are most likely to represent the functionality of this test case. The LLM is given the test’s purpose and scenario (derived from the test code or description) along with summaries of the candidate segments (file, line range, and code content). It returns a ranked subset of top-kk带有简短理由的片段。此步骤使后续重写阶段重点关注高影响区域。与功能级重写方法不同，SkillForge 可以选择由同一测试用例执行的多个关键部分，从而实现捕获存储库内跨组件交互的合成问题。segments with brief justifications. This step keeps the subsequent rewriting phase focused on high-impact regions. Unlike function-level rewriting approaches, SkillForge may select multiple critical segments exercised by the same test case, enabling synthetic issues that capture cross-component interactions within the repository.

代码重写。Code rewriting.对于每个选定的细分市场，我们要求法学硕士For each selected segment, we ask an LLM to重写rewrite通过重新完成本地功能对应的代码。至关重要的是，LLM 并没有提供原始的实现；相反，它只接收有限的上下文信息：段之前和之后的行、段的位置和缩进以及测试目标的高级描述。该模型被提示生成一个合理的替代实现，保留预期的 API，同时可能简化逻辑。这种“严格屏蔽”设计不是明确地注入预定义的错误，而是通过在受限环境下引发实际的实施错误，暴露了代理的一般编码知识和存储库的项目特定知识之间的差距。the corresponding code by re-completing the local functionality. Crucially, the LLM is not provided with the original implementation; instead, it receives only limited contextual information: the lines before and after the segment, the segment’s location and indentation, and a high-level description of the test’s goal. The model is prompted to produce a plausible alternative implementation that preserves the intended API while potentially simplifying logic. V 讨论Discussion

V-A 精炼技能的质量和法学硕士生成的问题陈述Quality of Distilled Skills and LLM-Generated Problem Statements

我们手动检查了提炼技能和综合问题陈述的质量。对于提炼出来的技能，我们验证了它们基于相应的存储库实体、解决轨迹和黄金补丁，提供了正确且可操作的特定于项目的指导，而没有幻觉的 API 或误导性的建议。对于综合的问题陈述，我们验证了它们忠实地描述了由功能级重写引起的可观察到的故障，而不会泄漏实现细节。We manually inspected the quality of the distilled skills and synthesized problem statements. For the distilled skills, we verified that they are grounded in the corresponding repository entities, resolution trajectories, and golden patches, providing correct and actionable project-specific guidance without hallucinated APIs or misleading advice. For the synthesized problem statements, we verified that they faithfully describe the observable failures induced by functionality-level rewriting without leaking implementation details.

我们还将综合问题的问题类型分布与来自相同存储库的真实 SWE 基准问题的问题类型分布进行了比较。这两个分布不重叠，表明综合问题不仅仅再现了用于评估的相同类别的实际问题。相反，他们倾向于暴露当前 LLM 如何使用特定于项目的函数、API 和跨函数交互的更细粒度的模型偏差。因此，SkillForge 的好处不是教代理解决类似的问题类型，而是揭示可以跨不同实际问题类别转移的特定于项目的功能使用陷阱。We also compared the issue-type distribution of synthesized issues with that of real SWE-bench issues from the same repositories. The two distributions do not overlap, suggesting that the synthesized issues do not merely reproduce the same categories of real issues used for evaluation. Instead, they tend to expose finer-grained model biases in how the current LLM uses project-specific functions, APIs, and cross-function interactions. Thus, the benefit of SkillForge is less about teaching the agent to solve similar issue types and more about surfacing project-specific function-use pitfalls that can transfer across different real issue categories.

V-B 有效性的威胁Threats to Validity

外部效度。External validity.

SkillForge 依靠存储库测试来综合问题并提炼特定于项目的知识。因此，可运行测试很少执行的代码区域提供的学习信号较少，这可能会降低测试覆盖范围有限的存储库中所学知识的有效性。SkillForge relies on repository tests to synthesize issues and distill project-specific knowledge. Consequently, code regions that are rarely exercised by runnable tests contribute fewer learning signals, which may reduce the effectiveness of the learned knowledge in repositories with limited test coverage.

内部效度。Internal validity.

遵循标准 SWE 工作台风格的合成实例合成管道Following standard SWE-bench-style synthetic instance synthesis pipelines[20, 50, 39]，综合问题的问题陈述是使用法学硕士生成的。我们手动验证了合成的故障是否对应于功能级重写引起的可执行错误，并且生成的描述正确反映了可观察的行为，而不会泄漏实现细节。然而，与之前的工作一样，LLM 生成的问题陈述可能仍然与开发人员编写的问题报告不同。, problem statements for synthesized issues are generated using an LLM. We manually verified that the synthesized failures correspond to executable bugs induced by functionality-level rewriting and that the generated descriptions correctly reflect observable behaviors without leaking implementation details. However, as in prior work, LLM-generated problem statements may still differ from developer-written issue reports.

最近的工作Recent work[53, 18, 42]探索了综合软件问题或可执行环境来改进软件工程代理。现有方法主要将合成实例视为可扩展的训练数据。瑞典史密斯has explored synthesizing software issues or executable environments to improve software engineering agents. Existing methods primarily view synthesized instances as scalable training data. SWE-Smith[50]通过独立重写各个 API 级函数来构建综合错误修复任务。 R2E-健身房constructs synthetic bug-fixing tasks by independently rewriting individual API-level functions. 相比之下，SkillForge 使用合成问题来实现根本不同的目的：主动获取特定于项目的知识，而不是训练模型。 SkillForge 的目标不是最大化合成任务的数量或多样性，而是公开无法仅从静态存储库中轻松推断出的项目特定知识。它的问题构建在粒度上也有所不同：SkillForge 不是重写孤立的 API 级函数、随机选择多个函数进行联合重写或生成新功能，而是从存储库测试的功能开始，并使用测试执行跟踪来识别共同实现相同功能的代码区域。解决由此产生的问题揭示了代理的一般编码先验如何与特定于项目的实现模式和 API 交互相背离。In contrast, SkillForge uses synthetic issues for a fundamentally different purpose: proactive project-specific knowledge acquisition rather than training models. Instead of maximizing the number or diversity of synthesized tasks, SkillForge aims to expose project-specific knowledge that cannot be readily inferred from static repositories alone. Its issue construction also differs in granularity: rather than rewriting isolated API-level functions, randomly selecting several functions for joint rewriting, or generating new features, SkillForge starts from repository-tested functionalities and uses test execution traces to identify the code regions that jointly implement the same functionality. Solving the resulting issues reveals how the agent’s general coding priors diverge from project-specific implementation patterns and API interactions.

七VII结论Conclusion

我们提出了 SkillForge，一个自蒸馏框架，用于解决项目特定问题解决中的冷启动问题。 SkillForge 不依赖存储库历史记录或昂贵的每个问题测试时探索，而是通过综合项目特定问题并提炼其解决轨迹，主动从存储库直接获取项目特定知识。这些知识被表示为一个双层的、基于实体的技能存储库，支持未来的问题解决。实验表明，SkillForge 持续改进了问题解决性能，在 DeepSeek-V3.2 和 GPT-5-mini 的 SWE-bench Verified 上获得了 +5.8%/+5.6% 的绝对 Pass@1 增益，在 SWE-bench Pro 上获得了 +5.8%/+4.1% 的绝对增益。总体而言，我们的结果表明，在解决实际问题之前主动获取特定于项目的知识是从存储库历史记录或在线探索中被动获取知识的有效且可扩展的替代方案。We presented SkillForge, a self-distillation framework for addressing the cold-start problem in project-specific issue resolution. Rather than relying on repository history or costly per-issue test-time exploration, SkillForge proactively derives project-specific knowledge directly from the repository by synthesizing project-specific issues and distilling their resolution trajectories. This knowledge is represented as a dual-level, entity-grounded skill repository that supports future issue resolution. Experiments demonstrate that SkillForge consistently improves issue resolution performance, yielding absolute Pass@1 gains of +5.8%/+5.6% on SWE-bench Verified and +5.8%/+4.1% on SWE-bench Pro for DeepSeek-V3.2 and GPT-5-mini, respectively. Overall, our results suggest that proactively acquiring project-specific knowledge before real issue resolution is an effective and scalable alternative to reactive acquisition from repository history or online exploration.
