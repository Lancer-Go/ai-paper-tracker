1. 简介Introduction

随着大型语言模型 (LLM) 不断提高其推理和理解能力，LLM 驱动的代理已成为主要研究焦点As large language models (LLMs) continue to improve their reasoning and understanding capabilities, LLM-powered agents have emerged as a major research focus(Moonshot AI (2025); 6; 9; 13; 2)。以 OpenAI Deep Research 为例. As exemplified by OpenAI Deep Research(OpenAI, 2025)和马努斯and Manus(Manus, 2025)，LLM充当代理人的“大脑”。它将复杂的任务分解为一系列子步骤，并在每个步骤调用外部工具与外界交互。通过降低使用强大而复杂的工具的障碍，人们普遍期望代理能够推动生产力革命。于是，很多企业都投入了数百亿美元在这一行的研发上。, the LLM acts as the “brain” of the agent. It decomposes a complex task into a sequence of sub-steps and invokes external tools at each step to interact with the outside world. By lowering the barrier to using powerful and complex tools, agents are widely expected to drive the productivity revolution. As a result, many companies have invested tens of billions of dollars in this line of research and development(Luo et al., 2025; Zhang et al., 2026; Giusti et al., 2025).

机会。Opportunities.面对上述问题，我们找到了优化工具执行的机会。具体来说，我们可以采用推测执行来预先执行工具，从而减少工具执行时间在整个执行过程中所占的比例。例如，在深度研究任务中，获取相关URL后，我们可以直接提前下载这些网页，以减少网页下载所消耗的时间。Faced with the aforementioned problems, we identify an opportunity to optimize tool execution. Specifically, we can adopt speculative execution to pre-execute tools, thereby reducing the proportion of tool execution time in the overall execution process. For example, in a deep research task, after acquiring relevant URLs, we can directly download these web pages in advance to reduce the time consumed by web page downloading.

挑战。Challenges.然而，利用上述机会并非易事。由于 LLM 请求是独特的，因此快速准确地预测下一个要使用的工具非常具有挑战性。更重要的是，仅仅预测工具是不够的。我们还需要预测工具所需的参数，这更具挑战性。此外，不准确的预执行可能会破坏原始代理执行工作流程，这对将工具预执行集成到当前系统设计中提出了另一个挑战。However, leveraging the aforementioned opportunity is non-trivial. Since LLM requests are unique, it is highly challenging to quickly and accurately predict the next tool to be used. More importantly, merely predicting the tool is insufficient; we also need to predict the parameters required by the tool, which is even more challenging. Furthermore, inaccurate pre-execution could disrupt the original agent execution workflow, which poses another challenge to integrate tool pre-execution in the current system design.

2. 背景和动机Background and Motivation

2.1. LLM代理基础知识The LLM Agent Basics

2.1.1. LLM代理时代The Era of LLM Agents

大型语言模型 (LLM) 的发展已将计算范式从静态文本生成转变为自主问题解决，包括深入研究The evolution of Large Language Models (LLMs) has shifted the computing paradigm from static text generation to autonomous problem solving, including deep research(OpenAI, 2025; Moonshot AI, 2025), 错误修复帮助, bug-fix assistance(2; 9)，以及代理员工, and agent employee(13; Manus (2025))。虽然标准 LLM 推理将模型视为函数. While standard LLM inference treats the model as a functionf​(t​e​x​t)→t​e​x​tf(text)\to text，LLM代理将模型重新构建为更广泛的控制循环的认知核心。代理不仅由其底层模型定义，还由其通过使用外部工具（例如 Python 解释器、Web 检索 API、向量数据库）和长期记忆来编排多步骤任务的能力来定义。, LLM Agents reframe the model as the cognitive core of a broader control loop. An agent is defined not just by its underlying model, but by its ability to orchestrate multi-step tasks through the use of external tools (e.g., Python interpreters, web retrieval APIs, vector databases) and long-term memory.

这种转变对系统设计具有深远的影响。与相对较短且独立的传统推理工作负载不同，代理工作负载是长时间运行、有状态且高度连续的。单个用户请求（例如，“分析此数据集并绘制趋势”）会触发许多可能需要几分钟的中间推理步骤和工具执行。因此，系统必须从优化单个请求延迟（Time-to-First-Token）转变为优化端到端延迟。This shift has profound implications for system design. Unlike traditional inference workloads that are relatively short and independent, agent workloads are long-running, stateful, and highly sequential. A single user request (e.g., “Analyze this dataset and plot the trends”) triggers many intermediate reasoning steps and tool executions that may span minutes. Consequently, the system must transition from optimizing individual request latency (Time-to-First-Token) to optimizing the end-to-end latency.

2.1.2. 代理执行模型The Agent Execution Model

LLM代理自然遵循LLM agents naturally follow an迭代法学硕士——工具循环Iterative LLM–Tool Loop，如图所示, as shown inFigure 2。在每次迭代中，LLM 都会以当前上下文和执行历史记录为条件，然后 (i) 发出最终答案并终止，或者 (ii) 决定调用具有具体参数的工具。如果调用工具，系统将执行该调用，将工具输出附加回会话状态，并在更新的上下文上恢复 LLM 推理。. In each iteration, the LLM is conditioned on the current context and execution history, and then either (i) emits the final answer and terminates, or (ii) decides to invoke a tool with concrete parameters. If a tool is invoked, the system executes the call, appends the tool output back into the session state, and resumes LLM inference on the updated context.

重复此循环，直到法学硕士确定已收集足够的证据并生成最终结果作为会话输出。从系统角度来看，端到端延迟是由LLM推理和工具执行共同决定的。This loop repeats until the LLM determines that enough evidence has been gathered and produces the final result as the session output. From a system perspective, end-to-end latency is jointly determined by LLM inference and tool execution.

2.2.2. 当前方法的低效率Inefficiencies of Current Approaches

现有的无服务器工作流程和微服务优化通常需要Existing serverless workflow, and microservice optimizations typically require a静态的static，端到端执行图（通常是 DAG）来做出调度决策并优化缓存和数据移动, end-to-end execution graph (often a DAG) to make scheduling decisions and optimize caching and data movement(Liu et al., 2023; Zhang et al., 2024, 2025b; Marcelino and Nastic, 2024; Wu et al., 2024; Marcelino et al., 2025)。当这些系统执行预测时，它很大程度上取决于完整的静态 DAG（即，预测给定图的下一个分支或请求）。 对于代理工作负载，这种假设不成立：控制流是在线生成的，并且在 LLM 完成当前步骤之前不知道下一个工具调用。如果没有完整的 DAG 先验，提前调度和基于图形的预取带来的好处有限。. When these systems perform prediction, it is largely conditioned on the complete static DAG (i.e., predicting the next branch or request given the graph). This assumption breaks for agentic workloads: the control flow is generated online, and the next tool call is not known until the LLM finishes the current step. Without the full DAG a priori, ahead-of-time scheduling and graph-based prefetching provide limited benefit.

2.2.3. 机遇与挑战Opportunities and Challenges

首先，预测下一个要使用的工具非常具有挑战性。与 CPU 中的传统分支预测（在有限且结构良好的指令集上运行）不同，代理请求是高度多样化且非结构化的。因此，很难设计一种可以实现高精度刀具预测的简单方法。如果预测器未能早于 LLM 本身识别工具调用，则推测不会提供任何性能优势。First, predicting the next tool to be used is highly challenging. Unlike traditional branch prediction in CPUs, which operates over a limited and well structured set of instructions, agent requests are highly diverse and unstructured. It is therefore difficult to design a simple method that can achieve highly accurate tool prediction. If the predictor fails to identify the tool invocation earlier than the LLM itself, speculation provides no performance benefit.

其次，仅预测下一个工具是不够的。系统还必须准确预测该工具所需的确切输入参数。这种意图加参数预测在计算上是困难的，因为参数（例如特定的代码片段、文件路径或搜索查询）通常是动态生成的，并且在很大程度上取决于当前上下文。Second, predicting the next tool alone is not sufficient. The system must also accurately predict the exact input parameters required by that tool. This intent plus argument prediction is computationally difficult because the arguments, such as specific code snippets, file paths, or search queries, are often generated on the fly and depend heavily on the current context.

第三，由于代理工具的状态突变性质，集成预执行变得复杂。与只读操作不同，不准确的预执行可能会破坏环境（例如通过安装不兼容的依赖项）并破坏原始工作流程。恢复一致性需要昂贵的回滚机制和复杂的系统设计。Third, integrating pre-execution is complicated by the state mutating nature of agent tools. Unlike read only operations, inaccurate pre-execution can corrupt the environment, such as by installing incompatible dependencies, and disrupt the original workflow. Restoring consistency then requires expensive rollback mechanisms and intricate system design.

9. 结论Conclusion

在本文中，我们解决了现代 LLM 支持的代理中的基本序列化瓶颈，其中严格顺序的“LLM 工具”循环迫使昂贵的资源在外部工具执行期间保持空闲。我们引入了 PASTE，这是一种推测性工具执行方法，可将这种反应式工作流程转变为主动式流水线架构。使用新的模式元组抽象，PASTE 将稳定的应用程序级控制流与动态数据流依赖性解耦，从而实现稳健的后期绑定工具预测。结合具有风险意识和机会主义的调度程序，该系统利用瞬态的闲置资源来隐藏工具延迟，同时保持权威任务的严格性能。In this paper, we address the fundamental serialization bottleneck in modern LLM powered agents, where a strictly sequential “LLM-tool” loop forces expensive resources to remain idle during external tool execution. We introduce PASTE, a speculative tool execution method that transforms this reactive workflow into a proactive and pipelined architecture. Using a new Pattern Tuple abstraction, PASTE decouples stable application-level control flows from dynamic data flow dependencies, which enables robust and late binding tool prediction. Combined with a risk-aware and opportunistic scheduler, the system exploits transient slack resources to hide tool latency while preserving strict performance for authoritative tasks.
