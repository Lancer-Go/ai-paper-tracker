摘要Abstract

Errors that occur early in execution may propagate through both the agent context and environment state, and their effects may be difficult to reverse through subsequent actions. 简介Introduction

LLM 代理通过工具介导的与其环境的交互来解决任务。与非代理法学硕士不同，他们观察环境状态，调用工具，并根据反馈调整后续行动（Yao et al. 2023；Liu et al. 2024）。它们越来越多地应用于长期任务，例如迭代科学实验、跨应用程序工作流程和存储库级软件工程（Kon 等人，2026 年；Li 等人，2026 年；Jimenez 等人，2024 年）。因此，提高他们在此类任务上的表现是一个重要的研究目标。LLM agents solve tasks through tool-mediated interaction with their environments. Unlike non-agentic LLMs, they observe environmental states, invoke tools, and adjust subsequent actions based on feedback (Yao et al. 2023; Liu et al. 2024). They are increasingly applied to long-horizon tasks such as iterative scientific experimentation, cross-application workflows, and repository-level software engineering (Kon et al. 2026; Li et al. 2026; Jimenez et al. 2024). Improving their performance on such tasks is therefore an important research objective.

然而，长期运营对法学硕士代理人来说是一个明显的挑战。例如，智能体可能在执行初期制定了错误的计划，导致后续行动朝着错误的方向进行（ValmeekamHowever, operating over long horizons presents distinct challenges for LLM agents. 倒带模块Rewind Module

AgentRewind 将倒带作为代理的附加控制操作公开。当代理决定调用倒带时，AgentRewind 将记录的轨迹组织到检查点元数据条目中。每个条目都总结了 LLM 输出以及下一个 LLM 输出之前发生的工具交互和环境更改。基于当前执行轨迹、检查点元数据、环境反馈和累积的倒带内存，代理选择一个检查点并生成一个新的倒带内存，该内存总结了当前轨迹中的有用信息，例如伪造的假设和替代策略。AgentRewind exposes rewind as an additional control action to the agent. When the agent decides to invoke rewind, AgentRewind organizes the recorded trajectory into checkpoint metadata entries. Each entry summarizes an LLM output together with the tool interactions and environment changes that occur before the next LLM output. Based on the current execution trajectory, checkpoint metadata, environment feedback, and accumulated rewind memory, the agent selects a checkpoint and generates a new rewind memory that summarizes useful information from the current trajectory, such as falsified hypotheses and alternative strategies.

在倒带执行期间，AgentRewind 终止当前执行并将外部环境和代理上下文恢复到选定的检查点。前面的LLM输出和工具结果是从执行日志中恢复的，而不是重新生成或重新执行。然后，AgentRewind 将累积的倒回内存注入到恢复的上下文中。然后，代理开始根据恢复的状态生成新的后缀。During rewind execution, AgentRewind terminates the current execution and restores both the external environment and the agent context to the selected checkpoint. The preceding LLM outputs and tool results are restored from the execution log rather than regenerated or re-executed. AgentRewind then injects the accumulated rewind memory into the restored context. The agent then begins generating a new suffix from the restored state.

外部环境恢复边界External Environment Recovery Boundary

AgentRewind 恢复的受控环境是工作区目录树，无论代理在本地运行还是在隔离容器中运行。在每个检查点，AgentRewind 都会记录文件级别的更改；倒回可恢复后来的修改、恢复已删除的文件以及删除新创建的文件。工作区文件系统外部的影响（例如网络请求、外部服务调用和外部运行时状态）无法撤消。由于保留的前缀是从执行日志中恢复的，因此不会再次触发这些效果。The controlled environment restored by AgentRewind is the workspace directory tree, whether the agent runs locally or in an isolated container. At each checkpoint, AgentRewind records file-level changes; rewinding reverts later modifications, restores deleted files, and removes newly created files. Effects outside the workspace filesystem, such as network requests, external-service calls, and external runtime state, cannot be undone. 它必须至少有四个按顺序运行的阶段，其中每个阶段只能在前一个阶段产生可交付成果后才能启动。其后期的可交付成果必须在至少两个地方引用早期阶段在运行时实际生成的值，例如摘要、计数或标识符；因此，跳过或伪造早期阶段的代理无法填写后续阶段。它必须包含至少两个必须依次修复的缺陷（修复第一个缺陷会暴露第二个缺陷），或者包含至少 30 个必须重建的记录条目的日志。并且它必须包含至少五个验收标准，这也是已发布的集合中最小的数量。It must have at least four stages that run in sequence, where each stage can only start once the previous stage has produced its deliverables. Its later deliverables must quote values that earlier stages actually produced at run time, such as digests, counts, or identifiers, in at least two places; an agent that skips or fakes an earlier stage therefore cannot fill in a later one. It must contain either at least two defects that have to be repaired one after another, where fixing the first exposes the second, or a log of at least 30 recorded entries that has to be reconstructed. C.5 不回滚的内容C.5 What Is Not Rolled Back

工作区文件系统之外的效果没有撤消路径，正如主要论文所述：网络请求、对外部服务的调用或工作区之外的进程中留下的状态都会在倒带后保留下来。工作空间内还有两个值得一提的间隙。首先，我们的快照会跳过 .git 目录中的所有内容，因此存储库的历史记录不属于其中。为了能够恢复该历史记录，我们复制工作区中的每个 .git 目录，例如 repo/，并将这些副本与日志一起保留。我们不这样做的地方是工作区根目录本身。因为 .git 目录既没有快照也没有复制，所以回滚不会影响它：代理所做的提交以及它执行的任何变基或重置，之后仍记录在该 .git 中，而工作树中的文件照常恢复。这会影响很少的任务：82 个任务中的 4 个将其存储库保存在子目录中并完整恢复，这 4 个任务包括其分配涉及重写历史记录的每个任务； 2 个任务本身就是一个存储库；其余 76 个不包含存储库。其次，空目录和除可执行位之外的任何权限位都不会在快照中表示，因此不会被恢复。Effects outside the workspace filesystem have no undo path, as the main paper states: a network request, a call to an external service, or state left in a process outside the workspace all survive a rewind. Inside the workspace there are two further gaps worth naming. First, our snapshot skips everything inside a .git directory, so a repository’s history is not part of it. To be able to put that history back, we copy each .git directory inside the workspace, such as repo/, and keep those copies with the log. The one place we do not do this is the workspace root itself. Because a .git directory there is neither snapshotted nor copied, a rewind leaves it untouched: the commits the agent made, and any rebase or reset it performed, are still recorded in that .git afterwards, while the files in the working tree are restored as usual. This affects few tasks: 4 of the 82 keep their repository in a subdirectory and are restored in full, and those 4 include every task whose assignment involves rewriting history; 2 tasks are themselves a repository; the remaining 76 contain no repository. Second, an empty directory and any permission bit other than the executable bit are not represented in a snapshot and so are not restored.
