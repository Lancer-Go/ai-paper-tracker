摘要Abstract

我们提出了多智能体推理和协调（MARC），这是一个开源框架，用确定性多智能体编排代替单一的 LLM 提示进行临床推理。 MARC 协调角色专用代理进行提取、推理、答案生成和评估，并具有显式上下文传递和可追踪的中间输出，从而实现阶段性故障归因。我们还引入了一个 Decomposer 模块，该模块可以根据简单语言描述生成特定于任务的代理提示，从而消除手动提示工程。该框架支持基于 API 和本地 CPU 兼容的部署，并且完全可配置，无需修改代码。 MARC 被设计为与模型无关、可解释，并且无需编程专业知识的临床领域专家也可以使用。完整的框架可在We present Multi-Agent Reasoning and Coordination (MARC), an open-source framework that replaces monolithic LLM prompting with deterministic multi-agent orchestration for clinical reasoning. MARC coordinates role-specialized agents for extraction, reasoning, answer generation, and evaluation, with explicit context passing and traceable intermediate outputs, enabling stage-wise failure attribution. We additionally introduce a Decomposer module that generates task-specific agent prompts from a plain-language description, eliminating manual prompt engineering. The framework supports both API-based and local CPU-compatible deployments and is entirely configurable, without code modifications. MARC is designed to be model-agnostic, interpretable, and accessible to clinical domain experts without programming expertise. 一、简介1. Introduction

人工智能和大语言模型 (LLM) 已在医学领域得到快速采用，在自动报告生成、临床问答和医学图像解读方面展现出强大的性能Artificial intelligence and large language models (LLMs) have seen rapid adoption across medicine, demonstrating strong performance in automated report generation, clinical question answering, and medical image interpretation1–5。最近的视觉语言模型已经显示出从胸片生成放射学报告的能力，而法学硕士（例如 GPT-5）. Recent vision-language models have shown the ability to generate radiology reports from chest radiographs, while LLMs such as GPT-56和 Med-PaLM 2 在医学问答基准和临床推理任务上取得了强劲的表现and Med-PaLM 2 have achieved strong performance on medical question-answering benchmarks and clinical reasoning tasks1–3。与此同时，MedGemma 等多模态医学模型已将这些功能扩展到图像文本推理，支持医学视觉问答、胸部 X 射线判读和其他医学成像任务中的应用. In parallel, multimodal medical models such as MedGemma have extended these capabilities to image-text reasoning, supporting applications in medical visual question answering, chest X-ray interpretation, and other medical imaging tasks4。除了一般基准性能之外，最近的工作还将法学硕士应用于结构化放射学工作流程，包括从放射学报告中提取信息、识别关键发现、生成结构化报告以及提取或生成后续成像建议. Beyond general benchmark performance, recent work has applied LLMs to structured radiology workflows, including information extraction from radiology reports, identification of critical findings, structured report generation, and extraction or generation of follow-up imaging recommendations7-117–11。这些发展使法学硕士成为增强放射科医生决策和实现可扩展的临床人工智能工作流程的有前途的工具；然而，它们的临床部署仍然需要仔细验证、特定领域的适应和保障措施，以确保可靠性、透明度和患者安全. These developments position LLMs as promising tools for augmenting radiologist decision-making and enabling scalable clinical AI workflows; however, their clinical deployment still requires careful validation, domain-specific adaptation, and safeguards to ensure reliability, transparency, and patient safety11,12 .

尽管取得了这些进步，大多数部署的系统仍然依赖于单一提示策略，其中单个 LLM 实例的任务是同时执行提取、推理、验证和操作生成Despite these advances, most deployed systems still depend on single-prompting strategies, in which a single LLM instance is tasked with simultaneously performing extraction, reasoning, validation, and action generation13。这种整合没有充分利用模型的潜力并限制了可解释性. This consolidation underutilizes the model's potential and limits interpretability13。在放射学中，最佳决策需要来自多个信息源的上下文，并且可能需要多个步骤或多轮推理才能形成决策. In radiology, optimal decisions require context from multiple information sources, and it may take multiple steps or rounds of reasoning to form a decision14,15 .

代理人工智能系统通过将法学硕士从单步生成扩展到迭代工作流程，提供了一种潜在的解决方案，在迭代工作流程中，模型可以规划、跨中间输出进行推理、使用外部工具或信息源，并根据先前的结果调整后续操作Agentic AI systems offer a potential solution by extending LLMs beyond single-step generation toward iterative workflows in which models can plan, reason across intermediate outputs, use external tools or information sources, and adapt subsequent actions based on prior results16。此类系统与需要顺序推理、验证和异构信息集成而不是单一模型响应的临床任务特别相关。然而，有效的代理工作流程需要精心编排来定义任务如何分解、信息如何在组件之间传递以及如何在采取下游操作之前评估中间输出。多代理框架通过引入模块化、专业化和可追踪推理来解决这些限制，其中代理可以通过咨询多个信息源并基于先前代理的输出来自适应地处理多步骤任务. Such systems are particularly relevant to clinical tasks that require sequential reasoning, validation, and integration of heterogeneous information rather than a single model response. However, effective agentic workflows require deliberate orchestration to define how tasks are decomposed, how information is passed between components, and how intermediate outputs are evaluated before downstream actions are taken. Multi-agent frameworks address these limitations by introducing modularity, specialization, and traceable reasoning, where agents can adaptively handle multi-step tasks by consulting multiple sources of information and building on prior agents' outputs13–17 .

2. 框架2. Framework

MARC 框架是一个用 Python 实现的与领域无关的多代理系统，它利用 LangChain 库与各种大型语言模型进行交互。该架构强调顺序、模块化的管道，其中专门的代理通过显式上下文传递和可选的检索增强生成来处理信息。The MARC framework is a domain-agnostic, multi-agent system implemented in Python, which leverages the LangChain library to interface with various large language models. The architecture emphasizes a sequential, modular pipeline in which specialized agents process information through explicit context passing and optional retrieval-augmented generation.

2.1 多Agent设计2.1 Multi-Agent Design

MARC 采用结构化工作流程设计模式（2 级自治）MARC employs a structured workflow design pattern (Level 2 autonomy)20，其中专门代理按预定顺序执行任务，并在阶段之间进行明确的切换。与 RadFabric 等固定管道方法不同, where specialized agents execute tasks in a predetermined sequence with explicit handoffs between stages. Unlike fixed-pipeline approaches such as RadFabric21，MARC 通过基于 YAML 的配置文件概括了这种模式，这些配置文件定义代理序列、模型分配和知识增强，而无需修改代码。, MARC generalizes this pattern through YAML-based configuration files that define agent sequences, model assignments, and knowledge augmentation without requiring code modifications.

每个代理都封装了一个语言模型、一个特定于任务的提示和一个可选的领域知识检索增强生成（RAG）模块Each agent encapsulates a language model, a task-specific prompt, and an optional retrieval-augmented generation (RAG) module for domain knowledge22。代理是在 YAML 配置文件中而不是代码中以声明方式定义的，因此用户可以更改代理的模型、提示或知识源，而无需修改底层实现。这种声明式方法直接解决了法学硕士在固定、多步骤工作流程中独立运行的局限性，如之前的单代理医疗人工智能系统中所确定的那样，通过使非开发人员能够修改代理工作流程、交换基础模型以实现成本性能优化，以及通过知识文件注入领域专业知识，而无需 Python 编程. Agents are defined declaratively in a YAML configuration file rather than in code, so users can change an agent's model, prompt, or knowledge sources without modifying the underlying implementation. This declarative approach directly addresses the limitation of LLMs operating in isolation within fixed, multi-step workflows, as identified in prior single-agent medical AI systems, by enabling non-developers to modify agent workflows, swap foundation models for cost-performance optimization, and inject domain expertise through knowledge files without Python programming13。补充中提供了完整的配置详细信息。. 2.2 分解器模块2.2 Decomposer Module

为了解决固定管道和手动提示工程的局限性，我们引入了 MARC Decomposer。给定简单语言的任务描述，Decomposer 使用 MedGemma 4B 来解释任务，将其分解为三个子任务，并自动为每个代理生成特定于角色的提示模板（图 1）。 Decomposer 在单个对话轮次中运行，输出包含代理名称、角色和完整提示模板的结构化 JSON 规范。To address the limitations of fixed pipelines and manual prompt engineering, we introduce the MARC Decomposer. Given a plain-language task description, the Decomposer employs MedGemma 4B to interpret the task, decompose it into three subtasks, and automatically generate role-specific prompt templates for each agent (Figure 1). The Decomposer operates in a single conversational turn, outputting a structured JSON specification containing agent names, roles, and full prompt templates.

生成的提示在写入磁盘并加载到 MARC 管道之前，会根据一组结构约束进行验证，强制执行正确的变量绑定（{input}、{previous_agent_output}）、VERDICT 格式约定和输出长度限制。这使得跨异构临床任务的动态管道构建成为可能，无需手动提示设计，并将 MARC 推广到其默认放射学配置之外。Generated prompts are validated against a set of structural constraints, enforcing correct variable bindings ({input}, {previous_agent_output}), VERDICT formatting conventions, and output length restrictions, before being written to disk and loaded into the MARC pipeline. This enables dynamic pipeline construction across heterogeneous clinical tasks without manual prompt design, and generalizes MARC beyond its default radiology configuration.

2.3 代理提示策略2.3 Agent Prompting Strategy

所有代理均在温度 = 0 时进行零射击操作，确保运行期间的输出具有完全确定性和可重复性。每个提示模板围绕四个组件构建：(1) 建立代理的临床身份和范围的角色定义，(2) 指定提取、分析或生成内容的显式任务指令，(3) 定义格式、长度和有效响应标签的输出约束，以及 (4) 在推理时注入的运行时变量。All agents operate zero-shot at temperature = 0, ensuring fully deterministic and reproducible outputs across runs. Each prompt template is structured around four components: (1) a role definition establishing the agent's clinical identity and scope, (2) explicit task instructions specifying what to extract, analyze, or produce, (3) output constraints defining format, length, and valid response labels, and (4) runtime variables injected at inference time.

图 2. MARC 管道架构：Figure 2. MARC pipeline architectures:(A) 三代理生物医学 QA 管道：提取器 → 推理器 → 具有顺序上下文传递的应答代理。 (B) 具有条件路由的扩展放射学工作流程：异常报告通过分类器和后续代理进行；所有报告均汇聚至评估器。(A) Three-agent biomedical QA pipeline: Extractor → Reasoner → Answer Agent with sequential context passing. (B) Extended radiology workflow with conditional routing: abnormal reports proceed through Classifier and Follow-Up agents; all reports converge at the Evaluator.

每个代理将其结构化输出传递到下一个代理，因此信息可以干净地从一个管道阶段流向下一个管道阶段，而无需代理发明或丢失先前的上下文。推理代理以最终代理定位并逐字返回的标准化判决线结束，从而使最终预测易于提取，无需额外解析。变量绑定和判决格式的完整细节在补充（S2）中提供。Each agent passes its structured output to the next, so information flows cleanly from one pipeline stage to the next without agents inventing or losing prior context. The reasoning agent ends with a standardized verdict line that the final agent locates and returns verbatim, making the final prediction easy to extract without additional parsing. Full details of the variable bindings and verdict formatting are provided in the Supplement (S2).

2.4 代理专业化2.4 Agent Specialization

MARC 通过基于角色的提示而不是模型架构差异化来实现异构代理专业化。在默认管道中，三个专门代理按顺序运行（图 2）：MARC implements heterogeneous agent specialization through role-based prompting rather than model architecture differentiation. In the default pipeline, three specialized agents operate in sequence (Figure 2):

  • 代理1（信息提取）：Agent 1 (Information Extraction):接收原始临床输入并提取 2-4 个任务相关证据的简明要点，包括关键实体、临床发现、约束条件和适用的答案选择。明确指示代理人不要回答问题或得出结论，以确保证据收集和推理之间的清晰分离。Receives the raw clinical input and extracts 2-4 concise bullet points of task-relevant evidence, including key entities, clinical findings, constraints, and answer choices where applicable. The agent is explicitly instructed not to answer the question or produce a conclusion, ensuring clean separation between evidence gathering and reasoning.

  • Agent 2（分类与分析）：Agent 2 (Categorization and Analysis):接收原始输入和代理 1 提取的证据。执行结构化多步骤推理，根据提取的证据评估选项或假设，明确处理歧义，并产生中间推理。以编码最终决策标签的标准化判决线终止。Receives both the original input and Agent 1's extracted evidence. Performs structured multi-step reasoning, evaluating options or hypotheses against the extracted evidence, handling ambiguity explicitly, and producing intermediate reasoning. Terminates with a standardized verdict line encoding the final decision label.

  • 代理 3（推荐生成）：Agent 3 (Recommendation Generation):接收代理 2 的完整推理输出，并被指示找到判决行并仅返回其值，而不进行任何解释或重新格式化。纯粹作为结构化提取器来生成干净、可解析的最终答案。Receives Agent 2's full reasoning output and is instructed to locate the verdict line and return only its value, with no explanation or reformatting. Acts purely as a structured extractor to produce a clean, parseable final answer.

2.5 代理协作2.5 Agent Collaboration

MARC 管道按照配置文件中定义的严格顺序执行代理。对于给定的输入，执行过程如下：The MARC pipeline executes agents in strict sequential order as defined in the configuration file. For a given input, execution proceeds as follows:

  • 代理 1 接收没有先前上下文的原始用户输入。Agent 1 receives the original user input with no prior context.

  • 代理 2 接收原始输入和代理 1 的完整输出。Agent 2 receives both the original input and Agent 1's complete output.

  • 代理 3 接收原始输入和代理 2 的输出，并隐式访问代理 2 响应中嵌入的代理 1 的分析。Agent 3 receives the original input and Agent 2's output, with implicit access to Agent 1's analysis embedded in Agent 2's response.

这种链接策略确保每个代理在最大的相关上下文中运行，同时保持清晰的角色边界（图 2）。每个阶段都会记录中间输出，从而能够对管道中错误的来源进行事后分析。This chaining strategy ensures each agent operates with maximal relevant context while maintaining clear role boundaries (Figure 2). Intermediate outputs are logged at each stage, enabling post-hoc analysis of where in the pipeline errors originate.

2.6 部署2.6 Deployment

MARC 支持两种部署模式（图 4）。基于 API 的部署通过 Google AI Studio 使用 Google 的 Gemini 模型系列（gemini-2.0-flash、gemini-1.5-flash），并且仅需要在 .env 文件中配置 API 密钥。本地部署使用 Ollama 进行 CPU 兼容推理，从而可以在机构环境中使用而无需外部 API 依赖。两种模式都通过agents.yaml进行相同的配置；唯一的区别是每个代理指定的模型标识符。该框架已通过 Ollama 使用 MedGemma 4B 进行临床推理任务测试，并使用 Gemini 模型进行通用测试。MARC supports two deployment modes (Figure 4). API-based deployment uses Google's Gemini model family (gemini-2.0-flash, gemini-1.5-flash) via Google AI Studio and requires only an API key configured in the .env file. Local deployment uses Ollama for CPU-compatible inference, enabling use in institutional environments without external API dependencies. Both modes are configured identically through agents.yaml; the only difference is the model identifier specified per agent. The framework has been tested with MedGemma 4B via Ollama for clinical reasoning tasks and with Gemini models for general-purpose use.

3. 使用案例3. Use Cases

MARC 被设计为通用临床推理框架，仅通过提示和配置更改即可适应广泛的任务。三个代表性用例说明了该框架的灵活性。MARC is designed as a general-purpose clinical reasoning framework and can be adapted to a wide range of tasks through prompt and configuration changes alone. Three representative use cases illustrate the framework's flexibility.

  • 生物医学问答：Biomedical question answering:在三代理 QA 管道中，代理 1 从研究摘要中提取相关证据，代理 2 对提取的证据执行多步骤推理，代理 3 返回干净的是/否/可能的结论。此配置直接映射到 PubMedQA 和 MedQA USMLE 等基准（图 2A）。In a three-agent QA pipeline, Agent 1 extracts relevant evidence from a research abstract, Agent 2 performs multi-step reasoning over the extracted evidence, and Agent 3 returns a clean yes/no/maybe verdict. This configuration maps directly to benchmarks such as PubMedQA and MedQA USMLE (Figure 2A).

  • 放射学报告生成：Radiology report generation:在扩展的放射学管道中，代理 1 从胸部 CT 报告中提取临床结果，代理 2 对已识别的病理进行分类，代理 3 生成结构化印象，代理 4 生成后续建议，代理 5 根据参考标准评估完整输出（图 2B）。条件路由允许普通报告绕过分类并直接进入评估器。In an extended radiology pipeline, Agent 1 extracts clinical findings from a chest CT report, Agent 2 classifies identified pathologies, Agent 3 generates a structured impression, Agent 4 produces follow-up recommendations, and Agent 5 evaluates the full output against reference criteria (Figure 2B). Conditional routing allows normal reports to bypass classification and proceed directly to the Evaluator.

  • 通过 Decomposer 构建任务自适应管道：Task-adaptive pipeline construction via Decomposer:对于默认放射学配置之外的任务，Decomposer 根据简单语言任务描述生成完整的代理管道。这使得能够在异构临床任务中快速部署，无需手动提示设计，正如胸部 CT 病理分类和 USMLE 式临床推理所证明的那样。For tasks outside the default radiology configuration, the Decomposer generates a complete agent pipeline from a plain-language task description. This enables rapid deployment across heterogeneous clinical tasks without manual prompt design, as demonstrated on chest CT pathology classification and USMLE-style clinical reasoning.

4. 讨论4. Discussion

大多数部署的临床法学硕士系统将几个不同的认知步骤压缩为单个模型调用，这使得很难确定系统成功或失败的原因。当产生不正确的输出时，错误可能源于遗漏的信息提取、有缺陷的推理、不良的指令遵循或答案格式，但这些故障模式隐藏在一个不透明的响应中。相反，MARC 将这些功能分离为通过显式上下文传递连接的角色专用代理，并记录每个中间输出。这使得能够进行阶段性的失败归因，并更清楚地了解最终答案是如何产生的，这在临床环境中很重要，因为可解释性是审查、调试、验证和建立信任的实际要求。Most deployed clinical LLM systems collapse several distinct cognitive steps into a single model call, which makes it difficult to determine why a system succeeds or fails. When an incorrect output is produced, the error may originate in missed information extraction, flawed reasoning, poor instruction following, or answer formatting, but these failure modes are hidden inside one opaque response. MARC instead separates these functions into role-specialized agents connected through explicit context passing, and logs each intermediate output. This enables stage-wise failure attribution and a clearer view of how a final answer was produced, which matters in clinical settings where interpretability is a practical requirement for review, debugging, validation, and trust-building.

MARC 的一个核心贡献是它将编排视为可配置层而不是固定实现。通过将代理定义、模型分配、提示模板和可选上下文文件外部化到 YAML 配置文件中，该框架允许用户修改临床 AI 工作流程，而无需更改底层代码。这降低了了解任务和期望行为但缺乏高级编程专业知识的临床研究人员和领域专家的障碍，并且它支持跨模型、提示和任务结构的快速实验。 Decomposer 模块通过将简单语言任务描述转换为结构化多代理管道，进一步扩展了这种可访问性，从而减少了手动提示工程的需要。这对于异构临床任务尤其有价值，其中问题的最佳分解可能事先并不明显。A central contribution of MARC is that it treats orchestration as a configurable layer rather than a fixed implementation. By externalizing agent definitions, model assignments, prompt templates, and optional context files into YAML configuration files, the framework lets users modify clinical AI workflows without changing the underlying code. This lowers the barrier for clinical researchers and domain experts who understand the task and desired behavior but lack advanced programming expertise, and it supports rapid experimentation across models, prompts, and task structures. The Decomposer module extends this accessibility further by converting a plain-language task description into a structured multi-agent pipeline, reducing the need for manual prompt engineering. This is especially valuable for heterogeneous clinical tasks, where the optimal decomposition of a problem may not be obvious in advance.

MARC 还解决了医疗保健领域的一个重要部署问题：对数据和基础设施的机构控制。许多临床环境在将患者数据发送到外部 API 方面面临限制，尤其是在处理受保护的健康信息时。通过 Ollama 支持基于 API 的模型和本地 CPU 兼容的推理，MARC 可以适应一系列机构设置。具有开放或轻量级医疗模型的本地部署可以允许临床团队测试和完善多代理工作流程，同时保持对数据移动、成本和可重复性的更好控制。MARC also addresses an important deployment concern in healthcare: institutional control over data and infrastructure. Many clinical environments face restrictions on sending patient data to external APIs, especially when working with protected health information. By supporting both API-based models and local CPU-compatible inference through Ollama, MARC can be adapted to a range of institutional settings. Local deployment with open or lightweight medical models may allow clinical teams to test and refine multi-agent workflows while maintaining greater control over data movement, cost, and reproducibility.

该框架也是与模型无关的，随着临床人工智能超越单一模型评估，这一点变得越来越重要。由于模型可以在代理级别交换，因此可以根据成本、延迟、领域专业化、隐私要求或性能将管道的不同阶段分配给不同的模型系列。随着新的基础模型的出现，这使得系统更具适应性。The framework is also model-agnostic, which is increasingly important as clinical AI moves beyond single-model evaluations. Because models can be swapped at the agent level, different stages of the pipeline can be assigned to different model families based on cost, latency, domain specialization, privacy requirements, or performance. This makes the system more adaptable as new foundation models become available.

尽管有这些优点，MARC v1 也有一些局限性。当前的默认实现强调顺序代理执行，这提高了可解释性，但可能不适用于所有任务。一些临床工作流程可能受益于并行代理、动态路由、分歧解决或迭代细化循环。同样，虽然三代理架构对于许多推理任务很有用，但更复杂的工作流程可能需要具有专门评估器、检索器、安全检查或人机交互审核步骤的可变深度管道。 MARC 的未来版本应该探索更灵活的编排策略，包括条件分支、并行执行和自适应代理选择。Despite these strengths, MARC v1 has several limitations. The current default implementation emphasizes sequential agent execution, which improves interpretability but may not be optimal for all tasks. Some clinical workflows may benefit from parallel agents, dynamic routing, disagreement resolution, or iterative refinement loops. Similarly, while the three-agent architecture is useful for many reasoning tasks, more complex workflows may require variable-depth pipelines with specialized evaluators, retrievers, safety checks, or human-in-the-loop review steps. Future versions of MARC should explore more flexible orchestration strategies, including conditional branching, parallel execution, and adaptive agent selection.

另一个限制是本手稿主要介绍框架设计和代表性用例，而不是全面的经验基准。未来的评估应该跨不同的临床任务、数据集和模型后端测试 MARC，以确定与单提示基线相比，多代理编排何时可以提高性能、可靠性、可解释性或稳健性。此类评估不仅应包括基于准确性的指标，还应包括错误定位、可重复性、延迟、成本和临床医生可用性。这些因素对于确定多智能体系统是否在现实临床人工智能部署中提供实用价值至关重要。Another limitation is that this manuscript primarily presents the framework design and representative use cases rather than a comprehensive empirical benchmark. Future evaluation should test MARC across diverse clinical tasks, datasets, and model backends to determine when multi-agent orchestration improves performance, reliability, interpretability, or robustness compared with single-prompt baselines. Such evaluation should include not only accuracy-based metrics but also error localization, reproducibility, latency, cost, and clinician usability. These factors are essential for determining whether multi-agent systems provide practical value in real-world clinical AI deployment.

总之，MARC v1 提供了一个实用且可扩展的框架，用于通过确定性多代理编排构建可解释的临床 AI 工作流程。它将临床推理构建为透明、可配置和可检查的阶段，支持调试、适应、本地部署和特定于任务的管道构建，而不是将 LLM 视为单步答案生成器。随着法学硕士和多模式基础模型越来越多地融入放射学和更广泛的临床工作流程，优先考虑模块化、透明度和机构可部署性的框架对于安全和可扩展的临床人工智能至关重要。In summary, MARC v1 provides a practical and extensible framework for building interpretable clinical AI workflows through deterministic multi-agent orchestration. Rather than treating LLMs as single-step answer generators, it structures clinical reasoning into transparent, configurable, and inspectable stages that support debugging, adaptation, local deployment, and task-specific pipeline construction. As LLMs and multimodal foundation models become more integrated into radiology and broader clinical workflows, frameworks that prioritize modularity, transparency, and institutional deployability will be essential for safe and scalable clinical AI.

5. 结论5. Conclusion

MARC 提供了一个实用框架，用于构建可解释、可访问且可机构部署的临床人工智能系统。通过将编排逻辑与模型选择、提示设计和执行代码分离，MARC 使临床团队能够构建、修改和验证推理管道，而无需高级编程专业知识。其模块化多代理结构支持透明的中间输出、灵活的模型部署以及跨临床工作流程的特定任务适应。随着代理系统越来越多地融入放射学和更广泛的医疗实践中，优先考虑透明度、可配置性和可重复性的框架对于超越单一提示转向更安全、更可扩展的临床人工智能部署至关重要。MARC provides a practical framework for building interpretable, accessible, and institutionally deployable clinical AI systems. By separating orchestration logic from model selection, prompt design, and execution code, MARC enables clinical teams to construct, modify, and validate reasoning pipelines without requiring advanced programming expertise. Its modular multi-agent structure supports transparent intermediate outputs, flexible model deployment, and task-specific adaptation across clinical workflows. As agentic systems become increasingly integrated into radiology and broader medical practice, frameworks that prioritize transparency, configurability, and reproducibility will be essential for moving beyond monolithic prompting toward safer and more scalable clinical AI deployment.
