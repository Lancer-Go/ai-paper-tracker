为了验证 MemDocAgent 的有效性，我们根据现有基线从四个维度对其进行评估：完整性、真实性、有用性和信息充分性。现有的指标捕获了覆盖率、准确性和有用性，但忽略了实际代码理解的实现级别的充分性。因此，我们引入信息充分性作为一种定量指标，用于衡量生成的文档是否单独提供了足够的信息来重现原始源代码。 根据经验，MemDocAgent 在所有四个标准中均实现了最佳性能，这表明其文档捕获了支持实际软件开发工作流程所需的广度和深度。To validate the effectiveness of MemDocAgent, we evaluate it against existing baselines along four dimensions: completeness, truthfulness, helpfulness, and information sufficiency. Empirically, MemDocAgent achieves the best performance across all four criteria, demonstrating that its documentation captures both the breadth and the depth required to support real software development workflows.

2 相关工作Related work

2.1 长视野编码剂Long-horizon coding agents

最近的编码代理已经从解决孤立的编程任务发展到通过大量顺序工具调用和推理步骤执行扩展轨迹Recent coding agents have advanced from solving isolated programming tasks to executing extended trajectories with numerous sequential tool calls and reasoning steps[56, 50, 60, 40, 5, 10, 31, 59, 29]。这种长期制度建立在 ReAct 等代理基础之上. This long-horizon regime builds on agentic foundations such as ReAct[58], 反射, Reflexion[44]和多代理框架, and multi-agent frameworks[18, 42, 51]。一个关键的挑战是工作记忆在转弯时累积并超出上下文窗口，导致智能体失去对先前目标的跟踪或在整个轨迹中传播错误. A key challenge is that working memory accumulates across turns and exceeds the context window, causing agents to lose track of prior objectives or propagate errors throughout the trajectory[28, 45, 48].

为了处理长上下文，先前的工作已经探索了在模型外部维护和动态组织上下文的外部存储系统To handle long contexts, prior work has explored external memory systems that maintain and dynamically organize context outside the model[37, 36, 49, 62, 16, 54, 19]，以及基于摘要和压缩的上下文管理技术, along with summarization and compression based techniques for context management[52, 21, 27]。 然而，这些方法是针对单一输出设置而设计的，其中内存支持单一最终答案，并且当多个顺序生成的输出必须保持相互一致时，这些方法就显得不足了。. However, these methods are designed for single output settings where memory supports a single final answer, and fall short when multiple sequentially generated outputs must remain mutually consistent.

早期的代码文档方法侧重于功能级摘要、训练模型来为各个代码单元生成简短的自然语言描述Early code documentation methods focused on function-level summarization, training models to produce short natural language descriptions for individual code units[35, 20, 25, 7, 41]。随着法学硕士的出现，这一范围扩大到课堂和项目层面的总结. With the emergence of LLMs, this scope expanded to summarization at the class and project levels[22, 30, 33, 15, 2, 46, 6]，并且最近的系统已经开始在整个存储库上运行。回购代理, and recent systems have begun to operate over entire repositories. RepoAgent[32]提取依赖关系并通过 LLM 管道按拓扑顺序生成组件级文档字符串，而 DocAgentextracts dependency relations and generates component-level docstrings in topological order through an LLM pipeline, while DocAgent[55]采用多代理管道来实现相同的组件级目标。代码维基adopts a multi-agent pipeline for the same component-level objective. 虽然这些方法成功地将文档生成扩展到存储库规模，但它们将每个组件视为独立的单元，从而无法在长期文档轨迹中保持跨文档一致性或依赖感知推理。 这种按组件进行的处理会导致冗余检索和文档间矛盾，从而破坏最终文档的实际效用。While these methods successfully extend documentation generation to the repository scale, they treat each component as an independent unit, thereby failing to maintain cross-document consistency or dependency-aware reasoning across the long-horizon documentation trajectory. This per-component processing leads to redundant retrievals and inter-document contradictions that undermine the practical utility of the resulting documentation.

局限性Limitation

长期代理文档任务需要计算资源，因为输入上下文和生成的输出都可能在轨迹上变得很大。此外，由于智能体依赖于模型的推理能力，因此有时可能会进入重复循环而没有完成子任务。尽管总体影响很小，在我们的实验中只有 0.08% 的组件在未达到验证阈值的情况下终止，但仍应考虑这一限制。未来的工作应该探索更有效的轨迹控制、自适应停止标准和更强的恢复机制。Long-horizon agentic documentation task requires computational resources because both input context and generated outputs can grow large over the trajectory. In addition, because the agent depends on the model’s reasoning ability, it may occasionally enter a repeated loop without completing the sub-task. Although the overall impact is minimal, with only 0.08% of components terminating without meeting the verification threshold in our experiments, this limitation should still be considered. Future work should explore more efficient trajectory control, adaptive stopping criteria, and stronger recovery mechanisms.
