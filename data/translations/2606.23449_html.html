AOHP：用于个性化、高效和安全交互的开源操作系统级代理工具AOHP: An Open-Source OS-Level Agent Harness for Personalized, Efficient and Secure Interaction

人工智能代理正在推动一种新的软件范例，能够自主调用工具、提取信息、管理内存以及完成跨应用程序和数据源的任务。然而，大多数现有的最终用户操作系统都是为以应用程序为中心的工作流程而设计的，几乎没有为人工智能代理提供原生支持。这种不匹配限制了代理的更广泛采用，并在传统系统上运行代理时导致执行开销和安全风险。AI agents are driving a new software paradigm, with the ability to autonomously call tools, extract information, manage memory, and complete tasks that span applications and data sources. Most existing end-user operating systems, however, are designed for application-centric workflows and offer little native support for AI agents. This mismatch limits the wider adoption of agents and leads to execution overhead and safety risks when running agents on conventional systems.

虽然代理本机操作系统的概念正在兴起，但研究界缺乏一个开放的测试平台来探索代理介导的交互所需的架构原语。我们提出了 AOHP（Android 开放线束项目），这是一个基于 Android 开源项目 (AOSP) 构建的操作系统级代理线束。 AOHP 的核心设计原则是将代理视为一流的操作系统参与者，从而实现自适应用户界面和代理友好的运行时环境。 AOHP保留了成熟的Android软硬件生态系统，同时引入了三种面向Agent的系统机制：个性化的服务组合、高效的Agent接口和安全的信息流。基于涵盖操作系统代理关键功能的挑战性任务的初步实验，AOHP 在任务完成（+21.12% 完成率）、执行成本（-51.55% 代币成本）和安全策略合规性方面显示出明显的优势。While the concept of agent-native operating systems is emerging, the research community lacks an open testbed to explore the architectural primitives desired for agent-mediated interaction. We present AOHP (Android Open Harness Project), an OS-level agent harness built on the Android Open Source Project (AOSP). The core design principle of AOHP is to treat agents as first-class OS actors, enabling adaptive user interfaces and agent-friendly runtime environments. AOHP preserves the mature Android software and hardware ecosystem while introducing three agent-oriented system mechanisms: personalized service composition, efficient agent interfaces, and secure information flow. Based on preliminary experiments on challenging tasks covering key capabilities of OS agents, AOHP shows clear advantages in task completion (+21.12% completion rate), execution cost (-51.55% token cost), and security-policy compliance.

一、简介1. Introduction

人工智能代理正在从根本上改变人类与数字环境交互的方式，从孤立的聊天界面转向操作系统本身。现代代理可以调用​​命令行工具、检查图形界面、使用应用程序 API 以及协调多步骤任务 [25,13,​​2]。代理介导的交互改变了操作系统的角色：操作系统仍然托管应用程序，但它还需要支持观察服务、调用功能并跨应用程序边界强制执行用户意图的代理。AI agents are fundamentally changing how humans interact with digital environments, moving from isolated chat interfaces into the operating system itself. Modern agents can call command-line tools, inspect graphical interfaces, use application APIs, and coordinate multi-step tasks [25, 13, 2]. Agentmediated interaction changes the role of the operating system: the OS still hosts applications, but it also needs to support agents that observe services, invoke capabilities, and enforce user intent across app boundaries.

传统的个人操作系统在设计上以应用程序为中心。接口由系统和应用程序开发人员固定。 GUI 是为了直接的人类视觉操作而不是代理操作而呈现的。软件生命周期假设一次有一个活动应用程序，权限机制在应用程序边界强制实施保护，但无法跨代理上下文和工具调用跟踪敏感数据。这些假设为代理介导的工作流程带来了巨大的执行开销和安全漏洞。Conventional personal operating systems are app-centric by design. Interfaces are fixed by system and application developers. GUIs are rendered for direct human visual operation rather than agent manipulation. Software lifecycle assumes one active app at a time, and permission mechanisms enforce protections at app boundaries but fail to track sensitive data across an agent’s context and tool calls. These assumptions create significant execution overhead and security gaps for agent-mediated workflows.

AOHP 通过操作系统级抽象和框架修改将 Android 重新设计为代理本机工具，从而解决了这一差距。它保留了 Android 的硬件支持、开源框架和应用程序兼容性，同时添加了使服务可组合、高效且可审计的机制，可供操作系统级代理使用。AOHP addresses this gap by redesigning Android as an agent-native harness via OS-level abstractions and framework modifications. It preserves Android’s hardware support, open-source framework, and app compatibility while adding mechanisms that make services composable, efficient, and auditable for OS-level agents.

2. 背景与动机2. Background & Motivation

对 AOHP 的需求来自于以下方面的变化The need for AOHP comes from a change in如何how用户与数字服务交互。users interact with digital services.

2.1.自适应用户界面的新兴需求2.1. Emerging Demand of Adaptive User Interfaces

传统操作系统通过应用程序定义的接口公开功能。用户可以看到操作系统和应用程序开发人员选择的菜单、按钮、页面和工作流程。这意味着用户只能被动地适应开发者确定的服务和信息，这可能是乏味和分散注意力的，甚至会偏差用户的认知。随着应用程序变得越来越大并且占据主导地位，这个问题变得越来越严重。Traditional operating systems expose functionality through app-defined interfaces. Users see menus, buttons, pages, and workflows chosen by the OS and app developers. This means that users can only passively adapt to the services and information determined by the developers, which may be tedious and distracting, even biasing the users’ perception. The issue becomes increasingly severe as the apps are growing larger and dominating.

开发自适应用户界面的一个有前景的解决方案。在自适应操作系统中，用户界面可以围绕用户意图进行深度个性化。例如，在多个市场购物的用户不需要推理哪个应用程序拥有哪种功能。相反，操作系统可以生成一个购物入口，聚合来自不同服务的产品搜索、比较、优惠券、交付限制和购买操作。入口不是一个开发者安装的静态应用程序；它由应用程序、GUI、CLI 和 API 接口组装而成，并通过系统内存进行个性化。A promising solution to develop adaptive user interfaces. In an adaptive OS, the user interface can be deeply personalized around user intent. For example, a user who shops across multiple marketplaces should not need to reason about which app owns which capability. Instead, the OS can generate a shopping entrance that aggregates product search, comparison, coupons, delivery constraints, and purchase actions from different services. The entrance is not a static app installed by one developer; it is assembled from app, GUI, CLI, and API interfaces and personalized by system memory.

2.2.代理成为主要工作量2.2. Agents Become a Major Workload

人工智能代理有望实现这种自适应体验。现代代理可以操作应用程序、发出命令以及与 Web 或应用程序服务交互。在许多工作流程中，代理可以充当用户意图和应用程序级操作之间的执行层：它读取应用程序状态、调用系统功能、跨服务传输数据、等待异步事件以及随着时间的推移重复执行操作。AI agents are promising to enable such adaptive experiences. Modern agents can operate applications, issue commands, and interact with web or app services. In many workflows, the agent can serve as an execution layer between user intent and app-level operations: it reads application state, invokes system functions, transfers data across services, waits for asynchronous events, and acts repeatedly over time.

代理介导的交互暴露了传统操作系统设计中的缺陷。现有系统采用应用程序介导的交互，而代理具有不同的操作属性。它们比像素更有效地处理结构化文本，并行运行多个任务，保留长期上下文，并使工具调用比用户检查它们的速度更快。围绕应用程序介导的交互设计的系统无法通过构造使代理执行高效或安全。Agent-mediated interaction exposes a gap in conventional OS design. Existing systems assume appmediated interaction, while agents have different operational properties. They process structured text more efficiently than pixels, run multiple tasks in parallel, retain long-lived context, and make tool calls faster than users can inspect them. A system designed around app-mediated interaction cannot make agent execution efficient or safe by construction.

2.3.为什么我们需要操作系统级安全带2.3. Why We Need A OS-level Harness

为了使代理介导的自适应用户界面可行、高效和安全，系统和框架层中的许多组件应该重新设计，同时许多其他组件可以重用。因此，在现有的成熟操作系统上构建一个工具是一个理想的选择。出于实际原因，我们选择 Android 作为 AOHP 的底层。To make the agent-mediated adaptive user interfaces feasible, efficient and secure, many components in the system and framework layers should be redesigned, while many other componnents can be reused. Therefore, building a harness over an existing mature OS is an ideal choice. We choose Android as the substrate for AOHP for practical reasons.

丰富的应用生态。Rich application ecosystem.Android 提供了广泛的应用程序生态系统，涵盖通信、生产力、商务、内容和设备控制，这对于培育丰富的定制服务非常有用。Android offers a broad app ecosystem covering communication, productivity, commerce, content, and device control, which is useful to foster rich custom services.

成熟的硬件支持。Mature hardware support.Android 已经在广泛的设备上运行，并为驱动程序、传感器、网络和电源管理提供了支持。Android already runs on a wide spectrum of devices with established support for drivers, sensors, networking, and power management.

开源可访问性。Open-source accessibility.Android 开源项目允许对系统服务、框架层、UI 堆栈和运行时策略进行深入修改，这使其成为细粒度系统研究的实用基础 [8]。The Android Open Source Project allows deep modifications to system services, framework layers, UI stacks, and runtime policies, which makes it a practical base for fine-grained systems research [8].

4、个性化服务构成4. Personalized Service Composition

AOHP 最明显的变化是交互界面变得个性化和生成，而不是完全预定义。传统的应用程序公开开发人员选择的功能。 AOHP 让操作系统代理围绕重复目标综合服务入口，将交互从应用程序导航转变为任务级服务访问。The most visible change in AOHP is that interaction surfaces become personalized and generated rather than fully predefined. A conventional app exposes developer-chosen functions. AOHP lets the OS agent synthesize service entrances around recurring goals, shifting interaction from app navigation to task-level service access.

4.1.生成的服务入口4.1. Generated Service Entrances

生成的入口是面向用户的 shell，由操作系统管理的服务组合支持。购物入口可以聚合来自多个提供商的产品搜索，标准化产品属性，应用尺寸和预算等偏好，并公开用于比较和购买的特定于任务的界面。Generated entrances are user-facing shells backed by OS-managed service composition. A shopping entrance can aggregate product search from multiple providers, normalize product attributes, apply preferences such as size and budget, and expose a task-specific interface for comparison and purchase.

每个入口包含三个部分：任务模式、服务图和呈现策略。任务模式定义用户试图完成的任务，例如“比较预算内的鞋子”或“补充家庭用品”。服务图将此任务映射到具体的服务功能。呈现策略决定哪些中间结果应显示给用户以及哪些可以保留在代理内部。这种分离使 AOHP 可以个性化入口，而无需隐藏相应的决定。Each entrance contains three parts: a task schema, a service graph, and a presentation policy. The task schema defines what the user is trying to accomplish, such as “compare shoes under a budget” or “refill household supplies”. The service graph maps this task to concrete service capabilities. The presentation policy decides which intermediate results should be shown to the user and which can remain agent-internal. This separation lets AOHP personalize the entrance without hiding consequential decisions.

4.2.能力发现与构成4.2. Capability Discovery and Composition

AOHP 通过跨 API、CLI 和 GUI 渠道发现服务功能来构建这些入口。每个功能都用输入/输出模式、先决条件、副作用和策略标签来表示。然后，操作系统代理可以将功能组合到更高级别的工作流程中。这种设计允许旧应用程序通过 GUI 导出参与，同时允许更新的服务公开更直接的 API。AOHP builds these entrances by discovering service capabilities across API, CLI, and GUI channels. Each capability is represented with input/output schemas, preconditions, side effects, and policy labels. The OS agent can then compose capabilities into a higher-level workflow. This design lets legacy apps participate through GUI export while allowing newer services to expose more direct APIs.

4.3.跨服务个性化4.3. Cross-Service Personalization

系统内存让个性化不受应用程序限制。在使用一项服务时了解到的偏好可以改进另一项服务，但须遵守政策。例如，在比较来自另一个市场的产品时，可以使用从一个购物工作流程中了解到的用户的首选交付窗口。设计要求是内存仍然以操作系统为中介：个性化可以共享、审核和撤销，而不依赖于每个应用程序的私有数据模型。System memory lets personalization survive app boundaries. Preferences learned while using one service can improve another service, subject to policy. For example, a user’s preferred delivery window learned from one shopping workflow can be used when comparing products from another marketplace. The design requirement is that memory remains OS-mediated: personalization can be shared, audited, and revoked without depending on each app’s private data model.

AOHP 区分持久配置文件内存、任务本地内存和敏感内存。持久的配置文件内存存储稳定的偏好。任务本地内存存储临时状态，例如候选产品或部分完成的表格。敏感内存通过沙箱索引存储私有值。这种区别可以防止个性化成为私人环境的不受控制的积累。AOHP distinguishes between persistent profile memory, task-local memory, and sensitive memory. Persistent profile memory stores stable preferences. Task-local memory stores temporary state, such as candidate products or partially completed forms. Sensitive memory stores private values through sandbox indices. This distinction prevents personalization from becoming an uncontrolled accumulation of private context.

5. 高效的代理接口5. Efficient Agent Interfaces

AOHP 将执行环境、UI 语义、存储和事件公开为代理本机原语。这些抽象减少了代理介导的工作流程中的视觉处理开销、严格的顺序执行和脆弱的跨应用程序切换。AOHP exposes execution environments, UI semantics, storage, and events as agent-native primitives. These abstractions reduce visual-processing overhead, rigid sequential execution, and brittle cross-app handoffs in agent-mediated workflows.

5.1.并行后台交互5.1. Parallel Background Interaction

传统的移动操作系统将应用程序生命周期与物理显示器结合在一起。 AOHP 通过轻量级虚拟显示器将执行与屏幕解耦，允许代理在后台运行等待繁重或独立的工作流程，而无需抢占活动的前台会话。Conventional mobile OSes couple app lifecycles to the physical display. AOHP decouples execution from the screen through lightweight virtual displays, allowing agents to run waiting-heavy or independent workflows in the background without preempting the active foreground session.

5.2.代理感知 UI 增强5.2. Agent-aware UI Enhancement

传统的应用程序 GUI 包含代理推理不需要的渲染细节。 AOHP 将 GUI 抽象为具有更低冗余和更丰富语义的结构化表示，同时保留可视组件的渲染 GUI 回退。Conventional app GUIs contain rendering details that are unnecessary for agent reasoning. AOHP abstracts GUIs into structured representations with lower redundancy and richer semantics, while retaining rendered GUI fallback for visual components.

5.3.本机沙箱运行时5.3. Native Sandbox Runtime

应用程序介导的 GUI、API 和 CLI 路径并不涵盖所有代理工作。代理通常需要本地执行基础来进行计算、转换和工具。 AOHP 包括一个本机的、操作系统管理的沙箱运行时，可以将其创建和重置为独立于面向应用程序的接口的执行表面。代理可以在沙箱内执行代码、处理数据和托管长时间运行的服务，然后将结构化结果返回到任务上下文，而无需在代理上下文中放置中间步骤。App-mediated GUI, API, and CLI paths do not cover all agent work. Agents often need a local execution substrate for computation, transformation, and tooling. AOHP includes a native, OS-managed sandbox runtime that can be created and reset as an execution surface independent of app-facing interfaces. Agents can execute code, process data, and host long-running services inside the sandbox, then return structured results to the task context without placing intermediate steps in the agent context.

5.4.统一文件快捷方式5.4. Unified File Shortcut

跨应用程序代理工作流程通常依赖文件作为共享中间工件，例如在一个应用程序中保存附件并在另一个应用程序中重用它。在库存系统上，这些工件仍然是隐式的：GUI 操作可能会创建或修改存储，但代理缺乏对结果的稳定的操作系统级别的说明。相反，程序化文件操作没有统一的方式来调用应用程序本机可供性，例如当目的地需要它们时系统共享流。 AOHP 将文件视为操作系统边界上的一流任务对象。影响存储的 GUI 交互会以结构化文件观察的形式反映回来，因此代理可以推断发生了什么变化，而无需从屏幕截图或每个应用程序选择器推断路径。在相反的方向上，同一层允许代理将已解析的工件传递到另一个界面，无论是通过直接编程访问还是通过在选定的显示器上启动适当的系统 UI 流。这将文件生成 GUI 步骤和文件消耗编程步骤统一到单个跨应用程序数据平面中，并减少了不透明存储布局之间的脆弱切换。Cross-app agent workflows often rely on files as shared intermediate artifacts, such as saving an attachment in one app and reusing it in another. This unifies file-producing GUI steps and file-consuming programmatic steps into a single cross-app data plane and reduces brittle handoffs across opaque storage layouts.

这种抽象将事件生成与消耗分开，允许代理对系统和环境变化做出反应，而无需重复轮询。The abstraction separates event generation from consumption, allowing agents to react to system and environmental changes without repeated polling.

6. 安全信息流6. Secure Information Flow

AOHP 将敏感数据视为操作系统控制的状态，而不是代理可见的上下文。默认情况下，私有明文在到达代理之前会被替换为键入的引用；受信任的系统组件调解明文操作、外部传输和批准，同时保留审计证据。此模型是必要的，因为代理任务跨越应用程序、工具、内存和服务边界，而传统应用程序权限无法跟踪私有数据的传播方式。AOHP treats sensitive data as OS-controlled state rather than agent-visible context. By default, private plaintext is replaced with typed references before it reaches the agent; trusted system components mediate plaintext operations, external transfers, and approvals while preserving evidence for audit. This model is necessary because agent tasks cross app, tool, memory, and service boundaries where conventional app permissions cannot track how private data propagates.

6.1.政策执行6.1. Policy Enforcement

For each sensitive operation, the policy layer evaluates the data source, requested purpose, destination, action sensitivity, and approval state. This lets ordinary non-sensitive flows proceed while requiring consent or blocking transfers and state-changing actions involving private data.

6.2.敏感源消毒6.2. Sensitive Source Sanitization

AOHP 对敏感源采取保守的保护策略。在敏感内容进入代理上下文之前，AOHP 会使用键入的占位符替换纯文本，例如AOHP adopts a conservative protection strategy for sensitive sources. 系统维护一个数据仓库，在不透明标识符后面存储敏感值。 AOHP 清理支持的源，包括应用程序页面、文件、事件流、API 响应、系统内存和用户交互。开发者提供的注解可以显式标记敏感字段；当注释不可用时，AOHP 会应用保守的检测规则来保护可能的敏感内容。The system maintains a data vault that stores sensitive values behind opaque identifiers. AOHP sanitizes supported sources, including application pages, files, event streams, API responses, system memory, and user interactions. Developer-provided annotations can mark sensitive fields explicitly; when annotations are unavailable, AOHP applies conservative detection rules to protect likely sensitive content.

6.3.可信保管库和执行6.3. Trusted Vault and Execution

当代理需要对敏感信息进行操作时，它会使用相应的占位符向受信任的保管库执行器提交意图。执行者检查策略，必要时获得用户批准，并在可信环境内执行格式化、比较、验证或组合等操作。如果结果仍然敏感，执行器将返回另一个占位符而不是明文。When an agent needs to operate on sensitive information, it submits an intent to a trusted vault executor using the corresponding placeholder. The executor checks policy, obtains user approval when necessary, and performs operations such as formatting, comparison, validation, or composition inside the trusted environment. If the result is still sensitive, the executor returns another placeholder rather than plaintext.

受信任的执行者还调解到外部接口的敏感传输。对于GUI使用，可以直接填写批准的字段；对于 API 或 CLI 使用，它可以在系统边界替换纯文本，同时将其排除在代理上下文之外。这种设计使代理可以完成需要私有数据的任务，同时仅向受信任的系统组件公开敏感值。The trusted executor also mediates sensitive transfers to external interfaces. For GUI use, it can fill an approved field directly; for API or CLI use, it can substitute plaintext at the system boundary while keeping it out of the agent context. This design lets agents complete tasks that require private data while exposing sensitive values only to trusted system components.

6.4.数据流污点跟踪6.4. Data-Flow Taint Tracking

消毒可保护入口点的敏感源；污点跟踪会在使用后保留它们的来源。一旦敏感数据进入 AOHP，它就会与通过复制、转换、组合和传输跟随该值的污点元数据相关联。这使得 AOHP 能够保留信息流链，即使在多个任务步骤中间接使用私有数据时也是如此。Sanitization protects sensitive sources at entry points; taint tracking preserves their provenance after they are used. Once sensitive data enters AOHP, it is associated with taint metadata that follows the value through copying, transformation, composition, and transfer. This allows AOHP to preserve the information-flow chain even when private data is used indirectly across multiple task steps.

在系统出口和其他与策略相关的边界处，AOHP 在显示、存储、提交或传输受污染的数据之前对其进行检查。生成的污点路径还提供了审计跟踪，用于解释哪个源通过哪些任务步骤到达哪个接收器。通过这种方式，代理可以对敏感引用进行推理，而操作系统仍然负责跟踪和控制私有数据何时离开可信组件。At system exits and other policy-relevant boundaries, AOHP checks tainted data before it is displayed, stored, submitted, or transmitted. The resulting taint path also provides an audit trail for explaining which source reached which sink through which task steps. In this way, the agent can reason over sensitive references, while the operating system remains responsible for tracking and controlling when private data may leave trusted components.

八、相关工作8. Related Work

8.1. GUI 代理和移动任务自动化8.1. GUI Agents and Mobile Task Automation

最近的工作表明，基于大型语言模型的代理可以通过图形界面操作计算机和智能手机。现有方法涵盖模块化系统和端到端策略。 AutoDroid 系列、Agent S 和 OS-Copilot 等模块化系统组成了规划器、检索器、内存模块和接地组件，以提高重用和错误恢复[17,18,1,20]。 AppAgent、UI-TARS、Mobile-Agent 和 SeeAct 等端到端方法直接从当前观察中推断操作，通常在屏幕截图或 UI 描述上使用多模态模型 [28,14,29,16,26]。相关基准测试，例如 AndroidWorld、OSWorld、AndroidLab 和 MobileWorld，评估动态 GUI 环境中的代理 [15,22,23,10]。Recent work has shown that large-language-model-based agents can operate computers and smartphones through graphical interfaces. Existing approaches span modular systems and end-to-end policies. Modular systems such as the AutoDroid series, Agent S, and OS-Copilot compose planners, retrievers, memory modules, and grounding components to improve reuse and error recovery [17, 18, 1, 20]. End-to-end approaches such as AppAgent, UI-TARS, Mobile-Agent, and SeeAct directly infer actions from current observations, often using multimodal models over screenshots or UI descriptions [28, 14, 29, 16, 26]. Related benchmarks, such as AndroidWorld, OSWorld, AndroidLab, and MobileWorld, evaluate agents in dynamic GUI environments [15, 22, 23, 10].

这些系统提高了 GUI 代理的性能，但它们主要将操作系统视为固定基底。 AOHP 研究执行环境本身：它不是仅仅提出更强的代理策略，而是重新设计了此类策略所依赖的操作系统接口和执行机制。These systems improve GUI-agent performance, but they mainly treat the operating system as a fixed substrate. AOHP studies the execution environment itself: instead of proposing only a stronger agent policy, it redesigns the OS interfaces and enforcement mechanisms that such policies depend on.

8.2. Android 自动化和接口抽象8.2. Android Automation and Interface Abstraction

在 LLM 代理兴起之前，Android 自动化和测试系统已经探索了如何以编程方式与移动界面进行交互。 DroidBot 等系统强调 UI 引导的探索，而早期的指令跟踪工作将自然语言请求映射到移动动作序列 [12, 11]。最近的界面理解模型，包括 ScreenAI、OS-ATLAS、Aguvis 和其他 GUI 基础方法，改进了屏幕内容的语义解释 [3,21,24,4]。Before the rise of LLM agents, Android automation and testing systems had already explored how to interact with mobile interfaces programmatically. Systems such as DroidBot emphasized UI-guided exploration, while earlier instruction-following work mapped natural language requests into mobile action sequences [12, 11]. More recent interface-understanding models, including ScreenAI, OS-ATLAS, Aguvis, and other GUI grounding methods, improve semantic interpretation of screen content [3, 21, 24, 4].

AOHP 将屏幕理解作为一个组件。现有的自动化和 GUI 代理系统仍然继承以应用程序为中心的渲染路径、面向前台的执行假设以及应用程序定义的交互界面。 AOHP 将这些问题转移到操作系统抽象中，包括个性化服务入口、代理感知 UI 增强、并行后台交互和系统管理的任务跟踪。AOHP uses screen understanding as one component. Existing automation and GUI-agent systems still inherit app-centric rendering paths, foreground-oriented execution assumptions, and app-defined interaction surfaces. AOHP moves these concerns into operating-system abstractions, including personalized service entrances, agent-aware UI enhancement, parallel background interaction, and system-managed task traces.

8.3.系统安全性、来源和可恢复性8.3. System Safety, Provenance, and Recoverability

最近的安全研究表明，使用工具的代理面临着广泛的攻击面，其中不受信任的外部内容可以劫持工具执行或窃取私人数据。间接提示注入首先暴露了 LLM 集成应用程序如何模糊数据和指令之间的界限 [9]； InjecAgent 和 AgentDojo 等基准测试在实际工具使用设置中进一步系统化了这些风险 [27, 6]。这些结果激发了调解数据、权限和操作的系统机制，而不仅仅是依赖于模型级的稳健性。Recent security studies show that tool-using agents face a broad attack surface in which untrusted external content can hijack tool execution or exfiltrate private data. Indirect prompt injection first exposed how LLM-integrated applications blur the boundary between data and instructions [9]; benchmarks such as InjecAgent and AgentDojo further systematize these risks in realistic tool-use settings [27, 6]. These results motivate system mechanisms that mediate data, authority, and actions rather than relying only on model-level robustness.

最近的系统防御已转向执行边界的确定性执行。 FIDES 和 f-secure LLM 系统将信息流控制应用于代理规划器和 LLM 管道，使用标签、污点传播和策略检查来防止不受信任的数据引导敏感决策 [5, 19]。 AOHP 遵循这种面向系统的方向，但将执行边界移至移动操作系统。 AOHP 以 TaintDroid [7] 的移动污点跟踪谱系为基础，跨应用程序 UI、文件、事件流、库引用、生成的入口和用户审批循环跟踪和调解敏感数据。Recent systems defenses have moved toward deterministic enforcement at execution boundaries. FIDES and f-secure LLM systems apply information-flow control to agent planners and LLM pipelines, using labels, taint propagation, and policy checks to prevent untrusted data from steering sensitive decisions [5, 19]. AOHP follows this systems-oriented direction but moves the enforcement boundary to the mobile OS. Building on the mobile taint-tracking lineage of TaintDroid [7], AOHP tracks and mediates sensitive data across app UI, files, event streams, vault references, generated entrances, and user approval loops.

9. 结论和未来工作9. Conclusion and Future Work

AOHP 是 Android 的原生代理开放分支，用于代理介导的个人计算。它保持了 Android 兼容性，同时添加了个性化的服务组合、高效的代理接口和安全的信息流。 OpenClaw 的初步结果显示，与原生 Android 相比，任务完成率更高，执行成本更低；安全案例研究表明，敏感数据可以在系统边界进行编辑、跟踪和调解。AOHP is an agent-native open fork of Android for agent-mediated personal computing. It keeps Android compatibility while adding personalized service composition, efficient agent interfaces, and secure information flow. Preliminary results with OpenClaw show higher task completion and lower execution cost than stock Android; the security case study shows that sensitive data can be redacted, tracked, and mediated at system boundaries.

兼容性覆盖。Compatibility coverage.未来的工作应该扩大对具有自定义渲染、反自动化逻辑和未记录行为的应用程序的支持。这需要更强大的结构化 UI 提取、可预见失败的渲染 GUI 后备，以及为应用程序开发人员提供更清晰的兼容性指南。Future work should expand support for apps with custom rendering, antiautomation logic, and undocumented behavior. This requires stronger structured UI extraction, renderedGUI fallback that fails predictably, and clearer compatibility guidelines for app developers.

能力发现。Capability discovery.AOHP 依赖于准确的服务描述、副作用标签和策略元数据。未来的版本应该将开发人员提供的描述符与自动功能推断相结合，以便可以通过更少的手动注释来集成遗留应用程序。AOHP depends on accurate service descriptions, side-effect labels, and policy metadata. Future versions should combine developer-provided descriptors with automatic capability inference so that legacy apps can be integrated with less manual annotation.

资源调度。Resource scheduling.后台执行必须遵守移动资源、热量和内存限制。更完整的原型应该公开虚拟显示、沙箱运行时、事件流和前台用户活动的调度策略。Background execution must respect mobile resource, thermal, and memory limits. A fuller prototype should expose scheduling policies for virtual displays, sandbox runtimes, event streams, and foreground user activity.

政策的可用性。Policy usability.细粒度的信息流控制取决于用户可以在不过度中断的情况下理解的批准。未来的工作应该改进审批 UI、跟踪审查以及目的、目的地、保留和同意的政策解释。Fine-grained information-flow control depends on approvals that users can understand without excessive interruption. Future work should improve approval UI, trace review, and policy explanations for purpose, destination, retention, and consent.
