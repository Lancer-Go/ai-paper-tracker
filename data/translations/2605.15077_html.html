无需模型更改的并发性：Concurrency without Model Changes:
LLM 基于 Future 的异步函数调用Future-based Asynchronous Function Calling for LLMs

1University of California, Berkeley
摘要Abstract

函数调用，也称为工具使用，是现代 LLM 代理的核心功能，但通常受到同步执行语义的限制。在这些语义下，LLM 解码会被阻止，直到每个函数调用完成为止，从而导致端到端延迟增加。在这项工作中，我们引入了 AsyncFC，这是一个纯执行层框架，它将 LLM 解码与函数执行解耦，从而在依赖关系允许的情况下实现模型解码和函数执行之间的重叠以及函数间并行性。 AsyncFC 分层于现有模型和未修改的函数实现之上，无需对标准同步函数调用协议进行微调或更改。在标准函数调用基准和改编的软件工程基准中，AsyncFC 显着减少了端到端任务完成时间，同时保持了任务准确性。此外，这些结果表明，法学硕士拥有对代表未解决的执行结果的符号未来进行推理的本机能力，从而为模型工具交互提供了异步范例。Function calling, also known as tool use, is a core capability of modern LLM agents but is typically constrained by synchronous execution semantics. Under these semantics, LLM decoding is blocked until each function call completes, resulting in increasing end-to-end latency. In this work, we introduce AsyncFC, a pure execution-layer framework that decouples LLM decoding from function execution, enabling overlap between model decoding and function execution as well as inter-function parallelism when dependencies permit. AsyncFC layers over existing models and unmodified function implementations, requiring no fine-tuning or changes to the standard synchronous function-calling protocol. Across standard function-calling benchmarks and adapted software engineering benchmarks, AsyncFC significantly reduces end-to-end task completion time while preserving task accuracy. Furthermore, these results reveal that LLMs possess a native capability to reason over symbolic futures that represent unresolved execution results, enabling an asynchronous paradigm for model-tool interaction.

1 简介Introduction

函数调用 (FC) 已成为现代大语言模型 (LLM) 代理的标准功能Function calling (FC) has become a standard capability in modern large language model (LLM) agents[19, 14, 26, 27]。它使模型能够与外部 API 交互、检索信息并在世界中采取行动. It enables models to interact with external APIs, retrieve information, and take actions in the world[1, 5, 9, 16, 18, 21, 24]。现代 LLM 函数调用遵循标准同步函数调用协议：模型发出结构化函数调用，运行时执行它，然后返回结果 在模型恢复解码之前附加到对话历史记录中。重复此过程，直到模型产生最终响应，并且每个函数调用必须紧随其在对话历史记录中的相应结果. Modern LLM function calling follows a standard synchronous function calling protocol: the model emits a structured function call, the runtime executes it, and the result is appended to the conversation history before the model resumes decoding. This process repeats until the model produces a final response, and each function call must be immediately followed by its corresponding result in the conversation history[8, 17, 23, 22, 31].

在实践中，大多数系统使用同步执行语义来实现此工作流。发出函数调用后，模型解码会阻塞，直到函数执行完成。 这种序列化限制了并发性并增加了端到端延迟。 先前的方法通过公开正在进行的功能来解决这个瓶颈 执行以继续模型生成或通过转移并发管理 模型方面的复杂性，经常改变 FC 协议 或需要更改型号In practice, most systems implement this workflow with synchronous execution semantics. After emitting a function call, model decoding blocks until the function execution completes. This serialization limits concurrency and increases end-to-end latency. Prior approaches address this bottleneck by exposing in-progress function executions to continued model generation or by shifting concurrency management complexity onto the model side, often altering the FC protocol or requiring model changes[6, 11, 28].

相反，我们认为管理执行并发性应该从模型卸载到系统运行时。 受到异步编程的启发In contrast, we argue that managing execution concurrency should be offloaded from the model to the system runtime. Inspired by asynchronous programming[2, 13]，我们介绍了 AsyncFC，一个具有自动模式适应功能的执行层框架，可将模型解码与函数执行解耦。 这种设计是根据我们的观察来指导的，即法学硕士可以本机对代表未解决的执行结果的符号未来占位符进行操作。 AsyncFC 支持异步函数调用，同时保留模型期望的标准同步调用返回语义，无需修改底层模型或函数实现。, we introduce AsyncFC, an execution-layer framework with automatic schema adaptation that decouples model decoding from function execution. This design is guided by our observation that LLMs can natively operate over symbolic future placeholders representing unresolved execution results. AsyncFC enables asynchronous function calling while preserving the standard synchronous call–return semantics the model expects, requiring no modifications to the underlying models or function implementations.

为了实现这一目标，AsyncFC 通过自动转换同步函数模式以支持未来值的输入和输出，并通过引入轻量级模型，向模型公开未来。To achieve this, AsyncFC exposes futures to the model by automatically transforming synchronous function schemas to support future-valued inputs and outputs, and by introducing a lightweight等待未来await_future允许模型解析 future 的函数。收到函数调用后，AsyncFC 将底层同步函数实现分派给后端执行器，并立即将未来占位符返回给 LLM。通过满足预期的调用返回协议，AsyncFC 允许模型继续解码，就好像函数调用已经返回一样，而底层函数在后台异步执行。一旦函数执行完成，结果就会在轮次边界处集成到上下文中。这些功能共同加速了后续函数调用的生成，从而最大限度地利用并行性。为了安全地并行执行函数，AsyncFC 具有一个调度程序，该调度程序默认保守地序列化执行，但利用开发人员提供的资源交互注释来解锁依赖安全的函数间并行性。因此，AsyncFC 支持两种形式的并发：解码和函数执行之间的重叠，以及依赖安全的函数间并行性。function that allows the model to resolve futures. Upon receiving a function call, AsyncFC dispatches the underlying synchronous function implementation to a backend executor and immediately returns future placeholders to the LLM. By satisfying the expected call–return protocol, AsyncFC allows the model to continue decoding as if the function call had already returned, while the underlying function executes asynchronously in the background. Once function execution completes, results are integrated into the context at turn boundaries. Together, these capabilities accelerate the generation of subsequent function calls, thereby maximizing exploitable parallelism. To safely execute functions in parallel, AsyncFC features a scheduler that conservatively serializes execution by default, but leverages developer-supplied resource interaction annotations to unlock dependency-safe inter-function parallelism. As a result, AsyncFC enables two forms of concurrency: overlap between decoding and function execution, and dependency-safe inter-function parallelism.

除了加速代理工作流程之外，AsyncFC 还可以作为一个框架来探索 LLM 对未解决的未来表示的推理能力。 AsyncFC 证明该模型可以原生地对符号占位符表示进行操作，并适应稍后集成的解析输出。这种功能无需任何额外的微调即可展示，在模型和函数之间带来了新的交互模式。Beyond accelerating the agentic workflow, AsyncFC serves as a framework to explore an LLM’s reasoning capability over unresolved future representations. AsyncFC demonstrates that the model can natively operate over symbolic placeholder representations and adapt to the resolved outputs integrated in later turns. This capability—demonstrated without requiring any additional fine-tuning—brings a new interaction pattern between the model and the functions.

由于 AsyncFC 纯粹在执行层运行，因此它适用于现成的同步模型。它使仅限于顺序函数调用的模型能够实现实质性的函数间并行性，并超过缺乏此类执行层支持的并行函数调用模式的加速。 此外，当应用于支持本机并行函数调用的模型之上时，AsyncFC 可以提供超出其本机并行性的额外延迟减少。它还提供了现有并行函数调用 API 经常未指定的显式执行顺序语义，从而减少了由同轮状态调用之间的竞争条件引起的故障模式。此外，由于 AsyncFC 使用相同的基于未来的执行接口来表示所有长延迟操作，因此它自然地超越了外部函数，扩展到了异步思维。 与训练模型显式分叉和连接子查询的异步思维方法不同Because AsyncFC operates purely at the execution layer, it is applicable across off-the-shelf synchronous models. It enables models restricted to sequential function calling to achieve substantial inter-function parallelism and exceed the speedup of the parallel function-calling modes that lack such execution-layer support. Furthermore, when applied on top of models supporting native parallel function calling, AsyncFC delivers additional latency reductions beyond their native parallelism. It also provides explicit execution-order semantics that existing parallel function-calling APIs often leave underspecified, reducing failure modes caused by race conditions among same-turn stateful calls. Moreover, because AsyncFC represents all long-latency operations using the same future-based execution interface, it naturally extends beyond external functions to asynchronous thinking. Unlike asynchronous thinking approaches that train models to explicitly fork and join subqueries[4]，AsyncFC 仅通过执行层更改来公开这种并行性。, AsyncFC exposes this parallelism through execution-layer changes alone.

However, existing Parallel FC APIs leave ambiguity in function execution order. Some model providers encourage concurrent function execution but do not specify the handling of partial failure and race conditions from concurrent execution; others imply serial execution in model-emitted order through example code rather than an explicit semantic contract, avoiding race conditions but weakening the latency benefit of Parallel FC. AsyncFC addresses this gap by making execution semantics explicit. The runtime uses dependency annotations to determine overlap and serialization across calls. On Sequential FC models, AsyncFC recovers Parallel-FC-like concurrency by allowing independent calls across turns to execute concurrently. On Parallel FC models, AsyncFC serializes conflicting calls in model-emitted order while executing dependency-safe calls concurrently. Given the model-emitted call order, this makes state updates, function returns, and the resulting model context deterministic. Its inter-turn function parallelism can also recover parallelism missed by conservative model-side grouping. In both settings, AsyncFC additionally enables decode–execution overlap.

These approaches can expose cross-turn parallelism, but depart from the standard turn-by-turn function-calling protocol and shift dependency reasoning into the model, often requiring model modification or additional training. They also remain synchronous and block decoding until function execution completes. By contrast, AsyncFC achieves cross-turn parallelism, preserves the standard function calling protocol, derives dependencies online, and adds a complementary source of concurrency by overlapping model decoding with in-flight function execution, all without model modification.

However, they expose incomplete function executions to the model’s reasoning process, depart from the standard function-calling protocol, and require the model to reason about whether new calls are safe while previous calls remain pending. This often requires model-side protocol changes or explicit model modification. Additionally, these approaches generally do not expose function results as futures or promises, preventing unresolved results from being passed as arguments to subsequently decoded function calls. In contrast, AsyncFC shifts responsibility for enforcing dependency-safe function execution from the model to a dependency-aware scheduler. Incomplete function executions are abstracted behind symbolic futures, allowing the model to treat each function as logically complete in its context and thereby avoiding model modification. Furthermore, these symbolic futures can be passed as arguments during decoding, enabling additional decode–execution overlap.

3 方法Method

AsyncFC 扩展了基于值的模型功能交互，以支持基于未来的交互。为了将这些 future 暴露给模型，AsyncFC 自动转换同步函数模式来描述 future 兼容的 API，并为模型引入额外的函数来解析 future。收到解码后的调用后，运行时会异步分派函数执行并立即将符号未来标识符返回给模型，从而允许模型解码继续进行而不会阻塞。在内部，运行时维护未来执行关联，强制执行依赖性感知执行，并主动将函数执行结果和潜在错误消息集成到轮次边界的上下文中。AsyncFC extends value-based model-function interaction to support future-based interaction. To expose these futures to the model, AsyncFC automatically transforms synchronous function schemas to describe future-compatible APIs and introduces additional functions for the model to resolve futures. Upon receiving decoded calls, the runtime asynchronously dispatches function executions and immediately returns symbolic future identifiers to the model, allowing model decoding to proceed without blocking. Internally, the runtime maintains future–execution associations, enforces dependency-aware execution, and proactively integrates function execution results and potential error messages into the context at turn boundaries.

3.1 非阻塞解码Non-Blocking Decoding

标准函数调用协议要求每个函数调用后立即跟随其在对话历史记录中的返回值，从而有效地阻止解码，直到执行完成。 为了消除阻塞，AsyncFC 将模型解码的同步函数分派给异步后端执行器，并立即向模型返回未来占位符。通过提供立即返回，该占位符满足协议约束。Standard function-calling protocol requires each function invocation to be immediately followed by its return value in the conversation history, effectively blocking decoding until execution completes. To remove blocking, AsyncFC dispatches the synchronous function decoded by the model to an asynchronous backend executor and immediately returns to the model a future placeholder. By providing an immediate return, this placeholder satisfies protocol constraints.

为了使返回值与暴露给模型的函数模式一致，AsyncFC 自动转换函数模式以支持返回单个未来对象作为函数输出。这允许运行时返回的符号 future 充当函数的立即返回值，因此模型可以继续解码后续调用，就好像函数调用已经返回一样。为了在执行完成之前进一步最大化解码， AsyncFC 自动转换模式中的函数输入以接受具体值或未来标识符。这种双类型模式允许模型利用其本机功能对未来占位符进行推理，并使用未解决的未来作为参数来解码后续调用。To make the return value consistent with the function schema exposed to the model, AsyncFC automatically transforms function schemas to support returning a single future object as the function output. This allows the symbolic future returned by the runtime to serve as the function’s immediate return value, so the model can continue decoding subsequent calls as if the function call had already returned. To further maximize decoding before execution finishes, AsyncFC automatically transforms function inputs in the schema to accept either concrete values or future identifiers. This dual-typed schema allows the model to leverage its native capability to reason over future placeholders and decode subsequent calls with unresolved futures as arguments.

在许多情况下，只需要函数返回值的子集或特定字段作为后续调用的输入。为了支持这一点，AsyncFC 允许开发人员在示例返回值中提供输出模式注释。当提供时，运行时会自动将这些示例转换为结构化表示，其中具体字段被符号未来标识符替换，从而有效地保留底层函数返回的结构。将此结构作为立即返回值返回给模型，可以使模型在构造下游调用时细粒度地访问待处理的执行结果。在所有转换中，函数描述、参数类型和返回定义都在架构级别更新，无需修改底层函数实现。除了转换模式之外，AsyncFC 还公开了一个辅助函数，In many cases, only a subset or specific fields of a function’s return value are needed as inputs to subsequent calls. To support this, AsyncFC allows developers to provide output schema annotations in example return values. When provided, the runtime automatically converts these examples into structured representations where concrete fields are replaced by symbolic future identifiers, effectively preserving the structure of the underlying function’s return. Returning this structure to the model as the immediate return value gives the model fine-grained access to pending execution results when constructing downstream calls. In all transformations, function descriptions, parameter types, and return definitions are updated at the schema level, requiring no modifications to the underlying function implementation. In addition to transformed schemas, AsyncFC exposes an auxiliary function,等待未来await_future。该功能允许模型在需要具体值时明确请求一个或多个 future 的解析，为 LLM 提供最终答案的清晰推理轨迹，并防止发出重复的工具调用。. This function allows the model to explicitly request the resolution of one or more futures when concrete values are required, providing the LLM a clear reasoning trajectory to the final answer and preventing the issuance of repetitive tool calls.

3.3 依赖性感知任务调度Dependency-Aware Task Scheduling

顺序函数调用按解码顺序执行函数，这通过阻塞隐式强制调用之间的依赖关系。通过在回合边界解锁模型解码和集成函数执行结果，AsyncFC 使模型能够比标准阻塞执行设置更早地生成后续函数调用，从而为函数间并行性创造新的机会。然而，放宽严格的解码顺序执行会带来正确性风险，因为简单的并行化可能会过早地执行相关调用。Sequential function-calling executes functions in decode order, which implicitly enforces dependencies between calls through blocking. By unblocking model decoding and integrating function execution results at the turn boundary, AsyncFC enables the model to generate subsequent function calls earlier than in the standard blocking execution setting, creating new opportunities for inter-function parallelism. However, relaxing strict decode-order execution introduces correctness risk, as naive parallelization may execute dependent calls prematurely.

为了解决这个问题，AsyncFC 提供了一个调度程序，默认情况下，该调度程序过于保守地按解码顺序序列化所有函数执行，仅允许模型解码和函数执行之间的重叠。为了解锁额外的函数间并行性，系统允许开发人员提供显式声明函数资源访问的可选依赖注释。调度程序使用这些注释来自动派生函数依赖关系，仅在安全时才允许并发函数执行。To address this, AsyncFC provides a scheduler that overly conservatively serializes all function executions in decode order by default, enabling only the overlap between model decoding and function execution. To unlock additional inter-function parallelism, the system allows developers to supply optional dependency annotations that explicitly declare function resource accesses. The scheduler uses these annotations to automatically derive function dependencies, permitting concurrent function execution only when safe.

Upon a function’s execution completion, the executor fulfills the result future previously returned to the model and removes its access labels from the State Tree, resolving the access label futures and unblocking waiting functions.

3.4 错误处理Error Handling

当函数调用失败时，AsyncFC 会取消所有传递依赖于失败操作的后续函数调用，同时保持独立于失败操作的函数调用不变。然后，AsyncFC 使用用户消息为失败的呼叫和转弯边界处所有取消的呼叫注入失败返回消息。失败消息明确区分操作自身的执行错误和由于依赖失败操作而取消。最终解码轮次后集成的失败消息会触发额外的恢复轮次。When a function call fails, AsyncFC cancels all subsequent function calls that are transitively dependent on the failed operation while keeping function calls that are independent of the failed operation untouched. AsyncFC then uses user messages to inject failure return messages for the failed call and all canceled calls at the turn boundary. The failure messages explicitly distinguish between an operation’s own execution error and cancellation due to dependency on a failed operation. Failure messages integrated after the final decode turn trigger additional recovery turns.

3.5 异步思维的推广Generalization to Asynchronous Thinking

其他类别的长延迟 LLM 操作（例如异步思维）可以作为 AsyncFC 执行框架的直接专业化来实现。 从概念上讲，异步思维是一种范式，其中主模型充当协调员，将子任务委托给独立思考的代理并异步收集其结果以形成最终解决方案。 AsyncFC 可以通过将每个委托思考轮次视为长延迟函数调用来实现此范例，其中参数对子查询以及相关上下文进行编码，并且返回值对应于思考结果。思考函数发出模型调用，而该函数的解码、结果集成和执行遵循与标准函数相同的流程。这种设计还允许异步思维与异步函数执行交错。Other classes of long-latency LLM operations, such as asynchronous thinking, can be realized as direct specializations of the AsyncFC execution framework. Conceptually, asynchronous thinking is a paradigm where the main model acts as a coordinator, delegating sub-tasks to independent thinking agents and asynchronously gathering their results to form a final solution. AsyncFC can enable this paradigm by treating each delegated thinking turn as a long-latency function call, where the argument encodes a subquery along with relevant context, and the return value corresponds to the thinking result. The thinking function issues a model invocation, while the decoding, result integration, and execution of this function follow the same flow as standard functions. This design also allows asynchronous thinking to interleave with asynchronous function execution.

6 讨论和限制Discussion and Limitations

模型能力发现。Model Capability Discovery.AsyncFC 要求模型能够容忍未解析的符号引用。在整个评估过程中，AsyncFC 保持了准确性，提供了证据表明法学硕士可以在基于未来的上下文中对未解决的未来占位符进行本地推理。我们假设这种行为源于从大型软件工件库中学习到的模型先验，包括通常涉及稍后解决的符号句柄的异步模式（例如 futures/promise 和非阻塞 I/O）。 这种对异步模型-工具交互的本机支持开启了设计高效、灵活的代理工作流程的新范例。AsyncFC requires the model to tolerate unresolved symbolic references. Across evaluations, AsyncFC preserves accuracy, providing evidence that LLMs can natively reason over unresolved future placeholders in our future-based context. We hypothesize that this behavior arises from model priors learned from large corpora of software artifacts, including asynchronous patterns (e.g., futures/promises and non-blocking I/O) that routinely involve symbolic handles that are resolved later. Such native support for asynchronous model–tool interaction unlocks a new paradigm for designing efficient and flexible agentic workflows.

应用场景Application Scenarios。 AsyncFC 非常适合长延迟功能，其中解码进度不需要立即执行输出，例如“只写”操作（例如订票、发送电子邮件）。它还可以通过将推理与物理执行重叠来分摊现实世界的延迟，从而使网络物理系统和机器人技术受益。. AsyncFC is ideal for long-latency functions where immediate execution outputs aren’t needed for decode progress, such as "write-only" actions (e.g., booking tickets, sending emails). It also may benefit cyber-physical systems and robotics by overlapping reasoning with physical execution to amortize real-world delays.

潜在的优化。Potential Optimization.虽然顺序模型以固定的线性顺序生成函数调用，但此输出仅代表底层任务特定函数依赖 DAG 的一种有效线性化。因此，多个解码顺序可能与任务的逻辑约束一致。一种潜在的优化是采用波束搜索来并行探索这些替代轨迹。通过选择立即产生可执行函数的解码路径（其依赖关系已经得到满足），系统优化了并发执行吞吐量。While sequential models generate function calls in a fixed linear sequence, this output represents just one valid linearization of the underlying Task-specific Function Dependency DAG. Consequently, multiple decoding orders may be consistent with the task’s logical constraints. A potential optimization is to employ beam search to explore these alternative trajectories in parallel. By selecting decoding paths that immediately produce executable functions—those whose dependencies are already satisfied—the system optimizes the concurrent execution throughput.

系统副作用。Systems Side Effects.AsyncFC 可以通过减少请求特定的 KV 状态在 GPU 内存中保留的持续时间来提高 KV 缓存利用率。 通过将解码与函数执行重叠，AsyncFC 缩短了每个请求的挂钟生命周期，从而减少了其 KV 缓存的平均驻留时间。AsyncFC can improve KV-cache utilization by reducing the duration for which request-specific KV state remains in GPU memory. By overlapping decoding with function execution, AsyncFC shortens the wall-clock lifetime of each request, thereby reducing the mean residency time of its KV cache.

7 结论Conclusion

随着 LLM 代理越来越多地在具有丰富内部并行性和不可忽略的函数延迟的环境中运行，严格的同步执行成为关键瓶颈。 我们提出了 AsyncFC，一个基于未来的异步函数调用执行层框架，它将模型解码与函数执行解耦，同时保留标准函数调用协议。通过利用 future 和依赖项感知调度，AsyncFC 可以安全地实现解码执行重叠，并在依赖项允许时公开函数间并行性。 在不修改模型、协议或同步函数实现的情况下，AsyncFC 减少了端到端任务延迟并保持了准确性。除了这些效率提升之外，我们的结果还提供了证据，证明现代法学硕士可以对未来价值的占位符进行本地推理。这提出了一种异步模型-工具交互模式，可用于更灵活、更高效的代理工作流程。As LLM agents increasingly operate in environments with rich internal parallelism and non-negligible function latency, strict synchronous execution becomes a key bottleneck. We present AsyncFC, a future-based asynchronous function-calling execution-layer framework that decouples model decoding from function execution while preserving the standard function-calling protocol. By leveraging futures and dependency-aware scheduling, AsyncFC safely enables decoding-execution overlap and exposes inter-function parallelism when dependencies permit. Without modifying the model, protocol, or synchronous function implementation, AsyncFC reduces end-to-end task latency and preserves accuracy. Beyond these efficiency gains, our results provide evidence that modern LLMs can natively reason over future-valued placeholders. This suggests an asynchronous model–tool interaction pattern that can be leveraged for more flexible and efficient agentic workflows.

部分注释的鲁棒性。Robustness to Partial Annotation.所有注释都是可选的并且可以独立提供。对于未注释的函数，运行时默认为根级读写集，序列化函数执行，同时仍然允许模型解码与函数执行重叠。 这种保守的策略保证开箱即用的正确性，而不需要任何注释。为了超越这一基线，AsyncFC 启用了提高性能的增量路径。部分注释解锁了一些函数间并行性，而更精确的注释则逐渐暴露出并发执行和进一步加速的更多机会。All annotations are optional and may be provided independently. For unannotated functions, the runtime defaults to root-level read and write sets, serializing function execution while still allowing model decoding to overlap with function execution. This conservative strategy guarantees out-of-the-box correctness without requiring any annotations. To move beyond this baseline, AsyncFC enables an incremental path to performance. Partial annotations unlock some inter-function parallelism, while more precise annotations progressively expose additional opportunities for concurrent execution and further speedups.

会话相对路径。Session-Relative Paths.虽然许多资源访问可以使用状态空间中的绝对路径来表达，但某些函数调用对资源进行操作，其确切位置取决于先前的操作。为了支持这种情况，AsyncFC 允许使用会话相对路径来表达依赖标签。会话标签将函数调用的访问权限绑定到当前会话状态（隐式地从先前的函数执行派生），从而能够根据早期操作的效果动​​态解析路径。为了标记会话访问，读取会话状态的函数调用仅声明其对当前会话上下文的依赖性，而写入会话状态的函数调用另外指定会话如何前进。 这一进步导致了对访问会话的后续函数的排序约束。While many resource accesses can be expressed using absolute paths in the state space, some function calls operate on resources whose exact locations are dependent on prior operations. To support such cases, AsyncFC allows dependency labels to be expressed using session-relative paths. A session label binds a function call’s access to the current session state—implicitly derived from prior function executions—enabling paths to be resolved dynamically based on the effects of earlier operations. To label session access, a function call that reads session state only declares its dependence on the current session context, whereas a function call that writes to session state additionally specifies how the session advances. This advancement induces an ordering constraint on subsequent functions that access the session.

参数参数化路径。Argument-Parameterized Paths.除了会话相关寻址之外，某些函数调用还对资源进行操作，这些资源的确切位置由当前调用的参数确定。因此，AsyncFC 允许通过函数参数对依赖标签进行参数化，从而在调用被解码并提交给运行时后能够派生读写路径。In addition to session-relative addressing, some function calls operate on resources whose exact locations are determined by the arguments of the current invocation. AsyncFC therefore allows dependency labels to be parameterized by function arguments, enabling read and write paths to be derived after the call is decoded and submitted to the runtime.
