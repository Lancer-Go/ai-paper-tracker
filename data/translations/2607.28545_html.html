1 简介Introduction

大型语言模型 (LLM) 现在大规模地编写、重构、审查和调试代码，但它们尚未拥有其帮助构建的系统的可靠性。 当生产系统发生故障时，值班站点可靠性工程师 (SRE) 通常会在事件发生数小时后收到含糊的自然语言投诉，例如“用户在站点上遇到问题”或“结帐已损坏”。在短时间内和压力下，他们必须确定哪个功能、部署或组件导致了症状，这项任务称为Large language models (LLMs) now write, refactor, review, and debug code at scale—but they do not yet own the reliability of the systems they help build. When a production system breaks, an oncall site reliability engineer (SRE) is handed a vague natural-language complaint such as “users are having issues on the site” or “checkout is broken,” often hours after the incident began. In a short period of time and under stress, they must identify which feature, deploy, or component caused the symptom—a task known as根本原因分析root cause analysis（美国无线电公司）。 RCA 是现代微服务部署中缓解问题的诊断先决条件，它在质量上不同于软件工程基准测试中的静态存储库上的错误修复设置(RCA). RCA is the diagnostic prerequisite for mitigation in modern microservice deployments, and it is qualitatively unlike the bug-fix-on-a-static-repo setting on which software-engineering benchmarks(Jimenez et al., 2024; Yang et al., 2025; 2026; Bogomolov et al., 2024)推动了代理最近的进展：输入是一份含糊不清的报告，而不是失败的测试；证据是正在运行的微服务网格，而不是冻结的代码库；成功的标准是一个合理的诊断，而不是通过测试。 现有基准have driven recent agent progress: the input is an ambiguous report rather than a failing test; the evidence is a running microservice mesh rather than a frozen codebase; and the success criterion is a defensible diagnosis rather than a passing test. Existing benchmarks(Shetty et al., 2024; Jha et al., 2025; Xu et al., 2025; Clark et al., 2026)通过将合成故障注入微服务集群并要求代理说出根本原因来评估 RCA，但每种方法都至少去除了值班工程师所需要的三个工件中的一个：基于指标、日志和跟踪的遥测接口；实时负载下的服务生成的原始遥测数据；以及这些服务的源代码，并且没有系统地改变用户报告的特异性或事件发生和调查开始之间的检测时间（TTD）（evaluate RCA by injecting a synthetic fault into a microservice cluster and asking an agent to name the root cause, but each strips out at least one of the three artifacts an oncall engineer reaches for—a telemetry interface over metrics, logs, and traces; the raw telemetry generated by services under live load; and the source code of those services—and none systematically vary the specificity of the user report or the time-to-detection (TTD) between incident onset and investigation start (Tab.˜1）。 仅限 OpenRCA). Every dimension along which ORCA-bench simplifies real production points in the same direction: real oncall is harder. Each simplification below is a place where substantial engineering investment is required before frontier agents can credibly be trusted with production reliability.

  • •

    规模和活力。Scale and dynamism.我们的 50 GB/六天测试平台在具有预设功能标记故障的固定代码库上运行。实际生产每天在不断发展的代码库上生成数 TB 的数据，故障模式分布会随着新功能的发布而变化——代理在遇到真实系统时就会面临分布外故障。Our 50 GB/six-day testbed runs on a fixed codebase with preset feature-flag faults. Real production generates terabytes per day on a codebase that evolves continuously, with a failure-mode distribution that drifts as new features ship—agents will face out-of-distribution faults the moment they meet a real system.

  • •

    系统先验被纳入模型中。System priors are baked into the models.OpenTelemetry、天文商店及其文档是公开的，并且几乎肯定处于预训练阶段。真实的生产系统是私有的且特殊的；我们报告的系统故障，模型部分“知道”了它们不知道的系统上的差距下限。OpenTelemetry, the Astronomy Shop, and their documentation are public and almost certainly in pretraining. Real production systems are private and idiosyncratic; the failures we report on a system the models partially “know” lower-bound the gap on systems they do not.

  • •

    单任务隔离，无内存。Single-task isolation, no memory.每项任务都经过冷调查。人类 SRE 积累了数月的系统直觉（哪些服务不稳定，哪些警报嘈杂）；剔除这一点使得持续学习问题比我们的孤立任务数字所反映的更加困难。一旦被赋予持久记忆和跨事件学习的能力，这也是智能体最终可能超越人类的方向。Each task is investigated cold. Human SREs accumulate months of system intuition (which services are flaky, which alerts are noisy); stripping that out makes the continual-learning problem harder than our isolated-task numbers reflect. It is also a direction where agents may eventually outperform humans, once given persistent memory and the ability to learn across incidents.

  • •

    只读调查，无操作循环。Read-only investigation, no action loop.人类通过部署候选修复并观察症状解决来确认根本原因。我们故意省略这个动作循环，因为该领域还不信任生产变化的代理；弥补这一差距是一项重大工程投资，超出了此处测量的 RCA 差距。它也是更好的 RCA 本身的一个明显杠杆，因为成功（或失败）缓解的反馈信号正是代理完善假设所需的。A human confirms a root cause by deploying a candidate fix and watching the symptom resolve. We deliberately omit this action loop, since the field does not yet trust agents with production changes; closing it is a major engineering investment beyond the RCA gap measured here. It is also a clear lever for better RCA itself, since the feedback signal from a successful (or failed) mitigation is exactly what agents need to refine hypotheses.

  • •

    我们没有研究的方法。Methods we did not study.我们使用单个提示模板和单个代理工具来评估每个模型；通过快速工程、结构化工作流程或与因果推理 RCA 的混合可以恢复多少We evaluate each model with a single prompt template and a single agent harness; how much can be recovered through prompt engineering, structured workflows, or hybridization with causal-inference RCA(e.g., Pham et al., 2025)是正交且开的。is orthogonal and open.
