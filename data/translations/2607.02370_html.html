摘要Abstract

编译器错过优化是指编译器未能优化某些代码的情况。 需要许多编译器开发人员的努力来实现或修补此类错过的优化。 在本文中，我们对代理补丁编译器错过优化的程度进行了系统研究。 我们发现一个重大挑战，即修补错过的优化不仅需要修复报告的案例，还需要推广到类似的案例。 我们构建了现实世界中 LLVM 错过优化问题的基准，并 将代理生成的补丁与开发人员的补丁在优化范围方面进行比较。 我们的结果表明，编码代理通常会优化给定的示例，但许多生成的补丁要么仅覆盖开发人员预期范围的一部分，要么与其部分重叠；在某些情况下，它们会进一步推广到参考补丁之外。 我们进一步介绍了历史知识增强技术，该技术通过检索和蒸馏利用先前的 LLVM 优化拉取请求，表明它们可以提高与开发人员一致的泛化能力，并在应用于现实世界的 IR 时产生实际效益。Compiler missed optimizations refer to cases in which compilers failed to optimize certain code. It takes many compiler developers’ efforts to implement or patch such missed optimizations. In this paper, we present a systematic study of how well agents patch compiler missed optimizations. We identify a significant challenge that patching a missed optimization requires more than just fixing the reported case, and instead requires generalizing to similar cases. We construct a benchmark of real-world LLVM missed optimization issues and compare agent-generated patches with patches from developers in terms of optimization scope. Our results show that coding agents often optimize the given examples, but many generated patches either cover only part of the developer-intended scope or partially overlap with it; in some cases, they further generalize beyond the reference patch. We further introduce historical-knowledge augmentation techniques that leverage prior LLVM optimization pull requests through retrieval and distillation, showing that they improve developer-aligned generalization and yield practical benefits when applied to real-world IR.

I 简介Introduction

编译器优化是现代编译器设计和软件性能工程的基本组成部分。它的目的是在不改变程序预期行为的情况下提高生成代码的效率Compiler optimization is a fundamental component of modern compiler design and software performance engineering. It aims to improve the efficiency of generated code without altering the intended behavior of the program[1]。 现代编译器，例如 LLVM. Modern compilers, such as LLVM[2]，通常通过识别特定的代码模式并将其替换为更有效的等效代码来执行优化。 此过程通常需要编译器优化遍来枚举和匹配大量代码模式，以便识别目标代码中潜在的优化机会。, often perform optimizations by identifying specific code patterns and replacing them with more efficient equivalents. This process often requires compiler optimization passes to enumerate and match a large number of code patterns in order to identify potential optimization opportunities in the target code.

然而，在编译器优化规则的设计和实现过程中，许多优化机会可能未被编译器开发人员识别或未被利用，从而导致错过优化的问题。 这种错过的优化可能会导致生成的代码不理想，并且长期以来一直是编译器开发中的一个持续挑战However, during the design and implementation of compiler optimization rules, many optimization opportunities may remain unrecognized or unexploited by compiler developers, leading to the problem of missed optimizations. Such missed optimizations can result in suboptimal generated code and have long been a persistent challenge in compiler development[3]。 为了发现这些错失的机会，研究人员和编译器开发人员探索了广泛的技术，包括以 Souper 为代表的超级优化器. To uncover these missed opportunities, researchers and compiler developers have explored a broad spectrum of techniques, including superoptimizers represented by Souper[4]，以 Hydra 为例的基于合成的系统, synthesis-based systems exemplified by Hydra[5]，以及最近的人工智能驱动方法，例如 Italiano 和 Cummins 提出的方法, and more recent AI-driven approaches, such as the method proposed by Italiano and Cummins[6]和LPOand LPO[3]。 随着这些技术不断暴露大量错过的优化案例，主要瓶颈逐渐从识别优化机会转向将它们作为高质量补丁集成到编译器维护过程中。. As these techniques continue to expose large numbers of missed optimization cases, the main bottleneck is increasingly shifting from identifying optimization opportunities to integrating them as high-quality patches within the compiler maintenance process.

这种转变使得自动修补变得有吸引力。 特别是，由大型语言模型（LLM）支持的代理的最新进展表明了一条通过补丁生成自动解决编译器问题的有希望的途径，从而减少大量的手动工程工作This shift makes automated patching attractive. In particular, recent advances in agents powered by large language models (LLMs) suggest a promising path toward automatically resolving compiler issues through patch generation, thereby reducing substantial manual engineering effort[7]。 这些努力主要证明了 LLM 代理在传统编译器问题解决方面的潜力，特别是在错误修复方面。 然而，错过的优化补丁与传统的错误修复有着根本的不同。 对于错误修复，正确性通常通过补丁是否满足现有测试套件来近似. These efforts primarily demonstrate the potential of LLM agents in conventional compiler issue resolution, particularly in bug fixing. However, missed optimization patching is fundamentally different from conventional bug fixing. For a bug fix, correctness is often approximated by whether the patch satisfies the existing test suite[8, 9, 10]。 相比之下，错过的优化会带来不同的挑战，即目标不仅仅是使激励测试用例通过，而是以适当泛化到这些用例之外的方式实施优化。 例如，报告的错过优化可能仅公开更一般重写的具体实例：. 这种差异提出了一个核心挑战：泛化。This difference raises a central challenge: generalization.在实践中，开发人员通常通过面向泛化的工作流程来解决错过优化的问题。他们首先观察到特定的中间表示（IR）片段允许更优化的形式，而当前编译器无法执行相应的转换。从这个具体示例开始，开发人员推断并概括底层优化模式，以便它适用于更广泛的相关 IR 案例，而不仅仅是最初报告的单个实例。最后，他们根据通用模式修改编译器实现，生成可以解决此类优化机会的补丁。因此，我们将泛化定义为将特定的、非泛化的优化转换为更通用的优化规则的过程，该规则不仅适用于原始代码片段，而且适用于类似的代码场景，同时保留优化的正确性。因此，通过给定测试的代理生成的补丁可能仍然无法满足开发人员的意图，因为它太窄、太宽或与预期的优化模式不一致。In practice, developers often address a missed-optimization issue through a generalization-oriented workflow. They first observe that a particular intermediate representation (IR) fragment admits a more optimized form, while the current compiler fails to perform the corresponding transformation. Starting from this concrete example, developers then infer and generalize the underlying optimization pattern so that it applies to a broader class of related IR cases, rather than only to the single instance initially reported. Finally, they modify the compiler implementation according to the generalized pattern, producing a patch that can resolve this class of optimization opportunities. We therefore define generalization as the process of transforming a specific, ungeneralized optimization into a more general optimization rule that applies not only to the original code fragment but also to similar code scenarios, while preserving the correctness of the optimization. Consequently, an agent-generated patch that passes the given tests may still fail to match developer intent by being too narrow, too broad, or misaligned with the intended optimization pattern.

为了研究代理是否可以从初始测试用例推断广义优化模式并生成与开发人员意图一致的补丁，我们首先从现实世界的 LLVM 错过优化问题构建基准，然后设计用于受控补丁生成的代理工具，最后建立一个泛化评估程序，将生成的补丁与黄金补丁进行比较。To investigate whether agents can infer generalized optimization patterns from initial test cases and generate patches aligned with developer intent, we first construct a benchmark from real-world LLVM missed-optimization issues, then design an agent harness for controlled patch generation, and finally establish a generalization assessment procedure that compares generated patches with golden patches.

To provide a simple and reproducible reference point, we implement a lightweight agent harness for LLVM missed-optimization issues. The harness connects a model to an issue-specific LLVM workspace, a controlled tool interface, and a validation loop. If the agent exits before producing a valid patch, exceeds its interaction budget, or fails final validation, the run is counted as a failure. V 历史知识引导的概括Historical-Knowledge-Guided Generalization

在前面的部分中，我们展示了代理并不能始终如一地生成既优化初始测试用例又符合开发人员预期优化范围的补丁。尽管代理通常可以解决问题报告中描述的具体优化示例，但他们经常无法推断出相应黄金补丁所捕获的更广泛的优化范围。此外，添加面向泛化的指令并不能可靠地改善范围对齐，在某些情况下甚至会降低性能。In the previous sections, we showed that agents do not consistently generate patches that both optimize the initial test case and match the developer-intended optimization scope. Although agents can often address the concrete optimization example described in an issue report, they frequently fail to infer the broader optimization scope captured by the corresponding golden patch. Moreover, adding a generalization-oriented instruction does not reliably improve scope alignment and can even degrade performance in some cases.

一种可能的解释是，代理无法访问编译器开发人员在实现优化规则时隐式依赖的知识。在实践中，编译器开发人员很少单独设计优化。相反，它们建立在以前实现的转换、现有优化模式和代码库中的历史修复中积累的经验之上。这些历史知识通常为如何推广新发现的优化机会提供有价值的线索。One possible explanation is that the agents lack access to the knowledge that compiler developers implicitly rely on when implementing optimization rules. In practice, compiler developers rarely design optimizations in isolation. Instead, they build upon accumulated experience from previously implemented transformations, existing optimization patterns, and historical fixes within the codebase. Such historical knowledge often provides valuable clues about how a newly discovered optimization opportunity should be generalized.

受这一观察的启发，我们研究了提供历史知识是否可以帮助代理更好地使生成的补丁与开发人员的意图保持一致。具体来说，我们通过从先前的开发人员修复中收集的优化相关经验来增强代理，并评估这些额外的知识是否可以提高代理泛化到问题级示例之外的能力。通过这项研究，我们旨在回答以下研究问题：Motivated by this observation, we investigate whether providing historical knowledge can help agents better align their generated patches with developer intent. Specifically, we augment the agent with optimization-related experience collected from prior developer fixes and evaluate whether this additional knowledge improves the agent’s ability to generalize beyond the issue-level examples. V-A 历史知识增强Historical-Knowledge Augmentation

V-A1 历史知识来源Historical Knowledge Source

我们使用与第 1 节中描述的基准构建过程基本一致的过程来提取历史实例。We extract historical instances using a procedure largely consistent with the benchmark-construction process described in SectionIII-A。与基准构建不同，本研究从 GitHub 拉取请求而不是问题中收集实例，因为拉取请求提供了更大的开发人员实施的优化更改池。我们排除了基准测试中使用的所有拉取请求，以避免数据泄漏。我们总共收集了 869 个拉取请求作为历史优化实例的来源。. Unlike benchmark construction, this study collects instances from GitHub pull requests rather than issues, as pull requests offer a larger pool of developer-implemented optimization changes. We exclude all pull requests that are used in benchmark to avoid data leakage. In total, we collect 869 pull requests as the source of historical optimization instances.

对于每个拉取请求，我们收集源代码补丁和随附的测试，并总结优化的泛化行为以供检索。给定补丁和测试，LLM 识别关键模式，包括初始具体案例、PR 补丁涵盖的其他案例以及连接它们的转换逻辑。由于拉取请求没有明确区分预泛化测试和附加黄金测试，因此我们使用简单的启发式，将第一个测试用例视为初始用例，而其余测试则视为附加黄金用例。尽管这种启发式可能并不完全符合开发人员的测试编写顺序，但它始终近似于补丁如何从原始实例推广到更广泛的覆盖范围。For each pull request, we collect source-code patch and accompanying tests, and summarize optimization’s generalization behavior for retrieval. Given the patch and tests, the LLM identifies the key pattern, including the initial concrete case, the additional cases covered by the patch of PR, and the transformation logic connecting them. Since pull requests do not explicitly distinguish the pre-generalization test from additional golden tests, we use a simple heuristic under which the first test case is treated as the initial case, while the remaining tests are treated as additional golden cases. Although this heuristic may not exactly match the developer’s test-writing order, it consistently approximates how the patch generalizes from the original instance to broader coverage.

总体而言，每个历史实例都包含源代码补丁、提取的测试用例以及 LLM 生成的优化泛化细节摘要。这些实例构成了后续章节中基于 RAG 的增强和历史知识蒸馏所使用的历史知识源。Overall, each historical instance consists of the source-code patch, the extracted test cases, and an LLM-generated summary of the optimization’s generalization details. These instances constitute the historical knowledge source used by both RAG-based augmentation and historical knowledge distillation in the subsequent sections.

VI 真实世界的 IR 优化评估Real-World IR Optimization Evaluation

RQ3 表明历史知识提高了代理决定和调整优化范围的能力，从而与黄金补丁更加精确匹配，并提供更多覆盖开发人员预期范围的补丁。接下来我们将研究这些范围级别的改进是否也可以转化为下游 IR 的更大现实适用性。 我们使用优化命中作为补丁有效性的代理，因为它们捕获补丁是否在现实世界的 IR 上运行，这是产生任何现实世界优化效益的必要先决条件。尽管命中率并不直接衡量最终性能，但它们在许多本地 LLVM 错过优化的补丁中提供了可扩展且统一的信号。RQ3 indicates that historical knowledge improves agents’ ability to decide and adjust optimization scopes, resulting in more exact matches with the golden patch and also more patches that cover the developer-intended scope. We next examine whether these scope-level improvements also translate into greater real-world applicability on downstream IR. We use optimization hits as a proxy for patch effectiveness because they capture whether a patch is exercised on real-world IR, which is a necessary precondition for producing any real-world optimization benefit. Although hits do not directly measure final performance, they provide a scalable and uniform signal across many local LLVM missed-optimization patches.

IX 讨论Discussion

潜在的预训练数据泄漏。Potential pretraining-data leakage.由于 LLVM 补丁是公开的，基础模型可能在训练期间看到了一些基准测试修复。然而，生成的补丁通常在文本上与黄金补丁并不接近，并且通常在实现策略或代码位置上有所不同，这表明成功不太可能是简单的记忆。Since LLVM patches are public, base models may have seen some benchmark fixes during training. However, generated patches are usually not textually close to the golden patches and often differ in implementation strategy or code location, suggesting that successes are unlikely to be simple memorization.

随机性和评估设计。Stochasticity and evaluation design.我们使用开放且可控的代理工具，而不是带有隐藏提示、工具、策略或更新的产品化编码代理，确保所有实验都有固定的交互协议。虽然代理修复由于 LLM 采样和工具使用顺序而表现出随机性，但我们在固定执行预算下评估每个问题配置对，并记录单个代表性结果，以实现一致的问题级别比较和基于转换的分析。该设计的重点是测量由不同增强策略引起的系统变化，而不是运行间方差。四种基本模型和两种增强策略中观察到的趋势是一致的，并且得到了现实世界结果的进一步证实。We use an open and controllable agent harness rather than productized coding agents with hidden prompts, tools, policies, or updates, ensuring a fixed interaction protocol across all experiments. While agentic repair exhibits stochasticity due to LLM sampling and tool-use ordering, we evaluate each issue–configuration pair under a fixed execution budget and record a single representative outcome to enable consistent issue-level comparison and transition-based analysis. This design focuses on measuring systematic shifts induced by different augmentation strategies rather than run-to-run variance. The observed trends are consistent across four base models and two augmentation strategies and are further corroborated by real-world results.

X 结论Conclusion

我们研究了针对 LLVM 错过优化问题的基于代理的修补，重点关注生成的修补程序是否符合开发人员预期的泛化范围。结果显示，代理经常修复报告的示例，但相对于黄金补丁而言，概括不足或过度。通过检索或蒸馏，来自先前 LLVM 优化 PR 的历史知识可以改善范围对齐，并可以增加现实世界的 IR 优化命中率。总体而言，有效的自动编译器修补需要特定领域的历史知识，才能将具体报告转化为语义上范围广泛的补丁。We studied agent-based patching for LLVM missed-optimization issues, focusing on whether generated patches match developers’ intended generalization scope. Results show agents often fix reported examples but under- or over-generalize relative to golden patches. Historical knowledge from prior LLVM optimization PRs, via retrieval or distillation, improves scope alignment and can increase real-world IR optimization hits. Overall, effective automated compiler patching requires domain-specific historical knowledge to turn concrete reports into semantically well-scoped patches.
