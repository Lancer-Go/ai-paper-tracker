摘要Abstract

OpenClaw 在 2026 年初的崛起标志着数百万用户开始在日常生活中部署个人人工智能代理，委派从旅行计划到多步骤研究等任务。这种采用规模标志着两条平行的发展弧线已经达到了拐点。首先是人工智能工程的范式转变，从提示和上下文工程发展到利用工程——设计将不受约束的代理转变为可控、可审计和生产可靠的系统所需的完整基础设施。随着模型功能的融合，该控制层正在成为架构差异化的主要场所。其次，人机交互从离散任务发展为持久的、上下文感知的协作关系，这需要开放、值得信赖和可扩展的线束基础设施。我们呈现The rise of OpenClaw in early 2026 marks the moment when millions of users began deploying personal AI agents into their daily lives, delegating tasks ranging from travel planning to multi-step research. This scale of adoption signals that two parallel arcs of development have reached an inflection point. First is a paradigm shift in AI engineering, evolving from prompt and context engineering to harness engineering—designing the complete infrastructure necessary to transform unconstrained agents into controllable, auditable, and production-reliable systems. As model capabilities converge, this harness layer is becoming the primary site of architectural differentiation. Second is the evolution of human–agent interaction from discrete tasks toward a persistent, contextually aware collaborative relationship, which demands open, trustworthy and extensible harness infrastructure. We present塞玛爪SemaClaw，一个开源多代理应用程序框架，通过利用工程向通用个人人工智能代理迈出了一步，解决了这些转变。我们的主要贡献包括基于 DAG 的两阶段混合代理团队编排方法、PermissionBridge 行为安全系统、三层上下文管理架构以及用于自动化个人知识库构建的代理 wiki 技能。, an open-source multi-agent application framework that addresses these shifts by taking a step towards general-purpose personal AI agents through harness engineering. Our primary contributions include a DAG-based two-phase hybrid agent team orchestration method, a PermissionBridge behavioral safety system, a three-tier context management architecture, and an agentic wiki skill for automated personal knowledge base construction.

2.1 ReAct 循环：从单一推理到代理执行The ReAct Loop: From Single Inference to Agentic Execution

从作为被动文本生成器的语言模型到能够完成多步骤任务的主动代理的转变依赖于一种看似简单的架构洞察：推理和行动可以在单个推理循环中交织。反应框架The transition from language models as passive text generators to active agents capable of accomplishing multi-step tasks rests on a deceptively simple architectural insight: reasoning and acting can be interleaved within a single inference loop. The ReAct frameworkyao2023react形式化了这种模式，将代理的执行定义为三个操作的重复循环：, which formalized this pattern, defines an agent’s execution as a repeating cycle of three operations:

⬇
思想Thought →\rightarrow 行动Action →\rightarrow 观察Observation →\rightarrow 思想Thought →\rightarrow ...

2.1.2 从单循环到连续运行代理From Single Loop to Continuously Running Agent

状态坚持。State persistence.ReAct 循环在调用之间是无状态的：每个新任务都以新的上下文开始。对于旨在在多个会话中为同一用户提供服务的代理（积累知识、保持任务连续性以及熟悉用户的偏好），这种无状态性是一个基本限制。解决这个问题需要一个显式的内存架构，该架构存在于上下文窗口之外，并在每个任务开始时有选择地加载。A ReAct loop is stateless between invocations: each new task begins with a fresh context. 2.4 多代理编排：从调用链到协作团队Multi-Agent Orchestration: From Call Chains to Collaborative Teams

第 2.3 节中的四种扩展机制扩展了单个代理可以做和知道的事情，但它们并没有改变所有这些能力都在一个上下文窗口内行使的基本约束。当任务需要并发专业知识、跨独立工作流并行执行或超出任何单个窗口容量的认知负载时，进一步扩展单个代理是错误的解决方案。组成单位必须从能力转向行动者。The four extension mechanisms in Section 2.3 expand what a single agent can do and know—but they do not change the fundamental constraint that all of that capability is exercised within one context window. When tasks require concurrent expertise, parallel execution across independent workstreams, or a cognitive load that exceeds any single window’s capacity, extending a single agent further is the wrong solution. The unit of composition must shift from capability to agent.

问题不在于是否在代理之间分配工作，而在于如何构建协调：谁决定每个代理做什么、何时以及以什么顺序。当前实践中出现了三种主要的编排模型，每种模型都代表了该问题的不同答案，以及灵活性、可预测性和操作复杂性之间的一组不同的权衡。The question is not whether to distribute work across agents, but how to structure the coordination: who decides what each agent does, when, and in what order. Three principal orchestration models have emerged in current practice, each representing a different answer to that question—and a different set of trade-offs between flexibility, predictability, and operational complexity.

2.4.1 无状态群Stateless Swarm

无状态群体模型将多代理协调减少为单个原语：The stateless swarm model reduces multi-agent coordination to a single primitive:切换handoff。每个代理在自己的上下文中执行，直到确定另一个代理更适合继续；此时，它通过返回目标代理作为工具调用的结果来转移控制权。接收代理接收在切换边界传递的共享上下文变量并独立进行。不存在中央协调员；执行路径是从各个代理做出的切换决策序列中产生的。. Each agent executes within its own context until it determines that a different agent is better suited to continue; at that point, it transfers control by returning the target agent as the result of a tool call. The receiving agent picks up with the shared context variables passed at the handoff boundary and proceeds independently. No central coordinator exists; the execution path emerges from the sequence of handoff decisions made by individual agents.

OpenAI 的 Swarm 框架OpenAI’s Swarm frameworkOpenAI2024swarm是此模式的规范参考实现。它的设计显然是最小的——代理由系统提示和一组工具定义，切换只是返回另一个代理的工具调用，并且框架本身在轮次之间不维护任何状态。官方的定位很有启发性：Swarm 被描述为一个用于探索多智能体接口的教育框架，而不是一个生产系统。这种自我强加的范围边界反映了真正的架构约束，而不是虚假的谦虚。如果没有持久状态，已转移控制权的代理无法观察接下来发生的情况；如果没有协调器，就没有机制来检测整个任务何时偏离轨道或从失败的切换链中恢复。is the canonical reference implementation of this pattern. Its design is explicitly minimal—agents are defined by a system prompt and a set of tools, handoffs are just tool calls that return another agent, and the framework itself maintains no state between turns. The official positioning is instructive: Swarm is described as an educational framework for exploring multi-agent interfaces, not a production system. This self-imposed scope boundary reflects a genuine architectural constraint rather than false modesty. Without persistent state, an agent that has transferred control cannot observe what happens next; without a coordinator, there is no mechanism for detecting when the overall task has gone off track or for recovering from a failed handoff chain.

无状态模型的优势是真实的：推理简单、易于单独测试以及可组合——添加新代理只需要定义其提示和工具，而不需要重构工作流图。这些属性使其非常适合简短、定义明确的任务链，其中每个步骤的输出都是下一步的足够输入。它的局限性在长期运行的协调下变得明显：一个智能体推理中积累的上下文不会自动提供给接收切换的智能体，并且当切换链中断时，没有可以依靠的共享状态。The stateless model’s strengths are real: it is simple to reason about, easy to test in isolation, and composable—adding a new agent requires only defining its prompt and tools, not restructuring a workflow graph. These properties make it well-suited to short, well-defined task chains where each step’s output is a sufficient input for the next. Its limitations become apparent under long-running coordination: context accumulated in one agent’s reasoning is not automatically available to the agent that receives the handoff, and there is no shared state to fall back on when the handoff chain breaks.

2.4.4 开放问题：动态推理与显式 DAGOpen Question: Dynamic Reasoning vs. Explicit DAG

上述三种模型并不同样适合所有任务，它们之间的选择也不纯粹是技术性的，它反映了对给定部署环境中哪些故障模式更可接受的判断。无状态群为了简单性而优化，但牺牲了协调可见性。显式图结构以预先规范负担为代价优化了可预测性。动态编排以牺牲可调试性为代价来优化灵活性。The three models described above are not equally suited to all tasks, and the choice between them is not purely technical—it reflects a judgment about which failure modes are more acceptable in a given deployment context. Stateless swarms optimize for simplicity at the cost of coordination visibility. Explicit graph structures optimize for predictability at the cost of pre-specification burden. Dynamic orchestration optimizes for flexibility at the cost of debuggability.

更深层次的张力在于生产系统同时需要的两个属性之间的关系：处理事先未完全了解其结构的任务的能力，以及在故障发生时理解、测试并从故障中恢复的能力。当前的编排模型将这些视为一种权衡，而不是一种结合——获得一个就意味着放弃另一个。The deeper tension is between two properties that production systems require simultaneously: the ability to handle tasks whose structure is not fully known in advance, and the ability to understand, test, and recover from failures when they occur. Current orchestration models treat these as a trade-off rather than a conjunction—gaining one means conceding the other.

一个值得探索的方向是这两种方法是否可以组合而不是两者之间进行选择。动态推理任务结构的编排器可以首先生成其推断出的​​依赖关系图的显式表示，而不是立即分派子任务，即可以在执行开始之前检查、修改和验证的草案执行计划。然后，确定性图执行器将运行该计划，提供显式图编排的故障隔离和可重复性，同时编排器的动态推理处理无法预先指定的任务结构。这种两阶段方法的开销是否可以通过可调试性的改进来证明是合理的，以及 LLM 生成的执行计划是否足够可靠，可以作为确定性执行的基础，这些仍然是悬而未决的问题。One direction worth exploring is whether the two approaches can be composed rather than chosen between. An orchestrator that reasons dynamically about task structure could, rather than dispatching subtasks immediately, first produce an explicit representation of the dependency graph it has inferred—a draft execution plan that can be inspected, modified, and validated before execution begins. The deterministic graph executor would then run the plan, providing the failure isolation and reproducibility of explicit graph orchestration while the orchestrator’s dynamic reasoning handles the task structures that cannot be pre-specified. Whether the overhead of this two-phase approach is justified by the improvement in debuggability, and whether LLM-generated execution plans are reliable enough to serve as the basis for deterministic execution, remain open questions.

3.3 人在环：许可桥Human-in-the-Loop: The PermissionBridge

代理执行引入了一类行为，其后果足够严重，需要在执行之前获得明确的人工授权。生产线束必须满足这一要求，而不会将人类参与视为对代理循环的异常中断 - 它必须是运行时可以优雅处理的一流原语，从而在任意批准延迟之间保持会话连续性。Agentic execution introduces a class of actions whose consequences are significant enough to warrant explicit human authorization before they proceed. 3.3.2 权限分级Permission Tiering

并非所有工具调用都具有相同的风险状况，并且需要对每个工具调用进行明确批准将使代理在实践中无法使用。 SemaClaw 应用两层权限策略。Not all tool invocations carry the same risk profile, and requiring explicit approval for every tool call would make the agent unusable in practice. SemaClaw applies a two-tier permission policy.

内部工具（内存检索、工作区管理、代理间调度以及与运行时捆绑在一起的其他基础设施操作）均经过预先授权，无需用户交互即可调用。这些工具完全在代理自身的范围内运行，不能影响其之外的系统；他们的风险状况不保证每次调用都获得批准。Internal tools—memory retrieval, workspace management, inter-agent dispatch, and other infrastructure operations bundled with the runtime—are pre-authorized and invoke without user interaction. These tools operate entirely within the agent’s own scope and cannot affect systems outside it; their risk profile does not warrant per-invocation approval.

外部工具（用户安装的 MCP 服务器、文件系统操作、出站 API 调用以及超出代理内部环境的任何工具）默认情况下需要明确的每次调用同意。代理人提出拟议的行动及其论据；用户通过可用的批准界面（通道内联按钮或 Web UI）批准或拒绝。该边界反映了工具层应用的最小特权原则：代理不拥有对外部系统进行操作的环境权限；每一项此类行为都必须受到明确制裁。External tools—user-installed MCP servers, file system operations, outbound API calls, and any tool that reaches beyond the agent’s internal environment—require explicit per-invocation consent by default. The agent presents the proposed action and its arguments; the user approves or denies through whichever approval interface is available (channel inline buttons or Web UI). This boundary reflects the principle of least privilege applied at the tool layer: the agent holds no ambient permission to act on external systems; each such action must be explicitly sanctioned.

3.3.3 桥梁设计The Bridge Design

权限桥PermissionBridge作为在所有并发代理会话之间共享的单个实例运行。并发批准请求通过在暂停时分配的唯一请求标识符进行复用；通过匹配该标识符，每个响应都被路由回正确的等待执行上下文。这种设计允许多个代理同时进行待批准，而无需它们之间进行任何协调 - 桥接器透明地处理扇入和扇出。operates as a single instance shared across all concurrent agent sessions. Concurrent approval requests are multiplexed by a unique request identifier assigned at the point of suspension; each response is routed back to the correct waiting execution context by matching this identifier. This design allows multiple agents to have simultaneous pending approvals without any coordination between them—the bridge handles fan-in and fan-out transparently.

批准界面是通道原生的：请求在用户已处于的同一 Telegram 对话中以交互消息的形式出现，并带有用于批准和拒绝的内联操作按钮。并行 Web UI 路径可供喜欢仪表板视图的用户使用。两条路径汇聚在同一个桥上，因此通过任一接口的批准都会恢复相同的等待执行。代理的会话在整个审批窗口中保持有效；超时机制在“最后活动”模式下运行 - 任何用户交互（包括与批准提示的交互）都会延长会话生命周期，防止批准延迟导致虚假会话终止。The approval interface is channel-native: requests surface as interactive messages in the same Telegram conversation the user is already in, with inline action buttons for approve and deny. A parallel Web UI path is available for users who prefer a dashboard view. Both paths converge on the same bridge, so approval through either interface resumes the same waiting execution. The agent’s session remains live throughout the approval window; the timeout mechanism operates in "last active" mode—any user interaction, including engagement with the approval prompt, extends the session lifetime, preventing approval latency from causing spurious session termination.

3.3.4 信任作为设计原语Trust as a Design Primitive

PermissionBridge体现了对人类监督和代理自治之间关系的特定立场：两者并不紧张。事后附加的权限系统（会中断代理执行并需要特殊处理）鼓励系统设计者尽量减少其使用。运行时原生的权限系统具有清晰的分层和非阻塞行为，使人类监督成为阻力最小的路径，而不是障碍。The PermissionBridge embodies a specific position on the relationship between human oversight and agent autonomy: the two are not in tension. A permission system that is bolted on after the fact—one that interrupts agent execution and requires special handling—encourages system designers to minimize its use. A permission system that is native to the runtime, with clear tiering and non-blocking behavior, makes human oversight the path of least resistance rather than an obstacle.

这种设计立场符合更广泛的线束工程理念：结构上施加的约束比通过惯例施加的约束更可靠。要求外部工具调用通过批准门并不是对代理能力的限制，它是用户基于已证明的判断而不是假设的可信度逐步扩展代理的可信操作空间的机制。This design stance aligns with the broader harness engineering philosophy: constraints imposed structurally are more reliable than constraints imposed through convention. Requiring external tool invocations to pass through an approval gate is not a limitation on agent capability—it is the mechanism through which users extend the agent’s trusted action space incrementally, on the basis of demonstrated judgment rather than assumed trustworthiness.

3.6 一种四种模式的计划任务系统A Four-Mode Scheduled Task System

计划任务代表一类独特的代理工作负载：它们是由时间而不是用户输入触发的，其复杂程度从根本不需要模型推理的简单提醒到完全自主的多步骤代理执行。通过完整的代理管道路由每个计划任务的系统会在不需要的工作上浪费计算和令牌预算；仅支持轻量级自动化的系统无法解决受益于代理推理的用例。Scheduled tasks represent a distinct class of agent workload: they are triggered by time rather than by user input, and they range in complexity from a simple reminder that requires no model inference at all to a fully autonomous multi-step agent execution. A system that routes every scheduled task through a full agentic pipeline wastes both compute and token budget on work that does not require it; a system that only supports lightweight automation cannot address the use cases that benefit from agentic reasoning.

SemaClaw 通过定义四种执行模式来解决这个问题，每种模式都与不同的复杂性配置文件相匹配。SemaClaw addresses this by defining four execution modes, each matched to a distinct complexity profile.

The task is entirely deterministic: a scheduled time, a pre-authored message body, and a target channel. It consumes no tokens and completes with minimal latency.

纯脚本Pure script按计划执行确定性代码例程。该脚本在代理运行时之外运行——没有上下文窗口，没有模型调用，没有工具权限开销——并直接产生结构化输出或副作用。该模式适用于数据收集、文件处理、API 轮询以及其他逻辑完全可指定而无需 LLM 推理的任务。它的主要优点是稳定性（行为正是代码指定的，没有随机变化）和成本效率（无论执行频率或复杂性如何，零令牌消耗）。executes a deterministic code routine on schedule. 纯剂Pure agent在预定时间调用完整的代理执行。代理接收预先编写的提示，对其可用工具和内存进行推理，并自主生成响应或采取行动。这种模式适用于需要判断、综合或适应的任务——总结一周的活动、起草状态报告或启动一项研究任务——这些任务的内容无法提前确定，并受益于智能体的完整推理能力。invokes a full agentic execution at a scheduled time. The design implications are significant. A stateless tool can be invoked freely with no concern for side effects on the agent’s architecture; the worst case is a bad output that the user ignores. A stateful harness plugin changes persistent state, and a poorly designed one can introduce noise, contradictions, or structural drift into this knowledge layer that future sessions will operate on. This demands a different design standard: not just “does this produce a useful output” but “does this leave the agent’s persistent architecture better than it found it.”

4.5 超越个人代理——驾驭时代的社区形式Beyond the Individual Agent — Community Forms in the Harness Era

4.5.1 分析单位的转变A Shift in the Unit of Analysis

前面的问题都以单个代理或单个操作员控制下的代理团队为分析单位。系统提示、记忆、角色、技能：这些都是由一个用户配置的。这是个人人工智能代理设计的自然起点，也是当前大部分工程工作集中的地方。The preceding questions have all taken the individual agent—or a team of agents under a single operator’s control—as the unit of analysis. The system prompt, the memory, the persona, the skill set: these are all configured by and for one user. This is the natural starting point for personal AI agent design, and it is where most of the current engineering work is concentrated.

但开源代理生态系统已经产生了不适合这种模式的社区形式。 ClawHub 是最明显的例子：个人用户在其中发布他们创作的技能，其他用户则在其上安装和构建。这里的分析单位不是个体代理，而是代理社区，其能力由共享的、不断发展的技能共享所塑造。由一个用户的代理工作流程创作的技能可以成为其他数千人可用的功能。个人和集体通过共享基础设施层联系起来。But the open-source agent ecosystem is already producing community forms that do not fit this model. ClawHub is the clearest example: a registry where individual users publish skills they have authored, and other users install and build on them. The unit of analysis here is not the individual agent—it is the community of agents whose capabilities are shaped by a shared, evolving skill commons. Skills authored by one user’s agent workflow become capabilities available to thousands of others. The individual and the collective are linked through a shared infrastructure layer.

这种在技能维度上已经建立的模式提出了一个更大的问题：随着代理系统的成熟和扩散，将会出现哪些其他社区形式，以及它们需要哪些工程基础设施？This pattern, already established in the skill dimension, raises a larger question: as agent systems mature and proliferate, what other community forms will emerge—and what engineering infrastructure do they require?

The community forms that seem most valuable are the ones that are furthest from being buildable today.

在我们看来，这是个人人工智能代理领域最重要的长期工程问题：不是如何使单个代理更有能力，而是如何构建基础设施，使代理社区以及围绕代理组织起来的人类社区能够产生单个代理无法单独产生的集体智慧。本文中描述的线束工程工作是该基础设施的先决条件，而不是基础设施本身。考虑到本节中的所有五个问题，SemaClaw 的贡献是展示了个体代理级别的可能性；在此基础上形成的社区形式是生态系统需要共同解决的问题。This is, in our view, the most consequential long-horizon engineering question in the personal AI agent space: not how to make an individual agent more capable, but how to build the infrastructure that allows communities of agents—and communities of humans organized around agents—to produce collective intelligence that no individual agent could produce alone. The harness engineering work described in this paper is a precondition for that infrastructure, not the infrastructure itself. Taken across all five questions in this section, SemaClaw’s contribution is to demonstrate what is possible at the individual-agent level; the community forms that become possible on top of it are a problem for the ecosystem to solve together.

5 结论Conclusion

本文提出了一个持续的论点：个人人工智能代理系统的可靠性、安全性和长期有用性主要是工程属性——由模型周围的线束结构决定，而不是仅由模型决定——并且朝这个方向构建需要一个连贯的、分层的架构，其中每个设计决策都相互强化。This paper has made a single sustained argument: that the reliability, safety, and long-term usefulness of a personal AI agent system are primarily engineering properties—determined by the structure of the harness around the model, not by the model alone—and that building in this direction requires a coherent, layered architecture where each design decision reinforces the others.

Agent Teams add a coordination layer above the individual agent, enabling declarative DAG-driven multi-agent execution grounded in persistent personas rather than ephemeral role assignments. Scheduled tasks extend the system’s temporal reach, routing each job to the appropriate execution primitive based on its complexity class. The wiki-based personal knowledge infrastructure closes the loop between task execution and durable knowledge: intelligence produced through interaction is captured as a user-owned Markdown corpus the user can browse, edit, and reorganize, and from which future agent sessions retrieve as a curated knowledge layer.

The result is a system that is structurally safe by default—agent authority is bounded, human oversight is native to the execution path, and each extension point is governed—while remaining open and composable at every level. The architecture accommodates a range of deployment contexts, from a single user running a personal assistant for daily knowledge work to a small team operating a standing roster of specialized agents on shared projects. In both cases, the same layered harness governs execution, and the same mechanisms accumulate value over time.
