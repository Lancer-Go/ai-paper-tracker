1 简介Introduction

直到最近，从业务文档中提取结构化数据都是由人类执行的：知识工作者阅读财务文件、保险索赔、采购订单和政府表格，然后将相关值输入到下游工作流程的记录系统中。 这项工作通常是高度手工和重复性的，任何错误都可能造成高昂的代价Until recently, extracting structured data from business documents was performed by humans: knowledge workers read financial filings, insurance claims, purchase orders, and government forms, then keyed the relevant values into a system of record for downstream workflows. This work is usually highly manual and repetitive, and any mistakes can be costly[18, 5]。 随着大型语言模型和自主代理的最新发展，我们看到企业对部署代理来完成历史上由人类执行的以提取为中心的文档工作流程的需求快速增长。. With the recent development of large language models and autonomous agents, we see fast-growing demand from enterprises to deploy agents to complete extraction-focused document workflows historically performed by humans.

模式定义是提取工作流程的中心。 模式定义一个提取任务，在同一类型的所有文档之间共享。 例如，一个发票模式涵盖来自每个供应商的发票，无论每张发票看起来有多么不同。 鉴于企业几乎为每个新工作流程编写新模式，系统无法仅针对一个固定模板进行调整。 我们将提取任务定义为Schema definition is at the center of the extraction workflow. A schema defines one extraction task, shared across all documents of the same type. For example, one invoice schema covers invoices from every vendor regardless of how different each invoice may look. Given that enterprises write a new schema for almost every new workflow, a system cannot be tuned to just one fixed template. Second, tables fail in a way no other page element does: a complex table can be read correctly value by value and still be assembled into the wrong structure, a failure that the task and perception axes cannot isolate. The structure tags mark the layouts where this happens: merged or hierarchical headers (S1), a header that does not sit above its data (S2), a table that continues across pages (S3), a table beyond a thousand rows (S4), and a table packed inside a single cell (S5). Each layout has its own failure: a merged header attaches values to the wrong column, a pivoted header transposes the record, a cross-page table loses its continuation, a very large table stops early, and a packed cell comes back as one string instead of its fields.

文档长度。Document length.

文档分为三个长度桶：短（L1，最多 10 页）、中（L2，11 至 50 页）和 长（L3，超过50）。 长度有自己的轴，其原因与其他轴是分开的相同：相同的任务挑战 可以以任意长度出现，并且长度会增加其自身的失败，因为系统可以读取每个值 正确地在页面上，并且仍然在漫长的计划结束之前停止。Documents fall into three length buckets: short (L1, up to 10 pages), medium (L2, 11 to 50), and long (L3, more than 50). Length gets its own axis for the same reason the other axes are separate: the same task challenge can appear at any length, and length adds a failure of its own, since a system can read every value on a page correctly and still stop before the end of a long schedule.

2.3 模式和地面实况构建Schema and Ground-Truth Construction

为了正确评估模式引导的提取系统，提取任务本身需要明确指定：每个模式必须与其应用的文档一致，每个字段必须有明确的期望值。 如果模式与其文档族的一致性较差，或者其指令使提取目标不明确，则无法再归因错误，并且低分可能反映基准测试中的缺陷，而不是正在测试的系统中的缺陷。To properly evaluate a schema-guided extraction system, the extraction task itself needs to be well specified: each schema must be coherent with the documents it applies to, and every field must have a clear expected value. If a schema is poorly aligned with its document family, or its instructions leave the extraction goal ambiguous, errors can no longer be attributed and a low score may reflect a defect in the benchmark rather than in the system being tested.

创建定义良好的模式和与其相对应的基本事实是劳动密集型的，特别是当文档很长并且数据很密集时。 在这种规模下，手动检查每个字段在时间和成本上都令人望而却步，并且使用单个提取器的输出作为基本事实会重复其错误并使结果偏向该提取器。 这激发了可扩展的管道，无需完全手动注释即可生成高质量的模式和地面实况对。Creating well-defined schemas and ground truth that corresponds to them is labor-intensive, particularly when documents are long and the data is dense. Checking every field by hand is prohibitive in time and cost at this scale, and using a single extractor’s output as ground truth would repeat its mistakes and bias the results toward that extractor. This motivates a scalable pipeline that produces high-quality schema and ground-truth pairs without fully manual annotation.

为此，我们结合了三个文档源，每个文档都用适合它的方法进行注释：真实文档的前沿模型集成、合成长列表的编程生成以及扫描表单的人工标记器（To this end, we combine three sources of documents, each annotated by the method that fits it: frontier-model ensembles for real documents, programmatic generation for synthetic long lists, and human labelers for scanned forms (Figure˜2）。 真实文档提供了我们想要测试的布局、扫描噪声和域范围，但在其上画了一个框 他们的每一个领域都慢得令人望而却步。 合成长列表涵盖的文档太大而无法手动标记：数千条类似记录速度很慢 需要注释，容易误读。 扫描的表格是真实的文档，需要人来决定每个值，因为手写是 不清楚，并且标记可以位于两个字段之间。 来自这些来源的文档也会被重新捕获为降级扫描，这不需要新的 注释：值不会改变，因此干净文档的基本事实会保留。 我们使用这种方法来构建 ExtractBench，但它可以轻松扩展到更大的数据集。). Real documents supply the layouts, scan noise, and domain range we want to test, but drawing a box on every one of their fields is prohibitively slow. Synthetic long lists cover documents too large to label by hand: thousands of similar records are slow to annotate and easy to misread. Scanned forms are real documents that need a person to decide each value, because handwriting is unclear and a mark can sit between two fields. 4.2 文档提取方法Methods for Document Extraction

现代模式引导的提取系统分为三大类：直接生成输出的通用视觉语言模型、使用工具迭代检查文档的编码代理以及围绕文档处理工作流程设计的专用提取系统。 这些方法在完整性、视觉鲁棒性、基础性和成本方面做出了不同的权衡。Modern schema-guided extraction systems fall into three broad families: general-purpose vision-language models that generate outputs directly, coding agents that inspect documents iteratively with tools, and specialized extraction systems designed around document processing workflows. These approaches make different tradeoffs in completeness, visual robustness, grounding, and cost.

视觉语言模型。Vision-language models.

通用视觉语言模型是多模态推理器，它接受文本和图像并生成灵活的输出。 因此，文档提取可以重新表述为多模式生成：文档页面呈现为图像，模式表示为文本指令，模型返回提取的值作为提示文本或通过结构化输出 API 强制执行的符合模式的输出。 该系列中的系统包括封闭式通用模型General-purpose vision-language models are multimodal reasoners that accept text and images and generate flexible outputs. Document extraction can therefore be reformulated as multimodal generation: document pages are rendered as images, the schema is expressed as text instructions, and the model returns extracted values either as prompted text or as schema-compliant output enforced through a structured-output API. Systems in this family include closed general-purpose models[29, 13]，通用开放重量模型, general-purpose open-weight models[34, 14]，以及专门为提取而调整的模型, and models tuned specifically for extraction[7, 27]。 所有三个小组都接受新模式，无需针对特定任务进行再培训。 这种直接的一次性工作流程简单高效，但可能会丢失长重复结构中的值，并且此处评估的系统不会返回源证据。. All three groups accept new schemas without task-specific retraining. This direct, one-pass workflow is simple and efficient, but can miss values in long repeated structures, and the systems evaluated here do not return source evidence.

编码剂。Coding agents.

编码代理，例如 CodexCoding agents such as Codex[28, 30]和克劳德·代码and Claude Code[1, 2]通过迭代工具使用循环进行提取：将文档和架构作为文件给出，他们可以检查页面、编写解析代码、运行检查并修改最终的 JSON。 此循环比一次性生成更灵活，可以帮助处理长文档或重复记录，其中代理可以重新访问文档而不是依赖于单个模型响应。 同样的灵活性也会带来成本和可靠性风险：即使是简短的文档也可能会触发许多检查、编码、调试和验证步骤，并且不受约束的代理可以在生成少量提取之前运行许多步骤。 编码代理还需要具有文件系统访问和验证功能的代理运行时，这取决于文档的呈现方式以及可用的工具，并且不是围绕特定于提取的基础元数据而设计的。approach extraction through an iterative tool-use loop: given the document and schema as files, they can inspect pages, write parsing code, run checks, and revise the final JSON. This loop is more flexible than one-pass generation and can help with long documents or repeated records, where the agent can revisit the document rather than rely on a single model response. The same flexibility creates cost and reliability risks: even short documents may trigger many inspection, coding, debugging, and validation steps, and unconstrained agents can run for many steps before producing a small extraction. Coding agents also require an agent runtime with filesystem access and validation, depend on how documents are rendered and which tools are available, and are not designed around extraction-specific grounding metadata.

专门的文档提取器。Specialized document extractors.

商业平台Commercial platforms[36, 10, 6, 24]将提取公开为专用 API，而不是原始模型提示或编码环境。 作为托管服务，它们允许用户直接上传文件并处理格式支持、预处理、文档解析和模式引导提取，只需很少的配置。 它们还可以公开视觉基础和其他提取元数据，例如源页面，在某些情况下还可以公开单词级框，使输出比原始模型响应更容易审核。 然而，专用 API 在完整性、稳健性、接地质量和成本方面仍然存在很大差异。expose extraction as a purpose-built API rather than a raw model prompt or coding environment. As managed services, they let users upload files directly and handle format support, preprocessing, document parsing, and schema-guided extraction with little configuration. They can also expose visual grounding and other extraction metadata, such as source pages and, in some cases, word-level boxes, making outputs easier to audit than raw model responses. However, specialized APIs still differ substantially in completeness, robustness, grounding quality, and cost.

5 结论Conclusion

我们推出了 ExtractBench，这是一种带有挑战标记的基准，它将真正的模式引导提取的核心要求纳入一次评估中：正确且完整的输出、源可追溯性、跨文档挑战的稳健性以及大规模成本。 通过一起测量这些维度，ExtractBench 不仅可以显示哪些系统表现良好，还可以显示它们在何处以及为何失败。We introduced ExtractBench, a challenge-tagged benchmark that brings the core requirements of real schema-guided extraction into one evaluation: correct and complete outputs, source traceability, robustness across document challenges, and cost at scale. By measuring these dimensions together, ExtractBench shows not only which systems perform well, but where and why they fail.

直接 VLM 提取成本低廉，但通常会截断长记录列表；编码代理在这些工作负载上更强大，但成本更高。 专业 API 跨越了质量成本前沿，LlamaExtract Agentic Plus 以比编码代理更低的成本实现了最强的整体性能。 带有挑战标签的结果进一步表明，系统在长文档、密集模式、扫描、手写和巨大表格上的性能下降程度不同。Direct VLM extraction is inexpensive but often truncates long record lists; coding agents are more robust on these workloads but substantially more expensive. Specialized APIs span the quality–cost frontier, with LlamaExtract Agentic Plus achieving the strongest overall performance at a lower cost than the coding agents. Challenge-tagged results further show that systems degrade differently on long documents, dense schemas, scans, handwriting, and enormous tables.

接地仍然是最明显需要改进的领域。 默认情况下，评估的 VLM 和编码代理不会返回源证据，而即使对于返回盒子的专用系统，字级接地 F1 仍低于 50%。 总之，这些结果为可靠提取设定了明确的标准：完整的产出、可追溯的证据和大规模的可持续成本。Grounding remains the clearest area for improvement. The evaluated VLMs and coding agents do not return source evidence by default, while word-level grounding F1 remains below 50% even for specialized systems that return boxes. Together, these results set a clear bar for reliable extraction: complete outputs, traceable evidence, and sustainable cost at scale.
