摘要Abstract

计算机使用代理（CUA）被部署来浏览网络和操作桌面软件，但它们的基准分数仍然通常由脆弱的脚本预言机产生。分数是管道的输出，其中任务可能会过时，轨迹可能会忽略决定性的视觉证据，评估者可能会拒绝有效的替代方案，而汇总报告可能会隐藏失败的原因。我们将这些问题组织成一个涵盖任务构建、轨迹观察、评分和报告的可靠性框架。然后，我们审核了来自 5 个网络、企业工作流程和桌面控制基准的 150 个公共失败评分轨迹，发现 15.3% 的 FAIL 判决是错误的：10.7% 是评估者漏报，4.7% 是损坏的任务。对于真正的故障，三层诊断分类法表明验证/反馈和规划故障主导执行/接地错误，而单一标量成功率无法解释。我们将这些发现与更新的长期 CUA 基准联系起来，并得出用于 CUA 评估的特定阶段的设计规则。Computer-use agents (CUA) are being deployed to browse the web and operate desktop software, yet their benchmark scores are still commonly produced by brittle scripted oracles. A score is the output of a pipeline in which tasks can be stale, trajectories can omit decisive visual evidence, evaluators can reject valid alternatives, and aggregate reports can hide the cause of failure. We organize these problems into a reliability framework spanning task construction, trajectory observation, scoring, and reporting. We then audit 150 public failure-scored trajectories from five web, enterprise-workflow, and desktop-control benchmarks, find that 15.3% of FAIL verdicts are wrong: 10.7% are evaluator false negatives and 4.7% are broken tasks. For genuine failures, a three-tier diagnostic taxonomy shows that verification/feedback and planning failures dominate execution/grounding errors, while a single scalar success rate can not explain. We connect these findings to newer long-horizon CUA benchmarks and derive stage-specific design rules for CUA evaluation.

C.3 动态基准Dynamic Benchmarks

为了应对基准饱和和污染，评估环境的发展速度必须快于所测试的模型。To combat benchmark saturation and contamination, evaluation environments must evolve faster than the models they test.

(2025)。结合TRACE的进化提议者等任务进化机制. Combined with task-evolution mechanisms such as TRACE’s evolutionary proposerGuo et al. (2025)，这会在代理和基准之间造成“军备竞赛”，确保评估永远不会达到上限。 (ii) 程序生成：未来的基准测试可能会使用程序生成来创建任务的无限变化（例如，改变文件名、UI 布局和 OSWorld 中的数据值），以防止过度拟合和记忆, this creates an “arms race” between the agent and the benchmark, ensuring the evaluation never hits a ceiling. (ii) Procedural Generation: Future benchmarks will likely use procedural generation to create infinite variations of tasks (e.g., varying file names, UI layouts, and data values in OSWorld) to prevent overfitting and memorizationWang et al. (2019)。 (iii) 受控随机性（种子随机化）：为了协调现实性与再现性，基准可以注入“种子随机化”。通过显式随机种子引入网络延迟或瞬态 UI 漂移等随机元素，实验室可以针对现实世界的“混乱”测试代理，同时保持确定性的再现性。在这个框架中，系统快照提供了基础，而种子扰动则提供了现实层。. 排除标准。Exclusion criteria.

我们排除 (i) 纯文本生成、静态 QA、仅 API 工具使用以及没有 GUI 操作循环的仅代码或命令行基准测试； (ii) 仅多主体协调框架，不属于我们的单主体范围； (iii) 没有可评估方法的立场文件； (iv) 同一作品的重复版本（arXiv 和场地版本计算一次，引用可用的场地版本）。We exclude (i) pure text generation, static QA, API-only tool use, and code- or command-line-only benchmarks with no GUI action loop; (ii) multi-agent-only coordination frameworks, which fall outside our single-agent scope; (iii) position papers without evaluable methodology; and (iv) duplicate versions of the same work (arXiv and venue versions counted once, citing the venue version where available).
