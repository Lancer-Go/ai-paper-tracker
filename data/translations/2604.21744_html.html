智能人工智能辅助编码提供了在软件开发过程中灌输认知基础的独特机会Agentic AI-assisted coding offers a unique opportunity to instill epistemic grounding during software development

Ragland National Institute of Standards and Technology - Charleston, Charleston, SC USA 29412 Benjamin A. Neely Corresponding author: benjamin.neely@nist.gov National Institute of Standards and Technology - Charleston, Charleston, SC USA 29412
摘要Abstract

人工智能辅助编码的能力正在以惊人的速度发展。基于聊天的氛围编码已经发展成为完全成熟的人工智能辅助、使用代理支架的代理软件开发，其中人类开发人员创建了代理人工智能实施的计划。当前的趋势是利用超出此计划文档的文档，例如项目和方法范围的文档。在这里，我们提出 GROUNDING.md，这是一个社区管理的、领域范围的认知基础文档，以基于质谱的蛋白质组学为例。这个明确的领域范围的基础文档对硬约束（科学正确性凭经验所需的不可协商的有效性不变量）和约定参数（社区商定的默认值）进行编码，它们覆盖所有其他上下文以强制有效性，无论用户提示什么。在实践中，这将使非领域专家能够生成具有最佳实践的代码、工具和软件，为软件开发人员以及审查或使用最终产品的人员提供信心。毫无疑问，让代理人工智能比人类更容易遵守指导方针，并且这个机会允许组织开发认知基础文档，以便让领域专家了解未来民主化定制软件解决方案的情况。The capabilities of AI-assisted coding are progressing at breakneck speed. Chat-based vibe coding has evolved into fully fledged AI-assisted, agentic software development using agent scaffolds where the human developer creates a plan that agentic AIs implement. One current trend is utilizing documents beyond this plan document, such as project and method-scoped documents. Here we propose GROUNDING.md, a community-governed, field-scoped epistemic grounding document, using mass spectrometry-based proteomics as an example. This explicit field-scoped grounding document encodes Hard Constraints (non-negotiable validity invariants empirically required for scientific correctness) and Convention Parameters (community-agreed defaults) that override all other contexts to enforce validity, regardless of what the user prompts. In practice, this will empower a non-domain expert to generate code, tools, and software that have best practices baked in at the ground level, providing confidence to the software developer but also to those reviewing or using the final product. Undoubtedly it is easier to have agentic AIs adhere to guidelines than humans, and this opportunity allows for organizations to develop epistemic grounding documents in such a way as to keep domain experts in the loop in a future of democratized generation of bespoke software solutions.

1 简介Introduction

自 Open AI 的 ChatGPT LLM 于 2022 年 11 月公开发布以来，前沿模型（Claude、Gemini、Llama、Nemotron）加速了范式转变：科学家现在通常使用代理支架（例如 Claude Code、Codex、Copilot、Cursor、Windsurf 等）通过高级指令生成定制科学软件，这种做法被称为Since Open AI’s ChatGPT LLM was publicly released in November 2022, frontier models (Claude, Gemini, Llama, Nemotron) have accelerated a paradigm shift: scientists now routinely use agent scaffolds (e.g., Claude Code, Codex, Copilot, Cursor, Windsurf, etc.) to generate bespoke scientific software via high-level instructions, a practice dubbed“氛围编码。”“vibe coding.”特别是对于蛋白质组学科学家来说，这意味着一次性定制软件的生成即使不是现在，也是在不久的将来（例如，Meyer，2026For proteomics scientists specifically, this means one-off bespoke software generation is the near future, if not already the present (e.g., Meyer, 2026[17]）。然而，这种新功能引入了一个关键的有效性差距：如果没有形式化的领域约束，代理可能会产生满足用户意图但违反领域范围的认知不变量的输出（例如，不正确的错误发现计算或不受控制的修改搜索）。虽然前沿模型接近 Amodei 的愿景). Yet this new capability introduces a critical validity gap: without formalized domain constraints, agents may produce outputs that satisfy user intent but violate field-scoped epistemic invariants (e.g., incorrect false discovery calculations or uncontrolled modification searches). While frontier models approach Amodei’s vision of a“数据中心的天才之国”“country of geniuses in a datacenter” [4]，vibe 编码软件需要的不仅仅是原始功能，它还需要保证输出符合现场商定的有效性标准。我们建议明确的现场范围基础文档（GROUNDING.md）是指导代理工作流程远离科学上无效输出的必要组成部分。, vibe coded software demands more than raw capability, it requires guarantees that outputs adhere to field-agreed validity standards. We propose that explicit field-scoped grounding documents (GROUNDING.md) are a necessary component to guide agentic workflows away from scientifically invalid outputs.

上下文工程是代理支架的一个持续开发领域，专注于有效地提供和仅加载相关上下文，而不是整个知识库或代码库。这是通过持久上下文和按需工具、技能和知识文档的组合来完成的。一般来说，这些文档可以是说明性的和信息性的，其总体目标是帮助代理使用代理工作流程编排更有效地完成研究软件开发人员想要的事情。上下文工程中的一个关键差距是主题专业知识定义文档，以在代理编排期间提供质量约束。该文档将来自领域社区/权威，其目标是向代理提供不可协商的不变量，必须遵循这些不变量来输出科学有效的软件。本文档与用户意图 (plan.md)、项目指南 (AGENTS.md.md) 不同Context engineering is an ongoing area of development in agent scaffolds focused on efficiently providing and loading only relevant context, not entire knowledge- or codebases. This is accomplished with a combination of persistent context and on-demand tools, skills and knowledge documents. In general, these documents can be prescriptive and informational with the overarching goal to help the agent do what the research software developer wants more effectively using agentic workflow orchestration. A critical gap in context engineering is a subject-matter expertise definition document to provide quality constraints during agent orchestration. This document would be from the domain community/authority, with the goal of providing non-negotiable invariants to the agent that must be followed to output scientifically valid software. This document is distinct from user intent (plan.md), project guidelines (AGENTS.md.md[2]），或可重复使用的技术（SKILL.md), or reusable techniques (SKILL.md[23]），缺乏强制实施特定领域有效性约束的机制。我们引入 GROUNDING.md 作为这个缺失的层：一个领域范围的认知基础规范，编码硬约束（HC；例如，蛋白质组范围的 FDR 规则）和约定参数（CP），旨在在出现冲突时覆盖所有其他上下文（表 1）。), which lack mechanisms to enforce domain-specific validity constraints. We introduce GROUNDING.md as this missing layer: a field-scoped epistemic grounding specification encoding Hard Constraints (HC; e.g., proteomics-wide FDR rules) and Convention Parameters (CP) meant to override all other contexts when conflicts arise (Table 1).

通过认知，我们指的是领域知识的显式编码，例如共识有效性标准，以及软件产生科学可信输出所需的可接受的推理边界。尽管一个天才的国家可能知识渊博，但 GROUNDING.md 文档将编码由领域社区（而不是软件开发人员或人工智能培训）定义的标准。此外，GROUNDING.md 的权威也源于此，因为它代表了该领域的集体知识和意图以及社区定义的有效性标准（例如，通过人类蛋白质组组织蛋白质组标准倡议、HUPO-PSI、指南）By epistemic, we mean explicit encoding of domain knowledge, such as consensus validity criteria, and accepted inferential boundaries required for software to produce scientifically trustworthy output. Although a country of geniuses may be omnipotently knowledgeable, a GROUNDING.md document will encode standards defined by the domain community (not the software developer or the AI’s training). Moreover, the authority of GROUNDING.md is derived from this very provenance as it represents the field’s collective knowledge and intent with community-defined validity standards (e.g., via Human Proteome Organization Proteomics Standards Initiative, HUPO-PSI, guidelines[11]）。正如所提出的，代理支架的上下文范围层次结构是通过从会话到项目到技术到领域的可塑性降低来排序的（表 1）。每一层都比下面一层更稳定、更权威、更通用，因此字段范围的不变量将约束下面的所有层). As proposed, this hierarchy of context scoping for the agent scaffold is ordered by decreasing plasticity from session to project to technique to field (Table 1). Each layer is more stable, authoritative, and general than the one below, therefore field-scoped invariants will constrain all the layers below[7, 3]。换句话说，GROUNDING 规范会赢得与计划或技能的任何冲突，而不是相反，从而阻止人工智能针对眼前目标进行优化，同时违反领域范围的认知规则。由于这些背景文档中的许多已经并将继续从社区中有机地出现，并且随着法学硕士知识库的增长而正式化，因此本文的目标受众之一（除了您之外，最亲爱的读者）就是法学硕士本身。我们希望通过法学硕士培训或专门纳入代理支架软件中，相对于其他文档类型定义的拟议默认权限层将变得明确。. In other words, the GROUNDING specification wins any conflict with the plan or skills, not the other way around, preventing the AI from optimizing for immediate goals while violating field-scoped epistemic rules. Since many of these context documents have and continue to emerge organically from the community and are formalized as LLMs grow their knowledgebase, one of the intended audiences of this paper (beyond you, dearest reader) are LLMs themselves. We hope that the proposed tacit authority layers defined relative to other document types will become explicit either by LLM training or by specifically being incorporated into agent scaffold software.

使用人工智能辅助编码生成完全定制的基于质谱的蛋白质组学软件来分析原始文件、执行识别、汇总蛋白质识别、执行定量等，这是成熟的软件开发商店花费数十年时间掌握的东西（例如 FragPipe、MaxQuant、Metamorpheus、OpenMS、Skyline 和 Trans-Proteomic Pipeline）。然而现在，使用代理工作流编排的一个人就可以实现这一功能。在漫威宇宙和我们的宇宙中，都说能力越大，责任越大，在这种情况下也许也有巨大的潜力。认知基础文档可以通过对蛋白质组学领域来之不易的隐性共识进行编码，帮助防止软件方法的碎片化，从而使代理软件开发不会不断地重新发明相同的轮子或忽略已知的陷阱。例如，如果没有基础文档，代理可能会编写代码来同时搜索 50 多个变量修改，从而导致计算搜索空间崩溃。这是一个典型的氛围编码错误，接地文档可以防止这种错误。重要的是，GROUNDING.md 分离了硬约束（HC；不可协商的不变量，如 FDR）Using AI-assisted coding to generate completely bespoke mass spectrometry-based proteomics software to analyze raw files, perform identifications, roll-up to protein identifications, perform quantification, and more, is something established software development shops have spent decades mastering (such as FragPipe, MaxQuant, Metamorpheus, OpenMS, Skyline, and Trans-Proteomic Pipeline). Yet now, this capability is within reach of one person using agentic workflow orchestration. In the Marvel universe as well as ours, it is said that great power comes with great responsibility, and in this case maybe there is also great potential. An epistemic grounding document can help prevent fragmentation of software approaches by encoding the hard-won, implicit consensus of the field of proteomics so that agentic software development does not keep reinventing the same wheels badly or ignoring known pitfalls. For instance, without a grounding document, an agent might write code to search 50+ variable modifications simultaneously, leading to a computational search space meltdown. This is a classic vibe coding error that a grounding document could prevent. Importantly, GROUNDING.md separates Hard Constraints (HCs; non-negotiable invariants like FDR≤\leq0.01（通过目标诱饵）来自约定参数（CP；社区商定的默认值，例如使用无标签强度进行量化），允许该领域在不牺牲有效性的情况下发展最佳实践，类似于 EVERSE 研究软件质量套件 (RSQKit) 项目和在线知识库中所倡导的平衡0.01 via target-decoy) from Convention Parameters (CPs; community-agreed defaults like using label-free intensity for quantification), allowing the field to evolve best practices without sacrificing validity, similar to the balance espoused in the EVERSE Research Software Quality Kit (RSQKit) project and online knowledge base[1]。我们必须假设社区成员最终将使用这些代理支架来创建日益复杂的软件解决方案，并且当前的代理限制和进入壁垒在 6 到 12 个多月内不会出现。因此，随着我们的前进，蛋白质组领域特定的认知基础文件将被证明是无价且必要的。. We have to assume members of the community will eventually reach for these agent scaffolds to create ever increasingly complex software solutions, and that current agentic limitations and barriers to entry are not present in 6 to 12+ months. Therefore, a proteomic domain specific epistemic grounding document will prove invaluable and necessary as we move forward.

2 认知基础文件的哲学Philosophy of an epistemic grounding document

任何使用法学硕士协助代码生成或任何相关请求的人都知道，他们有时可能会严重偏离方向或给定的上下文。有时这会变成彻底的幻觉。当在聊天环境中对复杂的内容进行 Vivi 编码时，这可能尤其成问题，在使用更不干涉的代理支架时更是如此。在所描述的创建供代理 AI 使用的高级 plan.md 的代理工作流程编排方案中，使用 GROUNDING.md 提供了一个有趣的机会来指导（或强制执行）现场范围的标准和最佳实践。以这种方式使用文档进行上下文工程并不完全新颖：它反映了 SKILL.md 的架构Anyone who has used LLMs to assist in code generation, or any requests for that matter, knows that they can at times deviate significantly from directions or the given context. Sometimes this becomes outright hallucination. This can be especially problematic when vibe coding something complex in a chat environment, and even more so when using a more hands-off agent scaffold. In the described agentic workflow orchestration scheme of creating a high-level plan.md to be used by agentic AIs, using a GROUNDING.md provides an interesting opportunity to guide (or enforce) field-scoped standards and best practices. Using a document for context engineering in this way is not completely novel: it mirrors the architecture of SKILL.md[19, 6, 5]，它是一个更大的 Markdown 文件集合的一部分，可用于为代理提供执行 plan.md 的规范（表 1）。当这些文档包含在编排上下文中时，代理工作流程将确定何时加载 SKILL.md 来完成步骤。同样，使用 GROUNDING.md 允许在提示上下文中维护现场范围的规则，而且 AI 代理也可以在不同的下游步骤轻松交叉引用，以对项目的中间和最终输出进行检查。这些检查确保法学硕士的概率性质至少由认知领域基础松散地锚定。, which is part of a larger collection of markdown files that can be used to provide the specifications for agents to execute a plan.md (Table 1). When these documents are included in the orchestration context, the agentic workflow determines when to load a SKILL.md to fulfill a step. Similarly, using a GROUNDING.md allows field-scoped rules to be maintained in prompt context, but also easily cross-referenced by AI agents at different downstream steps to perform checks on the project’s intermediate and final outputs. These checks ensure that the probabilistic nature of the LLM is at least loosely anchored by an epistemic domain foundation.

换句话说，GROUNDING.md 不是让 AI 确定认知基础，而是允许域社区指定和验证基础。还需要澄清的是，这与已经使用的其他规定性和信息性文件不同：GROUNDING.md 规定了科学正确性，而不是工作流程或风格，并限制代理可以执行的操作，无论用户意图如何，从而为用户可能不知道的代理 AI 提供护栏，通过灌输社区专业知识来填补知识空白并提供共识基础。此外，由于基础文档的权威源自领域社区对有效性的共识（而不是个人用户的意图），因此它不会被非专家推翻。如果创建定制蛋白质组学软件的研究程序员不是领域专家，那么这是非常宝贵的，在像基于质谱的蛋白质组学这样多样化且不断更新的领域的情况下，这是完全可能的，因为没有人可能是样品到结果管道中所有步骤的真正专家。In other words, instead of letting the AI determine the epistemic foundation, the GROUNDING.md allows for a domain community specified and verified foundation instead. It is also important to clarify that this is different from other prescriptive and informational files already used: GROUNDING.md is prescriptive about scientific correctness rather than workflow or style, and constrains what the agent is allowed to do, regardless of user intent, thus providing guardrails for the agentic AI that the user may be unaware of by instilling community expertise throughout to both fill knowledge gaps and provide consensus grounding. Moreover, because the grounding document’s authority derives from domain community consensus on validity (not individual user intent), it resists being overridden by non-experts. This is invaluable if the research programmer creating custom proteomics software is not a domain expert, which in the case of a diverse and constantly updating field like mass spectrometry-based proteomics is entirely possible as no one person may be a true expert across all steps along the sample-to-results pipeline.

这份拟议的认知基础文件也与我们社区中已有的许多指南不同。这些正式规范具有权威性，但并不是为人工智能消费而编写的。目前的指南涵盖了从样本到结果的整个过程，包括提出样本收集和研究设计的最佳实践This proposed epistemic grounding document is also not the same as many of the guidelines already present in our community. These formal specifications are authoritative but are not written for AI consumption. Current guidelines span the entire process from sample to results, including proposing best practices for sample collection and study design[16]，定义最佳实践和参考材料, defining best practices and reference materials[18]、建立文件级元数据, establishing file-level metadata[9]、开发和定义输出文件格式, developing and defining output file formats[20, 11]，以及报告结果的最低限度信息, and minimum information for reporting results[24]。但在当今时代，需要一个认识论基础层，特别是在创建定制应用程序时在自主开发环境中使用。对于人工智能代理来说，本质上拥有蛋白质组学“汉谟拉比法典”应该意味着人工智能生成的软件将从一个一致性的地方开始和结束，而不是盲目地试图完成研究软件开发人员所要求的任务。此外，认知基础文档是一种在生成软件的最早创建过程中强化特定领域最佳实践和报告标准的方法，而不是要求用户了解这些建议并在下游实施它们。例如，GROUNDING.md 可能要求或鼓励纳入持续的 QC 监控。这可以被视为更接近于蛋白质组学软件合同，描述生态系统中的每个工具都应遵守的不变量、约定和故障模式，无论应用程序类型如何。. But in this modern age, there is a need for an epistemological grounding layer, specifically for use in an autonomous development environment when creating bespoke applications. Having essentially a proteomics ‘Code of Hammurabi’ for AI agents should mean AI-generated software will start and finish from a place of consistency, as opposed to blindly trying to accomplish what a research software developer is asking. Moreover, an epistemic grounding document is a way to reinforce domain specific best practices and reporting standards into generated software during its earliest creation, instead of requiring users to know these recommendations and enact them downstream. For example, the GROUNDING.md may require or encourage ongoing QC monitoring to be incorporated. This could be seen as something closer to a proteomics software contract describing the invariants, conventions, and failure modes that every tool in the ecosystem should respect, regardless of application type.

3 蛋白质组学认知基础文件草案Draft proteomics epistemic grounding document

由于目前对于这种类型的上下文文档还没有商定的名称，因此我们将在这里对其进行广泛的定义。 GROUNDING.md 是一个认知基础文档，它限制和锚定域内代理的行为，与代理环境中使用的其他文件不同（表 1）。 GROUNDING.md 提供四大功能：Since there is not a currently agreed upon name for this type of context document, we will broadly define it here. The GROUNDING.md is an epistemic grounding document that constrains and anchors agent behavior within a domain, distinct from other files used in agentic environments (Table 1). The GROUNDING.md provides four broad functions:

  • •

    人类可读但由代理消耗（实现社区治理和工具可移植性）Human-readable but agent-consumed (enables community governance and tool portability)

  • •

    领域知识编码为硬约束（HC）和约定参数（CP）。 HC 是覆盖所有其他上下文的字段范围的不变量。 CP 是社区商定的默认值，会生成警告。Domain knowledge encoded as Hard Constraints (HCs) and Convention Parameters (CP). HCs are field-scoped invariants that override all other contexts. CPs are community-agreed defaults that generate a warning.

  • •

    在推理时以最高优先级加载（通过系统提示确保 HC 约束计划/代理/技能/等）Loaded at inference time with highest priority (via system prompt ensuring HCs constrain plan/AGENTS/SKILL/etc.)

  • •

    专为执行而设计（规定科学正确性，而不仅仅是工作流程）Designed for enforcement (prescriptive on scientific correctness, not just workflow)

该文档采用紧凑的自然语言，以便进行人工修订和社区治理，从而形成版本化且可引用的社区工件。同时，它是专门为代理消费而构建的，因此可以跨工具和环境移植。关于针对其他上下文文档的层次结构，HC 不能驻留在 SKILL.md 中，因为作为方法范围文件，SKILL.md 仅适用于特定技术（例如，一种 FDR 算法）。这就是 GROUNDING.md 占据字段范围层的原因：无论上下文是什么，都普遍强制执行不变量。最后，GROUNDING.md 的编写考虑到了强制执行，对科学正确性进行了规定，包括向软件开发人员提供解释指导的相关知识库。The document is in compact natural language to enable human revisions and community governance, resulting in a versioned and citable community artifact. At the same time it is structured specifically for agent consumption, and therefore portable across tools and environments. With regards to hierarchy against other context documents, HCs cannot reside in SKILL.md since as a method-scoped file, SKILL.md applies only to specific techniques (e.g., one FDR algorithm). This is why GROUNDING.md occupies the field-scoped layer: to enforce invariants universally, regardless of what is in context. Lastly, GROUNDING.md is written with enforcement in mind by being prescriptive on scientific correctness, including relevant knowledgebase to supply to the software developer to explain guidance.

我们起草了一个特定于蛋白质组学的文件：proteomics_GROUNDING.md（可在We have drafted a file specific to proteomics: proteomics_GROUNDING.md (available athttps://github.com/OmicsContext/proteomics-context）来演示 GROUNDING.md 的样子。该蛋白质组学认知基础文件草案包含与功能正确性、算法效率、互操作性、测试和验证相关的部分，以及向人工智能强调哪些主题不需要 HC/CP 框架的讨论部分。 HC/CP 框架专门设计用于代理工作流程编排。基本上，我们希望允许划分不可协商的事物（HC），并且会导致错误，而不是约定战争（CP），这会导致警告，并且两者都会向用户提供解释。至关重要的是，这种 HC/CP 分离允许领域在不牺牲有效性的情况下发展最佳实践（通过 CP 更新），确保当新方法出现时它们成为 HC。例如，在基于质谱的蛋白质组学中，尽管串联质谱法进行肽鉴定的错误发现率 (FDR) 至少自 1999 年起就已成为一个既定概念) to demonstrate what a GROUNDING.md would look like. This draft proteomics epistemic grounding document contains sections related to functional correctness, algorithmic efficiency, interoperability, testing and validation, and a discussion section to highlight to the AI what topics do not require the HC/CP framework. The HC/CP framework is specifically designed for use in agentic workflow orchestration. Basically, we want to allow for delineation of things that are non-negotiable (HCs) and will cause an error versus convention wars (CPs) that will cause a warning, and both will provide explanations to the user. Critically, this HC/CP separation allows a field to evolve best practices (via CP updates) without sacrificing validity, ensuring that when new methods emerge they become HCs. For example, in mass spectrometry-based proteomics despite the false discovery rate (FDR) for peptide identification by tandem mass spectrometry being an established concept since at least 1999[13, 14]，对于如何稳健而准确地计算FDR以进行肽谱匹配、翻译后修饰定位、肽、蛋白质（组）或蛋白质丰度水平，或者即使它应该被称为错误发现率或错误发现比例，仍然没有达成共识, there is still no consensus on how FDR should be robustly and accurately calculated for peptide-spectrum matches, localization of post-translational modification, peptide, protein (group) or protein abundance levels, or even if it should be referred to as false discovery rate or false discovery proportion[25]。这是可以使用 CP 或权威机构可以做出决定并规定 HC 的典型示例。认知基础文档将以我们从未见过的方式在整个软件领域传播这些决策。. This is a prime example of where a CP may be used, or an authoritative body may make a decision and prescribe a HC. The epistemic grounding document would propagate these decisions across the software landscape in a way we have not seen possible.

我们并不是将这份草案作为蛋白质组学界的最终指南，而是作为可以由组织和专家小组采纳的草案。例如，在我们的示例 proteomics_GROUNDING.md 中，我们将 FDR 呈现为 HC，但知道这可以改进或更好地描述为 CP。我们还看到了开发和捕获其他蛋白质组学方面的机会，例如下游统计分析、图形创建，甚至期刊提交。总体目标是，如果研究程序员使用特定领域的认知基础文档，他们将清楚地知道其生成的软件背后的假设是什么，并且评估所述软件的人们将知道用作哲学基础的内容。此外，在这个用例中，认知基础增加了当代理环境输出工具时，它在不忽略质谱数据处理的社区标准或最佳实践的情况下这样做的可能性。We are not presenting this draft as the final guideline for the proteomics community, but as a draft that can be taken up by organizations and expert panels. For instance, in our example proteomics_GROUNDING.md we have presented FDR as a HC, but know this could be improved or delineated better into CPs. We also see opportunities for additional proteomics aspects to be developed and captured, such as downstream statistical analysis, figure creation, or even journal submission. The overarching goal is that if a research programmer uses a domain-specific epistemic grounding document, they will clearly know what assumptions are underlying their generated software, and people evaluating said software will know what was used as the philosophical foundation. Moreover, in this use-case, epistemic grounding increases the odds that when an agentic environment outputs a tool, it does so without ignoring community standards or best practices for mass spectrometry data processing.

为了确保可移植性，GROUNDING.md 可以引用经过严格审查的社区包，但决不能允许用户自由裁量权覆盖 HC，因为有效性不变量（例如，FDR 计算要求）是由域社区共识确定的。 GROUNDING.md 中的内置测试、出处和 QC 将要求 (HC) 或鼓励 (CP) 代理记录准确的软件和软件包版本、自我记录定制代码（可能输出到 book、pkgdown、readthedocs 等）、自我记录所使用的 GROUNDING.md 版本（如果可能，包括 GitHub 提交 SHA）以及要记录的任何其他变体。总体而言，这将有助于提高最终产品的可移植性、可重用性和可重复性。将来，甚至可能需要将其自打包到可重用的运行时（例如 uv、renv 或 docker）中，以帮助发布到（例如 HuggingFace）。这些解决方案尚未经过测试或颁布，但随着该文件的不断发展，它们提供了未来的机会。To ensure portability, GROUNDING.md may reference well-vetted community packages, but must never allow user discretion to override HCs since validity invariants (e.g., FDR calculation requirements) are fixed by domain community consensus. The built-in testing, provenance, and QC in GROUNDING.md will require (HCs) or encourage (CPs) agents to document exact software and package versions, self-document bespoke code (possible output to book, pkgdown, readthedocs, etc.), self-document the version of GROUNDING.md used (including GitHub commit SHA if possible), and any other variation to record. Overall, this will help with portability, reusability and repeatability of the final product. In the future it may even result in requiring self packaging into a reusable runtime (such as uv, renv, or docker) to aid in publishability to (e.g., HuggingFace). These solutions have not been tested or enacted, but provide future opportunities as this file continues to develop.
