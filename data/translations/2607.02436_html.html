推理努力，而不是工具访问，购买了代理代码生成的首次尝试可靠性：一项观察性研究Reasoning effort, not tool access, buys first-try reliability in agentic code generation: an observational study

阿钦特·梅塔Achint Mehta趋势人工智能TrendAI

摘要Abstract

代理编码助手越来越多地被赋予额外的功能，例如基于浏览器的测试工具和面向设计的系统提示，假设更多的功能会产生更好的软件。这项研究直接检验了这一假设。九十个独立代理运行构建了相同的应用程序，一个实时回顾板，根据一个详细的规范，并且每个代理都根据固定的 14 个标准功能评分标准（最多 42 分）以及视觉质量审查进行评分。运行跨越多个模型代、两个代理工具、两个推理工作级别、一个测试工具和两个面向设计的提示，并重复相同的配置。能力层主导结果：前沿模型聚集在上限附近，而低成本本地模型则降至 24 至 37 点之间。标准级别分析添加了运行总计隐藏的结果。容器部署是主要缺陷，44% 的运行中第一次尝试就失败了，而且其失败率在各代模型中急剧变化，而平均总数变化不到一个点。该测试工具将成本提高了 42％ 至 68％，而没有提高功能分数或可靠性，即使在界面可见标准上也是如此，而且重点是上下文重读而不是额外的代码。将推理努力从“高”提高到“xHigh”，将首次尝试完美运行率从 28% 提高到 89%，并将纠正提示减少约五倍，成本增加 9% 到 29%。面向设计的提示提高了视觉质量，5 分制中 4.5 与 3.0，没有提升功能，其设计指令的一段释义再现了整个提升，表明该功能只需要调用。实际的教训是将修复与失败相匹配：大多数首次运行失败来自弱推理，更强的模型或更多的努力可以防止这种情况，而不是检查工具可以捕获的可见缺陷。Agentic coding assistants are increasingly given extra capabilities, such as browser based testing tools and design oriented system prompts, on the assumption that more capability yields better software. This study tested that assumption directly. Ninety independent agent runs built the same application, a real time retrospective board, from one detailed specification, and each was scored on a fixed 14 criterion functional rubric (42 point maximum) together with a visual quality review. The runs spanned several model generations, two agent harnesses, two reasoning effort levels, a testing tool, and two design oriented prompts, with identical configurations repeated. Capability tier dominated outcomes: frontier models clustered near the ceiling while a low cost local model fell to between 24 and 37 points. A criterion level analysis added results that run totals conceal. Container deployment was the dominant defect, failing on the first attempt in 44 percent of runs, and its failure rate shifted sharply across model generations while mean totals moved by less than a point. The testing tool raised cost by 42 to 68 percent without improving functional score or reliability, even on interface visible criteria, with the premium going to context re-reading rather than additional code. Raising reasoning effort from High to xHigh lifted first try perfect runs from 28 percent to 89 percent and cut corrective prompts about five fold, for 9 to 29 percent more cost. A design oriented prompt raised visual quality, 4.5 versus 3.0 on a 5 point scale, without lifting function, and a one paragraph paraphrase of its design directive reproduced the entire lift, showing the capability needs only invocation. The practical lesson is to match the fix to the failure: most first run failures came from weak reasoning, which a stronger model or more effort prevents, not from visible flaws a checking tool would catch.

简介Introduction

使用代理编码助手构建软件的团队通常会向代理添加功能，以期获得更好的结果。两个常见的附加功能是基于浏览器的工具，可让代理驱动和检查运行界面，以及系统提示，可推动代理走向精美的视觉设计。隐含的假设是，每次添加都会以预期的方式获得回报，测试工具使软件更加可靠，设计提示使界面更加精美，并且收益是值得其增加的成本的。在类似的基础上测试这一假设的成本很高，因为它需要在受控条件下多次运行相同的任务。Teams that build software with agentic coding assistants often add capabilities to the agent in the hope of better results. Two common additions are a browser based tool that lets the agent drive and inspect the running interface, and a system prompt that pushes the agent toward polished visual design. The implicit assumption is that each addition pays off in the way it is meant to, the testing tool by making the software more reliable and the design prompt by making the interface more polished, and that the gain is worth its added cost. Testing that assumption on a like for like basis is costly, because it requires running the same task many times under controlled conditions.

编码代理的公开比较通常使用单个短指令并报告每个模型的单次运行。该设计隐藏了实践中重要的两件事。它隐藏了单个样本无法显示的运行间差异，并将模型的选择与工具的选择、提示和推理工作混为一谈。 This study used a different design. It hides the run to run variation that a single sample cannot show, and it conflates the choice of model with the choice of tools, prompt, and reasoning effort. This study used a different design. 评分Scoring

每次运行均根据相同的 14 项功能标准进行评分。如果该功能在第一次尝试中有效，则每个标准将获得 3 分；如果第一次失败并在单个纠正提示后得到修复，则获得 2 分；如果仍未解决，则获得 1 分。纠正提示仅描述了观察到的错误或失败行为，并未提供如何修复它的指导，因此 2 分反映了模型自身仅从症状诊断和修复故障的能力。纠正提示Each run was scored against the same 14 functional criteria. Each criterion received a 3 if the feature worked on the first try, a 2 if it failed at first and was fixed after a single corrective prompt, or a 1 if it remained unresolved. The corrective prompt described only the observed error or failing behavior and offered no guidance on how to fix it, so a score of 2 reflects the model's own ability to diagnose and repair the fault from the symptom alone. 推理努力换来初次尝试的可靠性Reasoning effort buys first-try reliability

该工具未提供的可靠性可以通过推理工作获得。汇集 Opus 4.7 扫描条件，将努力从 High 提高到 xHigh 提高了第一次尝试时完美的跑步比例，这意味着在没有纠正提示的情况下得分为 42，从 28%（18 例中的 5 例）到 89%（18 例中的 16 例），无论以任何标准衡量，这一对比都很大（Fisher 精确 p < 0.001）；图3按条件分解了首次尝试率，增益出现在每个扫描单元中。综合平均分从 41.0 上升至 41.8。就修复负担而言，18 个 High 运行需要 16 个纠正提示，而 18 个 xHigh 运行则需要 3 个纠正提示，大约减少了五倍的人为干预。 High level 未命中主要集中在首次运行环境故障，即 npm 安装、Docker 构建和运行，以及重启时数据丢失的情况，这些正是在工作交还之前更多深思熟虑发现的缺陷。这一成果的成本并不高。在条件固定的情况下，xHigh 的成本溢价中值约为 9%（基本运行）、29%（使用工具）和 21%（使用设计提示）；在基本条件下，xHigh 运行发出的输出令牌与 High 运行基本相同（表 4），因此额外的考虑不仅仅是额外生成。表 5 报告了完整的 Opus 4.7 网格；上面的汇总对比使用了六个扫描单元，并且在下面的消融中采用了删节的提示单元。The reliability that the tool did not provide was available from reasoning effort. The control a practitioner would normally reach for to make repeated runs more deterministic is therefore unavailable or discouraged on these models, so the run to run spread reported here cannot simply be dialed down, and raising reasoning effort, the lever that did compress it, is the one that remains.

讨论Discussion

统一的教训是将添加的资源与故障模式相匹配。在此任务中，主要的失败是构建和环境问题，例如本机 SQLite 模块无法在最小容器中编译，以及 Web 框架中删除通配符路由的重大更改；标准级别配置文件使这一点变得具体，两个环境标准占所有首次尝试失败的一半以上（表 3）。专门针对这些故障的工具（例如容器构建或冒烟测试）原则上可以捕获它们，因此重点并不是没有工具可以提供帮助。问题在于，这里添加的工具（一种用于测试正在运行的前端的可视化自动化和测试工具）与发生故障的位置不匹配，并且令牌分解显示其成本溢价流向了上下文重读，而不是任何其他工程。在实践中，匹配是困难的部分，因为它需要预测会出现哪种故障模式并添加相应的工具，而每个添加的工具都会增加成本。相比之下，提高推理工作量可以提高跨故障模式的可靠性，而无需在基础和工具条件下进行猜测，这就是为什么花在工作上的相同预算可以直接购买可靠性；这种消融显示了该杠杆的一个边界，因为设计提示消耗了通过其他方式努力购买的部分或全部可靠性。The unifying lesson is to match the added resource to the failure mode. In this task the dominant failures were build and environment problems, such as a native SQLite module that does not compile in a minimal container and a breaking change in a web framework that removed a wildcard route; the criterion level profile makes this concrete, with the two environment criteria accounting for over half of all first try failures (Table 3). A tool aimed specifically at these faults, for example a container build or smoke test, could in principle have caught them, so the point is not that no tool could help. It is that the tool added here, a visual automation and testing tool that exercises the running front end, was not matched to where the failures occurred, and the token decomposition shows its cost premium went to context rereading rather than to any additional engineering. In practice the matching is the hard part, because it requires anticipating which failure mode will arise and adding the corresponding tool, and each added tool adds cost. Raising reasoning effort, by contrast, improved reliability across failure modes without that guesswork in the base and tool conditions, which is why the same budget spent on effort would have bought the reliability directly; the ablation shows the one boundary of that lever, since a design prompt consumed part or all of the reliability that effort otherwise buys.

修复后总计低估了型号之间的差异Post repair totals understate differences between models

标准级别的结果对代理基准具有方法论意义。在这个标题下，就像在大多数允许修复的分级评估中一样，失败然后修复标准的模型保留了大部分功劳，因此总分主要衡量模型最终可以达到的目标，而不是它在没有帮助的情况下交付的结果。在这里，家族意味着不到一点的差距，掩盖了 Docker 首次尝试通过率在前沿世代之间从 19% 上升到 75%，以及从容器构建转变为软件包安装的故障模式。对于选择模型或工作设置的团队来说，重要的可交付成果通常是独立的第一次尝试，而纠正干预的数量是直接的人力成本。如果基准报告将首次尝试的可靠性和维修负担与维修后总数一起发布，那么它们将提供更多信息；在此数据集中，这些轴可以分隔总计无法分隔的配置。The criterion level results carry a methodological implication for agent benchmarks. Under this rubric, as in most graded evaluations that allow repair, a model that fails and then fixes a criterion retains most of the credit, so aggregate scores mostly measure what a model can eventually reach rather than what it delivers unaided. Here, family means less than a point apart concealed a Docker first try pass rate that moved from 19 percent to 75 percent between frontier generations, and a failure mode that shifted from container builds to package installation. For teams choosing a model or an effort setting, the deliverable that matters is usually the unaided first attempt, and the number of corrective interventions is a direct human cost. Benchmark reports would be more informative if they published first try reliability and repair burden alongside post repair totals; in this dataset those axes separate configurations that totals cannot.

存在抛光功能，但必须调用Capability for polish is present but must be invoked

设计提示结果具有违反直觉的形状。默认情况下生成简单界面的相同模型在出现提示时会生成营销质量的界面，即使提示不包含详细的视觉说明，并且笼统地只要求提供精美的结果。这表明生成精美界面的能力已经存在于模型中，不需要进行教导，但除非明确调用，否则不会表达出来。推理努力并没有引发它；一个简短的、通用的设计说明就做到了。删节强调了这一点：为本研究编写的一段释义再现了两代模型的全部提升，因此调用既不需要长度也不需要强调，只需要询问本身。想要视觉质量的从业者应该在项目说明中直接要求它，而不是期望它从更大的模型或更高的努力设置中出现，并且应该为更雄心勃勃的界面在其最交互的重功能中携带的小功能风险做好预算，这种风险在消融中的更高努力设置中持续存在。The design prompt result has a counterintuitive shape. The same models that produced plain interfaces by default produced marketing quality interfaces when prompted, even though the prompt did not contain detailed visual instructions and asked only, in general terms, for a polished result. This suggests that the capacity to produce a polished interface is already present in the model and does not need to be taught, but that it is not expressed unless it is explicitly invoked. Reasoning effort did not invoke it; a short, general design instruction did. The ablation sharpens the point: a one paragraph paraphrase written for this study reproduced the entire lift on both model generations, so the invocation needs neither length nor emphasis, only the ask itself. Practitioners who want visual quality should ask for it directly, in as little as a paragraph of project instructions, rather than expecting it to emerge from a larger model or a higher effort setting, and should budget for the small functional risk the more ambitious interface carries in its most interaction heavy features, a risk that persisted at the higher effort setting in the ablation.

由代理和服务后端注入的隐藏提示Hidden prompts injected by agents and serving backends

本次工作中使用了Antigravity代理，发现注入了用户看不到也无法控制的系统提示。这与本研究无关。当服务后端或代理添加自己的隐藏提示时，输出会反映用户指令和注入的文本，并且研究人员通过两个不同的后端比较两个模型可能会比较两个不同的隐藏提示，就像比较两个模型一样。同样的机制是一个已知的安全和治理问题，因为不受信任的注入指令可以改变模型行为 [4]。合理的建议是，任何人比较模型或审核输出时，首先确定服务路径添加的隐藏提示（如果有），然后报告。本研究中的设计提示对比实际上是这一现象的受控版本，隔离了此类注入提示的影响。During this work, the Antigravity agent was used, and it was found to inject a system prompt that the user does not see and does not control. This is relevant beyond the present study. When a serving backend or an agent adds its own hidden prompt, the output reflects both the user instruction and the injected text, and a researcher comparing two models through two different backends may be comparing two different hidden prompts as much as two models. The same mechanism is a known security and governance concern, because untrusted injected instructions can change model behavior [4]. A reasonable recommendation is that anyone comparing models or auditing outputs first establish what hidden prompt, if any, the serving path adds, and report it. The design prompt contrast in this study is, in effect, a controlled version of this phenomenon, isolating the effect of one such injected prompt.

结论Conclusion

在一个规范的 90 次匹配和重复运行中，模型的选择决定了质量，推理工作首先以便宜的价格购买了可靠性，测试工具购买了成本但没有可靠性，简短的设计提示购买了视觉修饰而不改变功能，提示的一段版本购买了相同的修饰。在标准层面上，修复后总数掩盖了前沿世代之间首次尝试可靠性的巨大差异，以及在它们之间发生变化而不是消失的故障模式，这支持在最终分数的同时报告首次尝试可靠性和修复负担。下面的实际规则很简单。花费精力和能力来获得可靠的软件，在重要时明确要求视觉质量，并且不要指望验证工具可以修复它看不到的故障。Across 90 matched and repeated runs of one specification, the choice of model dominated quality, reasoning effort bought first try reliability cheaply, a testing tool bought cost without reliability, and a short design prompt bought visual polish without changing function, with a one paragraph version of the prompt buying the same polish. At the criterion level, post repair totals concealed large differences in first try reliability between frontier generations and a failure mode that shifted rather than disappeared across them, which argues for reporting first try reliability and repair burden alongside final scores. The practical rule that follows is simple. Spend on capability and effort to get reliable software, ask explicitly for visual quality when it matters, and do not expect a verification tool to fix failures it cannot see.
