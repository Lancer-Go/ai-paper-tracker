1. 简介Introduction

代码审查是现代软件开发中基本的质量保证实践。在将提议的更改合并到主代码库之前，开发人员会检查拉取请求 (PR) 以检测缺陷、执行项目标准并维护长期代码质量。传统上，此过程依赖于人工审阅者，他们仔细检查拉取请求 (PR) 并向作者提供反馈。 软件工程代理的最新进展显着加速了编写代码的过程。人工智能系统现在可以自动生成大量代码，用于实现新功能Code review is a fundamental quality assurance practice in modern software development. Before a proposed change is merged into the main codebase, developers inspect pull requests (PRs) to detect defects, enforce project standards, and maintain long-term code quality. Traditionally, this process relies on human reviewers who carefully examine pull requests (PRs) and provide feedback to authors. Recent progress in software engineering agents has significantly accelerated the process of writing code. AI systems can now generate large amounts of code automatically, both for implementing new features(Li et al., 2025b; Zhou et al., 2026)以及为了解决问题and for resolving issues(Xie et al., 2025; Zhang et al., 2024)在现有存储库中。随着这些系统越来越多地集成到开发工作流程中，它们有助于生成越来越多的代码和提交的 PRin existing repositories. As these systems become increasingly integrated into development workflows, they contribute to a growing number of generated code and submitted PRs(Robbes et al., 2026; Pham and Ghaleb, 2026)。然而，人类审阅者的能力并没有以同样的速度扩展. However, the capacity of human reviewers has not scaled at the same pace(Hassan et al., 2025)，在开发流程中造成了新的瓶颈：虽然代码生成日益自动化，但确保生成代码的质量仍然严重依赖于人工检查。, creating a new bottleneck in the development pipeline: while code generation is increasingly automated, ensuring the quality of generated code still relies heavily on manual inspection.

这一挑战推动了自动代码审查代理的开发，该代理可以分析拉取请求并生成审查反馈This challenge has motivated the development of automated code review agents that analyze pull requests and generate review feedback(Tang et al., 2024; Rasheed et al., 2024; Li et al., 2025a; Tantithamthavorn et al., 2026)。最近有人提出了几种工具和系统来自动生成评审意见，旨在识别错误​​、设计问题或可维护性问题。然而一个核心问题仍然存在：. Several tools and systems have recently been proposed to automatically produce review comments aimed at identifying bugs, design issues, or maintainability concerns. Yet a central question remains:这些自动审核工具在多大程度上可以识别人类审核员会提出的相同问题？to what extent do these automated review tools identify the same issues that human reviewers would raise?

现有的评价方法并不能很好地回答这个问题。大多数基准测试使用文本重叠或嵌入相似性指标将生成的评论与人工撰写的评论进行比较Existing evaluation methods do not answer this question well. Most benchmarks compare generated comments against human-written reviews using textual overlap or embedding similarity metrics(Tufano et al., 2021, 2022; Naik et al., 2025; Jiang et al., 2025; Hu et al., 2025)。此类指标主要衡量措辞的相似性，而不是审查是否识别出代码中有意义的问题。然而，我们认为这些评估方法不太适合衡量人工智能生成的评论与人类评论者提出的问题的吻合程度。人工审稿意见通常是审稿过程中嘈杂的产物：它们可能包括澄清问题、主观风格建议或审稿人和作者之间的来回讨论。因此，评论的措辞并不总是直接对应于所提出的根本问题。因此，衡量评论之间的相似度是有问题的。生成的评论可能与人工评论非常相似，但无法捕获代码中的实际问题。另一方面，评论可能使用完全不同的措辞正确识别有效问题，但仍然获得较低的相似度分数。. Such metrics primarily measure resemblance in wording rather than whether a review identifies a meaningful issue in the code. However, we posit that these evaluation approaches are not well suited for measuring how closely AI-generated reviews align with the concerns raised by human reviewers. Human review comments are often noisy artifacts of the review process: they may include clarification questions, subjective stylistic suggestions, or back-and-forth discussions between reviewers and authors. As a result, the wording of a comment does not always correspond directly to the underlying issue being raised. Measuring similarity between comments is therefore problematic. A generated review may closely resemble a human comment while failing to capture the actual problem in the code. On the other hand, a review may correctly identify a valid issue using entirely different wording and still receive a low similarity score.

其他评估方法也存在类似的局限性，例如本地化指标Similar limitations also arise in other evaluation methods, such as localization metrics(Guo et al., 2025; Zhang et al., 2026)和法官法学硕士and LLM-as-a-judge(Guo et al., 2025)。本地化指标仅评估是否在与真实人类审查相同的代码位置识别问题，而忽略审查的实质内容。此外，法学硕士作为法官的方法可能对提示设计和固有的随机性很敏感，导致他们的判断难以可靠地再现。. Localization metrics only assess whether an issue is identified at the same code location as the ground truth human reviews while ignoring the substance of the review. Furthermore, LLM-as-a-judge approaches can be sensitive to prompt design and inherent randomness, causing their judgments difficult to reproduce reliably.

为了解决这些局限性，评估应重点关注评审工具是否能够识别人工评审员通常会提出的 PR 中存在的根本问题，而不是依赖于评审质量的间接代理，例如与人工撰写的评论的相似性、位置匹配或法学硕士评审员的判断。这需要一种评估机制，能够客观地确定报告的问题是否对应于代码中人类审阅者通常会识别的实际问题。To address these limitations, evaluation should focus on whether review tools identify the underlying issues present in a PR that human reviewers would typically raise, rather than relying on indirect proxies for review quality, such as resemblance to human-written comments, location matching, or judgments from LLM-based evaluators. This requires an evaluation mechanism that can objectively determine whether a reported issue corresponds to a real problem in the code that human reviewers would typically identify.

2.1. 自动代码审查工具Automated Code Review Tools

自动代码审查工具可大致分为基于静态分析的方法和基于人工智能的方法。 静态分析工具根据预定义的规则、模式或数据流分析来检测漏洞和代码质量问题。 相比之下，基于人工智能的审查工具通常利用法学硕士根据法学硕士培训期间学习的模式以及通过提示或代理支架提供的上下文知识来检测问题。 当在 GitHub、GitLab 或 BitBucket 上打开拉取请求 (PR) 时，通常会触发这些审核工具。 当触发时，基于人工智能的审查工具会收集必要的上下文，例如 PR 中修改的行、周围的代码上下文以及存储库级别的上下文（例如依赖关系图）。 然后，法学硕士会对收集到的背景进行分析，以识别潜在的问题。 一些基于人工智能的审核工具可能会在将审核呈现给开发人员之前执行额外的后处理，例如误报过滤或严重性排名。 作为输出，大多数评论工具将评论呈现为 PR 中的摘要评论或内嵌评论。 在本文中，我们特别关注基于人工智能的代码审查工具的评估。Automated code review tools can be broadly categorized into static analysis-based approaches and AI-based approaches. Static analysis tools detect vulnerabilities and code quality issues based on pre-defined rules, patterns, or data-flow analysis. In contrast, AI-based review tools typically leverage LLMs to detect issues based on learned patterns during LLM’s training, as well as contextual knowledge provided through prompts or agentic scaffold. These review tools are typically triggered when a Pull Request (PR) is opened on GitHub, GitLab, or BitBucket. When triggered, AI-based review tools collect necessary context, such as the modified lines in the PR, the surrounding code context, and repository-level context such as dependency graphs. This collected context is then analyzed by an LLM to identify potential issues. Some AI-based review tools may perform additional post-processing, such as false positive filtering or severity ranking, before the reviews are presented to developers. As output, most review tools present the reviews as a summary comment or inline comments in the PR. In this paper, we focus specifically on the evaluation of AI-based code review tools.

2.3. 代码审查的评估方法Evaluation Methods for Code Reviews

4.1. 蟹蟹c-CRAB概述Overview

4.2.1. 评论过滤Review Filtering

过滤阶段的目标是仅保留可以转化为高质量测试用例的评审意见，作为基准目标。在原始公关讨论中，并非每个人的评论都反映了候选补丁中具体且可操作的担忧。许多评论本质上是对话式的，例如要求澄清、致谢或赞扬。虽然此类评论可能仍然在现实世界的协作中发挥重要作用，但它们不适合我们的基准，因为它们无法明确映射到可执行的预言机。此外，这些类型的注释通常不会由自动代码审查工具生成。包含它们会在管理流程中引入噪音并降低结果测试的有效性。因此，过滤阶段的目标是识别表达可验证问题的评审意见，其解决方案原则上可以通过执行得到验证。为了以可扩展的方式实现这一目标，我们通过提示法学硕士设计了一个自动过滤分类器。The objective of the filtering stage is to retain only review comments that can be translated into high-quality test cases serving as benchmark targets. In raw PR discussions, not every human comment reflects a concrete and actionable concern in the candidate patch. Many comments are conversational in nature, such as requests for clarification, acknowledgments, or praise. While such comments may still play an important role in real-world collaboration, they are not suitable for our benchmark because they cannot be mapped unambiguously to executable oracles. Furthermore, these types of comments are generally not expected to be produced by automated code review tools. Including them would introduce noise into the curation pipeline and reduce the validity of the resulting tests. Therefore, the goal of the filtering stage is to identify review comments that express verifiable issues whose resolution can, in principle, be validated through execution. To achieve this in a scalable manner, we design an automated filtering classifier by prompting an LLM.

6. 可行的见解Actionable Insights

我们的研究结果为自动化代码审查工具的从业者和开发人员提供了一些可行的见解。Our findings suggest several actionable insights for both practitioners and developers of automated code review tools.

a.自动审核工具应被视为人类审核员的补充而不是替代品。a. Automated review tools should be viewed as complements to human reviewers rather than replacements.在 RQ1 中，尽管经常产生更多的审阅意见，但所有评估的工具的通过率均远低于人工审阅者。 RQ2 中的进一步分析表明，这种差距至少部分是由所提出问题类型的差异来解释的：自动化工具倾向于强调某些类别（例如，稳健性和测试），而没有很好地涵盖人类经常识别的其他类别。总而言之，这些发现表明了未来审核工作流程中分工的可能性。In RQ1, all evaluated tools achieve substantially lower pass rates than human reviewers, despite often producing more review comments. Further analysis in RQ2 suggests that this gap is at least partly explained by differences in the types of issues raised: automated tools tend to emphasize certain categories (e.g., robustness and testing) while does not cover well others that humans frequently identify. Taken together, these findings point to the possibility for division of labor in future review workflows.

b.存储库特定的上下文可能是改进自动审查工具所缺少的要素。b. Repository-specific context is a likely missing ingredient for improving automated review tools.在 RQ2 中，自动化工具很少提出与可维护性、设计和文档相关的问题，这些类别通常依赖于特定于存储库的知识。一个具体的例子可以在 Lightning-AI 项目的人工审查中找到In RQ2, automated tools rarely raise issues related to maintainability, design, and documentation, categories that often depend on knowledge specific to a repository. More broadly, executable tests also suggest a useful future direction for training review systems, since they reward issue identification that leads to verifiable improvements in code.

7. 有效性的威胁Threats to Validity

a.内部有效性。a. Internal Validity.我们的评估管道依赖于编码代理根据审查意见修改补丁。因此，结果不仅可以反映审稿意见的质量，还可以反映代理人的能力。 为了减轻这种混淆因素，我们在包含之前使用人工编写的注释来验证基准实例，并且在验证和评估管道中使用相同的编码代理。 这确保了所有保留的实例都是可解的。Our evaluation pipeline relies on a coding agent to revise patches based on review comments. As a result, the outcomes may reflect not only the quality of the review comments but also the capability of the agent. To mitigate this confounding factor, we validate benchmark instances using human-written comments prior to inclusion, and the same coding agent is used in both the validation and the evaluation pipeline. This ensures that all retained instances are solvable.

b.外部有效性。b. External Validity.我们的基准测试是根据 SWE-CARE 构建的，包括 184 个拉取请求实例，以及跨 56 个存储库的 234 个可验证预言机。虽然这种管理提高了可靠性，但它可能会限制更广泛的软件生态系统的代表性。尽管如此，数据集可以轻松扩展，因为管道可以应用于新的拉取请求实例。Our benchmark is constructed from SWE-CARE and includes 184 pull request instances with 234 verifiable oracles across 56 repositories. While this curation improves reliability, it may limit representativeness with respect to the broader software ecosystem. Nevertheless, the dataset can be easily extended, as the pipeline can be applied to new pull request instances.

c.构造有效性。c. Construct Validity.我们管道中的过滤阶段利用基于 LLM 的分类器，该分类器可能会保留边界注释。为了减轻这种风险，我们在测试生成过程中利用严格的先失败后通过的标准，并使用原始的人类评论来验证是否可以在验证阶段解决每个问题。此外，评论的手动分析涉及人为判断。为了缓解这种情况，两位作者独立进行了标记。The filtering stage in our pipeline leverages an LLM-based classifier, which may retain borderline comments. To mitigate this risk, we leverage a strict fail-then-pass criterion during test generation and verify whether each problem can be solved during the validation phase using the original human comments. Moreover, manual analysis of the reviews involve human judgment. To mitigate this, two authors independently performed labeling.

8. 结论Conclusion

基于人工智能的代码生成的快速发展使得生成代码变得越来越容易和可扩展。另一方面，审查代码的过程仍然是一个瓶颈。已经提出了几种自动代码审查工具，但评估其有效性是一个公开的挑战。The rapid advancement of AI-based code generation has made generating code becomes increasingly easy and scalable. On the other hand, the process of reviewing the code remains a bottleneck. Several automated code review tools have been proposed, but evaluating their effectiveness is an open challenge.
