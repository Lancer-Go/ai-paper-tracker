衡量安全性而不自欺欺人：Measuring Security Without Fooling Ourselves:
为什么对标代理很难Why Benchmarking Agents Is Hard

Sahar Abdelnabi1, Chris Hicks2, Konrad Rieck3, and Ahmad-Reza Sadeghi4
1 ELLIS Institute Tübingen & MPI-IS & Tübingen AI Center, Germany
2 The Alan Turing Institute, London, UK
3 BIFOLD & Technische Universität Berlin, Germany
4 Technische Universität Darmstadt, Germany

摘要Abstract

用于评估安全关键角色的人工智能代理的基准存在严重缺陷。根据最近的经验证据，我们描述了破坏安全评估的三个核心挑战：The benchmarks used to evaluate AI agents in security-critical roles suffer from crucial weaknesses. Building on recent empirical evidence, we characterize three core challenges that undermine security evaluations:基准漏洞benchmark vulnerabilities, 暂时陈旧temporal staleness, 和, and运行时的不确定性runtime uncertainty。然后，我们概述了构建更强大、更值得信赖的评估框架的实用方向。. We then outline practical directions toward building more robust and trustworthy evaluation frameworks.

1 简介Introduction

在安全环境中评估人工智能代理是一项根本性的挑战。我们寻求衡量的能力，即对抗性推理，可能会破坏评估本身。负责发现漏洞的代理也可能会利用基准环境中的弱点，而不是解决预期的任务，从而在测量的性能和模型功能之间造成不匹配。Evaluating AI agents in security settings presents a fundamental challenge. The very capability we seek to measure, adversarial reasoning, can undermine the evaluation itself. An agent tasked with discovering vulnerabilities may also exploit weaknesses in the benchmark environment instead of solving the intended task, creating a mismatch between measured performance and model capability.

应对这一挑战需要转变视角：对人工智能代理进行基准测试不仅是为了衡量效率或任务性能，而且本身也是一个系统安全问题。与传统的基准测试不同，传统的基准测试可能足以假设一个可信的静态评估设置，而使用安全代理进行实验的研究人员必须将基准测试视为可以攻击和操纵的敌对暴露系统。Addressing this challenge requires a shift in perspective: benchmarking AI agents is not only about measuring efficiency or task performance, but is also itself a systems security problem. Unlike traditional benchmarking, where it might be adequate to assume a trusted and static evaluation setup, researchers running experiments with security agents must treat the benchmark as an adversarially exposed system that can be attacked and manipulated.

最近的工作已经产生了一个不断增长的安全基准生态系统。 Cybench 评估代理的专业级夺旗挑战Recent work has produced a growing ecosystem of security benchmarks. Cybench evaluates agents on professional-level capture-the-flag challenges[1], CyberGym 测试现实世界 CVE 中的漏洞重现, CyberGym tests vulnerability reproduction across real-world CVEs[2]，和PentestGPT建立了第一个LLM驱动的渗透测试的系统评估, and PentestGPT established the first systematic evaluation of LLM-driven penetration testing[3]。 尽管取得了这些进展，但这些基准测试都不是为了承受它们旨在衡量的对抗能力而设计的。因此，经验证据已经表明，智能体可以利用基准的弱点来获得近乎完美的分数，而无需解决预期的任务. Despite this progress, none of these benchmarks are designed to withstand the adversarial capabilities they aim to measure. Consequently, empirical evidence already shows that agents can exploit benchmark weaknesses to achieve near-perfect scores without solving the intended tasks[10].

为了使这一挑战具体化，我们引入一个简化的运行示例。根据虚构的漏洞发现基准评估代理To make this challenge concrete, we introduce a simplified running example. An agent is evaluated on the fictional vulnerability discovery benchmark破碎的长凳BrokenBench，它可以访问在隔离容器内运行的程序。代理可以检查源代码、执行二进制文件并使用分析工具来识别漏洞。 BrokenBench的评估环境不仅包括这些程序，还包括周围的基础设施，例如容器运行时、配置文件、编排逻辑和评分机制。, where it is given access to programs running inside isolated containers. The agent can inspect source code, execute binaries, and use analysis tools to identify vulnerabilities. The evaluation environment of BrokenBench includes not only these programs, but also the surrounding infrastructure, such as the container runtime, configuration files, orchestration logic, and scoring mechanisms for grading.

至关重要的是，此环境是代理攻击面的一部分。因此，代理可以利用 BrokenBench 的基础设施，而不是分析预期的目标程序，例如，通过访问隐藏的解决方案数据、操纵评分过程或逃离隔离边界。在这种情况下，智能体在没有解决预期任务的情况下获得高分。这说明了以下核心张力：在对抗性环境中，利用基准比解决基准更容易。Crucially, this environment is part of the attack surface for the agent. Rather than analyzing the intended target programs, the agent may thus exploit the infrastructure of BrokenBench, for example, by accessing hidden solution data, manipulating the scoring process, or escaping isolation boundaries. In such cases, the agent achieves high scores without solving the intended task. This illustrates the following core tension: in adversarial settings, it can be easier to exploit the benchmark than to solve it.

在此背景下，本文强调了当前安全基准的三个关键局限性。首先，Against this backdrop, this article highlights three critical limitations of current security benchmarks. First,基准漏洞benchmark vulnerabilities允许代理操纵或逃离评估环境，从而威胁结果的完整性。第二，allow agents to manipulate or escape evaluation environments, threatening result integrity. Second,暂时陈旧temporal staleness意味着静态基准在不断变化的威胁环境中很快就会过时。三、means that static benchmarks quickly become outdated in an evolving threat landscape. Third,运行时的不确定性runtime uncertainty由随机行为、代码生成和外部依赖性引起的风险会带来现有基准测试中很少捕获的风险。, arising from stochastic behavior, code generation, and external dependencies, introduces risks that are rarely captured in existing benchmarks.

这些挑战表明，人工智能代理的安全基准测试不仅是一个评估问题，而且本身就是一个系统安全问题。稳健的评估需要重新考虑基准，将其视为动态的、具有对抗性的稳健且持续验证的环境，以反映现代网络安全的现实。These challenges reveal that security benchmarking for AI agents is not only an evaluation problem but a systems security problem in itself. Robust assessment requires rethinking benchmarks as dynamic, adversarially robust, and continuously validated environments that reflect the realities of modern cybersecurity.

2 基准漏洞Benchmark Vulnerabilities

如果代理旨在解决任务，例如查找软件中的复杂漏洞，它也可以在基准环境本身中找到捷径，从而产生中心悖论。也就是说，它可能是If an agent is designed to solve a task, such as finding complex vulnerabilities in software, it can also find shortcuts in the benchmark environment itself, creating a central paradox. That is, it may be更容易easier打破环境胜过解决预定任务。to break the environment than to solve the intended task.

例如，在 BrowseComp 基准测试中，代理需要在线查找难以找到的信息，处理了大约 3000 万个令牌的代理开始意识到他们正在接受测试并在线搜索基准规范本身For example, in the BrowseComp benchmark which tasks agents with locating hard-to-find information online, agents that had processed approximately 30 million tokens began to recognize they were being tested and searched online for the benchmark specification itself[11]。系统审计发现，代理可以通过配置文件注入代码来重写测试结果，检查 Git 日志以逆向工程基准构建，并在包括 SWE-bench 和 Terminal-Bench 在内的基准上实现 100% 的利用率. A systematic audit found that agents could inject code via configuration files to rewrite test outcomes, inspect Git logs to reverse-engineer benchmark construction, and achieve 100% exploitation rates on benchmarks including SWE-bench and Terminal-Bench[10].

这一意想不到的结果表明了安全基准测试尚未认识到的一个要求：评估环境必须比正在测试的目标更安全。 例如，如果目标是经过严格审查的加密库，并且基准测试在普通 Linux 系统上运行，则代理可能会发现溜过容器比挖掘库中的细微缺陷更容易。This unexpected outcome points to a requirement that security benchmarking has yet to recognize: the evaluation environment must be more secure than the target being tested. For example, if the target is a well-vetted cryptographic library and the benchmark runs on an average Linux system, the agent may find it easier to slip past the container than to dig out a subtle flaw in the library.

2.1 内部和外部保护Inner and Outer Protections

在这个悖论的背景下，我们发现区分In the context of this paradox we find it useful to distinguish between内在的保护inner protections（对代理行为的基于对齐的约束）和(alignment-based constraints on the agent’s behavior) and外部保护outer protections（评估环境的架构限制）。当前的基准测试几乎完全依赖于内部保护；相信智能体将尝试解决预期任务而不是利用其周围环境。对于安全基准来说，这是错误的假设，在安全基准中，对抗性思维是被衡量的能力。(architectural constraints on the evaluation environment). Current benchmarks rely almost entirely on inner protections; trusting that the agent will attempt to solve the intended task rather than exploit its surroundings. This is the wrong assumption for security benchmarks where adversarial thinking is the capability being measured.

稳健的评估需要外部保护：硬件强制隔离、代理和答案的单独特权域以及任务完成的验证。然而，即使设计良好的沙箱也并非无懈可击。容器逃逸是一种已知的漏洞类别，并且代理生成的漏洞利用的复杂性正在增加。这意味着外部保护必须针对其所包含的介质进行持续监控、强化和测试。Robust evaluation requires outer protections: hardware-enforced isolation, separate privilege domains for the agent and the answers, and verification of task completion. However, even well-designed sandboxes are not invulnerable. Container escapes are a known vulnerability class, and the sophistication of agent-generated exploits is increasing. The implication is that outer protections must be continuously monitored, hardened and tested against the agents they are meant to contain.

2.2 金丝雀Canaries

由于基准测试本身无法得到完全保护，我们借用了系统安全中一个熟悉的想法：Since the benchmark itself cannot be fully protected, we borrow a familiar idea from systems security:金丝雀代币canary tokens，隐藏在环境中的随机值，诚实的求解器没有理由观察。如果代理在评估过程中复制了这些金丝雀之一，则它已经到达了基础设施中原本不应该访问的部分，并且其分数不得可信。 这与蜜罐的经典概念相结合：检测某些内容何时未按计划运行。 金丝雀已经用于检测模型是否在特定数据集上进行了训练：预先将独特的金丝雀注入数据中，然后检查模型是否重现它们, hidden and randomized values embedded in the environment that an honest solver has no reason to observe. If an agent reproduces one of these canaries during evaluation, it has reached parts of the infrastructure that were never meant to be accessible and its score must not be trusted. This bridges to the classical concept of honeypots: detecting when something is not running as planned. Canaries are already used for detecting whether a model was trained on a particular dataset: unique canaries are injected into the data beforehand and the model is later checked for whether it reproduces them[13]。我们认为这应该被采纳为常见做法，不仅适用于训练数据，也适用于智能体在推理时可能读取的所有可能导致基准作弊的来源。. We believe this should be adopted as common practice, not just for training data, but for all sources that the agent may read at inference time that may enable benchmark cheating.

2.3 故意作弊Deliberate Cheating

最近的审计A recent audit[10]据透露，基准测试的利用并不限于意外的捷径。代理可以被设计为revealed that benchmark exploitation is not limited to accidental shortcutting. Agents can be designed to故意deliberately作弊。当给出鼓励利用评估环境的指令时，代理系统地识别并利用测试工具、配置文件和评分机制中的漏洞。这就提出了一个实际问题：我们是否可以使用负责故意作弊的代理来揭示环境中可利用的限制和捷径？cheat. When given instructions encouraging exploitation of the evaluation environment, agents systematically identified and leveraged vulnerabilities in test harnesses, configuration files, and scoring mechanisms. This raises a practical question: can we use agents tasked with deliberate cheating to reveal limitations and shortcuts in the environment that can be exploited?

特别是，计算成本可以被视为安全性的粗略代理。 通过设定预算，例如，“如果在 10,000 美元之后，代理没有损害环境，我们认为它有效地安全 ”，技术强化可以与经济激励相辅相成。这不是保证，但它提高了标准：如果任务的完成时间低于预算，并且代理不能在预算内作弊，那么基准测试结果更有可能与能力相对应。In particular, computational cost can be treated as a coarse proxy for security. By setting a budget, e.g., “if after $10,000 the agent has not compromised the environment we consider it effectively secure ”, technical hardening can be complemented with economic incentives. This is not a guarantee, but it raises the bar: if tasks are completed for less than the budget, and agents cannot cheat within the budget, then benchmark results are more likely to correspond to capability.

3 时间陈旧性Temporal Staleness

昨天安全的东西今天并不安全，威胁模型会随着时间的推移而变化。漏洞不断被发现和修补，新的攻击面不断出现，防御措施不断发展。然而，不断增长的安全基准和评估框架生态系统使用固定数据集What was secure yesterday is not secure today and threat models change over time. Vulnerabilities are discovered and patched continuously, new attack surfaces emerge, and defensive measures evolve. Yet a growing ecosystem of security benchmarks and evaluation frameworks use fixed datasets[1, 2, 3, 4].

固定基准的后果在安全领域是众所周知的。 20 世纪 90 年代初的入侵检测数据集尽管在发布后两年内就过时了，但仍然广泛使用了十多年The consequences of stationary benchmarks are well understood in security. Intrusion detection datasets from the early 1990s remained in widespread use for over a decade despite becoming obsolete within two years of release[5]。我们冒着重复这种模式的风险：CyberGym 的 1,507 个漏洞和 Cybench 的 40 个 CTF 挑战 随着底层软件和代理的修补、新的漏洞类别的出现以及模型在基准数据上的训练，所有这些都会老化。. We risk repeating this pattern: CyberGym’s 1,507 vulnerabilities and Cybench’s 40 CTF challenges will all age as the underlying software and agents are patched, new vulnerability classes emerge, and models are trained on the benchmark data.

陈旧性导致的另一个问题是Another problem resulting from staleness is长凳最大兴benchmaxxing：在基准格式和评估环境上微调模型: fine-tuning models on benchmark formats and evaluation environments[14]。我们还假设，在有关基准测试工作原理的元知识（例如多项选择安全问题的格式或 CTF 挑战的结构）上训练的模型，即使不接触特定的基准测试实例，也可能会表现出更高的性能，无论其真实功能如何。这可能会挑战避免直接进行基准训练就足够的假设。基准最大化的风险随着基准的使用年限和围绕基准的公共材料的数量而增加。. We also hypothesize that models trained on meta-knowledge about how benchmarks work, such as the format of multiple-choice security questions or the structure of CTF challenges, may show improved performance even without exposure to specific benchmark instances, regardless of their true capabilities. This could challenge the assumption that avoiding direct training on benchmarks is sufficient. The risk of benchmaxxing grows with the age of a benchmark and the volume of public material surrounding it.

3.1 动态基准Dynamic Benchmarks

我们认为，安全基准应该像消费者价格指数一样发挥作用：随着底层安全形势的变化而更新的代表性任务篮子。正如价格指数反映了人们购买的实际商品组合如何随时间变化一样，安全基准也应反映企业主机、关键服务器和代理本身如何随时间进行修补和升级。We argue that security benchmarks should function like a consumer price index: a representative basket of tasks that updates as the underlying security landscape changes. Just as a price index reflects how the actual mix of goods people buy evolves over time, a security benchmark should reflect how enterprise hosts, critical servers, and agents themselves are patched and upgraded over time.

这需要从静态数据集转变为This requires a shift from static datasets to动态dynamic基准环境。一种方法借鉴了模糊测试模型，该模型每隔几个月就会进行新一轮的挑战，从而使排名随着目标和竞争对手的发展而变化benchmark environments. One approach draws on the model of fuzzing competitions, which run new rounds every few months with fresh challenges, allowing rankings to change as both the targets and the competitors evolve[6]。另一种方法是构建基准系统，定期从漏洞数据库（例如 CVE 目录）生成新任务，从而生成经过校准难度的新任务，而无需每个实例的人工创作。. Another is to build benchmark systems that generate novel tasks from vulnerability databases (such as the CVE catalog) at regular intervals, producing fresh tasks of calibrated difficulty without human authorship of each instance.

3.2 现场评估Live Evaluation

更激进的方法是A more radical approach is现场评估live evaluation：针对当前部署的真实系统而不是冻结快照对代理进行基准测试。事实上，错误赏金平台已经以这种方式运行，针对漏洞情况每天都在变化的生产环境进行测试。调整此模型以进行代理评估意味着不断刷新目标环境，包括当前补丁级别、真实配置和新披露的漏洞。: benchmarking agents against real, currently-deployed systems rather than frozen snapshots. In fact, bug bounty platforms already operate this way, testing against production environments where the vulnerability landscape shifts daily. Adapting this model for agent evaluation would mean continuously refreshing target environments with current patch levels, real configurations, and newly disclosed vulnerabilities.

挑战在于安全性和可重复性。实时评估牺牲了使基准测试相对安全（即避免对生产系统造成损害）并且跨时间和代理具有可比性的受控条件。混合方法可能更实用：维护一组稳定的安全任务用于纵向比较，同时补充一组从最近的 CVE 披露、当前的 CTF 竞赛和 LLM 漏洞中提取的实时任务。这反映了 NIST 国家漏洞数据库如何提供持续更新的流，原则上可以提供实时基准。The challenge is safety and reproducibility. Live evaluation sacrifices the controlled conditions that make benchmarks both relatively safe (i.e., to avoid doing harm to production systems) and comparable across time and agents. A hybrid approach may be more practical: maintaining a set of stable security tasks for longitudinal comparison while supplementing with a live set of tasks drawn from recent CVE disclosures, current CTF competitions, and LLM vulnerabilities. This mirrors how the NIST National Vulnerability Database provides a continuously updated stream that could, in principle, feed live benchmarks.

3.3 生成基准Generative Benchmarks

代理还可以用于生成实时基准测试环境，而不是依赖人类专家来管理基准（这是一个昂贵、缓慢且不可扩展的过程）；不断地向代理分配发现和修补最新代码库中的漏洞的任务，然后更新其他代理的基准任务。这将创造一种共同进化的动态，随着代理在发现漏洞方面的改进，它们生成的基准变得更加困难，反之亦然。Agents could also be used to generate a live benchmarking environment that, rather than relying on human experts to curate benchmarks (a process that is expensive, slow, and does not scale); continuously tasks agents with discovering and patching vulnerabilities in the latest codebases, and then updating the benchmark tasks for other agents. This would create a co-evolutionary dynamic where as agents improve at finding vulnerabilities, the benchmarks they generate become harder, and vice versa.

这个方向的早期工作很有希望。自动漏洞注入真实代码库已用于为静态分析工具创建训练数据Early work in this direction is promising. Automated vulnerability injection into real codebases has been used to create training data for static analysis tools[7]，并且类似的技术可以产生校准难度的评估任务。风险在于循环：如果生成基准的代理与正在测试的代理存在偏见，则最终的任务可能会越来越偏向于特定训练数据引发的狭窄漏洞集。尽管在完全生成基准中不能完全排除偏差，但模型、训练数据、工具配置和采样温度之间的多样性对于限制这种影响至关重要。, and similar techniques could produce evaluation tasks of calibrated difficulty. The risk is circularity: if the agent generating the benchmark shares biases with the agent being tested, the resulting tasks may become increasingly biased towards the narrow set of vulnerabilities that particular training data induces. Although biases cannot be completely ruled out in a fully generative benchmark, diversity across models, training data, tool configurations, and sampling temperatures is essential to limit this effect.

4 运行时的不确定性Runtime Uncertainty

最后，人工智能代理的行为受到运行时不确定性的多种来源的影响，每种来源都带来当前基准测试在其设计中通常无法捕获的安全隐患。Finally, the actions of AI agents are shaped by multiple sources of runtime uncertainty, each carrying security implications that current benchmarks often fail to capture in their design.

4.1 随机行为Stochastic Behavior

基于 LLM 构建的代理本质上是随机的。在每次迭代中，代理可能会利用各种各样的操作、工具和信息源，从而产生级联效应，其中早期的分歧会复合成下游截然不同的结果。因此，相同的智能体在执行相同的任务时可能会得出截然不同的结论。这种非确定性具有直接的安全影响：在一次运行中产生安全解决方案的代理可能在下一次运行中产生易受攻击的解决方案。当前的基准测试通常报告单次运行或平均性能，从而掩盖了对安全评估最重要的差异。 评估随机行为需要在同一任务上多次运行代理并报告分布统计数据：不仅是平均准确性，还有最坏情况的性能、方差和安全关键故障的频率Agents built on LLMs are inherently stochastic. At each iteration, an agent may draw on a large variety of actions, tools, and information sources, creating a cascade effect in which early divergence compounds into substantially different outcomes downstream. Consequently, the same agent given the same task can arrive at markedly different conclusions. This non-determinism has direct security implications: an agent that produces a secure solution in one run may produce a vulnerable one in the next. Current benchmarks typically report single-run or mean performance, obscuring the variance that matters most for security evaluation. Evaluating stochastic behavior requires running agents multiple times on the same task and reporting distributional statistics: not just mean accuracy but worst-case performance, variance, and the frequency of security-critical failures[12].

4.2 代码生成Code Generation

运行时不确定性的另一个来源是代码生成。在安全实验期间，代理可能会生成大量代码来探测环境、创建测试工具、监视执行和利用漏洞。这种代码生成支持代理安全分析，但也引入了新的故障点。由于 LLM 生成的代码通常包含很大一部分安全缺陷，因此代理生成的代码成为评估中最需要考虑的关键变量。Another source of runtime uncertainty is code generation. During a security experiment, an agent may produce a considerable amount of code to probe the environment, create test harnesses, monitor execution, and craft exploits. This code generation underpins agentic security analysis, but it also introduces new points of failure. Since LLM-generated code contains a significant share of security flaws in general, the code an agent produces becomes a crucial variable in the evaluation that most be considered.

对基准有效性最直接的威胁是自我干扰。代理可能会发现它自己引入的漏洞，或者错过它通过自己的操作意外修补的缺陷，从而无法将结果归因于目标系统而不是代理自己的代码。除此之外，基准环境的安全相关属性（例如编译器功能和内存保护机制）与代理生成的代码进行交互，从而进一步混淆结果。当前的基准测试将代理生成的代码视为透明工具，但更好地将其理解为需要控制以获得可靠结果的噪声源。The most direct threat to benchmark validity here is self-interference. An agent may uncover vulnerabilities it introduced itself, or miss flaws it accidentally patched through its own actions, making it impossible to attribute results to the target system rather than the agent’s own code. Beyond this, security-relevant properties of the benchmark environment, such as compiler features and memory protection mechanisms, interact with agent-generated code in ways that further confound results. Current benchmarks treat agent-generated code as a transparent instrument, but it is better understood as a source of noise that needs to be controlled for to obtain reliable results.

4.3 外部依赖External Dependencies

有效的代理在运行时依赖外部工具、API 和数据源。渗透测试代理可以查询漏洞数据库、调用网络扫描器或从存储库检索漏洞利用代码。每个外部依赖项都会引入一个潜在的不确定点：外部信息可能会干扰分析过程或提供解决基准任务的捷径，从而导致对代理能力的高估。 这里最严重的威胁是通过外部来源泄露信息。基准测试解决方案的某些部分可以通过公共漏洞数据库、存储库或在线文章直接访问，无论是作为明确的泄漏还是作为微妙的提示，引导代理找到正确的答案，而不直接透露它。在这两种情况下，当智能体主要是检索而不是推理时，它就显得有能力。Effective agents rely on external tools, APIs, and data sources at runtime. A penetration testing agent may query a vulnerability database, invoke a network scanner, or retrieve exploit code from a repository. Each external dependency introduces a potential point of uncertainty: external information may interfere with the analysis process or provide shortcuts to solving the benchmark task, leading to an overestimation of agent capabilities. The most critical threat here is information leakage through external sources. Parts of a benchmark solution may be directly accessible via public vulnerability databases, repositories, or online write-ups, either as an explicit leak or as subtle hints that steer the agent toward the correct answer without revealing it outright. In both cases, the agent appears capable when it is largely retrieving rather than reasoning.

除了泄漏之外，外部来源还可能返回不正确或敌对的数据，使代理面临很少经过测试的操纵。当前的安全基准不控制外部信息访问，因此无法完全区分代理能力和意外信息获取。Beyond leakage, external sources may return incorrect or adversarially crafted data, exposing agents to manipulation they are rarely tested against. Current security benchmarks do not control for external information access, making it impossible to completely distinguish agent capability from unintended information gain.

4.4 基准自省Benchmark Introspection

这些运行时不确定性的来源激发了实用的验证技术：These sources of runtime uncertainty motivate a practical validation technique:基准自省benchmark introspection。基准测试需要通过内省来监督和验证评估环境，而不是仅仅关注任务的结果。在最简单的情况下，这相当于分析代理在任务期间的推理痕迹。在更高级的形式中，内省可以通过在代理环境之外运行的适当技术从外部监视和记录代码生成、工具交互和文件系统访问。同样，外部信息可以通过代理的处理进行污染和跟踪，从而清楚地了解信息是如何收集和处理的。. Instead of focusing only on the outcome of a task, the benchmark needs to supervise and validate the evaluation environment through introspection. In the simplest case, this amounts to analyzing the reasoning traces of an agent during the task. In a more advanced form, introspection can externally monitor and document code generation, tool interactions, and filesystem access through appropriate techniques running outside the agent’s environment. Similarly, external information can be tainted and tracked through the processing of the agent, providing a clear picture of how information was collected and processed.

对任务解决过程的详细审核虽然要求很高，但可以帮助发现和减轻不确定性来源。虽然内省不能完全消除问题，但它提供了一种检测和控制破坏基准有效性的运行时因素的方法。This detailed auditing of the task-solving process, though demanding, can help uncover and mitigate sources of uncertainty. While introspection cannot eliminate the problem entirely, it provides a means for detecting and controlling for the runtime factors that undermine benchmark validity.

5 讨论Discussion

从更广泛的角度来看，基准测试漏洞、时间过时性和运行时不确定性并不是安全基准测试所独有的，但它们在那里尤为严重。由此，我们可以得出几个结论：From a broader perspective, benchmark vulnerabilities, temporal staleness, and runtime uncertainty are not unique to security benchmarks, but they are uniquely acute there. From this, we can draw several conclusions:

(a) 对抗性推理是衡量的能力。(a) Adversarial reasoning is the capability being measured.

在非安全基准测试中，玩弄评估的代理会表现出不良行为。在安全基准测试中，具有相同的能力；发现并利用其环境中的漏洞正是我们想要衡量的。在这个领域中，作弊和能力是同一潜在能力的表达。必须相应地设计安全基准。In non-security benchmarks, an agent that games the evaluation is exhibiting undesirable behavior. In security benchmarks, the same capability; finding and exploiting vulnerabilities in its environment, is precisely what we are trying to measure. Cheating and competence are, in this domain, expressions of the same underlying capability. Security benchmarks must be designed accordingly.

(b) 计算机安全本质上是不稳定的。(b) Computer security is non-stationary by nature.

大多数基准衰减缓慢；安全基准的衰减速度与漏洞的披露和修补速度一样快。基于去年 CVE 的基准衡量对去年问题的熟悉程度。如果非安全评估可能依赖于既定实践和静态数据，则需要重新考虑安全基准，而不仅仅是刷新。Most benchmarks decay slowly; security benchmarks decay as fast as vulnerabilities are disclosed and patched. A benchmark built on last year’s CVEs measures familiarity with last year’s problems. Where non-security evaluations may rely on established practices and static data, security benchmarks need to be rethought, not merely refreshed.

(c) 代理人既是主体又是工具。(c) The agent is both the subject and the tool.

代理生成代码、与环境交互并做出决策——所有这些都具有复合而不是取消的安全隐患。检查代理是否发现正确漏洞的仅输出评估会错过它是否在此过程中引入了新漏洞。The agent generates code, interacts with environments, and makes decisions—all of which have security implications that compound rather than cancel. An output-only evaluation that checks whether the agent found the right vulnerability misses whether it introduced new ones along the way.

对于从业者来说，这些要点转化为具体的评估挑战，而现有的基准还没有完全解决这些挑战：For the practitioner, these points translate into concrete evaluation challenges that no existing benchmark fully addresses:

    代理可以攻击基准吗？Can the agent attack the benchmark?代理可以利用基础设施中的弱点吗？Can the agent exploit weaknesses in the infrastructure?

  • •

    代理能解决今天的问题吗？Is the agent solving today’s problems?基准测试的挑战是否源于仍然相关的漏洞和技术？Are the benchmark’s challenges grounded in vulnerabilities and techniques that remain relevant?

  • •

我们还注意到进攻和防守评估之间的差距。当前的基准测试几乎完全专注于攻击能力（发现和利用漏洞）或代理安全（抵抗即时注入和操纵）。没有现有的基准可以同时评估代理是否同时We also note a gap between offensive and defensive evaluation. Current benchmarks focus almost exclusively on offensive capabilities (finding and exploiting vulnerabilities) or on agent safety (resistance to prompt injection and manipulation). No existing benchmark simultaneously evaluates whether an agent is both有效的effective在安全任务和at security tasks and安全safe部署，但这正是从业者需要了解的。to deploy, yet this is precisely what practitioners need to know.

6 结论Conclusion

用于安全任务的人工智能代理的快速发展已经超过了足以应对挑战的评估方法的发展。我们已经确定了当前基准测试方法中的三类基本漏洞，并提出了不同的对策，其中基准内省是迈向更值得信赖的评估的整体第一步。The rapid development of AI agents for security tasks has outpaced the development of evaluation methodologies adequate to the challenge. We have identified three fundamental classes of vulnerability in current benchmarking approaches and proposed different countermeasures, with benchmark introspection as a holistic first step toward more trustworthy evaluation.

许多事情仍然开放。随着威胁形势的发展而发展的生成基准、针对代理生成的工件的运行时代码安全评估以及统一的攻防评估框架都代表了未来工作的重要方向。我们希望确定的是，安全社区应该以与任何其他提出安全声明的系统相同的对抗性怀疑态度来对待代理基准，因为基准本身尚不安全。Much remains open. Generative benchmarks that evolve with the threat landscape, runtime code security evaluation for agent-generated artifacts, and unified offensive-defensive evaluation frameworks all represent important directions for future work. What we hope to have established is that the security community should approach agent benchmarks with the same adversarial skepticism it brings to any other system making security claims—because the benchmarks themselves are not yet secure.
