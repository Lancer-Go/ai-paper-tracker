摘要Abstract

当前的计算机使用基准主要关注虚拟化系统中的软件操作任务，而科学仪器场景需要对复杂接口的协调控制以及反馈驱动的参数调整。 然而，由于成本高、安全风险、可及性有限以及难以确保可重复评估，直接在物理高精度仪器上评估试剂是不切实际的。 这就激发了对模拟但现实的测试台的需求，该测试台可以保留科学仪器的操作挑战，同时实现可扩展和安全的基准测试。 为此，我们介绍Current computer-use benchmarks primarily focus on software operation tasks in virtualized systems, whereas scientific instrumentation scenarios require coordinated control over complex interfaces, and feedback-driven parameter adjustment. However, directly evaluating agents on physical high-precision instruments is impractical due to high cost, safety risks, limited accessibility, and difficulty in ensuring reproducible evaluation. This motivates the need for a simulated yet realistic testbed that preserves the operational challenges of scientific instruments while enabling scalable and safe benchmarking. To this end, we introduce实验室操作系统台LabOSBench，这是基于一套基于网络的科学仪器模拟器构建的多模式 GUI 代理的具有挑战性的基准。 LabOSBench 直接通过浏览器进行操作，避免了占用大量资源的操作系统虚拟化，同时支持灵活的任务配置和基于执行的评估。 具体来说，LabOSBench 在八个仪器模拟器上构建了 96 个子任务，涵盖从样品加载、对齐、参数调整、数据采集到结果检查的工作流程。 我们在子任务和端到端级别评估通用视觉语言模型、专用 GUI 代理模型和高级代理框架。 我们的实验表明，虽然现有代理可以完成许多结构化 GUI 子任务，但它们仍然难以应对反馈驱动的操作和长期工作流程执行。 总体而言，LabOSBench 提供了一个可重复的、低成本的测试平台，用于推动计算机使用代理实现科学仪器控制。, a challenging benchmark for multimodal GUI agents built on a suite of web-based scientific-instrument simulators. Operating directly via a browser, LabOSBench avoids resource-heavy OS virtualization while supporting flexible task configuration and execution-based evaluation. Specifically, LabOSBench constructs 96 subtasks across eight instrument simulators, covering workflows from sample loading, alignment, parameter tuning, and data acquisition to result inspection. We evaluate general-purpose vision-language models, specialized GUI agent models, and advanced agentic frameworks at both subtask and end-to-end levels. Our experiments reveal that while existing agents can complete many structured GUI subtasks, they still struggle with feedback-driven operations and long-horizon workflow execution. Overall, LabOSBench provides a reproducible, low-cost testbed for advancing computer-using agents toward scientific-instrument control.

我们以两种互补的模式评估代理。在全集设置中，代理从初始模拟器状态开始，并且必须在预定义的步骤预算内完成整个工作流程。此设置衡量长期任务完成情况，并捕获由早期错误、错过的状态转换或不正确的参数设置引起的复合故障。We evaluate agents in two complementary modes. In the full-episode setting, the agent starts from the initial simulator state and must complete the entire workflow within a pre-defined step budget. This setting measures long-horizon task completion and captures compounding failures caused by early mistakes, missed state transitions, or incorrect parameter settings.

在子任务级别设置中，模拟器直接初始化为目标子任务之前的规范状态，并且仅在该单独的子任务上评估代理。 此模式隔离本地功能，例如定位特定于域的小部件、选择菜单项、拖动参数滑块或识别操作完成。 对于支持编程状态初始化的模拟器（例如 XRD），我们实现在浏览器窗口上公开的快进功能，例如，In the subtask-level setting, the simulator is initialized directly to the canonical state immediately preceding a target subtask, and the agent is evaluated solely on that individual subtask. This mode isolates local capabilities such as locating a domain-specific widget, selecting a menu item, dragging a parameter slider, or recognizing operation completion. Such fast-forwarding is utilized exclusively for diagnostic subtask evaluation and is disabled during full-episode evaluation.

这两个设置共同区分本地 GUI 接地故障和长期工作流程故障。 在子任务上成功但在整个事件中失败的代理可能会受到内存、顺序排序或错误恢复的限制，而单个子任务的失败则表明特定领域的科学控制基础薄弱。Together, the two settings distinguish local GUI grounding failures from long-horizon workflow failures. An agent that succeeds on subtasks but fails in full episodes may suffer from limitations in memory, sequential ordering, or error recovery, whereas failure on individual subtasks indicates weak grounding of domain-specific scientific controls.

5 结论Conclusion

我们推出了 LabOSBench，这是一个轻量级可执行基准测试，用于基于 Web 模拟器构建的科学仪器 GUI 控制。通过避免完全操作系统虚拟化，同时保留密集的界面、程序依赖性、连续参数调整和反馈驱动的视觉调整，LabOSBench 提供了一个实用的测试平台，用于评估科学工作流程中的多模式 GUI 代理。我们的评估表明，当前的智能体距离可靠的科学仪器操作还很远：强大的多模态模型可以解决许多离散的子任务，智能体框架可以提高鲁棒性，但在科学状态解释、精确空间基础、闭环调整和长视野工作流程方面仍然存在失败。 SEM 焦点分析和端到端研究进一步证明，成功的智能体不仅必须完成 GUI 操作，还要保持有效的中间科学状态并避免错误积累。总体而言，LabOSBench 强调科学仪器控制是一个具有挑战性且尚未充分探索的环境，它连接计算机使用代理评估We presented LabOSBench, a lightweight executable benchmark for scientific-instrument GUI control built on web-based simulators. By avoiding full OS virtualization while preserving dense interfaces, procedural dependencies, continuous parameter tuning, and feedback-driven visual adjustment, LabOSBench provides a practical testbed for evaluating multimodal GUI agents in scientific workflows. Our evaluation shows that current agents remain far from reliable scientific-instrument operation: strong multimodal models can solve many discrete subtasks, and agentic frameworks can improve robustness, but failures persist in scientific-state interpretation, precise spatial grounding, closed-loop adjustment, and long-horizon workflows. The SEM focus analysis and end-to-end study further demonstrate that successful agents must not only complete GUI actions, but also maintain valid intermediate scientific states and avoid error accumulation. Overall, LabOSBench highlights scientific-instrument control as a challenging and underexplored setting that connects computer-use agent evaluation(Xie et al., 2024; Zhou et al., 2024; Qin et al., 2025)拥有自主实验室系统with autonomous laboratory systems(Tom et al., 2024; Szymanski et al., 2023; Boiko et al., 2023)，我们希望它能鼓励未来在具有准确基础、状态感知规划和科学反馈解释的领域感知 GUI 代理方面的工作。, and we hope it encourages future work on domain-aware GUI agents with accurate grounding, state-aware planning, and scientific feedback interpretation.

局限性Limitations

尽管 LabOSBench 为科学仪器 GUI 控制提供了一个轻量级且可执行的测试平台，但它仍然存在一些局限性。首先，它是基于基于网络的模拟器而不是物理仪器构建的，因此它无法完全捕获硬件延迟、校准不确定性、安全约束或真实的实验室故障模式。其次，当前的基准涵盖了一组选定的仪器和工作流程，包括显微镜、光谱学、衍射和断层扫描，但尚未包括更广泛的实验室场景，例如湿实验室协议、机器人操作、化学合成或多仪器实验规划。最后，评估主要依赖于屏幕截图和记录的模拟器状态，而一些科学决策可能需要更丰富的观察、领域知识或多模态传感器信号超出当前环境。Although LabOSBench provides a lightweight and executable testbed for scientific-instrument GUI control, it still has several limitations. First, it is built on web-based simulators rather than physical instruments, so it cannot fully capture hardware latency, calibration uncertainty, safety constraints, or real laboratory failure modes. Second, the current benchmark covers a selected set of instruments and workflows, including microscopy, spectroscopy, diffraction, and tomography, but does not yet include broader laboratory scenarios such as wet-lab protocols, robotic manipulation, chemical synthesis, or multi-instrument experimental planning. Finally, the evaluation mainly relies on screenshots and logged simulator states, while some scientific decisions may require richer observations, domain knowledge, or multimodal sensor signals beyond the current environment.

LabOSBench 旨在评估模拟科学仪器环境中的代理，并且不提供对真实实验室硬件的直接控制。 然而，如果部署在物理设备上，科学仪器自动化可能会涉及安全关键操作。 未来的系统在连接到真实仪器之前应包括人工监督、权限控制、操作记录和安全联锁。 该基准旨在支持 GUI 代理的可重复研究，不应被解释为在没有适当安全验证的情况下在物理实验室设备上部署自主代理的建议。LabOSBench is designed for evaluating agents in simulated scientific-instrument environments and does not provide direct control over real laboratory hardware. Nevertheless, scientific-instrument automation may involve safety-critical operations if deployed on physical devices. Future systems should include human supervision, permission control, operation logging, and safety interlocks before being connected to real instruments. The benchmark is intended to support reproducible research on GUI agents and should not be interpreted as a recommendation to deploy autonomous agents on physical laboratory equipment without appropriate safety validation.

B.1 观察与行动空间Observation and Action Space

在每个交互步骤中，代理都会收到自然语言任务指令和模拟器界面的当前屏幕截图。 然后代理输出一个可执行的 GUI 操作。 我们在所有模拟器上使用统一的操作界面，以便相同的评估运行程序可以应用于不同的科学仪器工作流程。At each interaction step, the agent receives a natural-language task instruction and the current screenshot of the simulator interface. The agent then outputs one executable GUI action. We use a unified action interface across all simulators so that the same evaluation runner can be applied to different scientific-instrument workflows.

操作空间包括单击、双击、拖动、键入、选择下拉选项、按键、滚动和等待模拟器状态转换。 单击和双击操作用于按钮、面板和视觉目标区域；拖动动作支持滑块、舞台移动和图案放置；键入和选择操作处理数字输入和菜单；等待操作允许仪器动画、扫描、重建或状态转换完成。The action space includes clicking, double-clicking, dragging, typing, selecting dropdown options, pressing keys, scrolling, and waiting for simulator state transitions. Click and double-click actions are used for buttons, panels, and visual target regions; drag actions support sliders, stage movement, and pattern placement; type and select actions handle numeric inputs and menus; wait actions allow instrument animations, scans, reconstructions, or state transitions to complete.

对于基于坐标的操作，运行程序将代理生成的坐标映射到当前浏览器视口。 当操作针对标准 HTML 元素时，运行程序会尽可能使用 DOM 级事件调度。 对于类似画布或 JavaScript 渲染的控件，它会回退到鼠标事件。 这种混合执行策略使 LabOSBench 能够支持传统的 Web 小部件和模拟器特定的交互控件。For coordinate-based actions, the runner maps the agent-produced coordinate to the current browser viewport. When an action targets a standard HTML element, the runner uses DOM-level event dispatch when possible. For canvas-like or JavaScript-rendered controls, it falls back to mouse events. This hybrid execution strategy allows LabOSBench to support both conventional web widgets and simulator-specific interactive controls.

B.2 交互循环Interaction Loop

每个评估阶段都遵循闭环观察-行动-执行协议。 在剧集开始时，运行者启动目标模拟器页面，应用所需的初始状态，并向代理提供任务指令和初始屏幕截图。 在每一步中，代理都会根据指令和当前观察结果预测下一个 GUI 操作。 运行程序解析操作，在浏览器中执行它，等待模拟器状态更新，捕获新的屏幕截图，并查询页内基准测试状态。Each evaluation episode follows a closed-loop observe–act–execute protocol. At the beginning of an episode, the runner launches the target simulator page, applies the required initial state, and provides the agent with the task instruction and the initial screenshot. At each step, the agent predicts the next GUI action based on the instruction and the current observation. The runner parses the action, executes it in the browser, waits for the simulator state to update, captures a new screenshot, and queries the in-page benchmark state.

当目标子任务或工作流成功完成、步骤预算耗尽或运行器检测到不可恢复的执行错误时，循环终止。 无效或无法解析的操作将记录在事件日志中，并计为失败的交互尝试。 该协议允许基准测试捕获成功的任务完成和中间失败行为，例如重复点击、错误的坐标选择、无效的等待或不正确的参数操作。The loop terminates when the target subtask or workflow is successfully completed, when the step budget is exhausted, or when the runner detects an unrecoverable execution error. Invalid or unparsable actions are recorded in the episode log and counted as failed interaction attempts. This protocol allows the benchmark to capture both successful task completion and intermediate failure behavior, such as repeated clicks, wrong coordinate selection, ineffective waiting, or incorrect parameter manipulation.

B.3 子任务初始化Subtask Initialization

对于子任务级评估，每个模拟器在目标子任务之前立即初始化为规范状态。 此初始化隔离了目标操作所需的本地功能，并避免将子任务性能与早期工作流程阶段中积累的故障混为一谈。 例如，在评估参数设置子任务时，模拟器首先处于相关控制可用且所有先决子任务已完成的状态。For subtask-level evaluation, each simulator is initialized to a canonical state immediately before the target subtask. This initialization isolates the local capability required by the target operation and avoids conflating subtask performance with failures accumulated in earlier workflow stages. For example, when evaluating a parameter-setting subtask, the simulator is first placed into the state where the relevant control is available and all prerequisite subtasks have already been completed.

当模拟器支持编程状态控制时，我们使用通过浏览器窗口公开的特定于仪器的快进功能。 这些函数将先决条件子任务标记为已完成，并将 GUI 恢复到规范的子任务前状态。 快进仅用于诊断子任务级评估。 它不用于全集评估，其中代理必须从初始模拟器状态完成整个工作流程。When a simulator supports programmatic state control, we use instrument-specific fast-forward functions exposed through the browser window. These functions mark prerequisite subtasks as completed and restore the GUI to the canonical pre-subtask state. Fast-forwarding is used only for diagnostic subtask-level evaluation. It is not used in full-episode evaluation, where the agent must complete the entire workflow from the initial simulator state.

这种设计使 LabOSBench 能够区分本地 GUI 控制能力和长期工作流程执行。 在子任务初始化下成功但在全集评估中失败的代理可能会遇到规划、排序、内存或恢复问题。 相反，子任务初始化失败表明代理本身无法可靠地完成本地科学仪器操作。This design allows LabOSBench to distinguish local GUI-control ability from long-horizon workflow execution. An agent that succeeds under subtask initialization but fails in full-episode evaluation may suffer from planning, ordering, memory, or recovery problems. In contrast, failure under subtask initialization indicates that the agent cannot reliably complete the local scientific-instrument operation itself.

B.4 步骤预算和终止Step Budget and Termination

对于子任务级评估，每个模型每个子任务最多允许 50 个交互步骤。 如果在步骤预算内满足相应的成功条件，则子任务情节被标记为成功。 否则，在预算用完后，该剧集将被标记为失败。For subtask-level evaluation, each model is allowed up to 50 interaction steps per subtask. A subtask episode is marked as successful if the corresponding success condition is satisfied within the step budget. Otherwise, the episode is marked as failed after the budget is exhausted.

对于全集评估，代理从初始模拟器状态开始，并且必须按顺序完成所有必需的子任务。 仅当所有必需的工作流程阶段都在指定的工作流程级别步骤预算内完成时，整个情节才会成功。 此设置评估长期执行并捕获整个科学工作流程中的错误累积。For full-episode evaluation, the agent starts from the initial simulator state and must complete all required subtasks in order. A full episode is successful only if all required workflow stages are completed within the specified workflow-level step budget. This setting evaluates long-horizon execution and captures error accumulation across the entire scientific workflow.

一个情节可能会在以下三种情况下终止： (i) 所有目标成功条件均已满足， (ii) 达到允许的最大交互步骤数，或者 (iii) 运行者遇到不可恢复的执行错误。 所有终止原因都记录在事件日志中。An episode may terminate under three conditions: (i) all target success conditions are satisfied, (ii) the maximum number of allowed interaction steps is reached, or (iii) the runner encounters an unrecoverable execution error. All termination causes are recorded in the episode log.

B.6 实施说明Implementation Notes

评估运行器被实现为基于浏览器的轻量级管道。 它启动本地模拟器页面，捕获屏幕截图，调度 GUI 操作，并在每集之后导出结构化日志。 这种设计避免了完全操作系统虚拟化，同时保留了与现实科学仪器界面的可执行交互。 由于每个步骤都会记录模拟器状态，因此相同的跟踪可用于定量评分、故障定位和定性案例分析。The evaluation runner is implemented as a lightweight browser-based pipeline. It launches local simulator pages, captures screenshots, dispatches GUI actions, and exports structured logs after each episode. This design avoids full operating-system virtualization while retaining executable interaction with realistic scientific-instrument interfaces. Because the simulator state is logged at each step, the same traces can be used for quantitative scoring, failure localization, and qualitative case analysis.
