从资源流到可执行测试：Petri-Net 引导的并发状态 Rust API 的 LLM 测试生成From Resource Flow to Executable Tests: Petri-Net-Guided LLM Test Generation for Concurrent Stateful Rust APIs

Kaiwen Zhang, Guanjun Liu Tongji UniversityShanghai,China zhangkw@tongji.edu.cn
摘要。Abstract.

并发有状态库 API 通过不断发展的资源所有权、生命周期状态和竞争交错来公开行为。大型语言模型可以合成可执行的 Rust 测试，但它们的输出通常违反 API 前提条件、保持浅层或减少意外顺序跟踪的并发性。相反，基于模型的系统测试技术提供语义控制，但通常需要大量手写代码才能将抽象场景转化为可执行测试。本文解决了正式场景设计和低成本测试具体化之间的差距。Concurrent stateful library APIs expose behavior through evolving resource ownership, lifecycle states, and competing interleavings. Large language models can synthesize executable Rust tests, but their outputs often violate API preconditions, remain shallow, or reduce concurrency to accidental sequential traces. Conversely, model-based and systematic testing techniques provide semantic control but commonly require substantial handwritten code to turn abstract scenarios into executable tests. This paper addresses the gap between formal scenario design and low-cost test concretization.

我们提出了一种 Petri 网引导的方法，用于通过并发有状态 Rust API 进行测试生成。该方法将 API 资源、生命周期条件和因果依赖关系表示为彩色标记和转换；推导出合法的深层状态、准合法和偏序并发场景；并使用这些场景作为基于 LLM 的代码合成的约束中间表示。本地忠实契约和结构修复循环在具体化过程中保留了建模意图，而 Petri 引导的进度塑造优先考虑高冲突并发框架以进行系统探索。然后，分层语义预言机将合成失败与违反目标 API 预期行为的行为区分开来。We present a Petri-net-guided methodology for test generation over concurrent stateful Rust APIs. The method represents API resources, lifecycle conditions, and causal dependencies as colored tokens and transitions; derives legal deep-state, near-legal, and partial-order concurrent scenarios; and uses these scenarios as a constrained intermediate representation for LLM-based code synthesis. A local-faithfulness contract and structural repair loop preserve the modeled intent during concretization, while Petri-guided schedule shaping prioritizes high-conflict concurrency skeletons for systematic exploration. A layered semantic oracle then distinguishes synthesis failures from violations of the target API’s expected behavior.

我们实现了 Rust 并发库的原型，并定义了一个评估协议，用于检查可执行性、结构保真度、深层状态可达性、边界故障产量和冲突覆盖率。中心方法原则是分离职责：Petri 网指定语义意图、资源流、可达性、冲突和与错误相关的突变，而 LLM 实现特定于库的语法、任务支架和断言。该设计为研究正式的资源流模型是否可以使 LLM 生成的并发测试更加忠实、有状态且在诊断上有用提供了具体的基础。We implement a prototype for Rust concurrency libraries and define an evaluation protocol that examines executability, structural fidelity, deep-state reachability, boundary-failure yield, and conflict coverage. The central methodological principle is to separate responsibilities: the Petri net specifies semantic intent, resource flow, reachability, conflict, and bug-relevant mutations, whereas the LLM realizes library-specific syntax, task scaffolding, and assertions. This design provides a concrete basis for studying whether formal resource-flow models can make LLM-generated concurrency tests more faithful, stateful, and diagnostically useful.

1. 简介Introduction

许多 Rust 库 API 都不是孤立的函数接口。它们公开句柄、许可、闭包、缓冲状态和任务级交互模式，其行为取决于先前的操作和竞争调度。在这种情况下，Rust 的类型系统消除了广泛的内存错误，但它并不能证明库尊重其更高级别的协议。剩下的错误是语义错误：过时的功能仍然被接受，关闭操作使错误行为无效，缓冲值丢失，或者测试仅在特定交错达到深度状态后挂起。Many Rust library APIs are not isolated function interfaces. They expose handles, permits, closures, buffered state, and task-level interaction patterns whose behavior depends on prior operations and competing schedules. In this setting, Rust’s type system removes broad classes of memory errors, but it does not prove that a library respects its higher-level protocol. The bugs that remain are semantic faults: a stale capability is still accepted, a close operation invalidates the wrong behavior, a buffered value is lost, or a test hangs only after a specific interleaving reaches a deep state.

由于三个相互关联的原因，这些 API 很难测试。首先，有趣的行为具有很强的状态性：许多故障模式仅在合法前缀建立了重要的资源配置后才会出现。其次，前缀本身必须在语义上受到约束；否则后面的观察毫无意义，因为测试从未执行过有效的协议状态。第三，并发性在偏序级别而不是原始长度级别上很重要。如果长序列意外地序列化了本应公开的竞赛，那么它就没有用处。These APIs are difficult to test for three coupled reasons. First, interesting behaviors are strongly stateful: many failure modes appear only after a legal prefix establishes a nontrivial resource configuration. Second, the prefix itself must be semantically disciplined; otherwise later observations are meaningless because the test never exercised a valid protocol state. Third, concurrency matters at the level of partial order rather than raw length. A long sequence is not useful if it accidentally serializes the very race that should have been exposed.

现有的方法仅覆盖该空间的一部分。基于模型和依赖项感知的测试可以描述法律状态、资源流和边界条件，但将这些抽象转换为可执行的 Rust 测试仍然需要大量的手写脚手架、任务编排和特定于 API 的断言。直接 LLM 提示减少了编码负担，但也将语义责任推回到模型中。在实践中，法学硕士可能会发明事件、违反启用条件、将保留的功能与新的功能混淆、削弱断言或将并发行为扁平化为方便的顺序跟踪。Existing approaches each cover only part of this space. Model-based and dependency-aware testing can describe legal states, resource flow, and boundary conditions, but converting those abstractions into executable Rust tests still demands substantial handwritten scaffolding, task orchestration, and API-specific assertions. Direct LLM prompting reduces that coding burden, but it also pushes semantic responsibility back into the model. In practice, the LLM may invent events, violate enablement conditions, confuse reserved capabilities with fresh ones, weaken assertions, or flatten concurrent behavior into a convenient sequential trace.

我们在本文中的立场有意缩小。我们不要求法学硕士从头开始发现并发语义，我们也不声称消除建模工作。相反，我们使用 Petri-net 模型对资源多重性、因果关系、冲突和接近合法的边界情况进行编码，然后仅使用 LLM 将模型生成的场景实现为可执行的 Rust 代码。调度程序仍然探索运行时交错，并且仍然需要编写特定于 API 的不变量。重点是分离职责，以便语义意图保持在法学硕士之外，同时代码实现保持廉价。Our position in this paper is intentionally narrower. We do not ask the LLM to discover concurrency semantics from scratch, and we do not claim to eliminate modeling effort. Instead, we use a Petri-net model to encode resource multiplicity, causality, conflict, and near-legal boundary cases, then use the LLM only to realize model-produced scenarios as executable Rust code. The scheduler still explores runtime interleavings, and API-specific invariants still need to be authored. The point is to separate responsibilities so that semantic intent stays outside the LLM while code realization stays inexpensive.

这种权衡特别适合并发有状态 Rust API。 Petri 网可以将发送者、接收者、许可、容量、缓冲消息和观察义务表示为令牌，并且它可以表达精确的冲突和因果依赖性，从而使测试在诊断上有用。一旦该结构明确，法学硕士就可以做它相对擅长的事情：编写特定于目标的设置、任务创建、断言和清理。关键的设计规则很简单：模型写意义，LLM 写代码。This tradeoff fits concurrent stateful Rust APIs especially well. A Petri net can represent senders, receivers, permits, capacity, buffered messages, and observation obligations as tokens, and it can express the precise conflicts and causal dependencies that make a test diagnostically useful. Once that structure is explicit, the LLM can do what it is relatively good at: writing target-specific setup, task creation, assertions, and cleanup. The key design rule is simple: the model writes meaning, the LLM writes code.

这种设计的价格也一目了然。 SyncPetri 需要手动编写资源模型、适配器和场景不变量，其计划调整改进了 Loom 等工具之上的线束选择，而不是取代其内部搜索。我们预先声明这些限制，因为它们定义了适当的贡献：不是全自动并发验证，而是一种测试架构，它通过一些建模工作来换取对生成的测试进行更强的语义控制。The price of this design is also clear. SyncPetri requires manually authored resource models, adapters, and scenario invariants, and its schedule shaping improves harness selection above tools such as Loom rather than replacing their internal search. We state these limitations up front because they define the appropriate contribution: not fully automatic concurrency verification, but a testing architecture that trades some modeling effort for stronger semantic control over generated tests.

具体来说，SyncPetri 从彩色 Petri 网络中综合合法的深层追踪、近乎合法的边界探测和偏序并发场景；通过受限的提示和结构修复循环将它们具体化；并使用分层预言机来判断结果执行，该预言机将具体化失败与语义失败分开。结果是一个专为并发 Rust API 设计的测试管道，其硬错误存在于资源协议中，而不是独立的函数输出中。Concretely, SyncPetri synthesizes legal deep-state traces, near-legal boundary probes, and partial-order concurrent scenarios from a colored Petri net; concretizes them through a constrained prompt and structural repair loop; and judges the resulting executions with a layered oracle that separates concretization failure from semantic failure. The result is a testing pipeline designed for concurrent Rust APIs whose hard bugs live in resource protocols rather than in isolated function outputs.

8.3. RQ2：生成的运行程序是否保留调度敏感的结构？RQ2: Does the generated runner preserve schedule-sensitive structure?

该场景通过相对顺序区分两种合法线性化The scenario distinguishes two legal linearizations by the relative order ofe3和ande4，并且运行程序在运行时跟踪中保留了这种区别。每次执行都会发出相同的 14 条记录，均匀分布在两个计划中，并且评估器确认观察到的记录顺序与工件预言匹配。, and the runner preserves that distinction in the runtime trace. Each execution emits the same 14 records, split evenly across the two schedules, and the evaluator confirms that the observed record order matches the artifact oracle.

这很重要，因为这个例子不仅仅是“一些通过的测试”。这是一个小型的时间表家庭，其法律命令在最后的痕迹中仍然可见。这就是原型要保留的具体结构特性。This matters because the example is not merely “some test that passes.” It is a small schedule family whose legal orders remain visible in the final trace. That is the concrete structural property the prototype is meant to preserve.

8.4. RQ3：反馈修复能否在不改变场景的情况下从具体的不匹配中恢复？RQ3: Can feedback repair recover from a concrete mismatch without changing the scenario?

这里使用的修复源是有界运行时反馈修复的结果。修复将发出的操作标签调整为精确的场景字符串，同时保留相同的计划、相同的可观察行为和相同的记录计数。换句话说，修复修复了合同不匹配的问题，而不是将测试重写为不同的测试。The repaired source used here is the result of a bounded runtime-feedback repair. The repair adjusted the emitted operation labels to the exact Scenario strings, while preserving the same schedules, the same observable behavior, and the same record count. In other words, repair fixed the contract mismatch rather than rewriting the test into a different one.

这是当前原型的相关修复形式：生成的代码可能会改变其表面语法和证据管道，但它不应该默默地改变建模场景或削弱预言机。This is the relevant form of repair for the current prototype: the generated code may change its surface syntax and evidence plumbing, but it should not silently change the modeled scenario or weaken the oracle.

8.5. RQ4：工件边界是否足够严格以将通用管道与特定于主题的模型隔离？RQ4: Is the artifact boundary strict enough to isolate the generic pipeline from the subject-specific model?

通用 LLM 和评估器层使用可移植工件，而不是手写 MPSC 逻辑。特定于主题的语义存在于家庭板条箱中：经过审查的 CPN、经过审查的场景和运行时观察契约。然后，通用管道编译生成的源代码，执行它，并根据工件派生的预言机检查发出的 JSONL 记录。The generic LLM and evaluator layers consume the portable artifact, not handwritten MPSC logic. The subject-specific semantics live in the family crate: the reviewed CPN, the reviewed scenario, and the runtime observation contract. The generic pipeline then compiles the generated source, executes it, and checks the emitted JSONL records against the artifact-derived oracle.

限制是范围。这仍然是对一个正在运行的示例的初步评估，而不是大规模的突变研究或进度预算基准。结果支持可行性，而不是统计优势。The limitation is scope. This is still a preliminary evaluation on one running example, not a large-scale mutation study or a schedule-budget benchmark. The result supports feasibility, not statistical superiority.

8.6. 有效性的威胁Threats to Validity

主要威胁是规模。当前的评估涵盖了一项经过审查的 MPSC 主题和一项已修复的生成运行程序。它还不包括突变语料库、纯粹的提示基线或时间表探索比较。即便如此，现有的证据对于 arXiv 提交来说已经足够了，该提交声称有工作原型和经过验证的工件边界，而不是完整的基准测试。The main threat is scale. The current evaluation covers one reviewed MPSC subject and one repaired generated runner. It does not yet include a mutant corpus, a pure prompt baseline, or a schedule-exploration comparison. Even so, the available evidence is enough for an arXiv submission that claims a working prototype and a validated artifact boundary, rather than a completed benchmark.

9. 相关工作Related Work

使用 Petri 网进行基于模型的测试。Model-based testing with Petri nets.

Petri 网长期以来一直用于有状态系统中的形式建模、可达性推理和测试推导Petri nets have long been used for formal modeling, reachability reasoning, and test derivation in stateful systems(Murata, 1989; Manral, 2015)。这一系列工作解释了基于令牌的模型为何有用：它们比平面状态机更自然地表达多样性、因果关系和冲突。我们的设置添加了缺失的具体化问题。输出不得停在抽象跟踪处；它必须成为一个可编译的 Rust 测试，包含任务、所有权移动、时间限制和可执行断言。因此，SyncPetri 使用 Petri 网作为语义中间表示，而不是作为整个测试引擎。. That line of work establishes why token-based models are useful: they express multiplicity, causality, and conflict more naturally than flat state machines. Our setting adds a missing concretization problem. The output must not stop at an abstract trace; it must become a compilable Rust test with tasks, ownership moves, time bounds, and executable assertions. SyncPetri therefore uses the Petri net as a semantic intermediate representation rather than as the whole testing engine.

有状态 API 测试和深层状态探索。Stateful API testing and deep-state exploration.

REST-ler 表明，依赖感知生成对于有状态 API 是必要的，因为简单的请求组合很少达到有意义的深层状态REST-ler showed that dependency-aware generation is necessary for stateful APIs because naive request composition rarely reaches meaningful deep states(Atlidakis et al., 2018)。 StateAFL 和后来的有状态灰盒工作同样认为，故障通常只有在系统进入语义上不同的状态后才会出现. StateAFL and later stateful greybox work likewise argue that failures often emerge only after the system enters semantically distinct states(Natella, 2021; Ba et al., 2022)。我们有共同的动机，但目标和抽象不同。这些系统专注于面向网络或面向协议的接口，而 SyncPetri 则针对进程内 Rust 库 API，其硬行为依赖于资源所有权、处理失效、保留功能和调度敏感的部分顺序。我们的近乎合法的场景还针对模型定义的语义边界，而不是任意无效的输入。. We share that motivation, but the target and abstraction differ. Those systems focus on network-facing or protocol-facing interfaces, whereas SyncPetri targets in-process Rust library APIs whose hard behaviors depend on resource ownership, handle invalidation, reserved capabilities, and schedule-sensitive partial orders. Our near-legal scenarios also aim at semantic boundaries defined by the model, rather than at arbitrary invalid inputs.

基于 LLM 的测试生成。LLM-based test generation.

TitanFuzz 和 Fuzz4All 表明法学硕士可以在手动生成器成本高昂的领域生成各种测试和程序TitanFuzz and Fuzz4All showed that LLMs can generate diverse tests and programs in domains where manual generators are costly(Deng et al., 2022; Xia et al., 2023)。 CoverUp 进一步表明，即使对于强大的模型，外部反馈和结构仍然很重要. CoverUp further showed that external feedback and structure remain important even for strong models(Pizzorno and Berger, 2024)。 SyncPetri 采纳了这一教训，但改变了引导信号。我们不单独依赖开放式提示或覆盖，而是提供一个带有资源绑定、顺序约束、可接受的结果类和禁止的语义编辑的类型化事件图，然后用结构预言来判断结果。因此，其贡献不仅仅是使用 LLM 进行测试，而是将 LLM 限制为代码实现，同时将语义意图保留在模型之外。. SyncPetri adopts that lesson but changes the guidance signal. Instead of relying on open-ended prompting or coverage alone, we provide a typed event graph with resource bindings, order constraints, admissible outcome classes, and banned semantic edits, then judge the result with a structural oracle. The contribution is therefore not simply to use an LLM for testing, but to restrict the LLM to code realization while keeping semantic intent outside the model.

系统的并发探索。Systematic concurrency exploration.

Loom 为 Rust 并发代码提供受控的调度探索Loom provides controlled schedule exploration for Rust concurrent code(Tokio Contributors, 2026a)。我们的工作是互补的，而不是竞争的。 Loom 探索安全带内部的微交错； SyncPetri 首先尝试通过从资源模型中提取竞争窗口和冲突对来使该利用在语义上有意义。因此，调度塑造组件在调度程序之上运行：它优先考虑哪些并发框架值得探索预算，但它不会修改调度程序的内部搜索算法。. Our work is complementary rather than competitive. Loom explores micro-interleavings inside a harness; SyncPetri tries to make that harness semantically meaningful in the first place by extracting race windows and conflict pairs from the resource model. The schedule-shaping component therefore operates above the scheduler: it prioritizes which concurrency skeletons deserve exploration budget, but it does not modify the scheduler’s internal search algorithm.

定位。Positioning.

在这些工作中，缺少的组合是从资源感知并发语义到可执行 Rust 测试的模型驱动路线，而不将语义预言委托给 LLM。 SyncPetri 通过在一个测试工作流程中结合 Petri-net 场景综合、约束具体化、调度感知线束构建和分层运行时判断来占据这一空间。Across these lines of work, the missing combination is a model-driven route from resource-aware concurrency semantics to executable Rust tests without delegating the semantic oracle to the LLM. SyncPetri occupies that space by combining Petri-net scenario synthesis, constrained concretization, schedule-aware harness construction, and layered runtime judgment in one testing workflow.

10. 结论Conclusion

本文介绍了 SyncPetri，这是一种 Petri 网约束架构，用于通过并发状态 Rust API 生成基于 LLM 的测试。主要论点是模型结构应该控制语义、边界突变和并发暴露，而LLM应该只控制可执行的实现。为了支持该论文，我们形式化了目标域，定义了场景语言，指定了具体化和修复循环，提出了 Petri 引导的调度塑造，并引入了多层语义预言机。这些部分共同构成了一个主线大小的方法：不仅仅是 Petri 网和 LLM 可以组合的草图，而是如何将它们组合在测试生成系统中的具体设计。This paper presented SyncPetri, a Petri-net-constrained architecture for LLM-based test generation over concurrent stateful Rust APIs. The main thesis is that model structure should control semantics, boundary mutation, and concurrency exposure, while the LLM should only control executable realization. To support that thesis, we formalized the target domain, defined a scenario language, specified concretization and repair loops, proposed Petri-guided schedule shaping, and introduced a multi-layer semantic oracle. Together, these pieces form a main-track-sized methodology: not merely a sketch that Petri nets and LLMs can be combined, but a concrete design for how they should be combined in a test-generation system.
