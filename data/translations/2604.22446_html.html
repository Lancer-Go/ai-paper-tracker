5 讨论5 Discussion

局限性。Limitations.

应该承认一些限制。首先，我们的定量评估仅限于PRDBench（50个软件开发任务）；虽然案例研究证明了跨领域的适用性（内容生成、游戏开发、有声读物制作和学术研究），但对非编码基准的系统评估仍然是未来的工作。其次，自我进化机制（一对一、回顾、绩效评估）已经实施和部署，但尚未量化；分离每个机制的贡献需要对许多项目进行纵向研究。Several limitations should be acknowledged. First, our quantitative evaluation is confined to PRDBench (50 software development tasks); while the case studies demonstrate cross-domain applicability (content generation, game development, audiobook production, and academic research), systematic evaluation on non-coding benchmarks remains future work. Second, the self-evolution mechanisms (one-on-ones, retrospectives, performance reviews) have been implemented and deployed but not yet quantitatively ablated; isolating the contribution of each mechanism requires longitudinal studies across many projects.

成本与性能的权衡。Cost–performance trade-off.

OMC 的多代理协调会产生大量成本开销（每个 PRDBench 任务约 6.91 美元）。对于复杂的项目级任务来说，这种成本是合理的，其中正确性比令牌效率更重要，但可能不适合简单的单轮查询。因此，我们在OMC中引入了自适应调度模式：CEO可以选择将简单的任务路由到单个Agent，并为超过复杂性阈值的任务保留多Agent协调。OMC’s multi-agent coordination incurs significant cost overhead (approximately $6.91 per PRDBench task). This cost is justified for complex, project-level tasks where correctness matters more than token efficiency, but may not be appropriate for simple, single-turn queries. Therefore, we have introduced an adaptive dispatch mode in OMC: the CEO can choose to route simple tasks to a single agent and reserve multi-agent coordination for tasks that exceed a complexity threshold.

更广泛的影响。Broader implications.

激励 OMC 的人与企业的类比是刻意笼统的：管理-计划-雇用-学习的模式适用于任何领域，而不仅仅是软件开发。案例研究（内容生成、游戏开发、有声读物制作和自动化研究调查）提供了这种普遍性的初步证据。随着人才市场的增长和更多特工家族的出现，组织层应该变得更加有用，就像硬件多样性增加时操作系统变得越来越重要一样。The human-enterprise analogy that motivates OMC is deliberately general: the pattern of manage–plan–hire–learn applies to any domain, not just software development. The case studies (content generation, game development, audiobook production, and automated research survey) provide initial evidence of this generality. As the Talent Market grows and more agent families become available, the organisational layer should become more useful, much as operating systems gained importance when hardware diversity increased.

6 结论6 Conclusion

我们认为，人工智能组织设计，即异构代理劳动力的系统结构、协调和演化，是多代理研究中缺失的一层。 OMC 表明，人类公司的组织机制转移到了这种背景下。具有集成人才市场的类型化人才容器架构可处理劳动力管理；的We have argued that AI organisation design, the systematic structuring, coordination, and evolution of heterogeneous agent workforces, is a missing layer in multi-agent research. OMC demonstrates that the organisational machinery of human companies transfers to this setting. A typed Talent–Container architecture with an integrated Talent Market handles workforce management; theE2\text{E}^{2}R 树搜索通过结构化分解和审查门来协调项目执行；自我进化管道通过反思、回顾和正式的人力资源流程来闭合反馈循环。在 PRDBench 上，这种组合在跨越多个领域并需要长期推理的项目中取得了 84.67% 的成功率，超过了所有基线。主要的悬而未决的问题是这种优势是否在更大范围内保持，每个组件单独贡献多少，以及人才市场生态系统应如何发展以涵盖软件开发以外的领域。R tree search coordinates project execution through structured decomposition and review gates; and a self-evolution pipeline closes the feedback loop through reflection, retrospectives, and formal HR processes. On PRDBench, this combination yields an 84.67% success rate, surpassing all baselines, across projects that span multiple domains and require long-horizon reasoning. The main open questions are whether this advantage holds at larger scale, how much each component contributes in isolation, and how the Talent Market ecosystem should grow to cover domains beyond software development.

附录CAppendix C执行器后端和任务调度Executor Backends and Task Dispatch

按需调度。On-Demand Dispatch.

代理不会轮询工作。任务按需调度：分配任务后立即通过组织层开始执行，代理在空闲时不消耗任何资源。系统可以自然地扩展——添加代理不会增加空闲开销——并且可以从中断中恢复，因为所有状态都是持久的，而不是保存在正在运行的进程中。Agents do not poll for work. Tasks are dispatched on demand: execution begins immediately through the organisational layer when a task is assigned, and the agent consumes no resources when idle. The system scales naturally—adding agents does not increase idle overhead—and recovers from interruptions because all state is persisted rather than held in running processes.

三个参考后端。Three Reference Backends.

执行接口将任务分派与代理运行时解耦。提供了三种参考实现：(1) 用于工具使用任务的基于 LangChain 的反应式代理，(2) 用于长期推理的 Claude Code 会话，以及 (3) 用于轻量级或自定义运行时的基于脚本的执行器。因为组织层承载所有状态，所以每个执行器都保持无状态和最小化。无需更改现有代理或基础设施即可注册其他后端。The execution interface decouples task dispatch from the agent runtime. Three reference implementations are provided: (1) a LangChain-based reactive agent for tool-using tasks, (2) a Claude Code session for long-horizon reasoning, and (3) a script-based executor for lightweight or custom runtimes. Because the organisational layer carries all state, each executor is kept stateless and minimal. Additional backends can be registered without changes to existing agents or infrastructure.

故障恢复。Failure Recovery.

当代理任务失败时，将捕获失败，将错误上下文注入重试提示中，并使用更新的信息恢复执行。经过可配置的尝试次数后，任务将上报给监督代理进行审查和重新分配。该恢复循环完全通过组织接口运行，因此跨执行器后端的行为是一致的。When an agent fails a task, the failure is captured, error context is injected into the retry prompt, and execution resumes with updated information. After a configurable number of attempts, the task is escalated to the supervising agent for review and reassignment. This recovery loop operates entirely through the organisational interfaces, so the behavior is consistent across executor backends.

C.1 工具和技能系统C.1 Tool and Skill System

基于角色的工具访问。Role-Based Tool Access.

代理的行动空间由其有权使用的工具决定。该系统通过统一的工具注册表来强制执行此操作，该注册表按角色、显式权限授予和资产所有权来控制访问。权限在即时组装时解析：每个代理的上下文仅包含授权的工具，因此在代理开始推理之前会强制执行功能边界。An agent’s action space is determined by which tools it is authorized to use. The system enforces this through a unified tool registry that gates access by role, explicit permission grants, and asset ownership. Permissions are resolved at prompt assembly time: each agent’s context includes only authorized tools, so capability boundaries are enforced before the agent begins reasoning.

跨后端工具暴露。Cross-Backend Tool Exposure.

无论执行器后端如何，工具都通过标准接口公开。对于 Claude Code 会话，工具通过模型上下文协议 (MCP) 呈现，允许与基于 LangChain 的代理相同的组织功能。从平台角度来看，MCP桥接是一个执行器的实现细节——工具合约在后端是统一的。Tools are exposed through a standard interface regardless of executor backend. For Claude Code sessions, tools are surfaced via the Model Context Protocol (MCP), allowing the same organizational capabilities as LangChain-based agents. From the platform perspective, MCP bridging is an implementation detail of one executor—the tool contract is uniform across backends.

作为代理间协调的工具。Tools as Inter-Agent Coordination.

核心代理间工具涵盖了全方位的组织交互：将工作委派给下属、接受或拒绝子任务、召集多代理讨论以及将决策上报给首席执行官。每次交互都表示为流经组织层的工具调用，并产生所有代理可见的效果。Core inter-agent tools cover the full range of organizational interaction: delegating work to a subordinate, accepting or rejecting a subtask, convening a multi-agent discussion, and escalating a decision to the CEO. Each interaction is expressed as a tool call that flows through the organisational layer and produces effects visible to all agents.
