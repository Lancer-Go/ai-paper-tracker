摘要Abstract

设备上的小语言模型 (SLM) 承诺为移动用户提供完全离线、私有的 AI 体验（不依赖云，数据不会离开设备）。但这个承诺在实践中能实现吗？本文提出了一个纵向实践案例研究，记录了将 SLM（Gemma 4 E2B，2.6B 参数；Qwen3 0.6B，600M 参数）集成到 Palabrita（一款 Android 猜词游戏）中的工程挑战。为期 5 天的开发冲刺包含 204 项提交（On-device Small Language Models (SLMs) promise fully offline, private AI experiences for mobile users (no cloud dependency, no data leaving the device). But is this promise achievable in practice? This paper presents a longitudinal practitioner case study documenting the engineering challenges of integrating SLMs (Gemma 4 E2B, 2.6B parameters; Qwen3 0.6B, 600M parameters) into Palabrita, a production Android word-guessing game. Over a 5-day development sprint comprising 204 commits (∼\sim90 直接与 AI 相关），该系统经历了彻底的转变：从一个雄心勃勃的设计，其中法学硕士生成完整的结构化谜题（单词、类别、难度和五个 JSON 提示），到一个务实的架构，其中策划的单词列表提供单词，法学硕士仅生成三个简短的提示，如果失败，则有确定性的回退。我们确定了特定于设备上 SLM 集成的五类故障：输出格式违规、约束违规、上下文质量下降、延迟不兼容和模型选择不稳定。对于每个故障类别，我们记录了观察到的症状、根本原因以及有效缓解这些症状的提示工程和架构策略，包括多层防御解析、带有故障反馈的上下文重试、会话轮换、渐进提示强化和系统责任减少。我们的研究结果表明，设备上的 SLM 对于生产移动应用程序来说是可行的，但前提是开发人员接受一个基本约束：最可靠的设备上 LLM 功能是 LLM 做得最少的功能。我们将经验提炼成八个可操作的设计启发法，供从业者将 SLM 集成到移动应用程序中。90 directly AI-related), the system underwent a radical transformation: from an ambitious design where the LLM generated complete structured puzzles (word, category, difficulty, and five hints as JSON) to a pragmatic architecture where curated word lists provide the words and the LLM generates only three short hints, with a deterministic fallback if it fails. We identify five categories of failures specific to on-device SLM integration: output format violations, constraint violations, context quality degradation, latency incompatibility, and model selection instability. For each failure category, we document the observed symptoms, root causes, and the prompt engineering and architectural strategies that effectively mitigated them, including multi-layer defensive parsing, contextual retry with failure feedback, session rotation, progressive prompt hardening, and systematic responsibility reduction. Our findings demonstrate that on-device SLMs are viable for production mobile applications, but only when the developer accepts a fundamental constraint: the most reliable on-device LLM feature is one where the LLM does the least. We distill our experience into eight actionable design heuristics for practitioners integrating SLMs into mobile apps.

2.1 小语言模型Small Language Models

小语言模型 (SLM)（通常具有少于 30 亿个参数的模型）已成为设备上部署的实用选择。 Gemma 系列（Google DeepMind）以针对边缘设备优化的量化格式提供从 1B 到 4B 参数的模型Small Language Models (SLMs), typically models with fewer than 3 billion parameters, have become the practical choice for on-device deployment. The Gemma family (Google DeepMind) offers models from 1B to 4B parameters in quantized formats optimized for edge devices[4]。 Qwen3（阿里巴巴）提供0.6B参数起的模型. Qwen3 (Alibaba) provides models starting at 0.6B parameters[5]。 Phi-4 Mini（微软）瞄准3.8B参数范围. Phi-4 Mini (Microsoft) targets the 3.8B parameter range[6]。与云模型（GPT-4，Claude）相比，这些模型牺牲了功能，但获得了完全在消费类硬件上运行的能力。. These models sacrifice capability compared to cloud models (GPT-4, Claude) but gain the ability to run entirely on consumer hardware.

云和设备上模型之间的能力差距不仅仅是数量上的（每秒令牌更少，准确性稍差）。它是The capability gap between cloud and on-device models is not merely quantitative (fewer tokens per second, slightly worse accuracy). It is定性的qualitative：SLM 表现出不同的故障模式，需要不同的工程方法。提示输出 JSON 的云模型几乎总是会生成有效的 JSON。同样提示的 SLM 可能会将其 JSON 包装在 Markdown 代码围栏中，将 JSON 键翻译为输出语言，截断响应中间令牌，或者生成具有语义错误值的有效 JSON。这些定性差异在文献中记录很少，文献倾向于根据标准化基准来评估 SLM，而不是根据从业者需要的受约束的、特定于应用程序的任务。: SLMs exhibit different failure modes that require different engineering approaches. A cloud model prompted to output JSON will almost always produce valid JSON. An SLM prompted identically may wrap its JSON in markdown code fences, translate JSON keys into the output language, truncate the response mid-token, or produce valid JSON with semantically wrong values. These qualitative differences are poorly documented in the literature, which tends to evaluate SLMs on standardized benchmarks rather than on the constrained, application-specific tasks that practitioners need.

对于我们的用例（生成有关已知单词的短游戏提示），关键问题不是 SLM 是否与基准上的云模型匹配，而是它们是否能够在严格的约束下可靠地生成简单的结构化输出。我们的研究结果表明，这种可靠性明显低于云模型显示的可靠性，需要大量的工程补偿。For our use case (generating short game hints about known words), the key question is not whether SLMs match cloud models on benchmarks, but whether they can reliably produce simple structured output under tight constraints. Our findings show this reliability is significantly lower than cloud models suggest, requiring extensive engineering compensations.

2.3 约束模型的快速工程Prompt Engineering for Constrained Models

云法学硕士的即时工程有详细记录Prompt engineering for cloud LLMs is well-documented[7, 8]。思路链提示. Chain-of-thought prompting[7]、少样本示例以及系统/用户提示分离是标准技术。然而，SLM 在提示下的行为却截然不同：, few-shot examples, and system/user prompt separation are standard techniques. SLMs, though, behave very differently under prompting:

  • •

    格式合规性不可靠。Format compliance is unreliable.云模型几乎总是在出现提示时生成有效的 JSON。 SLM 经常添加 Markdown 代码围栏、将自然语言与 JSON 混合或翻译 JSON 键。Cloud models almost always produce valid JSON when prompted. SLMs frequently add markdown code fences, mix natural language with JSON, or translate JSON keys.

    数值推理能力较弱。Numerical reasoning is weak.计算单词中的字符数（例如，“‘estufa’有 5 个或 6 个字母吗？”）在低于 3B 的参数范围内是不可靠的。Counting characters in a word (e.g., “does ‘estufa’ have 5 or 6 letters?”) is unreliable at the sub-3B parameter scale.

  • •

    语言漂移是系统性的。Language drift is systematic.以英语为主的训练数据会导致 SLM 默认为英语输出，即使有明确指示，尤其是对于 JSON 键等结构化数据。English-dominant training data causes SLMs to default to English output even when explicitly instructed otherwise, especially for structured data like JSON keys.

  • •

In Palabrita, the user’s gameplay data (words guessed, hints requested, languages chosen) never leaves the device. There is no API call to intercept, no server log to subpoena, no training pipeline to inadvertently include user data. The privacy guarantee is not a policy promise; it is an architectural fact.

我们认为，该行业必须将其推理基础设施的很大一部分从集中式云转移到边缘：智能手机、个人电脑、物联网设备、本地服务器、自托管实例。硬件的能力越来越强（我们的 Pixel 7 Pro 仅在 CPU 上就以每秒 30 个令牌的速度运行 2.6B 参数模型）。框架正在成熟（LiteRT-LM、MLC LLM、llama.cpp）。模型正在缩小（Qwen3 0.6B 适合 614MB）。缺少的是工程文化：默认的假设是用户数据应保留在用户的设备上，除非有明确的、经同意的且合理的理由将其发送到其他地方。We believe the industry must move a significant portion of its inference infrastructure from centralized cloud to the edge: smartphones, personal computers, IoT devices, local servers, self-hosted instances. The hardware is increasingly capable (our Pixel 7 Pro runs a 2.6B parameter model at 30 tokens per second on CPU alone). The frameworks are maturing (LiteRT-LM, MLC LLM, llama.cpp). The models are shrinking (Qwen3 0.6B fits in 614 MB). What is missing is the engineering culture: a default assumption that user data should stay on the user’s device unless there is a clear, consented, and justified reason to send it elsewhere.

本文记录了该选择的工程成本。设备上的推理比云 API 调用更难。解析更加混乱，提示需要更多迭代，模型能力较差，并且后备是必不可少的。但这些都是工程问题和工程解决方案。数百万用户的隐私不是一个工程问题。这是一种设计选择，我们认为它应该是默认的。This paper documented the engineering cost of that choice. On-device inference is harder than a cloud API call. Parsing is messier, prompts require more iteration, models are less capable, and fallbacks are essential. But these are engineering problems with engineering solutions. The privacy of millions of users is not an engineering problem. It is a design choice, and we argue it should be the default one.
