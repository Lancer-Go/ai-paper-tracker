摘要。Abstract.

人工智能编码代理是通过推理和工具使用来自动化开发任务的软件工具，越来越多地通过插件市场进行扩展，但这些新兴存储库的结构、维护和共同进化动态仍未得到实证探索。 与通过源代码提供功能的传统软件包不同，代理插件通过自然语言指令文件、脚本和配置文件的组合来提供功能，这就提出了一个问题：这些插件是跨组件共同演化的维护工件，还是开发人员编写一次且不需要重新访问的一次性工件。 为了研究代理插件的维护和共同进化，我们对托管 Claude Code 插件市场的 1,926 个存储库进行了实证研究，分析了 2,018 个市场中的 8,351 个插件和 77,773 个提交。 我们发现市场正在迅速扩张，涉及插件的提交活动不断增长AI coding agents, software tools that automate development tasks through reasoning and tool use, are increasingly extended through plugin marketplaces, yet the structure, maintenance, and co-evolution dynamics of these emerging repositories remain empirically unexplored. Unlike traditional software packages that deliver functionality through source code, agent plugins deliver functionality through a combination of natural-language instruction files, scripts, and configuration files, raising the question of whether these plugins are maintained artifacts that co-evolve across components, or one-off artifacts that developers write once and do not need to revisit. 1. 简介Introduction

大型语言模型 (LLM) 代理已成为解决需要推理、工具使用以及与外部环境交互的复杂任务的自主工具。 这些代理可以使用插件进行扩展，开发人员可以通过插件打包和分发代理行为，包括技能、自定义命令、挂钩和模型上下文协议 (MCP) 服务器，使团队能够跨项目共享和重用一致的代理工作流程，而不是为每个项目独立地重新配置代理Large Language Model (LLM) agents have emerged as autonomous tools for addressing complex tasks that require reasoning, tool usage, and interaction with external environments. These agents can be extended using plugins, through which developers package and distribute agent behavior, including skills, custom commands, hooks, and model context protocol (MCP) servers, enabling teams to share and reuse consistent agent workflows across projects rather than reconfiguring the agent independently for each project(Anthropic, 2025c)。 我们使用这个术语. We use the term代理插件agent plugins11 1 https://agent-plugins.org/引用此类可分发的行为包，以将其与传统的软件插件区分开来。 Claude Code 由 Anthropic 开发，是最早支持代理插件系统的 AI 编码代理之一，尽管类似的功能已经传播到其他 AI 编码代理中。 代理插件通过称为的共享存储库分发to refer to such distributable behavior packages to distinguish them from traditional software plugins. Developed by Anthropic, Claude Code was one of the first AI coding agents to support an agent plugin system, though similar capabilities had already been spreading to other AI coding agents. Agent plugins are distributed through shared repositories called市场marketplaces，它充当可用插件的目录，用户可以使用 Claude Code 注册并从中安装, which act as catalogs of available plugins that users can register with Claude Code and install from(Anthropic, 2025b).

软件工件的维护和共同进化是传统软件工程中深入研究的主题The maintenance and co-evolution of software artifacts are well-studied topics in traditional software engineering(Swanson, 1976; Zaidman et al., 2008; Fluri et al., 2007)。 最近的其他研究已将此重点扩展到相邻的工件类，探索机器学习库的跨语言绑定的维护健康状况，识别技术滞后和不完整的发布覆盖范围. Other recent research has extended this focus to adjacent artifact classes, exploring the maintenance health of cross-language bindings for machine learning libraries, identifying technical lags and incomplete release coverage(Li and Bezemer, 2025)。 之前的工作还调查了代理技能的工件类别. Prior work has also investigated the artifact classes of agent skills(Ling et al., 2026)、通用AI助手商店, general-purpose AI assistant stores(Su et al., 2025; Yan et al., 2024)，以及传统的软件包生态系统, and conventional software package ecosystems(Kikas et al., 2017; Decan et al., 2019)。 然而，之前没有研究过代理插件的维护和共同进化，代理插件是一种新的工件类，其中自然语言指令文件和源代码工件作为主要分布式工件共存。. However, no prior work has studied the maintenance and co-evolution of agent plugins, a new artifact class in which natural-language instruction files and source code artifacts co-exist as primary distributed artifacts.

在多组件插件中，未能一起更新共同演化的组件可能会带来它们不同步的风险，可能会引入不一致和无声缺陷。 与通过源代码提供功能的传统软件包不同，Claude Code 插件主要依赖于 Claude 在运行时读取和解释的自然语言 Markdown 文件，以及支持脚本和配置文件。 这种区别提出了一个问题：软件工程方法是否是为源代码存储库开发的，源代码存储库本身通常结合了多种编程语言In multi-component plugins, failing to update co-evolved components together carries the risk of leaving them out of sync, potentially introducing inconsistencies and silent defects. Unlike traditional software packages, which deliver functionality through source code, Claude Code plugins rely primarily on natural-language Markdown files that Claude reads and interprets at runtime, alongside supporting scripts and configuration files. This distinction raises the question of whether software engineering methods developed for source-code repositories, which themselves often combine multiple programming languages(Li et al., 2024)，将传输到代理插件存储库。, would transfer to agent plugin repositories.

因此，我们研究代理插件的软件维护和共同进化，为该工件类别提供第一个经验基线，并检查传统的软件工程方法是否会转移到这个新的工件类别，其中自然语言文件是主要的分布式工件而不是源代码。 解决这个问题为未来研究这个独特的工件类的开发模式和维护奠定了基础。 如果没有此类工件的经验基线，研究人员就缺乏研究其发展模式、将其与传统生态系统进行比较或构建针对其独特特征进行校准的工具所需的基础。We hence study the software maintenance and co-evolution of agent plugins, providing the first empirical baseline for this artifact class, and examine whether traditional software engineering methods would transfer to this new artifact class, where natural-language files are the primary distributed artifact rather than source code. Addressing this issue establishes a foundation for future research into the development patterns and maintenance of this unique artifact class. Without an empirical baseline for this artifact class, researchers lack the foundation needed to study its development patterns, compare it with conventional ecosystems, or build tools calibrated to its unique characteristics.

5.1. 动机Motivation

之前的工作Prior work(Zeng et al., 2025)通过研究开发人员提交的更改类型（例如功能工作、错误修复和维护）来描述开发人员如何构建和维护传统软件。我们在 RQ1 中的发现表明，代理插件存储库在首次发布后不断累积提交，并且这些存储库主要由自然语言指令以及脚本和配置文件组成，而不是程序代码。由于更改中的工件与程序代码不同，因此插件提交背后的开发和维护活动也可能与传统软件报告的不同。此外，AI编码代理现已广泛应用于现实世界的软件开发中characterizes how developers build and maintain traditional software by studying the kinds of changes they commit, e.g., feature work, bug fix, and maintenance. Our findings from RQ1 show that agent plugin repositories keep accumulating commits after their initial release, and that these repositories consist primarily of natural language instructions alongside scripts and configuration files, rather than program code. Since the artifacts under change differ from program code, the development and maintenance activities behind plugin commits may also differ from those reported for traditional software. In addition, AI coding agents are now widely used in real-world software development(Li et al., 2026b; Li et al., 2025)，代理插件开发人员特别有可能将工作委托给代理，这就提出了这样的问题：有多少开发和维护工作是由人工智能辅助的。, and agent plugin developers are especially likely to delegate work to the agents, raising the question of how much of this development and maintenance work is AI-assisted.

6. 问题3： 插件组件如何共同进化？RQ3: How Do Plugin Components Co-Evolve?

6.1. 动机Motivation

先前的工作报告称，在传统的 OSS 中，基础设施代码和源代码紧密地共同演化，这需要负责这些更改的人员付出额外的努力，以保持项目的可编译、可部署或可执行Prior work reports that in traditional OSS, infrastructure code and source code co-evolve tightly, which introduces additional efforts for the people responsible for these changes to keep the project compilable, deployable, or executable(Jiang and Adams, 2015)。 我们从之前的研究问题中得到的结果表明，代理插件经常在同一存储库 (RQ1) 中结合多种组件类型和语言（自然语言和多种编程语言），其中 AI 编码代理 (RQ2) 做出了重大贡献。 组件、语言和贡献的不同组成表明，先前关于传统 OSS 上的共同进化和耦合的发现可能无法很好地转移到代理插件存储库。. Our findings from previous research questions show that agent plugins frequently combine multiple component types and languages (both natural language and multiple programming languages) within the same repository (RQ1), with significant contribution from AI coding agents (RQ2). The distinct composition of components, languages, and contributions indicates that the prior findings on co-evolution and coupling on traditional OSS might not transfer well to agent plugin repositories.

因此，我们研究代理插件在组件之间是否具有类似的耦合，在两个层面上检查潜在的协同演化：1）组件间和2）组件内。 由于开发主要是自然语言驱动的 (RQ2)，因此当脚本和 Markdown 文件一起更改时，对驱动组件间耦合的因素进行分类可以揭示维护自然语言工件与维护源代码的不同之处。 组件内协同演化在各个组件本身内部运行，在文件类型级别上也会出现同样的问题，因为技能和挂钩混合了可以在单个目录中共同演化的文件类型。 总之，这些答案为研究人员提供了人工智能原生存储库的第一个经验性共同进化测量，其中兴趣依赖性不是在两个代码文件之间运行，而是在实现脚本和代理在运行时读取的自然语言指令之间运行。Therefore, we investigate whether agent plugins have similar coupling between components, examining potential co-evolutions at two levels: 1) inter-component and 2) intra-component. Since development is predominantly natural-language driven (RQ2), when scripts and Markdown files change together, classifying what drives that inter-component coupling reveals how maintaining natural-language artifacts differs from maintaining source code. Intra-component co-evolution operates within individual components themselves, where the same question arises at the file-type level, since skills and hooks mix file types that could co-evolve within a single directory. Together, the answers offer researchers the first empirical co-evolution measurements for AI-native repositories, where the dependency of interest runs not between two code files but between an implementation script and the natural-language instructions an agent reads at runtime.

— rubric for ‘docs‘ —
You are re-classifying a commit a developer labeled ‘docs‘ in an AI-agent PLUGIN repo. Decide its TRUE Conventional Commit type from the DIFF.
AI-READ files (SKILL.md, agents/*.md, commands/*.md, skills/**, references/*.md) are the agent’s runtime instructions; changing their CONTENT changes behavior. HUMAN-READ files (README, CONTRIBUTING, CHANGELOG, and archived / context / userstory files) are ignored by the agent.
Judge by what the +/- lines DO:
- feat -> ADDS an instruction the agent will act on (new section, rule, step, capability, procedure, example), OR registers a NEW plugin/component entry in marketplace.json / plugin.json.
- fix -> CORRECTS existing agent behavior: a wrong tool/step/path/example, a rule, a script-invocation procedure, or a skill’s ‘description‘ / frontmatter TRIGGER (which controls WHEN the skill fires).
- chore -> ONLY version bumps, or REMOVING / reorganizing marketplace or plugin entries and metadata (not adding new ones).
- docs -> behavior unchanged: only human-facing or archived/context files; OR, even inside an AI-read file, only inert metadata (version, date, badge) or a LINK change (adding, removing, or fixing a source-attribution or bare reference link).
Read the DIFF, not the message. Key distinctions learned from real cases:
- Removing/fixing a source-attribution or dead link, or adding a bare reference/doc link, is informational -> docs (even in a SKILL.md).
- Adding a new plugin entry to marketplace.json -> feat; removing one or editing its metadata -> chore.
- Changing a skill’s ‘description‘/trigger, or the procedure the agent uses to invoke a script -> fix.
- A SKILL.md touched only by a version bump or whitespace -> docs; the real change may sit in a README while the AI-read file only got a bump -> docs.
— rubric for ‘ci‘ —
You are re-classifying a commit a developer labeled ‘ci‘ in an AI-agent PLUGIN repo. ‘ci:‘ is sometimes a real pipeline change, sometimes just a TOPIC prefix for a CI-themed plugin. Decide from the DIFF.

- feat -> the diff builds or extends a CI-EXPERT agent/skill/command (AI-read instruction files); no pipeline file changed.
- fix -> the diff corrects existing CI-expert instruction content; no pipeline file changed.
Read the DIFF, not the message. No workflow/CI-config file touched and the change is to SKILL.md/agents/commands -> feat/fix, not ci (the plugin’s TOPIC is CI, but nothing ran). A real workflow file changed -> ci, even if plugin files were also touched.

- feat -> the wording change adds or strengthens a directive so the agent does something new/different, or changes the verbatim text the agent outputs.

- The script changed, but the markdown does NOT closely reflect that specific change
