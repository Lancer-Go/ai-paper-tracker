Attackers can embed malicious instructions in external data—such as retrieved emails, web pages, or third-party tool outputs—to trigger harmful agent actions. 立场 1：动态（和安全意识）重新规划和安全策略更新对于复杂、动态的代理任务是必要的。Position 1: Dynamic (and security-aware) replanning and security policy updates are necessary for complex, dynamic agentic tasks.现有系统级防御中的一个流行想法是A popular idea in existing system-level defenses is计划与执行隔离plan-execution isolation [23, 6]：代理仅根据用户任务生成计划，然后基本上“按原样”执行。虽然此策略可以防止不受信任的数据直接篡改控制流，但它在动态环境中变得脆弱：即使是良性的运行时错误（例如，已弃用的 API、缺少依赖项）也可能会破坏代理工作流程。因此，我们认为重新规划对于保持通用代理的效用是必要的。: the agent generates a plan solely from the user task and then executes it largely “as is.” While this strategy prevents untrusted data from directly tampering with the control flow, it becomes brittle in dynamic environments: even benign runtime errors (e.g., deprecated APIs, missing dependencies) can break the agent workflow. 系统级防御的另一个常见策略是策略执行Another common strategy in system-level defenses is policy enforcement[17, 6]：系统预先对允许的行为进行推理并阻止可疑的行为。我们观察到，策略本质上与用户任务和当前计划相关：重新计划通常意味着策略更改。在开放式设置中，预先编写完全静态的策略可能很困难（或不可能）（例如，在调试期间，无法提前知道应该读取、写入或执行哪些文件或日志）。因此，动态策略更新是代理设计的另一个必要部分。: the system reasons about allowed behaviors beforehand and blocks suspicious actions. We observe that policies are inherently coupled to the user task and the current plan: replanning often implies policy changes. In open-ended settings, it can be hard (or impossible) to write a fully static policy upfront (e.g., during debugging, one cannot know in advance which files or logs should be read, written, or executed). Therefore, dynamic policy updates are another necessary part of agent design.

然而，我们认识到这种动态设计带来了一个关键的安全挑战：外部、不受信任的数据现在可以影响计划和策略。因此，中心研究问题是区分良性计划/政策更新和恶意更新。换句话说，我们必须研究如何在重新规划和策略更新过程中做出合理的安全决策。这个问题引出了我们的第二个立场。However, we recognize that this dynamic design creates a key security challenge: external, untrusted data can now influence plans and policies.
