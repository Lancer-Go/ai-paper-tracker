摘要Abstract

LiveCodeBench (LCB) 最近已成为广泛采用的基准，用于评估代码生成任务的大型语言模型 (LLM)。通过策划竞争性编程问题、不断向集合中添加新问题并按发布日期过滤它们，LCB 提供了污染感知评估并提供了编码能力的整体视图。然而，LCB 仍然仅限于 Python，这使得法学硕士是否可以泛化现实世界软件工程所需的各种编程语言仍然是一个悬而未决的问题。LiveCodeBench (LCB) has recently become a widely adopted benchmark for evaluating large language models (LLMs) on code-generation tasks. By curating competitive programming problems, constantly adding fresh problems to the set, and filtering them by release dates, LCB provides contamination-aware evaluation and offers a holistic view of coding capability. However, LCB remains restricted to Python, leaving open the question of whether LLMs can generalize across the diverse programming languages required in real-world software engineering.

我们推出了 Multi-LCB，这是一个评估跨 12 种编程语言（包括 Python）的法学硕士的基准。 Multi-LCB 将 LCB 数据集中的 Python 任务转换为其他语言的等效任务，同时保留 LCB 的污染控制和评估协议。 由于与原始 LCB 格式完全兼容，Multi-LCB 将自动跟踪未来的 LCB 更新，从而能够系统地评估跨语言代码生成能力，并要求模型维持远远超出 Python 的性能。We introduce Multi-LCB, a benchmark for evaluating LLMs across twelve programming languages, including Python. Multi-LCB transforms Python tasks from the LCB dataset into equivalent tasks in other languages while preserving LCB’s contamination controls and evaluation protocol. Because it is fully compatible with the original LCB format, Multi-LCB will automatically track future LCB updates, enabling systematic assessment of cross-language code generation competence and requiring models to sustain performance well beyond Python.

我们评估了 24 名法学硕士在 Multi-LCB 上的指令和推理能力，发现了 Python 过度拟合、特定语言污染以及多语言性能巨大差异的证据。我们的结果将 Multi-LCB 确立为多编程语言代码评估的严格新基准，直接解决了 LCB 的主要局限性并暴露了当前 LLM 能力的关键差距。We evaluated 24 LLMs for instruction and reasoning on Multi-LCB, uncovering evidence of Python overfitting, language-specific contamination, and substantial disparities in multilingual performance. Our results establish Multi-LCB as a rigorous new benchmark for multi-programming-language code evaluation, directly addressing LCB’s primary limitation and exposing critical gaps in current LLM capabilities.

1 简介Introduction

尽管有这些优势，LCBDespite these strengths, LCB(Jain et al., 2024)仅评估 Python。虽然很方便，但这种限制忽略了软件工程的一个核心现实：开发人员通常会使用不同的编程语言，每种语言都有自己的语法、语义和惯用实践。当系统编程需要 C++、企业软件需要 Java 或 Web 开发需要 JavaScript 时，仅能够用 Python 解决问题的法学硕士可能表现不佳。因此，目前的评估留下了一个关键问题：evaluates only Python. While convenient, this limitation overlooks a central reality of software engineering: developers routinely work across diverse programming languages, each with its own syntax, semantics, and idiomatic practices. An LLM capable of solving problems exclusively in Python may perform poorly when C++ is required for systems programming, Java for enterprise software, or JavaScript for web development. 语言覆盖范围和选择。Language Coverage and Selection.Multi-LCB 涵盖 12 种编程语言，但不包括一些重要语言，如 Swift、Haskell、R 等。语言选择基于 2025 年的流行度排名，可能不反映专业领域或新兴语言。此外，某些语言具有各种方言和版本，这些方言和版本未在我们的评估框架中考虑在内。Multi-LCB covers 12 programming languages but does not include some important languages such as Swift, Haskell, R, and others. The language selection is based on popularity rankings in 2025, which may not reflect specialized domains or emerging languages. Additionally, some languages have various dialects and versions that are not accounted for in our evaluation framework.

任务复杂性和领域。Task Complexity and Domain.虽然所选的编程语言跨越不同的领域（系统编程、网络开发、数据科学），但任务本身仍然植根于竞争性编程。尽管算法问题解决与工业编码能力具有间接相关性，但 Multi-LCB 并不直接评估现实世界的软件工程场景，例如 API 集成、调试遗留代码或协作开发工作流程。While the selected programming languages span different domains (systems programming, web development, data science), the tasks themselves remain rooted in competitive programming. Although algorithmic problem-solving has indirect relevance to industrial coding capabilities, Multi-LCB does not directly assess real-world software engineering scenarios such as API integration, debugging legacy code, or collaborative development workflows.

评估协议约束。Evaluation Protocol Constraints.严格的 STDIN/STDOUT 格式可能会导致性能下降，这不仅是由于算法推理限制，还因为语法不熟悉、解析输入格式困难或未能遵循输出规范。模型可能由于格式合规性问题而不是核心问题解决缺陷而失败，这可能会混淆我们对真正的多语言编码能力的评估。The strict STDIN/STDOUT format may introduce performance degradation not only due to algorithmic reasoning limitations but also due to syntax unfamiliarity, difficulty parsing input formats, or failure to follow output specifications. Models may fail tasks due to format compliance issues rather than core problem-solving deficits, potentially confounding our assessment of true multilingual coding competence.

模型选择偏差。Model Selection Bias.我们的评估仅关注公开可用的模型，不包括可能代表当前最先进技术的专有系统。这种限制意味着我们的结果仅反映了可用模型的子集，并且可能无法准确代表多语言代码生成能力的现实世界排行榜。Our evaluation focuses exclusively on publicly available models, excluding proprietary systems that may represent the current state-of-the-art. This limitation means our results reflect only a subset of available models and may not accurately represent the real-world leaderboard of multilingual code generation capabilities.

构造有效性。Construct Validity.从函数格式到 STDIN/STDOUT 的自动转换可能会以不同的编程语言改变任务复杂性。某些语言可能更自然地适合某些问题类型，可能会产生影响跨语言比较的不平等评估条件。The automatic conversion from functional format to STDIN/STDOUT may alter task complexity differently across programming languages. Some languages may be more naturally suited for certain problem types, potentially creating unequal evaluation conditions that affect cross-language comparisons.

内部有效性。Internal Validity.尽管基于日期的过滤，隐藏形式的污染可能会通过训练数据中存在的类似问题模式或解决方案模板持续存在。此外，模型可能会因训练期间接触不同编程语言的不同而表现出时间偏差。Despite date-based filtering, hidden forms of contamination may persist through similar problem patterns or solution templates present in training data. Additionally, models may exhibit temporal bias based on varying exposure to different programming languages during their training periods.
