摘要Abstract

大型语言模型日益从文本生成器发展成为能够理解用户请求、调用外部工具并通过交互完成复杂任务的通用代理。然而，现有的代理基准测试通常关注有限的场景、工具生态系统或交互格式，因此很难系统地表征跨异构应用程序设置的模型功能。我们介绍Large language models are increasingly evolving from text generators into general agents capable of understanding user requests, invoking external tools, and completing complex tasks through interaction. However, existing agent benchmarks often focus on limited scenarios, tool ecosystems, or interaction formats, making it difficult to systematically characterize model capabilities across heterogeneous application settings. We introduceOmniaBench，用于评估具有显式状态空间的不同场景的通用代理的基准。我们从应用商店、产品文档、行业资源、Web检索和人工提炼中获取面向应用的场景知识，形成跨越ToC、ToB和ToE、90个一级域和354个二级域的分层分类法。基于这种分类法，我们构建了可执行环境，并通过四个互补的途径综合单轮和多轮任务：DAG、DAG-S、Solver 和 Program。 OmniaBench 进一步引入了十维能力分类法和八个组成原子难度因子来支持细粒度的评估和分析。生成的数据集包含 1,431 个任务，以及 644 个任务的具有挑战性的子集，旨在降低评估成本并减轻公开发布后全套任务的潜在污染。该工作台对当前的前沿模型提出了巨大的挑战，甚至 Claude-Sonnet-5 和 GPT-5.6-Sol 的总体 Pass@1 分数也分别仅为 58.54 和 57.14。进一步的分析揭示了不同领域和能力之间的明显差异，以及规划、约束维护和自适应校正方面持续存在的局限性。 OmniaBench 提供了广泛的诊断基准来表征一般代理的能力边界。, a benchmark for evaluating general agents across diverse scenarios with explicit state spaces. We derive application-oriented scenario knowledge from app stores, product documents, industry resources, Web retrieval, and human refinement, forming a hierarchical taxonomy that spans ToC, ToB and ToE with 90 level-1 and 354 level-2 domains. Based on this taxonomy, we construct executable environments and synthesize single-turn and multi-turn tasks through four complementary routes: DAG, DAG-S, Solver, and Program. OmniaBench further introduces a ten-dimensional capability taxonomy and eight compositional atomic difficulty factors to support fine-grained evaluation and analysis. The resulting dataset contains 1,431 tasks, together with a challenging subset of 644 tasks designed to reduce evaluation cost and mitigate potential contamination of the full set after public release. The bench presents substantial challenges to current frontier models, with even Claude-Sonnet-5 and GPT-5.6-Sol achieving Overall Pass@1 scores of only 58.54 and 57.14, respectively. Further analyses reveal clear differences across domains and capabilities, as well as persistent limitations in planning, constraint maintenance, and adaptive correction. OmniaBench provides a broad and diagnostic benchmark for characterizing the capability boundaries of general agents.

1 简介1 Introduction

大型语言模型（LLM）的最新进展极大地提高了它们在语言理解、复杂推理、代码生成和多轮交互方面的能力[7,10,23]。这些进步正在逐渐将法学硕士从静态文本生成器转向能够执行现实世界任务的代理系统 [8, 14]。通过函数调用、检索增强、代码执行和协调工具使用，基于LLM的代理在软件开发、信息搜索、办公自动化、业务工作流程和个人协助方面显示出强大的潜力，吸引了学术界和工业界越来越多的关注[4,12,25,26]。与传统的问答或孤立推理任务[6, 24]相比，此类代理必须在更加开放的环境中运行，它们需要了解用户意图，制定多步骤计划，调用外部工具，维护任务状态，并通过交互逐步完成用户目标。Recent advances in large language models (LLMs) have substantially improved their capabilities in language understanding, complex reasoning, code generation, and multi-turn interaction [7, 10, 23]. These advances are gradually shifting LLMs from static text generators toward agentic systems capable of executing real-world tasks [8, 14]. Enabled by function calling, retrieval augmentation, code execution, and coordinated tool use, LLM-based agents have shown strong potential in software development, information seeking, office automation, business workflows, and personal assistance, attracting increasing attention from both academia and industry [4, 12, 25, 26]. Compared with conventional question answering or isolated reasoning tasks [6, 24], such agents must operate in more open-ended settings, where they need to understand user intents, formulate multi-step plans, invoke external tools, maintain task states, and progressively complete user goals through interaction.

围绕基于法学硕士的代理人评估，先前的工作已经在几个方向上取得了实质性进展。函数调用和工具使用基准评估模型是否可以选择适当的工具、生成有效的参数、组成多个工具调用以及满足执行约束[5,13,​​18,21]。交互式基准进一步引入模拟用户、动态状态和特定领域的规则，允许代理通过与外部环境的多轮交互来完成任务[3,11,26]。最近的研究将评估扩展到开放式和现实的环境，例如长期规划、专业工作流程、网络和应用程序环境、多模式证据基础和标准化工具生态系统[1,2,9,16,19,28]。尽管取得了这些进步，现有的基准测试通常是围绕一组有限的场景、工具生态系统或任务格式来组织的，从而在基准测试覆盖范围和现实世界代理用例的多样性之间留下了差距。在实践中，通用代理预计能够跨异构应用程序和用户需求进行操作，同时处理多轮交互、不断发展的任务状态、工具执行和用户特定的约束。这就激发了对具有更广泛场景覆盖、更丰富任务形式和更多诊断评估维度的通用智能体基准的需求。Around LLM-based agent evaluation, prior work has made substantial progress along several directions. Function-calling and tool-use benchmarks evaluate whether models can select appropriate tools, generate valid arguments, compose multiple tool calls, and satisfy execution constraints [5, 13, 18, 21]. Interactive benchmarks further introduce simulated users, dynamic states, and domain-specific rules, allowing agents to complete tasks through multi-turn interaction with external environments [3, 11, 26]. More recent studies have expanded evaluation toward open-ended and realistic settings, such as long-horizon planning, professional workflows, web and application environments, multimodal evidence grounding, and standardized tool ecosystems [1, 2, 9, 16, 19, 28]. Despite these advances, existing benchmarks are often organized around a limited set of scenarios, tool ecosystems, or task formats, leaving a gap between benchmark coverage and the diversity of real-world agent use cases. In practice, general agents are expected to operate across heterogeneous applications and user needs, while handling multi-turn interaction, evolving task states, tool execution, and user-specific constraints. This motivates the need for a general-agent benchmark with broader scenario coverage, richer task forms, and more diagnostic evaluation dimensions.

为了弥补这一差距，我们引入To bridge this gap, we introduceOmniaBench，一个多场景、交互式的评估总代理的基准。 OmniaBench 旨在从现实世界的应用程序生态系统构建代理任务，涵盖广泛的用户需求和应用程序工作流程。如图 2 所示，我们从流行的应用程序商店、产品需求文档 (PRD)、网络搜索代理和人工细化中收集和组织场景知识，从而形成完整的场景分类，将现实世界的代理应用程序分组为 ToC、ToB 和 ToE 设置。基于此分类法，OmniaBench 涵盖 90 个 1 级域和 354 个 2 级域，提供了比以单一工具生态系统或一小组任务环境为中心的基准测试更广泛的域空间。我们进一步将这些域实例化为具有工具、实体、状态和初始化配置的交互式环境，并跨不同的任务形式构建用户请求。因此，模型需要了解用户目标、调用工具、跟踪不断变化的状态并通过交互完成任务。, a multi-scenario and interactive benchmark for evaluating general agents. OmniaBench aims to construct agent tasks from real-world application ecosystems, covering a broad spectrum of user needs and application workflows. As illustrated in Figure 2, we collect and organize scenario knowledge from popular app stores, product requirement documents (PRD), web-search agents, and human refinement, resulting in a full scenario taxonomy that groups real-world agent applications into ToC, ToB and ToE settings. Built upon this taxonomy, OmniaBench covers 90 level-1 domains and 354 level-2 domains, providing a substantially broader domain space than benchmarks centered on a single tool ecosystem or a small set of task environments. We further instantiate these domains into interactive environments with tools, entities, states, and initialization configurations, and construct user requests across diverse task forms. As a result, models are required to understand user goals, invoke tools, track evolving states, and complete tasks through interaction.

OmniaBench 进一步整合了用于能力测量、任务难度和诊断评估的结构化设计。我们定义了十维能力分类法，涵盖任务理解、信息收集、规划和决策、状态管理、工具使用、代码和程序化操作、数据分析、办公和文档处理、交互式协作、可靠性和安全性。这种分类法允许对评估结果进行分解，使其超出总体成功率，从而暴露出代理执行的不同阶段的模型优势和劣势。我们还引入了组合原子难度设计，它围绕用户意图、角色约束、环境状态、工具执行、多轮交互和结果验证来组织任务挑战。结合评分细则清单和基于VerifyCode的评估，OmniaBench支持对领域类别、能力维度、任务复杂性、交互轮次和错误模式进行细粒度分析，提供当前通用代理能力边界的系统视图。OmniaBench further incorporates structured designs for capability measurement, task difficulty, and diagnostic evaluation. We define a ten-dimensional capability taxonomy covering Task Understanding, Information Gathering, Planning & Decision Making, State Management, Tool Use, Code & Programmatic Operations, Data Analysis, Office & Document Handling, Interactive Collaboration, Reliability & Safety. This taxonomy allows evaluation results to be decomposed beyond overall success rates, exposing model strengths and weaknesses across distinct stages of agent execution. We also introduce a compositional atomic difficulty design, which organizes task challenges around user intent, persona constraints, environment states, tool execution, multi-turn interaction, and result verification. Together with rubric checklists and VerifyCode-based assessment, OmniaBench supports fine-grained analyses over domain categories, capability dimensions, task complexity, interaction turns, and error patterns, offering a systematic view of the capability boundaries of current general agents.

2 相关工作2 Related Work

最近对基于 LLM 的智能体的评估已逐渐从静态问答转向工具使用、环境交互和任务执行。一系列基础工具使用基准研究模型是否可以选择适当的工具、生成有效的参数、组成多个函数调用以及满足执行约束。 BFCL[18]、ACEBench[5]和ToolSandbox[15]等代表作品从函数调用、组合工具使用、有状态执行和不同调用模式的角度进行了先进的标准化评估。这些基准为评估代理工具的使用提供了重要的基础，从而能够对工具选择、论证构建和执行控制方面的模型功能进行系统分析。Recent evaluation of LLM-based agents has gradually shifted from static question answering toward tool use, environment interaction, and task execution. A line of foundational tool-use benchmarks studies whether models can select appropriate tools, generate valid arguments, compose multiple function calls, and satisfy execution constraints. Representative works such as BFCL [18], ACEBench [5], and ToolSandbox [15] have advanced standardized evaluation from the perspectives of function calling, compositional tool use, stateful execution, and different invocation patterns. These benchmarks provide important foundations for evaluating agentic tool use, enabling systematic analysis of model capabilities in tool selection, argument construction, and execution control.

OmniaBench 采用统一的基于轨迹的评估框架，并具有特定路线的验证信号。除了基于计划的数据外，每项任务均由涵盖不同目标和约束的多个评估项目进行评估，这些评估项目汇总为任务级别分数和通过/失败结果。基于程序的任务评估为OmniaBench adopts a unified trajectory-based evaluation framework with route-specific verification signals. Except for Program-based data, each task is assessed by multiple rubric items covering distinct objectives and constraints, which are aggregated into task-level scores and pass/fail outcomes. Program-based tasks are evaluated with验证码VerifyCode，它直接决定了完整轨迹和最终观察的二元结果。对于多回合任务，我们采用基于角色的用户模拟器（详见附录 E），并通过用户偏好、沟通方式、信息披露策略和不同级别的对话复杂性来控制交互难度。文件系统和编码任务在受控沙箱中执行，其中预定义的文件工具和Python执行器通过与普通工具相同的接口公开，以确保安全性和可重复性。每次运行后，系统都会生成可视化的 HTML 报告，其中整合了对话、工具调用、环境反馈、最终观察结果、评分标准和失败原因，方便人工检查和案例级分析。, which directly determines the binary outcome from the complete trajectory and final observation. For multi-turn tasks, we employ persona-grounded user simulators (detailed in Appendix E) and control interaction difficulty through user preferences, communication styles, information-disclosure strategies, and varying levels of conversational complexity. Filesystem and coding tasks are executed in controlled sandboxes, where predefined file tools and a Python executor are exposed through the same interface as ordinary tools to ensure safety and reproducibility. After each run, the system generates a visual HTML report that consolidates the dialogue, tool calls, environment feedback, final observation, rubric scores, and failure reasons, facilitating manual inspection and case-level analysis.

OmniaBench builds executable environments from a hierarchical ToB, ToC, and ToE taxonomy and constructs tasks through multiple interaction routes. Experiments on frontier models demonstrate that OmniaBench remains challenging while revealing distinct capability profiles, domain specialization, tool-use efficiency, and failure patterns. OmniaBench provides a systematic foundation for evaluating and improving general agents.

B.2 原子难度系数B.2 Atomic Difficulty Factors

除了能力覆盖范围之外，我们还使用一组原子难度因素来描述任务复杂性。能力维度描述了代理需要做什么，而难度因素则描述了相应任务为何具有挑战性。这种分离允许评估相同主要能力的任务实例化不同的困难来源，例如不明确的需求、大型结构化状态、长证据上下文、动态依赖性或不一致的信息。In addition to capability coverage, we characterize task complexity using a set of atomic difficulty factors. Capability dimensions describe what an agent is required to do, whereas difficulty factors describe why the corresponding task is challenging. This separation allows tasks that evaluate the same primary capability to instantiate different sources of difficulty, such as ambiguous requirements, large structured states, long evidence contexts, dynamic dependencies, or inconsistent information.

难度原子在环境和任务构建期间用作组合设计原语。单个任务可以组合多个原子，并且相同的原子可以出现在不同的域和数据路径上。例如，DAG 任务可以结合渐进式信息披露、状态演化和动态多步骤规划，而 Solver 任务可以结合结构化信息复杂性和冲突约束。这些原子旨在支持受控任务多样化和细粒度错误分析，而不是定义相互排斥的任务类别。表 8 总结了八个原子难度因素及其典型实例。The difficulty atoms are used as compositional design primitives during environment and task construction. A single task may combine multiple atoms, and the same atom may appear across different domains and data routes. For example, a DAG task may combine progressive information disclosure, state evolution, and dynamic multi-step planning, while a Solver task may combine structured-information complexity with conflicting constraints. D 特定路线的评估协议D Route-Specific Evaluation Protocols

OmniaBench 包含四种数据路由，具有不同的交互和验证协议。 DAG路线采用多轮交互，而Solver、Program和DAG-S在单轮设置中评估。OmniaBench contains four data routes with different interaction and verification protocols. The DAG route adopts multi-turn interaction, whereas Solver, Program, and DAG-S are evaluated in single-turn settings.

D.1 DAG：多轮交互式评估D.1 DAG: Multi-turn Interactive Evaluation

对于 DAG 任务，基于角色的用户模拟器会发起对话，并根据交互历史记录逐步提供任务相关信息。每次，被评估的代理都可以响应用户、调用工具或请求澄清。当用户模拟器发出信号时交互终止For DAG tasks, a persona-grounded user simulator initiates the conversation and progressively provides task-relevant information according to the interaction history. At each turn, the evaluated agent may respond to the user, invoke tools, or request clarification. The interaction terminates when the user simulator emits###STOP###，或者当预定义的执行预算用完时。, or when the predefined execution budget is exhausted.

DAG评估流程DAG Evaluation Flow

  1. 用户模拟器根据任务规范和角色生成初始请求。The user simulator generates the initial request from the task specification and persona.

  2. 代理通过消息和工具调用与用户和环境进行交互。The agent interacts with the user and environment through messages and tool calls.

  3. 用户模拟器会在需要时显示附加信息或提供反馈。The user simulator reveals additional information or provides feedback when required.

  4. 多个评估项目评估是否满足所有任务目标和约束。Multiple rubric items assess whether all task objectives and constraints are satisfied.

该协议不仅评估任务执行，还评估澄清、约束跟踪、对用户反馈的适应以及多个回合的状态维护。This protocol evaluates not only task execution, but also clarification, constraint tracking, adaptation to user feedback, and state maintenance across multiple turns.

D.2 求解器和 DAG-S：单轮评估D.2 Solver and DAG-S: Single-turn Rubric Evaluation

求解器和 DAG-S 任务在轨迹开始时提供完整的用户请求。代理可以调用​​多个工具，但在初始请求之后不会引入额外的用户反馈。当代理提交其最终响应时，执行终止。Solver and DAG-S tasks provide the full user request at the beginning of the trajectory. The agent may invoke multiple tools, but no additional user feedback is introduced after the initial request. Execution terminates when the agent submits its final response.

两条路线均使用多个评估项目进行评估。每个项目对应于一个具体的任务目标或约束，并收到其分配的分数或零。仅当所有标题项均得到满足时，任务才被视为成功。求解器任务还强调约束满足以及生成的决策与底层规划、分配、调度或优化目标的一致性。Both routes are evaluated using multiple rubric items. Each item corresponds to a concrete task objective or constraint and receives either its assigned score or zero. A task is considered successful only when all rubric items are satisfied. Solver tasks additionally emphasize constraint satisfaction and the consistency of the produced decision with the underlying planning, allocation, scheduling, or optimization objective.

D.3 程序：单轮程序验证D.3 Program: Single-turn Programmatic Verification

程序任务也遵循单轮协议，但使用程序化验证而不是基于规则的判断。完成所需的工具交互后，代理提交最终响应。相关的Program tasks also follow a single-turn protocol, but use programmatic verification instead of rubric-based judgment. After completing the required tool interactions, the agent submits its final response. E角色设计E Persona Design

角色在 DAG 任务中用于创建多样化且真实的用户行为。每个角色指定三组属性：Personas are used in DAG tasks to create diverse and realistic user behaviors. Each persona specifies three groups of attributes:

  • 核心身份Core identity：职业角色、背景、人生阶段；: professional role, background, and life stage;

  • 交互特点Interaction characteristics：表达风格、情绪倾向、信息披露策略、决策偏好、耐心；: expression style, emotional tendency, information-disclosure strategy, decision preference, and patience;

  • 现实世界的限制Real-world constraints：时间、预算、隐私和其他与场景相关的考虑因素。: time, budget, privacy, and other scenario-dependent considerations.

这些属性控制用户如何表达请求、揭示缺失的信息、响应澄清以及确定交互是否应该继续。These attributes control how the user expresses requests, reveals missing information, responds to clarification, and determines whether the interaction should continue.
