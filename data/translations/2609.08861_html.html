API 基准分数无法可靠地传输到聊天机器人界面API Benchmark Scores Do Not Reliably Transfer to Chatbot Interfaces

Jennifer WangJoachim Baumann    Daniel E. Ho Affiliation: Equal senior authorship    Sanmi KoyejoStanford UniversityStanford, CA, USA Email: jennjwang,joachimbaumann,deho,sanmi@stanford.edu Affiliation: Equal senior authorship
摘要Abstract

基准分数是模型发布中的核心货币：它们为购买决策提供信息，塑造公众信任并影响政策。然而，基准分数背后的一个关键假设是，通过 API 测量的模型性能忠实地反映了已部署系统的行为。Benchmark scores are a central currency in model releases: they inform purchasing decisions, shape public trust, and influence policy. Yet, a key assumption underlying benchmark scores is that the model performance measured through APIs faithfully reflects the behavior of deployed systems.

我们通过审核 ChatGPT、Claude 和 Gemini 的七个系统和九个涵盖一般能力、社会偏见和阿谀奉承的基准来挑战这一假设。 我们发现系统性 API 接口在准确性和一致性方面存在差异。 平均而言，API 评估的准确率比相应的接口评估高 3.4 个百分点，重测一致性高 2.1 个百分点。 对于 ChatGPT，API 和接口访问之间的性能差异超过了 GPT 5.3 和 GPT 5.4 之间仅 API 的差异。换句话说，切换访问表面会降低性能，就像降低整个模型生成的性能一样。We challenge this assumption by auditing ChatGPT, Claude, and Gemini across seven systems and nine benchmarks spanning general capability, social bias, and sycophancy. We find systematic API–interface differences in both accuracy and consistency. On average, API evaluations score 3.4 percentage points higher in accuracy and 2.1 percentage points higher in test–retest agreement than corresponding interface evaluations. For ChatGPT, the performance difference between API and interface access exceeds the API-only difference between GPT 5.3 and GPT 5.4. Put differently, switching access surfaces can degrade performance as much as downgrading a full model generation.

我们进一步测试公开的 API 控件是否可以通过改变系统提示、采样参数和推理设置来重现界面行为。这些控制措施在某些情况下会改变行为，但不能可靠地消除差距。 我们的研究结果记录了上下文有效性差距：通过 API 获得的测量结果不一定能推广到相应的已部署接口，这使得使用 API 评估作为已部署系统的代理变得复杂化。We further test whether exposed API controls can reproduce interface behavior by varying system prompts, sampling parameters, and reasoning settings. These controls shift behavior in some cases but do not reliably eliminate the gap. Our findings document a context-validity gap: measurements obtained through APIs do not necessarily generalize to corresponding deployed interfaces, complicating the use of API evaluations as proxies for deployed systems.

3.4 实验对照Experimental Controls

由于商业聊天机器人平台不会公开其完整的请求管道，因此观察到的接口-API 差异可能反映了不相关的混淆。我们解决了杂散变异的五个潜在来源。As commercial chatbot platforms do not expose their full request pipeline, observed interface–API differences could reflect unrelated confounds. We address five potential sources of spurious variation.

请求路由。Request routing.

平台可能会将不同的帐户、会话或请求路由到不同的模型变体，而无需披露。我们固定了两个可观察的路由因素：所有请求都从同一网络发出，并且所有帐户都使用相同的订阅层。这些控制并不排除未观察到的路由机制，例如 A/B 测试。我们在附录中进行额外的稳健性检查Platforms may route different accounts, sessions, or requests to different model variants without disclosure. We hold fixed two observable routing factors: all requests are issued from the same network, and all accounts use the same subscription tier. These controls do not rule out unobserved routing mechanisms, such as A/B testing. We run additional robustness checks in AppendixH测试我们的主要发现是否对帐户和请求级别的分配敏感。to test whether our main findings are sensitive to account- and request-level assignments.

会话级个性化。Session-level personalization.

我们禁用所有面向用户的个性化功能，例如聊天记录和内存。但是，平台仍可能根据这些设置之外的会话级信号（例如会话令牌、浏览器指纹）来调节响应。为了缓解这个问题，我们在一个新的浏览器实例中发出每个查询，没有持久性 cookie、本地存储、对话历史记录或跨试验的浏览器状态。We disable all user-facing personalization features, such as chat history and memory. However, platforms may still condition responses on session-level signals beyond these settings (e.g., session tokens, browser fingerprint). To mitigate this, we issue each query in a fresh browser instance with no persistent cookies, local storage, conversation history, or browser state carried across trials.

工具调用。Tool Invocation.

聊天机器人系统经常调用网络搜索等外部工具，这可能会对输出产生重大影响。对于 ChatGPT 和 Claude，我们禁用了所有特定于平台的工具。对于无法禁用网络搜索的 Gemini，我们在前面添加了一条指令，要求模型不要使用网络搜索（请参阅附录Chatbot systems often invoke external tools such as web search, which can materially affect outputs. For ChatGPT and Claude, we disabled all platform-specific tools. For Gemini, where web search could not be disabled, we prepended an instruction asking the model not to use web search (see AppendixE.3).

时间漂移。Temporal drift.

持续的模型更新意味着不同时间收集的接口和API响应可能反映不同的模型版本。为了最大限度地降低这种风险，我们同步每个基准项目的请求。每个查询的屏障保留所有并行会话（每个模型和条件一个，包括 API 工作线程），直到每个会话选择了适当的模型、打开新的聊天或请求上下文并准备好提示。一旦所有会话达到此状态，就会在几秒钟内跨条件提交提示。Continuous model updates mean that interface and API responses collected at different times may reflect different model versions. To minimize this risk, we synchronize requests for each benchmark item. A per-query barrier holds all parallel sessions—one per model and condition, including API workers—until each session has selected the appropriate model, opened a fresh chat or request context, and prepared the prompt. Once all sessions reached this state, the prompts are submitted across conditions within seconds.

输出标准化。Output Normalization.

界面响应是通过 Markdown、引文和 UI chrome 呈现的，而 API 响应是原始文本。为了防止表面形状差异影响评分，我们将界面输出剥离为纯文本，并将这两个条件通过相同的特定于基准的提取和评分管道。Whereas interface responses are rendered with Markdown, citations, and UI chrome, API responses are raw text. To prevent surface-form differences from affecting scoring, we strip interface outputs to plain text and pass both conditions through the same benchmark-specific extraction and grading pipeline.

6 讨论Discussion

6.1 访问表面决定了评估声明的范围Access Surface Shapes the Scope of Evaluation Claims

基准分数是特定于评估环境的测量。我们的研究结果表明，这种背景很重要：七个系统的 API 和接口评估在准确性和一致性方面存在差异。先前的工作表明，基准分数对评估选择（例如提示格式、答案选项和系统指令）很敏感Benchmark scores are measurements specific to evaluation contexts. Our findings show that this context matters: API and interface evaluations diverge in accuracy and consistency across seven systems. Prior work shows that benchmark scores are sensitive to evaluation choices such as prompt formatting, answer options, and system instructions(salinas-morstatter-2024-butterfly; baumann2025large; sclar2024quantifying)。 我们的研究结果将这种担忧延伸到了访问面：即使使用相同的基准项目和评分程序，API 和接口评估也可能产生不同的结果。. Our findings extend this concern to the access surface: even with identical benchmark items and scoring procedures, API and interface evaluations can produce different results.

这些差异限制了 API 评估作为部署代理的使用 聊天机器人的行为。尽管 API 评估仍然是有关受控条件下模型行为的有用证据，但其结果描述了测试的 API 配置的特征，并且不会直接转移到已部署的产品。这种限制与个性化研究尤其相关。 交互和 AI 介导的用户体验，其中 API 评估可以模拟 面向用户的条件，无需复制部署中活动的产品层 界面。因此，在没有证据表明结果在不同访问界面上保持稳定的情况下，研究人员应避免将 API 结果推广到面向用户的产品行为。因此，基准测试报告应记录获得分数的访问路径和部署上下文。These differences limit the use of API evaluations as proxies for deployed chatbot behavior. Although API evaluations remain useful evidence about model behavior under controlled conditions, their findings characterize the tested API configuration and do not transfer directly to the deployed product. This limitation is especially relevant to research on personalized interaction and AI-mediated user experience, where API evaluations may simulate user-facing conditions without reproducing the product layers active in the deployed interface. Researchers should therefore avoid generalizing from API results to user-facing product behavior without evidence that the findings are stable across access surfaces. Accordingly, benchmark reports should document the access path and deployment context in which the score was obtained.

我们无法使用公开的 API 控件重现界面行为，这揭示了当前审计基础设施中的差距。 API 评估是可扩展的，但仅公开提供者提供的内容。接口审核针对已部署的行为，但很脆弱且难以重现。 两者都没有提供模型端点和响应之间的“中间层”（路由、检索、工具策略、个性化和后处理）的可审核视图Our inability to reproduce interface behaviors using exposed API controls reveals a gap in the current audit infrastructure. 7 局限性Limitations

这些结论有几个局限性。首先，我们无法验证匹配的 API 和接口标识符是否始终对应于相同的底层检查点；如果提供商跨表面提供不同的变体，则观察到的一些差距可能反映模型差异而不是界面层效应。其次，我们评估每个平台的单个订阅层，因此基于层的路由可能会为其他用户产生不同的差距。第三，我们的测量依赖于标准化基准，而不是自然的聊天机器人交互。系统组件可能会与更长、更多会话输入进行不同的交互。第四，审计涵盖三个提供商和七个模型，因此调查结果可能无法推广到其他提供商、未来版本或通过不同接口提供服务的开源模型。最后，我们的审计依赖于以编程方式查询平台接口。由于平台服务条款可能会限制浏览器自动化，因此外部研究人员在复制或扩展此类审核时可能会面临实际或法律限制。Several limitations qualify these conclusions. First, we cannot verify that matched API and interface identifiers always correspond to the same underlying checkpoint; if providers serve different variants across surfaces, some of the observed gap may reflect model differences rather than interface-layer effects. Second, we evaluate a single subscription tier per platform, so tier-based routing may produce different gaps for other users. Third, our measurements rely on standardized benchmarks rather than natural chatbot interactions. System components may interact differently with longer, more conversational inputs. Fourth, the audit covers three providers and seven models, so the findings may not generalize to other providers, future releases, or open-source models served through different interfaces. Finally, our audit relies on programmatically querying platform interfaces. Because platform terms of service may restrict browser automation, external researchers may face practical or legal constraints when reproducing or extending this kind of audit.

8 道德考虑Ethical Considerations

在这项工作中，我们以编程方式收集了已部署的聊天机器人界面的输出。由于这种形式的接口审核必然与实时商业系统进行交互，因此我们设计审核的目的是最大限度地减少提供商的负担并降低用户和平台的风险。我们的工作不涉及与真实用户或敏感或私人数据的任何交互。In this work, we programmatically collected outputs from deployed chatbot interfaces. Because this form of interface auditing necessarily interacts with live commercial systems, we designed the audit to minimize burden on providers and reduce risks to users and platforms. Our work did not involve any interactions with real users or with sensitive or private data.

为了避免施加过多的负载，我们将吞吐量限制为每三小时窗口 150 个查询，并在任何速率限制事件后施加两小时的冷却时间。尽管如此，平台服务条款可能会限制浏览器自动化，即使是出于研究目的。这给界面审计带来了实质性的限制：虽然该方法对于理解面向用户的行为很重要，但其他研究人员在复制或扩展这项工作时可能会面临法律或实际障碍。因此，我们发布了随附的自动化工具，其中包含负责任的使用指南，强调速率限制、遵守适用条款和法律以及避免敏感和专有数据收集。To avoid imposing excessive load, we capped throughput at 150 queries per three-hour window and imposed a two-hour cooldown after any rate-limit event. Still, platform terms of service may restrict browser automation, even for research purposes. This creates a substantive limitation for interface auditing: while the method is important for understanding user-facing behavior, other researchers may face legal or practical barriers when reproducing or extending this work. We therefore release the accompanying automation tool with responsible-use guidance emphasizing rate limiting, compliance with applicable terms and laws, and avoidance of sensitive and proprietary data collection.
