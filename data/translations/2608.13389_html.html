摘要Abstract

企业安全拓扑设计在设备配置之前开始。架构师必须将业务意图、监管要求和风险假设转化为区域、边界设备、区域间路径和访问控制策略。现有的 NetOps 自动化工具大多在该设计修复后运行：它们将策略转换为配置或解释现有图表，但为根据未指定的自然语言请求生成结构化安全拓扑提供有限的支持。Enterprise security topology design begins before device configuration. Architects must translate business intent, regulatory requirements, and risk assumptions into zones, boundary devices, inter-zone paths, and access-control policies. Existing NetOps automation tools mostly operate after this design has been fixed: they translate policies into configurations or interpret existing diagrams, but provide limited support for producing a structured security topology from an underspecified natural-language request.

我们描述We describe拓扑意图TopoIntent，一个将安全意图编译成可执行的、经过合规性检查的网络拓扑的系统。 TopoIntent 使用模式契约来约束拓扑生成，通过密集向量搜索从精选模板库中检索参考架构，并应用分阶段融合将意图模板对齐与 IG 级安全完成分开。然后，它根据 CIS Controls v8.1.2 防护措施检查生成的拓扑，其证据在拓扑层可见，记录需要手动审查的案例，并通过附加模式保留编辑修复结构间隙。最终的拓扑被导出到内核级的 Mininet 脚本中, a system that compiles security intent into executable, compliance-checked network topologies. TopoIntent uses a schema contract to constrain topology generation, retrieves reference architectures from a curated template library through dense-vector search, and applies staged fusion to separate intent-template alignment from IG-level security completion. It then checks the generated topology against CIS Controls v8.1.2 safeguards whose evidence is visible at the topology layer, records cases requiring manual review, and repairs structural gaps through additive schema-preserving edits. The final topology is exported to Mininet scripts with kernel-leveliptablesACL，以便可以执行可达性和允许/拒绝行为，而不是仅作为静态图进行检查。ACLs, so that reachability and allow/deny behavior can be exercised rather than inspected only as a static diagram.

我们根据参考安全架构图构建评估集，因为此需求到拓扑任务不存在公共基准。检索参考集包含跨五个场景的 22 个模板和 44 个合成意图；保留的评估集包含 7 个模板和 14 个来自检索索引之外的金融和政府情景的意图。我们通过结构覆盖、拓扑可见 CIS 满意度、Mininet 策略测试以及从第 5 阶段到第 4 阶段的诊断反馈来评估 TopoIntent。在保留集上，附加修复平均在不到 1.5 轮的时间内将首次通过的拓扑可见 CIS 满意度从 0.78/0.78 (IG2/IG3) 提高到 1.00。在端到端消融中，一轮反馈将 ACL 后政策通过率从 0.78 提高到 0.88。We build an evaluation set from reference security architecture diagrams because no public benchmark exists for this requirement-to-topology task. The retrieval reference set contains 22 templates and 44 synthetic intents across five scenarios; the held-out evaluation set contains 7 templates and 14 intents from finance and government scenarios excluded from the retrieval index. We evaluate TopoIntent with structural coverage, topology-visible CIS satisfaction, Mininet policy tests, and diagnostic feedback from Stage 5 to Stage 4. On the held-out set, additive repair raises first-pass topology-visible CIS satisfaction from 0.78/0.78 (IG2/IG3) to 1.00 in fewer than 1.5 rounds on average. In the end-to-end ablation, one feedback round raises the post-ACL policy pass rate from 0.78 to 0.88.

I 简介Introduction

企业网络安全设计在很大程度上仍然是一项手动工程任务。在部署网络之前，安全架构师必须将组织要求（例如监管暴露、业务功能和风险承受能力）转变为具有明确区域、边界设备、访问控制路径和监控点的拓扑。该设计还必须根据 CIS 控制等安全框架进行检查Enterprise network security design is still largely a manual engineering task. Before a network is deployed, security architects must turn organizational requirements—for example, regulatory exposure, business functions, and risk tolerance—into a topology with explicit zones, boundary devices, access-control paths, and monitoring points. The design also has to be checked against security frameworks such as CIS Controls[3]。在实践中，工程师起草图表，将其与合规性检查表进行比较，识别缺失的控制，并通过多次迭代修改设计。随着企业网络变得更大并且合规义务变得更加具体，这项工作缓慢、昂贵并且难以扩展。. In practice, engineers draft diagrams, compare them with compliance checklists, identify missing controls, and revise the design over multiple iterations. This work is slow, expensive, and difficult to scale as enterprise networks become larger and compliance obligations become more specific.

法学硕士最近被用于网络管理任务，包括将自然语言意图转换为设备配置LLMs have recently been used for network management tasks, including translating natural-language intents into device configurations[18, 14, 21, 17]，生成基于NETCONF/YANG的配置, generating NETCONF/YANG-based configurations[8]，并通过多代理工作流程支持网络操作, and supporting network operations through multi-agent workflows[20]。这些系统主要解决实现阶段：假设架构存在，并且模型帮助生成或修改设备级工件。早期的设计阶段仍然较少被探索。仅考虑到业务级要求，仍然没有标准方法来综合完整的安全区域拓扑、检查其结构合规性义务以及测试生成的连接和策略工件是否按预期运行。. These systems mainly address the implementation stage: the architecture is assumed to exist, and the model helps produce or modify device-level artifacts. The earlier design stage remains less explored. Given only a business-level requirement, there is still no standard way to synthesize a complete security-zone topology, check its structural compliance obligations, and test whether the resulting connectivity and policy artifacts behave as intended.

这种区别很重要。现有的意图驱动网络工具在已知架构中工作This distinction matters. Existing intent-driven networking tools work within a known architecture[18, 14, 21]。丙烷等正式合成系统. Formal synthesis systems such as Propane[1], 丙烷/AT, Propane/AT[2]和网络完成, and NetComplete[6]将正式规范作为输入并综合路由配置，而不是安全架构。基因网take formal specifications as input and synthesize routing configurations, not security architectures. GeNet[9]接受拓扑图并协助工程师修改它们，但它不是从自由形式的要求开始，也不包括合规性检查。我们研究一个不同的问题：如何从自然语言生成安全拓扑，保留用户意图，根据结构合规性约束检查拓扑，并在可执行环境中验证生成的可达性和访问控制行为。accepts topology diagrams and assists engineers in modifying them, but it does not start from a free-form requirement and does not include compliance checking. We study a different problem: how to generate a security topology from natural language, preserve the user intent, check the topology against structural compliance constraints, and validate the generated reachability and access-control behavior in an executable environment.

困难有两个来源。首先，自然语言要求通常是不完整的。请求可以指定一个扇区和一些关键服务，但忽略安全设计通常需要的 DMZ、管理平面、监控点或边界执行设备。其次，必要的设计知识分布在参考架构和合规性文档中。因此，一个有用的系统必须结合意图理解、设计先验、合规性约束和可执行验证，而不能将任务简化为单个不受约束的 LLM 生成步骤。The difficulty comes from two sources. First, natural-language requirements are often incomplete. A request may specify a sector and a few critical services, but omit the DMZ, management plane, monitoring points, or boundary enforcement devices that a secure design would normally require. Second, the necessary design knowledge is distributed across reference architectures and compliance documents. A useful system must therefore combine intent understanding, design priors, compliance constraints, and executable validation without reducing the task to a single unconstrained LLM generation step.

我们呈现We present拓扑意图TopoIntent，一个 LLM 辅助系统，用于基于意图的安全拓扑生成和合规性检查。 TopoIntent 遵循类似编译器的工作流程：它将用户意图解析为模式管理的拓扑契约，从策划的模板库中检索相关参考架构，将检索到的模板与用户意图融合，根据拓扑可见的 CIS Controls v8.1.2 要求检查结果，通过诊断反馈修复结构间隙，并将拓扑导出到 Mininet, an LLM-assisted system for intent-based security topology generation and compliance checking. TopoIntent follows a compiler-like workflow: it parses user intent into a schema-governed topology contract, retrieves relevant reference architectures from a curated template library, fuses retrieved templates with the user intent, checks the result against topology-visible CIS Controls v8.1.2 requirements, repairs structural gaps through diagnostic feedback, and exports the topology to Mininet[12]用于可达性和 ACL 验证。输出不仅是类似图表的拓扑，而且是一组可检查的工件：JSON/XML 拓扑记录、生成的策略、合规性决策、修复历史记录、可视化和可执行测试。for reachability and ACL validation. The output is not only a diagram-like topology, but a set of inspectable artifacts: JSON/XML topology records, generated policies, compliance decisions, repair history, visualization, and executable tests.

II 预赛Preliminaries

Ⅱ-AII-A 基于安全区域的网络架构Security Zone-Based Network Architecture

安全区域（也称为安全域或网段）是网络的逻辑分区，其中设备和服务共享公共安全策略、信任级别和访问控制状态A security zone (also referred to as a security domain or network segment) is a logical partition of a network in which devices and services share a common security policy, trust level, and access control posture[15]。基于区域的网络设计是推荐的基本方法 用于构建企业和机构网络的主要安全框架：网络不是应用扁平的、仅限外围的防御，而是划分为多个区域，例如面向互联网的区域 非军事区 (DMZ)、内部办公区域、数据中心区域和管理区域，每个区域均由防火墙和入侵防御系统 (IPS) 等边界执行设备分隔。. Zone-based network design is the foundational approach recommended by major security frameworks for structuring enterprise and institutional networks: rather than applying flat, perimeter-only defenses, the network is partitioned into multiple zones—such as an internet-facing demilitarized zone (DMZ), an internal office zone, a data center zone, and a management zone—each separated by boundary enforcement devices such as firewalls and intrusion prevention systems (IPS).

A 安全拓扑security topology指定 (i) 安全区域集及其逻辑边界，(ii) 区域边界安全设备的类型和位置，(iii) 管理允许或拒绝哪些流量的区域间访问控制策略，以及 (iv) 分配给每个区域的节点（服务器、端点、安全设备）。设计合规的安全拓扑需要将组织要求和监管要求同时转化为所有四个结构维度，这项任务需要深厚的领域专业知识和系统的合规知识。specifies (i) the set of security zones and their logical boundaries, (ii) the types and placement of security devices at zone boundaries, (iii) the inter-zone access control policies governing which traffic is permitted or denied, and (iv) the nodes (servers, endpoints, security appliances) assigned to each zone. Designing a compliant security topology requires translating organizational requirements and regulatory mandates into all four of these structural dimensions simultaneously—a task that demands both deep domain expertise and systematic compliance knowledge.

VI 讨论和限制Discussion and Limitations

TopoIntent 表明，自然语言安全要求可以转化为模式管理的拓扑，根据一系列 CIS 派生的结构保护措施进行检查，并在可执行网络模拟器中执行。其贡献是将设计任务分解为可检查的步骤：基于契约的拓扑综合、模板接地、结构修复和策略验证。应考虑当前系统的几个边界。TopoIntent shows that natural-language security requirements can be turned into schema-governed topologies, checked against a scoped set of CIS-derived structural safeguards, and exercised in an executable network emulator. The contribution is the decomposition of the design task into inspectable steps: contract-based topology synthesis, template grounding, structural repair, and policy validation. Several boundaries of the current system should be kept in view.

合规声明的范围。Scope of compliance claims.CIS Controls v8.1.2 用作规范源，但 TopoIntent 不证明组织完全符合 CIS。依赖于清单、程序、漏洞管理记录、培训或实时配置审核的控制位于拓扑层之外。因此，报告的 CIS 率仅涉及选定的安全措施，其证据可以在生成的拓扑中表示。CIS Controls v8.1.2 is used as a normative source, but TopoIntent does not certify full organizational CIS compliance. Controls depending on inventories, procedures, vulnerability-management records, training, or live configuration audits are outside the topology layer. The reported CIS rates therefore refer only to the selected safeguards whose evidence can be represented in the generated topology.

LLM判决。LLM judgments.该管道通过模式、重试、标准化、确定性后处理、多模型数据集构建和持久证据记录来约束 LLM 输出。尽管如此，检查和修复阶段仍可能会出现判断错误，特别是当拓扑仅微弱地暗示安全措施时。一个自然的扩展是，一旦每个保障措施的结构解释被固定，就用确定性图和策略谓词替换更多的检查。The pipeline constrains LLM outputs with schemas, retries, normalization, deterministic post-processing, multi-model dataset construction, and persistent evidence records. Still, the checker and repair stages can make judgment errors, especially when a safeguard is only weakly implied by a topology. A natural extension is to replace more of these checks with deterministic graph and policy predicates once the structural interpretation of each safeguard is fixed.

仿真保真度。Emulation fidelity.Mininet 验证为路径和允许/拒绝策略行为提供可执行证据，但它不是生产部署。模拟器将节点表示为 Linux 命名空间，将策略表示为Mininet validation gives executable evidence for paths and allow/deny policy behavior, but it is not a production deployment. The emulator represents nodes as Linux namespaces and policies asiptables规则。这足以检查生成的拓扑和生成的策略表之间的一致性，但它不会对状态防火墙语义、云控制平面、专有设备或应用程序层检查进行建模。rules. This is sufficient for checking consistency between the generated topology and the generated policy table, but it does not model stateful firewall semantics, cloud control planes, proprietary appliances, or application-layer inspection.

数据集规模。Dataset scale.当前的数据集有意保留在场景级别，以减少检索泄漏，但仍然适度。这些实验应被视为生成安全拓扑需求的可审核的第一个基准，而不是对企业架构的全面覆盖。更大的评估应该包括更多的部门、更大的图表、真正的从业者编写的要求以及对合规标签的独立专家审查。The current dataset is intentionally held out at the scenario level to reduce retrieval leakage, but it remains modest. The experiments should be read as an auditable first benchmark for requirement-to-security-topology generation, not as full coverage of enterprise architectures. Larger evaluations should include more sectors, larger diagrams, real practitioner-written requirements, and independent expert review of the compliance labels.

添加剂修复。Additive repair.附加修复保留了来源，因为用户指定的拓扑元素不会被静默删除。权衡是，当检查器保守时，系统可能会添加冗余设备或链路。 TopoIntent 通过请求最少的添加、拒绝无效元素和记录差异来限制这一点，但未来的版本应该增加明确的修复成本或图形编辑惩罚。Additive repair preserves provenance because user-specified topology elements are not silently deleted. The tradeoff is that the system may add redundant devices or links when the checker is conservative. TopoIntent limits this by requesting minimal additions, rejecting invalid elements, and recording diffs, but future versions should add explicit repair costs or graph-edit penalties.

反馈收敛。Feedback convergence.第 5 阶段反馈提供了有用的诊断，但并不能保证一轮就能通过每项政策测试。一些失败来自于相互矛盾的测试用例、未明确说明的意图或需要人类判断的设计选择。在这些情况下，系统应该暴露冲突，而不是强制进行不安全的自动修复。Stage 5 feedback supplies useful diagnostics, but it does not guarantee that one round will make every policy test pass. Some failures come from contradictory test cases, underspecified intent, or design choices that require human judgment. In these cases the system should expose the conflict rather than force an unsafe automatic repair.

七VII结论Conclusion

我们推出了 TopoIntent，这是一个用于将自然语言安全意图编译为可执行的、经过合规性检查的网络拓扑的系统。该系统将自由格式的需求转换为模式管理的拓扑契约，使用检索到的参考架构进行生成，根据一组范围内的 CIS Controls v8.1.2 防护措施修复结构间隙，并验证 Mininet/ 中的可达性和 ACL 行为We presented TopoIntent, a system for compiling natural-language security intent into executable, compliance-checked network topologies. The system converts free-form requirements into a schema-governed topology contract, grounds generation with retrieved reference architectures, repairs structural gaps against a scoped set of CIS Controls v8.1.2 safeguards, and validates reachability and ACL behavior in Mininet/iptables。该设计将静态拓扑生成与可执行证据联系起来，同时将拓扑、合规性决策、修复和策略测试保留为单独的可检查工件。在保留的评估集上，增材修复将拓扑可见的 CIS 满意度从 0.78/0.78 (IG2/IG3) 提高到 1.00，端到端消融显示，一轮第 5 阶段反馈将 ACL 后通过率从 0.78 提高到 0.88。结果表明，从需求到安全拓扑的生成可以被视为端到端设计工作流程，同时还明确了结构检查结束和生产级部署验证必须开始的位置。. This design links static topology generation with executable evidence while keeping topology, compliance decisions, repairs, and policy tests as separate inspectable artifacts. On the held-out evaluation set, additive repair raises topology-visible CIS satisfaction from 0.78/0.78 (IG2/IG3) to 1.00, and the end-to-end ablation shows that one Stage 5 feedback round raises post-ACL pass rate from 0.78 to 0.88. The results suggest that requirement-to-security-topology generation can be treated as an end-to-end design workflow, while also making clear where structural checking ends and production-grade deployment validation must begin.
