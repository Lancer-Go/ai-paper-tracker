PSI：共享状态作为个人人工智能代理中相干人工智能生成工具的缺失层PSI: Shared State as the Missing Layer for Coherent AI-Generated Instruments in Personal AI Agents

Zhiyuan Wang University of VirginiaCharlottesvilleVirginiaUSA vmf9pr@virginia.edu , Erzhen Hu University of VirginiaCharlottesvilleVirginiaUSA eh2qs@virginia.edu , Mark Rucker University of VirginiaCharlottesvilleVirginiaUSA mr2an@virginia.edu and Laura Barnes University of VirginiaCharlottesvilleVirginiaUSA lb3dp@virginia.edu
摘要。Abstract.

现在可以根据自然语言请求生成个人人工智能工具，但它们在创建后通常保持孤立状态。我们提出了 PSI，一种共享状态架构，它将独立生成的模块转变为一致的工具：通过 GUI 和通用聊天代理可访问的持久、连接和聊天补充工件。通过将当前状态和回写功能发布到共享个人上下文总线，模块可以实现跨模块推理和跨接口的同步操作。 我们通过在自主开发的个人人工智能环境中进行为期三周的自传式部署来研究 PSI，并表明后来生成的工具可以通过同一合约自动集成。 PSI 将共享状态视为缺失的系统层，它将人工智能生成的个人软件从孤立的应用程序转变为连贯的个人计算环境。Personal AI tools can now be generated from natural-language requests, but they often remain isolated after creation. We present PSI, a shared-state architecture that turns independently generated modules into coherent instruments: persistent, connected, and chat-complementary artifacts accessible through both GUIs and a generic chat agent. By publishing current state and write-back affordances to a shared personal-context bus, modules enable cross-module reasoning and synchronized actions across interfaces. We study PSI through a three-week autobiographical deployment in a self-developed personal AI environment and show that later-generated instruments can be integrated automatically through the same contract. PSI identifies shared state as the missing systems layer that transforms AI-generated personal software from isolated apps into coherent personal computing environments.

1. 简介Introduction

人们越来越依赖不断发展的个人数字工具生态系统：记录锻炼和睡眠的健康应用程序、跟踪时间和付款的停车服务、日历、位置轨迹、可穿戴传感器以及用于日常生活的轻型仪表板。每个工具单独使用时都很有用，但日常个人工作很少停留在单个应用程序中，并且许多数据是互连的。一个简单的情境问题，例如“People increasingly rely on a growing ecosystem of personal digital tools: health apps that log workouts and sleep, parking services that track time and payments, calendars, location traces, wearable sensors, and lightweight dashboards for everyday routines. Each tool is useful in isolation, yet everyday personal work rarely stays within a single application, and many data is interconnected. A simple situated question such as “我现在的心率是否太高？Is my heart rate too high right now?”可能需要结合最近的锻炼活动、当前的运动、睡眠质量，甚至上下文信号，例如用户是否仍在走回即将到期的停车位。 困难并不在于任何单个信号不可用；而是在于。这些信号在应用程序、服务和界面中仍然是分散的。” may require combining recent workout activity, current motion, sleep quality, and even contextual signals such as whether the user is still walking back to an expiring parking spot. The difficulty is not that any single signal is unavailable; it is that these signals remain fragmented across apps, services, and interfaces.

这种碎片化是个人信息学中长期存在的问题This fragmentation is a long-standing problem in personal informatics(Li et al., 2010; Epstein et al., 2015; Choe et al., 2014)。最近的人工智能编码代理使得人们越来越有可能根据自然语言意图生成轻量级、高度个性化的工具，但仅生成并不能解决集成问题。如果每个生成的工件都成为另一个孤立的应用程序，则个人软件会在数量上扩展，而不是在一致性上扩展. Recent AI coding agents make it increasingly plausible for one person to generate lightweight, highly personalized tools from natural-language intent, but generation alone does not solve the integration problem. If each generated artifact becomes another siloed app, personal software scales in quantity rather than coherence(Li et al., 2017, 2019; Ko et al., 2011; Nardi, 1993).

PSI adopts the intuition that chat should not be the only interface to personal AI, but pushes it toward an architectural claim: persistent GUI instruments and chat become complementary only when they operate over the same underlying state.

之前的系统支持个人人工智能工作流程的各个部分——生成、传感、自动化或对话访问——但在创建后体验就会崩溃，因为这些功能仍然是孤立的。 PSI介绍Prior systems support pieces of the personal AI workflow—generation, sensing, automation, or conversational access—but the experience breaks down after creation because these capabilities remain isolated. PSI introduces仪器instruments：持久的、连接的、聊天补充的工件，通过共享的个人上下文基础和提供商合同来解决这个缺失的层，让独立创建的模块能够互操作并通过 GUI 界面和聊天保持可访问性。: persistent, connected, chat- complementary artifacts that address this missing layer through a shared personal-context substrate and provider contract, letting independently created modules interoperate and remain accessible through both GUI surfaces and chat.

3.2. PSI架构PSI Architecture

PSI 由三层组成：用于编写模块的生成层、构建在共享个人上下文总线上的运行时层以及通过持久工具和聊天代理公开模块状态的交互层。PSI consists of three layers: a generation layer for authoring modules, a runtime layer built on the shared personal-context bus, and an interaction layer that exposes module state through both persistent instruments and a chat agent.

3.2.1. 生成层Generation Layer

PSI 支持代理编码工作流程，而不是固定的应用程序目录。模块是通过多阶段管道生成的，包括规范、代码生成、自动修复和编译验证。 架构贡献不是管道本身，而是每个生成的模块必须满足的提供者合同。正式合约是一个单一的 Swift 协议（PSI enables an agentic coding workflow rather than a fixed application catalog. Modules are generated through a multi-phase pipeline, consisting of specification, code generation, auto-fix, and compile verification. The architectural contribution is not the pipeline itself but the provider contract each generated module must satisfy. The formal contract is a single Swift protocol (工具包数据提供者ToolkitDataProvider）需要工具包标识符、相关关键字和一种方法——) requiring a toolkit identifier, relevance keywords, and one method—buildContextSummary() -> 字符串？buildContextSummary() -> String?—返回模块当前状态的标记的、人类可读的快照（例如，今天感测到的事件、最近的膳食、即将到来的日历条目）以及它公开的任何写回端点，因此相同的方法可以为聊天代理提供读取上下文和操作发现。共同进化的内存文件捕获在开发过程中发现但在编译时未强制执行的非正式约定（命名、数据格式）；这就是不同日期生成的模块如何适应一种架构的方式。—that returns a tagged, human-readable snapshot of the module’s current state (e.g., today’s sensed events, recent meals, upcoming calendar entries) together with any write-back endpoints it exposes, so the same method serves both read context and action discovery for the chat agent. A co-evolving memory file captures informal conventions (naming, data formats) discovered during development but not enforced at compile time; this is how modules generated on different days fit one architecture.

3.2.2. 共享个人上下文层Shared Personal Context Layer

共享个人上下文层是一个中央注册表，它从所有已注册的模块（内置模块和动态生成的模块）收集当前状态快照，并将它们作为单个标记块添加到每条聊天消息之前。每个快照捕获今天的数据而不是累积的历史记录；如果一个模块没有什么可报告的，它会被默默地忽略，因此系统会优雅地降级。这将集成变成了本地义务：新模块只需要实现提供者接口并注册，而不需要连接到每个现有模块。与状态仅限于单个任务的代理编排框架不同，PSI 的共享上下文是个人范围的——它在设备上跨任务和会话持续存在，不需要协调任务图，并且由所有接口使用。模块从不直接读取彼此的状态；所有跨模块通信均由法学硕士通过组装的上下文进行调解。The shared personal-context layer is a central registry that collects current-state snapshots from all registered modules—both built-in and dynamically generated—and prepends them as a single tagged block before every chat message. Each snapshot captures today’s data rather than cumulative history; if a module has nothing to report it is silently omitted, so the system degrades gracefully. This turns integration into a local obligation: a new module needs only to implement the provider interface and register, rather than wire into every existing module. Unlike agent orchestration frameworks where state is scoped to a single task, PSI’s shared context is person-scoped—it persists on-device across tasks and sessions, requires no coordinating task graph, and is consumed by all interfaces. Modules never read each other’s state directly; all cross-module communication is mediated by the LLM through the assembled context.

交互层提供了两个协调的接口：一个持久的GUI（The interaction layer provides two coordinated interfaces: a persistent GUI (Figure 2c1) 和一个通用聊天代理 (c1) and a generic chat agent (Figure 2c2）。 PSI 的贡献不仅仅是聊天和 GUI 的共存，而是它们作为同一个人范围的可变状态的同步入口点的作用。用户可以检查持久仪器中的状态，通过聊天对其进行修改，并立即在 GUI 中验证效果，而无需重复的状态路径或重新指定意图。例如，在 BoBo 中，行为时间线在 GUI 中始终保持一目了然，而 Facai 在后续查询中对相同的可见状态进行推理。c2). For example, in BoBo, the behavioral timeline remains persistently glanceable in the GUI while Facai reasons over the same visible state in follow-up queries.

5. 讨论与结论Discussion and Conclusion

从生成的应用程序到连贯的仪器。From generated apps to coherent instruments.此次部署表明，PSI 的价值不在于任何单个模块，而在于仪器实现的劳动分工。仪器支持一目了然的监控和例行控制——BoBo 时间线和停车控制通常在根本不打开聊天的情况下很有用——而聊天则处理跨模块合成和同一共享状态上的有状态操作。如果没有共享上下文层，每个生成的模块将仍然是本地成功，但会进入系统级死胡同；提供商合约通过使集成成为本地义务而不是成对问题，将孤立的应用程序变成了工具。The deployment suggests that the value of PSI lies not in any single module but in the division of labor that instruments enable. Instruments supported glanceable monitoring and routine control—the BoBo timeline and parking controls were often useful without opening chat at all—while chat handled cross-module synthesis and stateful actions over the same shared state. Without the shared-context layer, each generated module would remain a local success but a system-level dead end; the provider contract is what turns isolated apps into instruments by making integration a local obligation rather than a pairwise problem.

当前的设计赌注和限制。Current design bets and limitations.无条件注入以提示长度换取召回。在当前规模下，注入的上下文仍然是可管理的，但随着模块数量的增长，路由和选择将变得更加重要。该部署还暴露了系统特定的风险：Unconditional injection trades prompt length for recall. At current scale the injected context is still manageable, but routing and selection will matter more as module counts grow. The deployment also surfaces a system-specific risk:上下文污染context pollution (Liu et al., 2024)。由于所有接口都信任提供者摘要，陈旧或误导性的摘要可能会降低整个系统的响应质量。随着模块数量的增加，跨模块记录的重叠或冗余条目可能会给组装的上下文带来歧义，导致聊天代理错误归因、重复计数或自相矛盾，这是共享状态架构固有的一类故障，而在孤立的应用程序中不会出现这种故障。. Because all interfaces trust provider summaries, stale or misleading summaries can degrade responses system-wide. As the number of modules grows, overlapping or redundant entries logged across modules can introduce ambiguity into the assembled context, causing the chat agent to misattribute, double-count, or contradict itself, a class of failure inherent to shared-state architectures that would not arise in siloed apps.

未来的工作。Future work.我们的证据来自一位技术熟练的用户在三周内的时间，因此该论文应被视为多功能应用程序的概念验证。包括持久 GUI 和通用聊天代理的可重用工具旨在与用户无关，但当前的摘要、模块和部署实践特定于一种个人生态。重要的开放问题包括较大模块数量的路由、个人范围操作的隐私和授权，以及如何使非程序员可以访问合规模块生成。我们还计划在发布后发布可重用的工件组件，这将使这些后续问题更容易研究。Our evidence comes from a single technically skilled user over three weeks, so the paper should be read as a proof-of-concept for versatile applications. The reusable instrument that includes persistent GUI and generic chat agent are intended to be user-agnostic, but the current summaries, modules, and deployment practices are specific to one personal ecology. Important open questions include routing at larger module counts, privacy and authorization for person-scoped actions, and how to make compliant module generation accessible to non-programmers. We also plan to release the reusable artifact components after publication, which should make these follow-on questions easier to study.
