摘要Abstract

NL2SQL 系统旨在满足自然语言与数据交互日益增长的需求。然而，现实世界的信息需求很少映射到单个 SQL 查询，因为 (1) 用户跨多个话语迭代地表达查询 (2) 问题通常跨越单个数据库的封闭世界假设之外的多个数据源，以及 (3) 查询经常依赖于数据库中不存在的常识或外部知识。因此，满足现实的数据需求需要集成异构源、模式和上下文数据。在本文中，我们介绍了 Blue 的数据智能层 (DIL)，旨在支持多源、多模式和以数据为中心的应用程序。 Blue[5]是一个复合AI系统，为企业设置编排代理和数据，DIL作为其核心数据智能层，用于代理数据处理。 DIL 旨在通过统一结构化企业数据、通过法学硕士访问的世界知识以及通过交互获得的个人上下文，弥合用户意图和可用信息之间的语义差距。 DIL 的核心是一个数据注册表，它存储不同数据源和模式的元数据，以支持本机和自然语言查询。 DIL 将法学硕士、网络和用户视为源“数据库”，每个数据库都有自己的查询接口，将它们提升为一流的数据源。 DIL 依赖数据规划器将用户查询转换为可执行的查询计划。这些计划是声明性抽象，将关系运算符与跨多种模式的其他运算符统一起来。 DIL 规划器支持将复杂请求分解为子查询、从不同来源检索、最后推理和集成以产生最终结果。我们通过两个交互场景演示了 DIL，其中用户查询动态触发多源检索、跨模式推理和结果合成，说明复合 AI 系统如何超越单一数据库 NL2SQL。NL2SQL systems aim to address the growing need for natural language interaction with data. However, real-world information needs rarely map to a single SQL query because (1) users express queries iteratively across multiple utterances (2) questions often span multiple data sources beyond the closed-world assumption of a single database, and (3) queries frequently rely on commonsense or external knowledge not present in databases. Consequently, satisfying realistic data needs require integrating heterogeneous sources, modalities, and contextual data. In this paper, we present Blue’s Data Intelligence Layer (DIL) designed to support multi-source, multi-modal, and data-centric applications. Blue[5] is a compound AI system that orchestrates agents and data for enterprise settings, and DIL serves as its core data intelligence layer for agentic data processing. DIL aims to bridge the semantic gap between user intent and available information by unifying structured enterprise data, world knowledge accessible through LLMs, and personal context obtained through interaction. At the core of DIL is a data registry that stores metadata for diverse data sources and modalities to enable both native and natural language queries. DIL treats LLMs, the Web, and the User as source ‘databases’, each with their own query interface, elevating them to first-class data sources. DIL relies on data planners to transform user queries into executable query plans. These plans are declarative abstractions that unify relational operators with other operators spanning multiple modalities. DIL planners support decomposition of complex requests into subqueries, retrieval from diverse sources, and finally reasoning and integration to produce final results. We demonstrate DIL through two interactive scenarios in which user queries dynamically trigger multi-source retrieval, cross-modal reasoning, and result synthesis, illustrating how compound AI systems can move beyond singledatabase NL2SQL.

1 简介1 Introduction

关系数据库系统长期以来一直是管理结构化数据的支柱，为现代应用程序提供支持 [13, 17]。多年来，随着数据驱动的决策已从技术专家扩展到业务分析师和领域专家，对更易于访问的数据接口的需求不断增长。这推动了对自然语言到 SQL (NL2SQL) 系统的广泛研究 [8,11,18]，该系统将自然语言问题转换为可执行的数据库查询。Relational database systems have long served as the backbone for managing structured data that powers modern applications [13, 17]. Over the years, as data-driven decision-making has expanded beyond technical specialists to business analysts and domain experts, there has been growing demand for more accessible interfaces to data. This has fueled extensive research on natural language–to–SQL (NL2SQL) systems [8, 11, 18], which translate natural language questions into executable database queries.

现在，随着会话和代理应用程序的出现，自然语言数据交互的范围正在扩展到最终用户。在这些设置中，用户请求很少对应于单个格式良好的查询。相反，它们通常在多个话语中迭代展开，嵌入到更大的任务描述中，并依赖常识知识、外部事实或个人背景。这些特征挑战了传统的封闭世界假设，其中回答查询所需的所有信息都驻留在单个数据库模式中。在实践中，满足现实世界的请求通常需要集成异构数据源、模式和上下文数据。因此，弥合用户意图和可用数据之间的语义差距需要将结构化数据与外部知识和交互衍生的上下文相结合的机制。虽然法学硕士越来越多地提供获取世界知识的机会，但将其与企业数据库、组织知识和用户环境系统地集成仍然是一个开放的挑战。虽然新的方法正在出现，特别是在将法学硕士知识与关系数据融合、扩展到不同的模式、系统地解决多源环境中的优化以及处理企业规模的数据方面，但仍然有待探索的领域[1,2,4,6,7,9,10,12,14-16,20,21]。Now, the scope of natural language data interaction is expanding to end-users with the emergence of conversational and agentic applications. In these settings, user requests rarely correspond to a single, well-formed query. Instead, they often unfold iteratively across multiple utterances, are embedded within larger task descriptions, and rely on commonsense knowledge, external facts, or personal context. These characteristics challenge the traditional closed-world assumption, in which all information required to answer a query resides within a single database schema. In practice, satisfying real-world requests often requires integrating heterogeneous data sources, modalities, and contextual data. Bridging the semantic gap between user intent and available data therefore demands mechanisms that combine structured data with external knowledge and interaction-derived context. While LLMs increasingly provide access to world knowledge, systematically integrating them with enterprise databases, organizational knowledge, and user context remains an open challenge. While novel approaches are emerging, in particular on fusing LLM knowledge with relational data, expanding to different modalities, systematically addressing optimization in multi-source settings, and tackling enterprise-scale data remain underexplored areas [1, 2, 4, 6, 7, 9, 10, 12, 14–16, 20, 21].

数据注册表是支持数据发现、查询和集成的可用数据源的目录。与 Blue 中的代理注册表类似，它包含多个数据抽象级别的元数据（例如数据库、集合、实体、关系、属性、值），独立于底层存储。例如，图形数据库中的 PERSON 节点被视为相当于关系 PEOPLE 表中的行。注册表还维护描述、样本、统计数据、日志和学习表示，以支持代理推理、规划和解决（例如，验证和冲突处理）。其他功能包括数据同步、语义/统计丰富、本体/知识库对齐和价值语义发现。数据注册功能作为工具公开，供代理自主发现、解释和查询跨源数据。Data registry is a catalog for available data sources that supports data discovery, querying and integration. 3.2 数据来源3.2 Data Sources

数据源是任何底层数据系统的主要抽象。它标准化了代理和其他组件创建、更新和查询数据的访问。传统上，这些数据库包括关系数据库（例如 PostgreDB）、文档存储（例如 MongoDB）、图形数据库（例如 Neo4j）和矢量数据库（例如 ChromaDB）。为了满足传统数据库之外的现实需求，DIL 将数据源概括为包括：(1) 用于常识和世界知识的 LLMDB，(2) 用于捕获个人数据和上下文的 UserDB，(3) 用于捕获从 Web 内容中按需提取的 WebDB。每个源都被建模为一个数据库系统，具有自己的本机查询语言（例如 SQL、Cypher）以及对自然语言查询的支持。此外，所有源都公开结构化输出，以允许跨异构源进行集成。A data source is the primary abstraction for any underlying data system. It standardizes access for agents and other components to create, update, and query data. Traditionally, these include relational database (e.g. PostgreDB), document store (e.g. MongoDB), graph database (e.g. Neo4j), and vector database (e.g. ChromaDB). 5 结论5 Conclusion

为了使最终用户能够通过自然语言有效地利用数据，代理系统有机会弥合异构数据源、常识知识和个人上下文之间的语义、结构和模态差距。在本文中，我们提出了 Blue 的数据智能层 (DIL)，这是一个统一的框架，它将关系数据库、Web 数据、LLM 和用户视为一流的数据源，并通过多个注册表驱动的架构、可扩展的运算符层次结构以及可执行 DAG 上的声明性数据规划来集成它们。我们相信，这种架构代表着向企业和最终用户应用程序等提供更可靠、可扩展和基于语义的数据智能系统迈出了一步。To enable end-users effectively utilize data through natural language, agentic systems have an opportunity to bridge the semantic, structural, and modality gaps between heterogeneous data sources, common-sense knowledge, and personal context. In this paper, we presented Blue’s Data Intelligence Layer (DIL), a unified framework that treats relational databases, web data, LLMs, and users as first-class data sources, and integrates them through multiple registry-driven architecture, extensible operator hierarchy, and declarative data planning over executable DAGs. We believe this architecture represents a step toward more reliable, extensible, and semantically grounded data intelligence systems for enterprise and end-user applications alike.

黑客马拉松开发者体验调查 A.1 研究A Hackathon Developer Experience Survey A.1 Study

我们进行了一项研究，调查开发人员在为期一周的黑客马拉松后使用 Blue 平台构建人工智能驱动的应用程序的体验。该研究的目的是了解不同背景的开发人员在开发原型系统时如何与 Blue 的抽象、工具和工作流程进行交互。参加黑客马拉松的参与者完成了一项结构化调查，了解他们的专业背景、之前对相关技术（例如文本查询系统、检索增强生成和多代理系统）的熟悉程度以及他们之前对 Blue 平台的接触情况。We conducted a study to investigate the developer experience of building AI-driven applications using the Blue platform after a week-long hackathon. The goal of the study is to understand how developers with different backgrounds interact with Blue’s abstractions, tools, and workflows while developing prototype systems. Participants who took part in the hackathon completed a structured survey capturing their professional background, prior familiarity with relevant technologies (such as text-to-query systems, retrievalaugmented generation, and multi-agent systems), and their previous exposure to the Blue platform.

该调查问卷旨在评估开发人员体验的多个方面，包括入门和可学习性、Blue 数据抽象的可用性（例如数据注册表、数据源和数据规划组件）以及更广泛的开发工作流程。参与者评估这些概念的直观程度、发现和使用可用数据资源的容易程度，以及将查询结果集成到代理中的效率。其他问题捕获与文档、调试、API、性能和部署相关的摩擦点。调查最后对该平台的优势、劣势和改进建议进行了开放式反思。这些回应共同提供了对 Blue 作为构建以数据为中心的 AI 应用程序的开发环境的可用性和有效性的定量和定性见解。The questionnaire aims to evaluate several aspects of the developer experience, including on-boarding and learnability, the usability of Blue’s data abstractions (such as the data registry, data sources, and data planning components), and the broader development workflow. Participants assess how intuitive these concepts were, how easily they could discover and use available data resources, and how effectively they could integrate query results into agents. Additional questions capture friction points related to documentation, debugging, APIs, performance, and deployment. The survey concludes with open-ended reflections on the platform’s strengths, weaknesses, and suggested improvements. Together, these responses provide both quantitative and qualitative insights into the usability and effectiveness of Blue as a development environment for building data-centric AI applications.

A.3 结果和讨论A.3 Findings and Discussion

总之，虽然 Blue 的架构和灵活性受到高度赞赏，但实际的可用性改进（尤其是在设置、文档和简化学习曲线方面）始终得到推荐。参与者强调，该平台的模块化和数据抽象支持实验和快速原型设计，但一些摩擦点限制了生产力，特别是在调试、错误跟踪和编排多代理工作流程方面。In summary, while Blue’s architecture and flexibility were highly appreciated, practical usability improvements—especially around setup, documentation, and easing the learning curve—were consistently recommended. Participants highlighted that the platform’s modularity and data abstractions enabled experimentation and rapid prototyping, yet several friction points limited productivity, particularly in debugging, error tracing, and orchestrating multiagent workflows.

黑客马拉松的经历进一步揭示了分布式平台上多代理开发的固有挑战。参与者报告了推理交互代理之间的控制流和数据流的困难，特别是当多个代理并行执行并共享公共数据资源时。调试成为一项核心挑战，因为错误通常异步传播或仅在下游代理中可见，从而使根本原因的识别变得复杂。代理的协调、监控执行状态和确保数据一致性是影响生产力和实验结果信心的额外痛点。这些观察结果表明，Blue 或类似的多代理开发环境的未来迭代可以受益于用于可视化代理交互、记录和跟踪多代理执行以及支持工作流的确定性重放的增强工具。其他潜在的方向包括改进异步操作的错误消息传递，以及集成模拟或沙箱模式以在部署之前测试复杂的代理编排。解决这些挑战可以使多代理人工智能开发变得更加平易近人，并减少新手和经验丰富的开发人员的摩擦。The hackathon experience further revealed the inherent challenges of multi-agentic development in general on distributed platforms. Participants reported difficulties in reasoning about the control flow and data flow across interacting agents, especially when multiple agents executed in parallel and shared common data resources. Debugging emerged as a core challenge, since errors often propagated asynchronously or were only visible in downstream agents, complicating the identification of root causes. Coordination of agents, monitoring execution states, and ensuring data consistency were additional pain points that affected both productivity and confidence in experimental results. These observations suggest that future iterations of Blue—or similar multi-agent development environments—could benefit from enhanced tooling for visualizing agent interactions, logging and tracing multi-agent execution, and supporting deterministic replay of workflows. Other potential directions include improved error messaging for asynchronous operations, and integration of simulation or sandbox modes to test complex agent orchestration before deployment. Addressing these challenges can make multi-agentic AI development more approachable and reduce friction for both novice and experienced developers.
