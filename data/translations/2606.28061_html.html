摘要Abstract

大型语言模型 (LLM) 越来越多地从独立的文本生成系统转移到调用外部工具、访问环境和执行多步骤任务的代理。然而，传统的函数调用基准主要评估任务完成情况和API正确性，而隐私评估基准通常侧重于最终响应或隐私判断。这两种视角都无法捕获跨执行的多工具轨迹的特定目的的信息流。受当前代理评估中的这一限制的启发，Large language models (LLMs) have increasingly moved from standalone text generation systems to agents that invoke external tools, access environments, and execute multi-step tasks. However, conventional function-calling benchmarks mainly evaluate task completion and API correctness, while privacy evaluation benchmarks typically focus on final responses or privacy judgments. Neither perspective captures purpose-bound information flow across an executed multi-tool trajectory. Motivated by this limitation in current agent evaluation,工具隐私工作台ToolPrivacyBench审计任务私有原子是否仅路由到授权工具和下游接收器，从而评估工具使用过程中的任务完成情况和隐私过度披露。该基准包含 2,150 个案例，其中包括 1,150 个完全合成的隐私敏感业务工作流程和 1,000 个改编自现有多工具和函数调用基准的案例。每个案例都由一个策略知识库表示。代理针对模拟业务后端执行后，评估器会将记录的工具参数和后端审核日志与此策略知识库进行比较。该评估涵盖九种广泛使用的代理，以表征有目的的隐私过度披露。结果表明，成功的工具执行并不意味着适当的隐私泄露：代理可能会在通过中间工具调用传输不必要的私人信息的同时完成任务。因此，ToolPrivacyBench 正式确定了需要了解的披露边界，在该边界下，每个工具应仅接收其既定目的所需的信息，并使用轨迹级审计来识别多工具工作流程中的隐私过度披露。audits whether task-private atoms are routed only to authorized tools and downstream sinks, thereby evaluating both task completion and privacy over-disclosure during tool use. The benchmark contains 2,150 cases, including 1,150 fully synthetic privacy-sensitive business workflows and 1,000 cases adapted from existing multi-tool and function-calling benchmarks. Each case is represented by a policy knowledge base. After an agent executes against mock business backends, the evaluator compares recorded tool arguments and backend audit logs with this policy knowledge base. The evaluation covers nine widely used agents to characterize purpose-bound privacy over-disclosure. The results show that successful tool execution does not imply appropriate privacy disclosure: an agent may complete a task while transmitting unnecessary private information through intermediate tool calls. ToolPrivacyBench therefore formalizes a need-to-know disclosure boundary, under which each tool should receive only the information necessary for its stated purpose, and uses trajectory-level auditing to identify privacy over-disclosure in multi-tool workflows.

1 简介Introduction

随着大型语言模型（LLM）代理越来越多地用于调用外部工具并执行多步骤任务，其任务执行能力已成为中心评估目标。现有的代理基准测试为跨多回合、交互式和可执行设置测量工具使用和任务完成情况提供了重要基础As large language model (LLM) agents are increasingly used to call external tools and execute multi-step tasks, their task-execution capability has become a central evaluation target. Existing agent benchmarks provide an important basis for measuring tool use and task completion across multi-turn, interactive, and executable settings[Li et al., 2023, Yao et al., 2025, Trivedi et al., 2024]。然而，除了完成任务之外，还需要评估代理在执行过程中如何处理和披露私人信息。. Beyond task completion, however, it is also necessary to evaluate how agents handle and disclose private information during execution.

法学硕士的隐私评估提供了一个起点，但现有的工作主要研究记忆、训练数据提取、上下文隐私判断和生成文本中的隐私披露Privacy evaluation for LLMs provides a starting point, but existing work mainly studies memorization, training-data extraction, contextual privacy judgment, and privacy disclosure in generated text[Carlini et al., 2021, Shao et al., 2024]。它提供了关于 LLM 代理如何在工具调用期间处理和传输私人信息的有限系统证据。在多工具工作流程中，私有字段对于一个工具可能是必需的，但不应传递给另一个工具。因此，有必要评估代理在工具使用过程中是否尊重需要知道的披露边界。. It provides limited systematic evidence about how LLM agents handle and transmit private information during tool invocation. In a multi-tool workflow, a private field may be necessary for one tool but should not be passed to another. It is therefore necessary to evaluate whether agents respect need-to-know disclosure boundaries during tool use.

为了填补这一评价空白，To fill this evaluation gap,工具隐私工作台ToolPrivacyBench被引入作为多工具工作流程的有目的的隐私审核基准。该基准提出了一个核心问题：is introduced as a purpose-bound privacy auditing benchmark for multi-tool workflows. The benchmark asks a central question:当完成任务时，LLM代理是否只将私人信息传输给真正需要它的工具？when completing a task, does an LLM agent transmit private information only to the tools that actually need it?与简单地删除所有敏感信息不同，有目的的隐私要求评估者确定每个私有字段在当前工作流程阶段是否必要，并将该判断与后端系统实际收到的工具参数进行比较。因此，ToolPrivacyBench 将隐私泄露建模为基于知识的审计问题。它在明确的策略知识库中记录私有原子、工具用途、接收器类型、允许和禁止的现场工具关系、自由文本槽和后端审计证据。Unlike simply removing all sensitive information, purpose-bound privacy requires the evaluator to determine whether each private field is necessary at the current workflow stage and to compare that judgment with the tool arguments actually received by backend systems. ToolPrivacyBench therefore models privacy disclosure as a knowledge-based auditing problem. It records private atoms, tool purposes, sink types, allowed and forbidden field-tool relations, free-text slots, and backend audit evidence in an explicit policy knowledge base.

评估多工具代理中特定目的的隐私风险需要的不仅仅是一小组孤立的任务或单个应用程序域。 LLM 代理正在跨业务流程使用，例如医疗保健、金融、保险、税务、招聘、教育、IT 运营和软件安全，其中私人信息类型、工具用途和接收器边界各不相同。因此，ToolPrivacyBench 在这些领域构建了 2,150 个多工具案例。该基准包括 1,150 个完全合成的隐私敏感业务工作流程和 1,000 个根据现有多工具和函数调用基准改编的公共衍生案例。这种设计涵盖了高风险隐私场景，同时保留了实际工具使用任务的工作流结构，因此评估不限于单个任务系列或隐私字段类型。Evaluating purpose-bound privacy risk in multi-tool agents requires more than a small set of isolated tasks or a single application domain. 考虑到这种有目的的知识，评估必须观察实际代理执行期间的信息流，而不是仅检查最终答案。许多隐私披露不会出现在用户可见的响应中，而是出现在中间工具参数、票证描述、内部注释或团队交接中。因此，ToolPrivacyBench 通过 OpenClaw 堆栈和模拟后端系统执行代理任务，记录完整的工具调用轨迹、工具参数和后端审核日志。执行后，披露检测器和授权推理器将实际传输的信息与策略知识库允许的信息进行比较，确定私有字段是否被路由到未经授权的工具。Given this purpose-bound knowledge, evaluation must observe information flow during actual agent execution rather than checking only the final answer. ToolPrivacyBench therefore executes agent tasks through the OpenClaw stack and mock backend systems, recording complete tool-call trajectories, tool arguments, and backend audit logs. 策略知识库不会提供给基线代理作为执行时防御；仅在任务完成后用于审核。在任务执行期间，工具调用参数由模拟业务后端记录为审计日志。然后，披露检测器在执行的工具参数和后端日志中定位私有原子，授权推理器查询策略知识库以确定这些原子是否被传输到授权工具或接收器。最后，指标聚合器根据这些决策生成效用指标和隐私泄漏指标。The policy knowledge base is not provided to the baseline agent as an execution-time defense; it is used only after task completion for auditing. The disclosure detector then locates private atoms in executed tool arguments and backend logs, and the authorization reasoner queries the policy knowledge base to determine whether these atoms were transmitted to authorized tools or sinks. Finally, the metric aggregator produces utility metrics and privacy leakage metrics from these decisions.

这种设计使 ToolPrivacyBench 能够支持矩阵级统计和关系级诊断。一方面，现场工具授权矩阵为比较跨模型的总体隐私风险提供了统一的计算基础。另一方面，策略知识库保留了私有原子、工具用途和信息接收器之间的结构关系，从而能够分析模型行为违反了哪些工具类型、接收器类型和目的绑定的授权边界。This design allows ToolPrivacyBench to support both matrix-level statistics and relation-level diagnostics. On one hand, the field-tool authorization matrix provides a unified computational basis for comparing aggregate privacy risk across models. On the other hand, the policy knowledge base preserves structural relations among private atoms, tool purposes, and information sinks, enabling analysis of which tool types, sink types, and purpose-bound authorization boundaries are violated by model behavior.

5 指标Metrics

度量设计解决了目的绑定隐私评估的主要困难：代理通常需要将用户提供的隐私事实传输到某些工具，以完成多工具任务，但这些事实不应该进一步路由到与当前工具用途无关的接收器。因此，ToolPrivacyBench 不能仅通过任务成功来评估代理，也不能简单地检查是否出现敏感信息。前者会错过工具执行期间的过度披露，而后者会错误地惩罚完成任务所需的披露。The metric design addresses the main difficulty in purpose-bound privacy evaluation: an agent often needs to transmit user-provided private facts to some tools in order to complete a multi-tool task, but those facts should not be further routed to sinks that are unrelated to the current tool purpose. ToolPrivacyBench therefore cannot evaluate agents only by task success, nor can it simply check whether sensitive information appears. The former would miss over-disclosure during tool execution, while the latter would incorrectly penalize disclosures that are necessary for task completion.

这种困难在多工具工作流程中被放大。轨迹可能会显示出较低的泄露风险，因为代理拒绝采取行动、跳过工具或忽略必要的事实，但这样的轨迹尚未完成任务。另一个轨迹可以完成所有工作流程阶段，同时将不必要的私有上下文复制到票证、注释、通知或团队移交消息中。因此，ToolPrivacyBench 在合并之前将三个问题分开：工作流程是否有效完成、禁止的披露机会是否实现以及这些披露发生在工作流程中的何处。This difficulty is amplified in multi-tool workflows. A trajectory may show low disclosure risk because the agent refuses to act, skips tools, or omits necessary facts, but such a trajectory has not completed the task. Another trajectory may complete all workflow stages while copying unnecessary private context into tickets, notes, notifications, or team handoff messages. ToolPrivacyBench therefore separates three questions before combining them: whether the workflow is completed effectively, whether forbidden disclosure opportunities are realized, and where those disclosures occur in the workflow.

5.1 效用指标Utility Metrics

5.3 严重程度加权泄漏率Severity-Weighted Leakage Rate

FOR 对每一项禁止的披露都同等重要。这对于衡量一般合规性很有用，但不能反映风险强度。在现实环境中，披露安全秘密、支付凭证、医疗状况或政府标识符比披露低敏感度操作状态值更重要。因此，ToolPrivacyBench 引入了严重性权重，以区分频繁但低风险的披露和不太频繁但高风险的披露。FOR treats every forbidden disclosure as equally important. 6 实验装置Experimental Setup

本节介绍 ToolPrivacyBench 如何在统一的评估框架内衡量工具使用实用性和目的限制的隐私合规性。与仅检查最终答案是否泄露私人信息的评估不同，ToolPrivacyBench 检查代理如何在多工具业务流程中选择工具、构造参数以及将当前任务私有原子路由到不同的接收器。实验设计围绕四个研究问题进行：This section explains how ToolPrivacyBench measures tool-use utility and purpose-bound privacy compliance within a unified evaluation framework. Unlike evaluations that inspect only whether the final answer reveals private information, ToolPrivacyBench examines how an agent selects tools, constructs arguments, and routes current-task private atoms to different sinks during a multi-tool business process. The experimental design is organized around four research questions:

  • 1.

    问题一：RQ1:当前的法学硕士代理人能否完成多工具业务工作流程，同时保留需要了解的隐私边界？Can current LLM agents complete multi-tool business workflows while preserving need-to-know privacy boundaries?

  • 2.

To answer RQ1, the benchmark must contain executable multi-step workflows rather than isolated single-turn questions. To answer RQ2 and RQ3, it must record disclosure behavior by tool, sink type, workflow stage, and free-text field. To answer RQ4, all models must run under the same tool environment, schemas, and scoring implementation so that differences in utility and privacy metrics are attributable to model behavior rather than environment or evaluator differences.

这些故障对应于第 7 节中的接收器级、路径级和自由文本诊断。它们表明任务完成率高并不意味着信息流合规。模型可以调用正确的工具并完成业务流程，同时在生成摘要、通知和移交内容时失去目的约束。因此，对于使用工具的主体而言，隐私风险不仅来自敏感信息是否被使用，还来自该信息在完成其本地目的后是否继续携带、重述和转移。These failures correspond to the sink-level, path-level, and free-text diagnostics in Section 7. They show that high task completion does not imply compliant information flow. A model can call the correct tools and complete the business process while losing purpose constraints when generating summaries, notifications, and handoff content. For tool-using agents, privacy risk therefore arises not only from whether sensitive information is used, but also from whether that information continues to be carried, restated, and transferred after its local purpose has been completed.

9 讨论和启示Discussion and Implications

ToolPrivacyBench 表明任务完成和隐私合规性是不同的属性。代理可以调用​​正确的工具、更新后端状态并生成合理的通知，同时仍然将私有事实传送到不需要它们的工具或接收器中。因此，评估使用工具的代理应该将功能正确性与信息流正确性分开：一个值不仅仅是孤立地安全或不安全，而是相对于当前工具、接收器和目的而言是授权的还是过度的。ToolPrivacyBench shows that task completion and privacy compliance are distinct properties. An agent can call the correct tools, update backend state, and generate plausible notifications while still carrying private facts into tools or sinks that do not need them. Evaluating tool-using agents should therefore separate functional correctness from information-flow correctness: a value is not simply safe or unsafe in isolation, but authorized or excessive relative to the current tool, sink, and purpose.

这种区别具有直接的设计含义。隐私控制应应用于执行的轨迹和后端效果，而不仅仅是最终响应。消息、注释、摘要和切换等自由文本字段尤其重要，因为它们允许在更广泛的协作渠道中重述早期步骤中积累的上下文。 ToolPrivacyBench 使用的策略表示可以支持特定于工具的检索、调用前参数检查、接收器感知访问控制以及自由文本字段的编辑或重写。运行时监视器和特定目的授权网关是天然的互补干预措施，但应在减少泄漏、任务完成和工作流级传播方面对它们进行联合评估This distinction has direct design implications. Privacy controls should be applied to executed trajectories and backend effects, not only to final responses. Free-text fields such as messages, notes, summaries, and handoffs are especially important because they allow context accumulated in earlier steps to be restated in broader collaboration channels. The policy representation used by ToolPrivacyBench can support tool-specific retrieval, pre-call argument inspection, sink-aware access control, and redaction or rewriting for free-text fields. Runtime monitors and purpose-bound authorization gateways are natural complementary interventions, but they should be evaluated jointly on leakage reduction, task completion, and workflow-level propagation[Wang et al., 2025, Weis, 2026].

该基准应被解释为受控审核设置，而不是生产事故率的衡量标准。其合成和公共衍生的工作流程使用伪造或测试值、模拟后端和基于既定工具用途的策略注释；它们不会重现所有组织角色、保留规则、访问控制、模型更新或人工审核流程。因此，预期用途是受控评估和缓解比较，发布的工件不包括实时凭证、生产端点和真实系统的连接器。The benchmark should be interpreted as a controlled audit setting rather than a measurement of production incident rates. Its synthetic and public-derived workflows use fabricated or test values, mock backends, and policy annotations based on stated tool purposes; they do not reproduce all organizational roles, retention rules, access controls, model updates, or human review processes. The intended use is therefore controlled evaluation and mitigation comparison, with released artifacts excluding live credentials, production endpoints, and connectors to real systems.

10 结论Conclusion

工具隐私工作台ToolPrivacyBench评估使用工具的 LLM 代理人在完成多步骤工作流程时是否保留有目的的披露约束。其策略知识库将当前任务私有原子与工具用途、接收器、自由文本槽以及允许或禁止的关系联系起来，而模拟后端记录执行期间收到的参数。在九个代理中，高任务成功率与现场、接收器和自由文本的过度披露共存，特别是在票证、交接、描述、消息和工作笔记中。在带注释的工作流程和受信任的模拟后端设置中，API 的正确性并不能保证隐私合规性；需要工具调用轨迹和后端日志来确定私有事实的路由位置。evaluates whether tool-using LLM agents preserve purpose-bound disclosure constraints while completing multi-step workflows. Its policy knowledge base relates current-task private atoms to tool purposes, sinks, free-text slots, and allowed or forbidden relations, while mock backends record the arguments received during execution. Across nine agents, high TaskSuccess coexists with field-, sink-, and free-text over-disclosure, particularly in tickets, handoffs, descriptions, messages, and work notes. Within the annotated workflows and trusted mock-backend setting, API correctness does not establish privacy compliance; tool-call trajectories and backend logs are required to determine where private facts were routed.
